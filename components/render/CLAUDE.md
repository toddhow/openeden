# components/render

Renderer pieces with no game types: `Render::Engine` (wraps `vsg::Viewer`), render passes and attachments, screenshots, and the small scene helpers shared by the game and the editor. Read the root `CLAUDE.md` first. `components/` never includes `apps/`, so nothing here names `MWWorld`, `MWBase` or a game visibility mask.

## Shared with the editor (task 0014, B2)

- `debuggeometry.*`: lines and triangles submitted as data. The rules (threading, fixed capacity, one geometry per producer) are in its header and in `apps/openmw/mwrender/CLAUDE.md`.
- `simplewater.hpp`: the flat water plane; reads `Water_SurfaceTexture` and `Water_Map_Alpha` from `Fallback::Map`.
- `intersect.hpp`: `nearestIntersection` sorts an intersector's hits and returns the nearest as point, normal, ratio and first `Anim::Transform`. Turning that transform into a game object or an editor instance is the caller's job (`apps/openmw/mwrender/intersect.hpp` in the game).

## Hosting `Render::Engine` on someone else's viewer (task 0014, B3)

- `Engine(viewer, window)`: one Engine per window over one viewer. Everything an Engine does but `compile`, `loop` and `createCompileContext` is about one window (`createRenderGraph`, `createCommandGraph`, `setRenderPass`, `screenshotOperation`), so per-window keeps those as they are; one Engine with several windows would have to add a window argument to each.
- The host drives frames and calls `endFrame()` afterwards. `loop()` is not for it: it blocks.
- `setup()` appends to the viewer's task rather than calling `Viewer::addRecordAndSubmitTaskAndPresentation`, which replaces every task and leaves earlier compile contexts uploading through a dead `TransferTask`.
- `setup()` restarts the viewer's threading, so the last Engine's `threading` argument decides for all of them.
- `endFrame()` is the only thing that advances a hosted deletion queue, and the host calls it only after `recordAndSubmit` has returned. A frame is stamped in `advanceToNextFrame`, and its fence wait comes later, in `RecordAndSubmitTask::start`, so never call it from an event handler, an update operation or a detach. The queue holds `max(numFrames, 3) + 1` frames: the fence ring is three long however few swapchain images there are (`vsgUtil::DeletionQueue::sizeForPostFrameAdvance`).

## Pitfalls

- **A render area larger than the framebuffer renders nothing,** with no error without the validation layer (VUID-VkRenderPassBeginInfo-pNext-02852): the game then stays blank, not only that frame. The swapchain is rebuilt at the next frame's image acquisition, after the window event that asked for the new size, so never set `renderArea` from the event or from `extent2D()`, which already holds the new size. Set it from `Engine::swapchainExtent()` each frame (`RenderManager::syncExtents`). Graphs with a window or framebuffer need `windowResizeHandler = nullptr`, or VSG scales the area again by new/old.

## Repeatable captures (task 0072)

- **`OPENEDEN_FIXED_FRAME_TIME=<seconds>`** (test only, an environment variable): `Engine::loop` advances every frame by that time instead of the wall time. With `--random-seed`, a still Lua camera and `set timescale to 0`, two runs of the same binary differ only where AI or worker-thread timing moves something (a walking NPC); not byte-identical. Unset, empty or not a positive number, the frame time is the wall time.

## Screenshots (2026-11-04, four review rounds)

- **One request a frame:** F12 (the input update), Lua `debug.takeScreenshot()` (applied in `LuaManager::synchronizedUpdate`) and `--auto-screenshot N` all set one flag (`MWInput::ActionManager::screenshotRequest`). The loop callback in `OMW::Engine::go` (`apps/openmw/vsgengine.cpp`) reads it at its end and calls `Render::Engine::requestScreenshot`: two requests in one frame are one screenshot, and a request from Lua's `onFrame` in frame K gives the picture of frame K (shown by a frame counter on the HUD in the proof scene).
- **The copy is made inside the frame it shows (`framecapture.*`):** `RenderManager` gives the engine its GUI command graph (`Engine::setScreenshotGraph`): submit order 1, alone at it, so the last graph that writes the swapchain image in a frame (an editor view's only graph is its own). `FrameCapture` appends a `vsg::Switch` to it. When a request waits, `beforeRecord` (in `loop()`, just before `recordAndSubmit`) puts into the switch the copy of `imageIndex(0)`, the image acquired for this frame, at the swapchain's extent, into a host-visible image of its own (`createDownloadCommands` with `DownloadSync::BeforePresent`; the masks are `downloadSyncMasks`, tested). The first barrier's first scope is `ALL_COMMANDS` with `COLOR_ATTACHMENT_WRITE | TRANSFER_WRITE`: a barrier's first scope holds every command submitted before it, in submission order, at the stages it names (Vulkan specification, "Synchronization and Cache Control": synchronization scopes), so it directly includes the GUI pass's draws and its multisample resolve, and the pass's final layout transition is ordered before it by the same rule. It does not "chain" through the pass's implicit external dependency: that dependency's destination is only `BOTTOM_OF_PIPE` (`Render::standardDependencies` names no dependency out of the pass), and `BOTTOM_OF_PIPE` in a second scope names no stage (synchronization2's `NONE`), so nothing is ordered through it. After the copy the image goes back to `PRESENT_SRC_KHR` and the copy is made visible to the host (`HOST_READ` at `HOST`). `afterRecord` empties the switch and hands each finished copy to its `done`: a copy recorded `age` frames ago is finished when `RecordAndSubmitTask::fence(age)` has signalled, or once the ring no longer holds that frame, since `RecordAndSubmitTask::start` waited for it before reusing the fence (`copyState`; VSG 1.1.16, `RecordAndSubmitTask.cpp`, `start`, with no limit on that wait). So nothing waits for the GPU; the copy is usually handed over one frame later. `done` (`vsgengine.cpp`) is `Render::nameAndQueueScreenshot`: the name is taken only there, so a request that was dropped takes no number; the writer (`RenderManager`'s operation thread) reads the copy (`readDownloadedImage`), frees it, and writes the file.
- **The bookkeeping is a pure class (`CaptureQueue`, `framecapture.hpp`):** the waiting request, the armed copy and the copies in flight, oldest first; `FrameCapture` is its Vulkan shell and several exist (`Engine::addFrameCapture`: the screenshots', the save thumbnail's). `testframecapture.cpp` runs it against a fake of VSG's fence ring (`FakeRing`: three slots, a frame that leaves the ring has finished): the age moves once per recorded frame, `fence(age)` is read for the right frame, the search stops at the first copy still in flight, a frame never submitted is lost, requests merge, an empty switch after recording, `finish()`. The ring rests on two places of VSG 1.1.16 that no test reaches without a device: `Viewer::assignRecordAndSubmitTaskAndPresentation` makes every task with `numBuffers = 3` (`Viewer.cpp:501`), and `start()` waits for the slot's fence with no limit (`RecordAndSubmitTask.cpp:129` to `140`). The test `vsg_is_the_version_whose_fence_ring_the_queue_was_checked_against` pins the VSG version (1.1.16): it fails with another VSG, and the answer is to read those two places again and move the pin. The ring is three long whatever the swapchain has.
- **Why not the image presented last:** until 2026-11-04 (vsgopenmw's code, and round one of this fix) the game copied `imageIndex(1)`, the image presented in the frame before. `vkQueuePresentKHR` hands that image to the presentation engine, and Vulkan forbids any use of a presented image until it is acquired again; waiting for its frame's fence does not make that legal, so round one's copy was still against the specification. vsgopenmw's copy also ran late, in `operate()` on the operation thread after the writes queued before it, and by then the image had been acquired and drawn into again: with only the names fixed, requests at frames 3871 to 3876 held frames 3871, 3944, 4008, 4072, 4142 and 4209. (`imageIndex(1)` is the image acquired one frame earlier, `vsg::Window::acquireNextImage`. The swapchain has `vsg::SwapchainPreferences::imageCount` images, 3 by default, but `Swapchain.cpp:171` clamps that to the surface's `maxImageCount`, so a driver may give fewer, and with fewer than three an image is acquired again sooner. The screenshots do not depend on it: the copy is made in the frame, and the fence ring is three long whatever the swapchain has.)
- **The save thumbnail is the same machinery (round three, changed in round four):** `RenderManager::setupScreenshotInterface` asks a second `FrameCapture` (`mThumbnailCapture`, `DownloadSync::InFrame`) for a copy of the frame after the request, recorded at the end of the main command graph (after the scene, tonemap and post-process, before the GUI graph, so the picture has no HUD). It is read once that frame's fence has signalled. Before, `retrieve()` counted `numFrames()` calls (made by `SaveGame::run` in the loop callback), so it read the copy in the callback of frame K+3, before `RecordAndSubmitTask::start` of that frame had waited for K's fence (at K+2 with a 2-image swapchain), and the Transfer path's last barrier made the copy visible to `MEMORY_READ` at `TRANSFER`, not to the host. `InFrame`'s first scope is `COLOR_ATTACHMENT_OUTPUT | TRANSFER` with `COLOR_ATTACHMENT_WRITE | TRANSFER_WRITE` (the passes' attachment writes directly in it, not only through the layout transition), its second scope is `HOST | COLOR_ATTACHMENT_OUTPUT` (the host reads the copy; the transition back is ordered before the GUI pass's colour attachment reads and writes). A request that cannot be copied gives the save no thumbnail and a warning, and does not hold the save.
  - **Picture (round four, finding 3):** until round three the whole window was blitted with `VK_FILTER_NEAREST` into a linear-tiling host image, a decimation of 2.5x at 1280 x 720 (up to 8x at 4K) and stretched from 16:9 to the thumbnail's 1.95:1 (518 x 266: `savegame.hpp` asks for twice 259 x 133 "to get some nice antialiasing"). Neither fallback was run in the game (this device has the support).
  - **State (round four, findings 5 and 6):** the state shared between `request`, `retrieve` and the capture's callbacks is `MWRender::ThumbnailState` (`thumbnailstate.hpp`, pure, `testthumbnailstate.cpp`).   - **Headless (round four, finding 7):** `VSGOPENMW_INDIRECT` makes a headless engine, which has no `mThumbnailCapture` (no window, no swapchain), and round three left it with no thumbnail. The request now makes the same scaled copy of the headless colour image in a submission of its own that it waits for (`DownloadSync::Transfer`, `Render::submit`; the loop waits for every headless frame's fences and the image is never presented), and the picture has the HUD, as the code before round three had. ## The persistent pipeline cache (2026-11-09)

- **`[Rendering] pipeline cache`** (on by default). VSG v1.1.16 creates every pipeline with `VK_NULL_HANDLE` as the cache, so the driver recompiled the ubershader define sets on the main thread each run (`compile.vsg` 0.7 to 5 s each; a 9.4 s frame). `extern/patches/vsg_pipeline_cache.cmake` (a `PATCH_COMMAND`, see `docs/dependencies.md`) gives `vsg::Device` a `pipelineCache` member that graphics and compute pipeline creation pass on. `Render::Engine::enablePipelineCache(dir)` (called from `OMW::Engine` right after the engine exists) loads `pipelinecache-<vendor>-<device>-<cacheUUID>.bin` (`pipelinecache.hpp`: wrapper with size, FNV hash and a check of the driver header against the device; a mismatch, torn or oversized file is ignored with one warning and the cache starts empty), creates the `VkPipelineCache`, and starts `PipelineCache::Saver`: a thread that every 10 s asks the driver for the cache's size and, when it changed, writes the file atomically (temp file, rename); `~Engine` does a last save while the device is alive. Files of other driver versions of the same device are removed at start. Nothing on the main thread besides creating the cache.
- **A VSG without the patch still builds** (`requires { dev.pipelineCache; }` in a generic lambda): the setting then logs one warning and does nothing.
- **Not improved:** the first run on a machine (or after a driver update) compiles everything as before; a pipeline made for the first time in a session still stalls its frame. The Slang runtime cache is separate and was not the cause of these stalls.
- Tests: `apps/components_tests/render/testpipelinecache.cpp` (the pure parts and the saver with fake callbacks). The Vulkan calls in `engine.cpp` are covered only by in-game runs.

## GPU timing, the device report and Slang shaders (task 0023)

- **`gputiming.*`:** `[Rendering] gpu timing` (off by default). `Engine::enableGpuTiming()` makes a `GpuTimer` only when asked, so with the setting off there is no query pool and `loop()` records and reads nothing. Whoever builds a command graph wraps a pass with `GpuTimer::beginNode(pass)` and `endNode(pass)` (`timeChild` in `mwrender/rendermanager.cpp`). Rules:
  - The begin node resets the pass's two queries, and a reset is not allowed inside a render pass instance, so a pass is timed from a command graph's children or inside `SuspendRenderPass`, never from inside a render graph.
  - Passes are registered before the first frame (the frame stats file lists them in its header when `loop()` starts); the table holds 16.
  - Results are read three frames after recording, on the main thread, without waiting (`VK_QUERY_RESULT_WITH_AVAILABILITY_BIT`); a pass the GPU has not finished is skipped. The query ring has four frame slots so the slot being read is never the slot being recorded.
  - The frame stats file gains `gpu_frame` (the frame the GPU times belong to) and one column per pass only when timing is on; off, its header and lines are exactly as before.
- **`devicereport.*`:** `[Rendering] device report` writes the report to the log and `device-report.json`. The probe makes its own instance at the loader's version, because the questions need Vulkan 1.1 calls. The game's own instance is already at the loader's version (VSG's `WindowTraits` asks the loader), not Vulkan 1.0. Every entry is `present...`, `absent` or `unknown (...)`; a missing item never throws. `DeviceReport::add` has a `const char*` overload on purpose: without it a string literal picks the `bool` one.
- **Slang:** `[Rendering] slang shaders` (off by default) makes `Pipeline::Graphics::createShaderStage` swap the GLSL module for `<path>/main.<stage>.spv` when it exists. The GLSL is still read first, for its stage; it stays the fallback. The `.spv` files come from `openeden_add_slang_shader()` (`files/shaders/CMakeLists.txt`), which runs the `slangc` that `extern/CMakeLists.txt` downloads. ## The linear HDR path (task 0025, F2)

- **The passes' shaders are files (task 0072, stage g):** `Tonemap`, `Bloom`, `Velocity` and `AmbientOcclusion` take the shader options and read `files/shaders/post/` (`fullscreen.vert` for all four, then `tonemap.frag`, `bloomdown.frag` and `bloomup.frag`, `velocity.frag`, `ao.frag`) through `vsgUtil::readPassStages`, which compiles each stage on its own on a copy (never the stage the reader shares) and takes the Slang twins with `[Rendering] slang shaders` only when every stage of the pipeline has one. They used to be GLSL strings in these files; do not put shader text back into C++. A pass that cannot read or compile a stage logs `readPassStages`' reason (the file, glslang's message: `vsgUtil::CompilerMessageCapture`), because VSG's own logger writes to stderr, which openmw.log does not show (review of stage g).

- **`[Rendering] hdr`** (off by default, read at start by `MWRender::RenderManager` only; the editor and headless engines never take it). Off, none of the objects below exist and the renderer is as before.
- **`hdrmath.hpp`:** the pure parts (the gamma-2.2 conversion, tonemap curves, `resolveTonemap`, `useHdrPath`). The shaders repeat its constants (`files/shaders/post/tonemapconstants.glsl` and its Slang twin `.slang`, read back by `RenderTonemapConstants`; `lib/view/linear.glsl` has its own copy). Change both together.
- **`HdrTarget`:** the float scene target (RGBA16F, resolved copy sampled by the tonemap, depth resolved). Its render pass has dependencies of its own, because the same images are drawn into every frame while the previous frame's tonemap and the water's copy may still read them. On resize only the images and the framebuffer are replaced; the render pass object stays, since the scene's pipelines were compiled against it. F3 adds outputs through the constructor's `extraColorFormats`.

It has no view in its graph, so its draw is recorded under the view id of a view registered on the window (`vsgUtil::RecordWithViewId`); the view must be registered with `CompileManager::add(window, view)` before `setSource`, or `setSource` logs an error and fails.

The first suspect, a missing subpass dependency from the default main pass to the later copy of its depth and colour, was tried in task 0026 and made no difference (identical frame), so it is not the cause; the cause is unknown. Not changed in the default path (off means unchanged); see task 0025's and 0026's stage logs.

## The stored G-buffer (task 0026, F3)

- **`[Rendering] gbuffer`** (off by default, needs `hdr`, read at start by `MWRender::RenderManager`). It adds colour outputs to `HdrTarget`'s render pass: output 1 the view-space normal (RGBA16F, w = 1 where written), output 2 the linear depth (R32F, view-axis distance in game units), both all zero where nothing opaque was drawn. `HdrTarget::normalView()` and `linearDepthView()` are the resolved single-sample images; multisampling averages them, so edges are blended (`hdrtarget.hpp`). Hardware depth stays in its attachment layout, which is why linear depth is a colour output.
- **Which draws write them:** `Pipeline::writesGBuffer` (opaque, depth-writing, default shader, not a particle, not colour mode 3) plus the terrain. Everything else has a zero write mask for the extra entries (`Pipeline::gbufferBlendAttachments`).
- **Blend state:** `Pipeline::GBufferBlendState` always writes `1 + outputs` entries, whatever pass a pipeline is compiled for. The main, preview and map views share a view id, and VSG keeps one compiled pipeline per view id, reused for any view whose merged states compare equal, so a count that followed the pass gave whichever view compiled first its way. Trying a different view id for the main view, or for the preview and map, hung the game at start (task 0026, stage a log); do not retry that without a stack of the hang (a dump shows every thread waiting, `dumpstack2.exe ... all` in the scratchpad).
- **Pitfall:** `Graphics::gbufferOutputs` and `TerrainMapSettings::gbufferOutputs` must be set before the first pipeline or terrain builder is made (`RenderManager`'s constructor does, before the scene exists); the pipeline caches do not include them in their keys.
- **Debug view:** `gbuffer debug view` (`normals`, `depth`) makes `Tonemap` draw a stored image instead of the scene (`Tonemap::DebugSources`); the shader variant is chosen in `setSource`, so set the parameters first.
- **Velocity (stage b):** `Render::Velocity` is a fullscreen pass after the scene (RG16F, `currentUV - previousUV`) built from the linear depth and one matrix, `Velocity::toPreviousClip`, formed in double precision; `RenderManager::updateVelocity` resets the previous camera on the first frame, after a jump, and after a gap of a quarter of a second. Every pixel is treated as static, so only camera motion is in it. Its CPU twin is `GBuffer::reprojectVelocity`: change both together (shader: `files/shaders/post/velocity.frag` and `velocity.slang`).
- **Object motion (stage c):** output 3, RG16F, the screen motion of skinned actors' bones. `Anim::Skin::keepPreviousMatrices` (set by `RenderManager` before any model loads, with the G-buffer on) makes the NIF and COLLADA loaders allocate bone arrays twice as long, the second half being the previous frame's matrices (`Skin::apply` keeps it; any code reading a bone array must treat the first half as the bones). `GBUFFER_MOTION` is added to both stages of a skinned, G-buffer-writing draw. Rigid objects that move as a whole have camera motion only.

## Ambient occlusion (task 0029, R2)

- **`[Rendering] ao`** (off by default; needs `hdr`, `gbuffer` and `pbr`, read at start by `MWRender::RenderManager`), `ao radius`, `ao strength`, `ao slices`, `ao steps`. Off, none of the objects below exist: no ambient output, no `GBUFFER_AMBIENT` define, no pass, no tonemap variant.
- **The ambient output** is the fifth extra colour output (`GBuffer::ambientFormat`, `HdrTarget::ambientView()`): the ambient part of each opaque pixel's colour, which `default/main.frag` writes beside the colour (terrain: zero). The pass reads the stored linear depth and normals and writes a half resolution R8 image (`AmbientOcclusion`, `Ao::halfExtent`); the tonemap's AO variant filters it (5 by 5, `Ao::bilateralWeight`) and subtracts `ambient * (1 - ao)`.
- **The twins** are `aomath.hpp` and the shaders `files/shaders/post/ao.frag` (the slice integral, the horizon cosine) and `post/tonemap.frag` (the filter weights), each with its Slang twin (`ao.slang`, `tonemap.slang`): change them together. `ao radius`, `ao slices` and `ao steps` reach the shader through `ao.settings` (`Resource::ShaderSettings`; specialization constants 1100 to 1102 in the twin). The tonemap's push constants are the parameters, then the occlusion's (with AO), then the debug view's (with a debug view): `Tonemap::setSource` computes the offsets.
- **Pitfall:** GCC refuses a default argument of a nested struct type that has member initializers, so `Tonemap::setSource` has an overload instead of a default for `AoSources`.
- **Terrain (task 0048):** with `[Rendering] ao terrain` (off by default; only with `ao` on, `RenderManager` passes `TerrainMapSettings::aoTerrain`) the terrain pipeline gets the define `AO_TERRAIN` and `terrain/main.frag` writes the ambient part: the colour just before the lighting multiply (wetness and cover included) times the ambient light, the colour term (`getAmbient(vertexColor)`) and the scale that lighting branch uses (PBR: diffuse scale times the `_rmaos` occlusion; otherwise 1; the ambient light is the sky-visibility field's under `GI_SKY`), times the fog's share (`applyFog(1) - applyFog(0)`, as objects do). CPU twin: `Render::Ao::terrainAmbientPart`, `useTerrainAo`. Off, the terrain writes zero and the shader is as before. Terrain depth and normals always entered the pass, so terrain occludes objects with or without this. The shader edit is inside the existing terrain GLSL (decision 0009: new shaders only are Slang).

## Temporal accumulation of ambient occlusion (task 0076)

- **`[Rendering] ao temporal`** (off by default; needs `ao`, hence `hdr`, `gbuffer` and `pbr`; read at start by `MWRender::RenderManager`), `ao temporal history` (0.5 to 0.98, default 0.9), `ao temporal clamp` (0 to 4, default 0 = none since decision 0012; the clamp is Salvi's variance box, patent US10116916B2, so it is an opt-in; 1.0 halves the trail behind a rigid mover), `ao temporal debug` (`none`, `raw`, `weight`, `reject`, `static`; shown by `gbuffer debug view = ao`). Off, none of the objects below exist: `mAmbientOcclusion` (the fragment pass of task 0029) is made and everything is as before (frames compared in the stage log). On, **the compute pass replaces the fragment pass** (`mAmbientOcclusion` is not made); the tonemap's 5x5 filter (`aoFiltered`) stays the last step and reads the accumulated image through `aoSources()` unchanged.
- **Why a second generator and not an edit of `ao.frag`:** moving the noise needs a change in the generating shader, `PostPassesSwitchOff` pins the SPIR-V of `ao.frag`, and a Slang-only fragment stage cannot sit beside the GLSL `fullscreen.vert` (`files/shaders/CLAUDE.md`, "A mixed pipeline draws nothing"). So `files/shaders/post/aotemporal.slang` has its own copy of the GTAO maths (the twin of `Render::Ao::gtaoSliceVisibility` and `horizonCosine`, from `ao.slang`); change `ao.slang`, `aomath.hpp` and it together.
- **The pass** (`Render::AoTemporalPass`, `aotemporal.*`; maths `aotemporalmath.hpp`, `Render::Ao::Temporal`): three dispatches over the half-resolution image, node placed after the velocity pass and before the TAA node. `genMain` writes the raw value (R32F) with `rotateNoise(spatialNoise, noiseOffset(frame))`, Roberts' R2 sequence on a 64-frame cycle added to the interleaved gradient noise of the shipped pass (offset 0 is the shipped noise). `resolveMain` reads the history (RGBA32F: value, `log2(1 + depth)`, a count, an octahedral normal packed in 24 bits, exact in a float) at the four texels round `uv - velocity + jitterDelta`, each weighted `bilinear * (1 - depthMismatch) * normalMatch` (depth: the surface's depth in the previous camera, `w` of `toPreviousClip * (viewPosition, 1)`, against the stored one; normal: the current normal rotated into the previous view by `relativeRotation` against the stored one), limits the history value to the variance range of the same-surface 3x3 raw values (`ao temporal clamp`), and blends `confidence * min(base, count / (count + 1))`: a cumulative average at the start (0.5, 0.67, 0.75 ...), settling at `base` after nine frames. `copyMain` copies the result into the history (a separate image, as TAA). The result image is `GENERAL` while written and `SHADER_READ_ONLY_OPTIMAL` after, where the tonemap samples its first channel.
- **A 24-bit pack and 32-bit floats are on purpose:** the history cannot be 8 bit (an exponential average at 0.9 stalls: the step rounds away) and the G-buffer is overwritten every frame, so the history carries its own depth and normal.
- **Push constants:** six vec4 (96 bytes): the last row of `toPreviousClip` (only the previous depth is needed: the motion comes from the velocity image), three rows of the relative rotation with the projection's x and y scale and the history weight in their `w`, the noise offset and the TAA jitter delta, and the debug view and clamp. The occlusion's own settings (`ao radius`, `slices`, `steps`) are specialization constants 1100 to 1102 set on the pipeline stage by the pass, as `aosettings.slang` has them.
- **The centre texel rule (found by the frames):** a half-resolution pixel's centre lies exactly on the corner of four full-resolution texels. The fragment pass takes the surface's position at that corner but the depth of whichever texel the hardware's nearest filter picks by the rounding of its interpolated coordinate, and the horizon search is then measured from the corner: a fixed pattern of dots on planes and checks on walls in its picture, which averaging over frames cannot remove. The compute pass takes the lower right texel (with a 0.001 texel bias, so a float tie always goes the same way: without it the choice flipped pixel by pixel and the picture was almost white), its centre as the position, and measures the samples from there. So `ao temporal debug = static` (no noise offset, no history) is **not** the old picture: 21 percent of its pixels differ from `ao temporal = false` by more than 8 grey levels (the pattern is gone), the picture is a cleaner one. Anyone comparing the two must use this rule, not rounding noise.
- **TAA:** with `taa` on the pass takes `temporalState()`'s frame index and the delta of the two jitters (`jitterDeltaUv`: the history texel was written with the previous frame's shift); with it off a counter of its own and no jitter. The reset is `Render::Taa::historyReset` fed with the same camera data in `RenderManager::updateVelocity` in both cases, plus `warmupFrames` (3) after a build (a resize rebuilds the pass: the history is discarded on those frames).
- **What it cannot see:** rigid objects that move as a whole have camera motion only in the velocity image, so their history comes from the wrong place and only the depth and normal tests and the clamp reject it (a trail follows it while it moves and the picture is at the still level again when it stops; sliding barrel, stage log). The ambient image the tonemap subtracts from is still this frame's, not accumulated (at a silhouette it and the TAA-resolved colour differ by a sub-pixel, as before).
- **Cost** (RTX 4070, `gpu timing`, medians of the 500 rendered frames): the `ao temporal` pass takes 0.17 to 0.20 ms at 1280 x 720 against 0.15 to 0.17 for the `ao` pass (+0.02 to 0.03) and 0.42 to 0.47 against 0.36 to 0.41 at 1920 x 1080 (+0.06); memory: R32F raw (not R16F: it is not a guaranteed storage image format) + 2 RGBA32F at half resolution, 18.7 MB at 1080p. CPU frame time did not move beyond the spread. **A pitfall of the stats file:** `OPENEDEN_FRAME_STATS_FILE` also has one line for every idle loop iteration (about four times as many as rendered frames, 0.008 ms of GPU main scene each): take the median over rows whose `gpu_main_scene` is above 0.1.
- **Known limits:** at a grazing angle (distant ground) a half-resolution pixel spans more depth than `depthMismatch`'s window, so the history is partly rejected there; the tonemap's `aoFiltered` compares depth and normal at the pixel's corner while the pass computed the value for its lower right texel (predates the task); a history image that never got its layout (three `beginFrame` calls with no recorded frame) is guarded only by skipping non-finite taps.
- **Not built:** contact shadows (the renderer has no separate sun-diffuse term to darken, research note 0038 section 6), a narrower tonemap filter, a per-object motion for rigid movers, accumulating the ambient image.

## Subsurface scattering of skin (task 0033, R7)

- **`[Rendering] sss`** (off by default; needs `hdr`, `gbuffer` and `pbr`, read at start by `MWRender::RenderManager`), `sss strength` (0 to 1, default 0.8; was 0.5), `sss width` (game units, default 1.0; was 0.7). Off, no `SSS` define, no bindings, no push constant: the tonemap's shader is the one without it.
- **It lives in the tonemap's fragment shader** (`files/shaders/post/tonemap.frag` and `tonemap.slang`, `sssApply`), not in a pass of its own: for a pixel whose material output alpha (the skin mark) is set, each channel is multiplied by a gain, the wide Gaussian average of neighbouring skin on the same surface over a very narrow one. Bindings 10 to 12 (material, linear depth, normal), push constants after the occlusion's and before the debug view's (`Tonemap::setSource` computes the offsets). `Tonemap::Parameters::sssFocalPixels` is set every frame from the projection (`RenderManager::onFrame`), because the blur has a size in the world.

## The atmosphere (task 0034, R6 stages a to c)

- **`[Rendering] atmosphere`** (off by default; needs `hdr`), `atmosphere look` (`vanilla` or `physical`). Off, the weather manager hands the renderer its own result and nothing below runs.
- **`atmospheremath.hpp`** has no shader twin: the model runs on the CPU, once per frame, in `MWWorld::WeatherManager::applyAtmosphere` (`apps/openmw/mwworld/weather.cpp`), on a copy of the weather's result (`mAtmosphereResult`; `mResult` is never changed, so records, scripts, sounds and transitions are untouched). It changes the sky, ambient, sun, sun disc and fog colours and `mCloudTint`. The fog distance is not touched.
- **Blending rules:** weight = `dayWeight(sun height) * clearness`, and `clearness` is the weather's `Glare_View`. Night, and any weather with no glare, give the vanilla colours exactly. The sun height comes from the manager's own sun vector (negated at night, where the manager mirrors it), so the model follows the sun that is drawn.
- **Colour spaces:** all `Colours` are display-encoded, like the weather's own. The cloud shader multiplies encoded colours, so the cloud tint is encoded too (found by the reviewer).
- **Clouds:** `sky/clouds/main.frag` multiplies by `material.diffuse.xyz` (`Pipeline::Material::setTint`), white unless the atmosphere sets it.
- **Fixing the weather and hour for frames:** start in an interior, run `ChangeWeather "Bitter Coast Region" <id>`, `coc "Seyda Neen"` (entering a new region forces that weather at once, `WeatherManager::playerTeleported`), `set gamehour to <h>`, `set timescale to 1`.
- **Not built:** moon light, a sun glow in the fog (no room in the scene uniform block), volumetric clouds, surface wetness, snow and ash cover, precipitation changes.
- **The hour the model uses (decision 0010 answer 4):** with `[Rendering] sun follows colour tables` (default on, only matters with `atmosphere`), `WeatherManager::update` gives `applyAtmosphere` `Render::Sun::tableElevation(hour, windows)` (`sunmath.hpp`), not the drawn sun's height, so the sunset colours come at the middle of the colour tables' sunset window (about 18:30 by default, for the Sky table). Colours only: the drawn sun, the light direction and the shadows keep the orbit.
- **Eyes are not skin (decision 0010 answer 5):** `OverrideTable::resolveValues` does not give a skin-marked model's texture the mark when `Render::Pbr::isEyeTexture` says its name has the word eye or eyes in it.

## Exterior ambient light from a sky-visibility field (task 0036)

- **`[Rendering] gi exterior`** (off by default; needs `hdr`, `pbr` and `atmosphere`, read at start by `MWRender::RenderManager`), `gi exterior strength` (0 to 2). Off, no `GI_SKY` define exists, bindings 12 and 13 hold stand-ins and nothing below runs. It is independent of `gi` (interiors); `GI_SKY` implies the `GI` define, so the interior probe and reflection bindings must be bound (dummies) when only `gi exterior` is on.
- **What is baked** is only how much sky each place sees (never light): `skyvisibility.hpp` (the data and the `openeden.skyvis` v1 file: `openeden/probes/exterior/<x>_<y>.skyvis.json`, the parser with located errors and a canonical writer), `skyvismath.hpp` (the SH visibility maths, the sky projected to SH, `skyOcclusionNormal`), `skyvisbake.*` (the pure baker, deterministic: a probe's random numbers depend only on the seed and its place in the world's lattice, so two cells agree bit for bit on their shared border), `skyvisgpu.hpp` (the layout of the two buffers and the C++ twin of the shader), `skyvisdebug.hpp` (`gi debug` markers). `files/shaders/lib/view/skyvis.glsl` repeats the sampling and `skyOcclusionNormal`: change them together.
- **The lattice follows the ground:** 33 by 33 columns a cell (256 units apart, the cell's border columns shared with its neighbour), 8 levels a column from half a level spacing (64 units) above the ground height, 128 apart, so no probe is pruned whatever the terrain does. Numbers are stored as 16-bit integers over 4096 (about 450 KB a cell of JSON, measured).
- **The formula (a deliberate change from the spec's plain dot product, so that open ground equals the flat ambient):** the result is `flatAmbient * mix(1, kept, weightSum)`, `kept = max(1 - strength * (1 - occ), 0)`, `occ = skyOcclusionNormal(sky, V, normal)`: the share of the cosine weighted sky that the surface facing `normal` sees (`visCosine` of the interpolated visibility against what open flat ground gives, `0.5 + 0.5 z`), times the colour shift that comes from seeing only part of the sky (`skyOcclusion`, divided by the plain share so it is not counted twice). Open flat ground keeps all of the flat ambient for any sky; a point in the air is capped at the flat ambient. The sky is the atmosphere's sky colour (zenith) and fog colour (horizon) with a ground colour at `groundSkyFactor` of the horizon, projected to SH by `skyFromColours` and written to the header only when the colours move.
- **Cell borders:** `weightSum` is the share of the four surrounding columns that have data, so a baked cell next to an unbaked one fades to the flat ambient across one column, and two baked cells share their border columns exactly. Beyond the loaded set the field ends (flat ambient).
- **Buffers:** binding 12 the cells' floats (`skyPoolVec4s`, 8.6 MB, up to 27 default cells), binding 13 the header (sky SH, strength, a slot per cell of a 7 by 7 window). The pool is rewritten only when the set of loaded cells changes (`RenderManager::exteriorCellLoaded` / `Unloaded`, called from `Scene::loadCell` / `unloadCell`, files read once per load and parsed on the render thread in `onFrame`). Every creator of a view descriptor set must add `View::dummySkyVis()` and `View::dummySkyVisSky()`; the editor's `SceneHost` does.
- **The terrain** takes the field too (`GI_SKY` in `terrain/main.frag`, `TerrainMapSettings::giSky`); actors, statics and groundcover use `default/main.frag`.
- **Baked enclosed probes are filled in:** a probe from which no ray escapes and every ray stops within `defaultEnclosedDistance` (2048) is taken to be inside a closed room or a solid mass and filled from its neighbours, since its darkness would otherwise leak onto the outside of the walls (found by the frame check: a house wall went nearly black at dusk).
- **The sky environment image (stage d)** is one octahedral reflection probe (`skyenvmath.hpp`) written into the reflection buffer (binding 11) while any exterior cell is loaded, rebuilt only when the sky or horizon colour moves by more than `skyEnvironmentTolerance`; `RenderManager::mSkyEnvOwns` says who owns the buffer (an interior's own reflection probes take it back when it loads).
- **What is not built:** bounce light (D12); a sun term in the sky (the sky depends on the height of the direction only); lobe-aware colour (the colour shift is normal independent); distance beyond the loaded cells; the editor's view of the field. Terrain slopes and hills lower the visibility (open ground in Seyda Neen reads about 0.8, not 1), so the default strength darkens ambient there: judge it by eye.

- **`wetnessmath.hpp`** (`Render::Wetness`) holds the pure parts: the curve (`target`, `step`), `darkening`, `roughness`, `flatness`, `puddleFill`, `noise`, `puddleMask`, `exposure`, `waterFresnel`, `ripple`. `files/shaders/lib/material/wetness.glsl` repeats them (the hash and the noise bit for bit): change both together. Tests: `apps/components_tests/render/testwetnessmath.cpp`.
- **The value** is worked out by `MWWorld::WeatherManager::updateWetness` (`weather.cpp`): it heads for `target(!mResult.mRainEffect.empty(), mResult.mPrecipitationAlpha)` (rain and thunderstorm wet; snow, ash, clear and cloudy do not), rises over 20 s of game time, falls over `wetness dry time`, and is told to the renderer as 0 indoors. It is not saved: after a load it builds up again. `RenderManager::setWetness` keeps it; `updateSceneData` writes `1 + wetness * strength` into `Scene.ambient.w` (the scene block cannot grow). The shaders read `max(ambient.w - 1, 0)`, so the map, the preview and the editor (alpha 1 or 0) see a dry world. Later weather effects (snow cover, task 0039) can read the same value, and `mWetness` is the place to add a second state.
- **Where it is applied:** `default/main.frag` (`WET_LIT`: lit surfaces with `PBR`: statics, actors, groundcover) and `terrain/main.frag`, defines `WETNESS`, `WETNESS_PUDDLES`, `WETNESS_DEBUG` added by `Pipeline::Graphics` (`wetnessEnabled`...) and `Pipeline::terrain` (`WetnessOptions`, through `TerrainMapSettings::wetness`). Darker (diffuse times `darkening`, rougher surfaces more), glossier (`roughness` towards 0.18, never rougher), puddles on near-horizontal surfaces (slope under about 8 degrees fully, 20 degrees not at all) where a two-octave value noise is high, with the shading normal flattened and tilted by ripples while it rains (`scene.rainIntensity`), mirroring the sky: the sky environment image (binding 11) when `gi exterior` owns it, else a gradient from the fog to the sky colour. Skin (`material.subsurface`), glowing surfaces and metals (for the darkening) stay dry; the G-buffer's stored roughness is the dry one.
- **Shelter (a decision, spec D3):** not a new top-down depth map. The sky visibility field of task 0036 already says how much sky a flat surface facing up sees (`skyVisUp` in `lib/view/skyvis.glsl`, `visCosine(V, up)`), so `exposure` fades wetness by it: under a roof, bridge or eave wider than the field's 256 unit spacing it is zero. Without `gi exterior`, or in a cell with no baked file, nothing says a place is covered and everything outdoors gets wet. The existing precipitation occluder (`weather particle occlusion`) was not used: it exists only while it rains, only around the camera, and its map is bound in the per-material texture set, not the view set.
- **Pitfall:** `skyVisAmbient` now calls `skyVisSample`, the interpolation it used to hold; `skyVisUp` is the same lookup for the up direction. Change them together.
- **Not built:** wet maps for the material model's metalness, drips, ground water in dips (puddles do not know about hollows, only slope and noise), the shelter of individual eaves narrower than the field, wetness of particles and water.

## Cloud shading and cloud shadows (task 0038)

- **`[Rendering] clouds`** (off by default; needs `hdr`), `clouds look` (`lit` or `flat`), **`cloud shadows`** (off; needs `hdr` and `atmosphere`), `cloud shadow strength` (0 to 1), `cloud shadow debug` (shows only the clouds' shadow, ignoring the shadow maps). All are read at start. Off, nothing below exists: the cloud shader's `cCloudsLit` is a constant `false`, `shadow.settings` has no `CLOUD_SHADOW`, and the header buffer holds a stand-in.
- **`cloudmath.hpp`** (`Render::Cloud`) is the pure part: `thickness` (from a picture pixel's brightness and alpha), the lit look (`transmittance`, `forwardPhase`, `silverLining`, `undersideShade`, `litMultiplier`, `strength`, `weatherShare`), the dome (`domePoint`, `domeUv`: the cloud model `meshes/sky_clouds_01.nif` is a dome whose UVs are a flat projection of the vertex's X and Y, read from the file's vertices) and the shadow (`shadowDirection`, `sunFade`, `shadowFactor`, the 64 by 64 grid `buildGrid` and `sampleGrid`). `files/shaders/sky/clouds/lit.glsl` and `files/shaders/lib/view/cloudshadow.glsl` repeat it: change them together. Tests: `apps/components_tests/render/testcloudmath.cpp`.
- **Lit clouds** are in `sky/clouds/main.frag` (after the existing tint, in linear light). The vertex shader gives it the vertex in dome space and the sun direction in dome space. The weather's share of the effect (`weatherShare`: storms 0, the rest by glare, no less than half) is moved to its target over 3 s of game time by `Sky::update` and rides in the cloud material's `specular.a` (unused by the cloud shader; 0 when the look is off).
- **Cloud shadows** are one term in `shadow()` (`lib/view/shadow.glsl`), the single place every sun term (statics, terrain, groundcover, actors, water glints) takes its shadow from, so there are no hunks in the lit shaders. The ground point is sent along the sun's direction to a layer 15000 units up (`layerHeight`), seen from the camera, and that direction is looked up in the grid of each cloud layer through the dome's UV mapping, the scroll and the layer's rotation, so the shadow is the very pixel of the picture the sky draws in that direction. At the camera the sun's own direction gives the cloud at the sun.
- **The data path (no new view binding):** the grids (one per picture, built on the CPU from the pixels when the picture is first read, `Sky::getOrCreateCloudTexture`), scroll, rotations and strength sit at the end of binding 13 (`skyHeader`, `cloudgpu.hpp`), after the sky-visibility entries, and are written every frame by `RenderManager::updateCloudShadow`. With `cloud shadows` on and `gi exterior` off the main view binds the real header and a stand-in pool; `skyvis.glsl` leaves out its own declaration of the header when `CLOUD_SHADOW` is defined (`cloudshadow.glsl` declares it first). Every other view's stand-in (`View::dummySkyVisSky`) is as long as the real header, so a view that does not write it reads strength 0.
- **Night and uploads:** the strength is also scaled by the light's luminance (`Render::Cloud::strength`), so the night's mirrored light casts no shadows; the scroll goes up as its fraction (the grids wrap). `RenderManager::updateCloudShadow` uploads the header only when the grids, strength, rotation or layer set change, or the scroll moves by `Render::Cloud::scrollStep` (cost: `docs/research/0019-cloud-cost.md`).
- **Pitfall:** the clouds' pictures are 8 bit BGRA `.dds` files read as `VK_FORMAT_B8G8R8A8_UNORM`; another format gives a warning in the log and no shadow (`buildCloudGrid`).
- **Not built:** ray marched volumetric clouds (task 0042); shadows from the moon; clouds casting shadows on other clouds.
- **What a volumetric cloud pass would need (stage e, notes only, nothing built):**
  - *A density field.* The two flat layers have a 64 by 64 thickness grid per picture (`Sky::mCloudGrids`); a 3D field would be 3D noise shaped by that grid as the coverage map, or a froxel volume in front of the camera. The grids, the weather's `weatherShare`, the blend and the scroll already reach the GPU (`cloudgpu.hpp`) and can seed it; the dome's UV mapping (`domePoint`, `domeUv`) says where the picture's feature sits for a direction.
  - *Light.* The sun's direction and colour are in the scene block (`lightViewPos`, `lightDiffuse`); the ray's march toward the sun can reuse `shadowFactor`'s exponential. The sun shadow cascades (`shadow()`) are for geometry only and are not needed for sky; the cloud shadow term inside `shadow()` is the place to read the field's transmittance toward the sun instead of the grid.
  - *A temporal filter.* A marched field is noisy at a low step count; F3's velocity buffer (`Render::Velocity`, camera motion only) would reproject last frame's result. That needs the field drawn into its own target and composited in the tonemap or before it, and a history that is rejected when the weather changes.
  - *Budget.* The lit look above is a few tens of operations per sky pixel; a march is dozens of steps. Task 0042's quality tiers (step count, resolution, half-resolution target) are the place to buy it back. The cost measurement method of `docs/research/0019-cloud-cost.md` is the place to start.

## Snow and ash cover (task 0039)

- **`[Rendering] cover`** (off by default; needs `hdr` and `pbr`, read at start by `MWRender::RenderManager`), `cover strength` (0 to 1), `cover build time` (seconds of game time of steady snow or ash to bury the ground, default 1200), `cover melt time` (seconds for snow to melt, default 7200; ash fades four times slower), `cover debug` (cover amount in red, upwardness in green, the covered share in blue). Off, no `COVER` define exists and the scene's ambient alpha is not touched.
- **`covermath.hpp`** (`Render::Cover`) holds the pure parts: the state and its step (`step`, `dominant`), `upwardness`, `coverNoise`, `coverMask`, the kinds' `colour` and `roughness`, and `pack` / `unpack`. `files/shaders/lib/material/cover.glsl` repeats them; a unit test reads the shader's constants back from the file (`RenderCover.shaderTwinHoldsTheSameConstants`). Change both together. Tests: `apps/components_tests/render/testcovermath.cpp`.
- **The value** is worked out by `MWWorld::WeatherManager::updateCover` (`weather.cpp`) from the kind of particles the weather result has: `weathersnow` or `weatherblizzard` build snow, `weatherashcloud` or `weatherblightcloud` build ash, anything else (rain, clear, cloudy, mod weathers with other particle files) builds nothing. It follows `mPrecipitationAlpha` through a transition, is not saved, and is told to the renderer as nothing indoors (`RenderManager::setCover`).
- **How it reaches the shaders:** the scene block has no spare float, so the cover shares `Scene.ambient.w` with the wetness: `1 + wetness + 2 x code`, the code being 0 (bare), 1 to 128 (snow, in steps of 1/128) or 129 to 256 (ash). Without cover the alpha is exactly task 0037's `1 + wetness`; `wetness.glsl` takes the code out before it reads the wetness (`raw -= 2 floor(raw / 2)`), so the two work together. The renderer sends only the larger of the two kinds on the ground.
- **Where it is applied:** `default/main.frag` (`COVER_LIT`: lit surfaces with `PBR`) and `terrain/main.frag` (defines `COVER`, `COVER_DEBUG` from `Pipeline::Graphics::coverEnabled` and `Pipeline::CoverOptions`, through `TerrainMapSettings::cover`). A pixel's cover share is `coverMask(amount, upwardness, exposure, noise)`: the world normal's Z, shelter from `wetExposure(skyVisUp)` (the same field and the same limits as the wetness: it needs `gi exterior` and a baked cell), and the wetness task's value noise at 36 units. The surface colour is replaced by the kind's colour and its roughness raised, metalness removed; skin and glowing surfaces stay bare. The terrain also loses the hue of its colour map under cover (it keeps the shading), or snow would come out green.
- **Not built:** wet snow (gloss), footprints, a different cover on groundcover only (it takes the same path as statics), telling actors from statics (armour on an actor gets cover on its upward faces), cover from two kinds at once in one place (the larger shows).

## Precipitation, lightning and the sun's glow (task 0040)

- **Settings** (all off by default, read at start): `[Rendering] precipitation lighting` (needs `hdr`), `lightning`, `lightning strength` (0 to 2), `lightning debug age` (-1 = off) (need `hdr`), `sun glow`, `sun glow strength` (0 to 2), `sun glow debug` (need `hdr` and `atmosphere`). Off, nothing changes: the shaders' new code is behind a define (`PRECIPITATION_LIT`) or a constant in `fog.settings` (`cSunGlow`), and clear weather is frame-identical even with all three on (haze 0, no strike).
- **Lightning** (`lightningmath.hpp`, `Render::Lightning`; the weather manager runs it, `MWWorld::WeatherManager::updateLightning`): the vanilla thunder schedule (`Weather::calculateThunder`, which also plays the sound) is unchanged and reports each strike (`Weather::takeStrike`); a strike starts a flash unless one started less than `minInterval` (1.5 s) ago. The flash is a double flicker (`envelope`) of brightness at most `peakCap` (1, the closest vanilla strike) whatever the setting, as a cold white-blue add (`colourAdd`) to the sun, ambient and fog colours **in place of** the vanilla white flash, and the sun's light (and so the shadows) tilts towards a direction in the clouds (`direction(seed, strikeCount)`, a hash, no generator state and no clock) by the flash's share of the light (`mergedDirection`, `RenderManager::updateSceneData`). One merged light, not a second light in the shaders: it needs no shader code, buffer or descriptor, and the flash shadows come free; the price is that a flash has one direction for all surfaces (no sun and flash shadows at once) and that it lights from the cloud direction even where the sun is. Time is the frame time summed while the game runs (`mLightningTime`), rebased each hour; indoors the renderer is told 0. **Photosensitivity:** the cap and the interval are the limits, unit-tested over dense storms, and two strokes of a flash 0.22 s apart with flashes 1.5 s apart mean at most two peaks in any second (WCAG 2.2 2.3.1 allows three). Do not raise either without toddhow. `lightning debug age = A` holds one flash at age A seconds in any exterior weather: it is the way to frame a flash, since the vanilla schedule is random.
- **Sun glow** (`atmospheremath.hpp`, `sunGlow` and its parts; twin: the top of `files/shaders/lib/view/fog.glsl`): a Henyey-Greenstein lobe (g 0.7) added to the fog colour (`applyFog(src, viewPos)`, so statics and terrain) and to the sky dome (`sky/atmosphere`, with a view direction from its vertices), with brightness from the fog's own, colour from the air model's sun transmittance for hazy air (warm when the sun is low), weight from the weather's haze (`1 - Glare_View`, read from `scene.skyColor.w`: clear weather has none) and fading out when the light is too dim to be the sun. The cloud layer, the water's own fog and the sun disc have no glow of their own.
- **Precipitation light** (`precipitationmath.hpp`; twin: `files/shaders/lib/light/precipitation.glsl`): rain (`MWRender::Rain`, pipeline mode `PRECIPITATION_LIT`) is lit as scattering streaks: ambient from every side, the sun by a soft forward lobe (g 0.5), every lamp near it without regard to its side (the light grid, `precipPointLights`), with far streaks fading out and fast rain drawn longer (`streakStretch`). Snow (and blizzard) keeps the shader's ambient lighting but loses the NIF's constant emissive glow (0.3 on every flake, which lit them at night): the emissive is replaced each frame by the sun's part (`snowSunLight`, `WeatherEffects::setSunLight`), one colour for the whole fall. Ash falls as before, and snow gets no lamp light.
- **Not built:** a second real light for lightning (and its shadow beside the sun's), lightning through windows, lamps on snow, glow in the cloud layer, the glow in the editor (its views leave `cSunGlow` as the editor's own settings say: off).

## Volumetric fog and light shafts (task 0041)

- **Settings** (read at start): `[Rendering] volumetrics` (off; needs `hdr`), `volumetrics quality` (`low`, `medium`, `high`: froxel grids of 80x45x32, 160x90x64, 240x135x96), `volumetrics density` (1 = the weather's own fog), `volumetrics anisotropy` (the Henyey-Greenstein lobe, -0.95 to 0.95), `volumetrics temporal` (not at `low`), `volumetrics debug` (the fog holds the sun's shadow: red the shadow, green cascades set, blue the last cascade has a split). Off, nothing below exists: the view set binds stand-ins (bindings 14 and 15, parameters that say "off"), `cVolumetrics` in `fog.settings` is false, no image, no pipeline, no bin.
- **What it is:** a grid of boxes that follow the camera's view ("froxels": x and y across the screen, z along the view axis in exponentially spaced slices, `sliceDepth`). `files/shaders/comp/volume/volume.slang` (Slang, decision 0009) has three passes: `fillMain` (per froxel: the fog's density, and the light it scatters: the weather's fog colour, the lamps of the light grid, the sun times its shadow cascade lookup times a Henyey-Greenstein lobe), `temporalMain` (blend with last frame's blend, found through the previous camera's matrices) and `integrateMain` (front to back, exact for a slice of uniform fog). `View::VolumeFog` (`components/view/volumefog.*`) owns the images and commands; `Render::Volume` (`volumemath.hpp`, `volumegpu.hpp`) is the pure part and the parameter block (`buildParams`).
- **Twins, change together:** `volumemath.hpp` (`sliceDepth`, `sliceCoordinate`, `henyeyGreenstein`, `integrateSlice`, `fogExtinction`, `jitter`), `volume.slang`, `lib/view/volume.glsl` (the reader: slice coordinate, the texel convention: texel i holds the fog up to the far side of slice i, at position i + 0.5, so slice coordinate c is looked up at (c - 0.5) / slices and blends in from nothing below 1), and the parameter block in `volumegpu.hpp`, `volume.glsl` and `volume.slang` (a test compares the member order and the bindings).
- **The read is in `applyFog(src, viewPos)`** (`lib/view/fog.glsl`): the volume gives a transmittance T and scattered light S; the fog is mixed as `mix(toEncoded(src), toEncoded(S / (1 - T)), 1 - T)`, in the display encoding like the old fog, so a volume holding only the fog colour looks like the old exponential fog. Past the grid the same density goes on. The old fog and the sun glow (task 0040) are skipped where the volume applies; the sky dome keeps the glow; water's fog and underwater (`enabled` = 0 under water) are the old ones.
- **Order on the GPU:** shadow cascades (submit order -3), light grid (-2), volume (-1), scene (0), only with the volume on; graphs with the same order submit in whatever order their threads finish recording, so a graph that reads another's output needs its own number. The commands begin with a barrier that drops the images' old contents (UNDEFINED to GENERAL; the history images only on the first frame) and covers the shadow depth writes and the light grid writes; the images stay in GENERAL layout.
- **Shadows:** the volume uses the cascades only when `[Shadows] enable shadows` is on and never forces them. `enable shadows` alone draws nothing into them: `object shadows`, `terrain shadows`, `actor shadows` and `player shadows` default to off. Without cascades the sun lights the whole fog evenly (a glow, no shafts). `object shadows = true` used to crash the game (a shadow cascade's view kept a default `vsg::ViewDependentState`; fixed in task 0052, see `apps/openmw/mwrender/CLAUDE.md`); with it on, buildings and trees cut the sun's light in the fog (a glow broken by a trunk's shadow, task 0052 frames).
- **Not in version 1:** cloud shadows in the fog, local fog volumes from a data file, particles that write density, underwater volumes, the editor (its `SceneHost` binds the stand-ins), soft shadows in the fog.
- **What a volumetric cloud pass (task 0042) can share:** the froxel grid and its slice mapping (`sliceDepth`) for clouds in front of the camera, the sun lookup `sunShadow` in `volume.slang` (cascade choice and fade, port of `shadowMaps`), the Henyey-Greenstein function and `integrateSlice`, `View::VolumeFog`'s image and barrier handling, and the temporal blend with the previous camera's matrices. The clouds' own shadow data is in binding 13 (`cloudgpu.hpp`) and is not read by the volume yet.

## Ray-marched volumetric clouds (task 0042)

- **Settings** (read at start): `[Rendering] volumetric clouds` (off; needs `hdr` and `atmosphere`), `volumetric clouds quality` (`low`, `medium`, `high`: the march image is 1/8, 1/4 or 1/2 of the screen, 24, 40 or 64 steps, 4, 5 or 6 sun samples a step), `volumetric clouds coverage scale` (0 to 2) and `density` (0 to 4), `volumetric clouds shadows` (on: the ground shadow), `volumetric clouds debug` (`none`, `transmittance`, `shape`, `detail`, `curl`). Off, nothing below exists: no images, pipelines, bin or graph; the view set's binding 16 holds a one texel stand-in (`View::dummyCloudShadow`), `cVolumetricClouds` and `VOLUME_CLOUD_SHADOW` are not defined, and the cloud dome's material flag is 0, so frames equal the previous build (the only difference between two runs is the vanilla clouds' scroll timing).
- **What it is:** a flat layer 1500 to 4000 m up (`layerBaseMeters`, `layerTopMeters`; metres become game units only in `metersToUnits`), filled with a density built from three noise textures the compute pass makes at start from a fixed seed (shape 128 cubed RGBA8: Perlin-Worley and three Worley; detail 32 cubed: three Worley and their fBm; a 128 squared curl noise). `files/shaders/comp/cloud/cloud.slang` (Slang, decision 0009; loaded whenever the setting is on, whatever `slang shaders` says; a missing file turns the clouds off with a log line) has seven passes: `noiseShape/Detail/CurlMain` (first three frames only), `marchMain` (the ray march: a cheap shape-only lookup skips empty space, then detail and the sun's light through 4 to 6 samples, `multiScatter` with 3 octaves, a powder term, ambient by height, haze by distance), `resolveMain` (full size: bicubic Catmull-Rom read of the march image shifted by this frame's jitter, history looked up through the camera's rotation only and clamped to the 3 by 3 march neighbourhoods of the four nearest texels mixed by the fraction, blend 0.9), `copyMain` (the history) and `shadowMain`.
- **Twins, change together:** `cloudvolumemath.hpp` (`Render::CloudVolume`: height gradient, density, Beer, powder, dual lobe phase, multi scatter, layer span, noise hash, Worley, Perlin; the GPU repeats the noise bit for bit and a test reads the shader's constants), `cloudvolumegpu.hpp` (the 10 vec4 parameter block, which lives in the cloud passes' own compute set, binding 10), `cloud.slang`. `apps/components_tests/render/testcloudvolumemath.cpp` holds regression values for the hash and noise: a port must reproduce them.
- **Weather (D4, D13):** the weather records have no coverage value, so the coverage comes from the cloud picture: the mean of its 64 by 64 thickness grid (`buildCloudGrid` of task 0038, built whenever `volumetric clouds` is on) through `coverageFromThickness`'s table (clear 0.19 gives 0.39, cloudy 0.43 gives 0.63, overcast 0.96 gives 1), blended by the manager's blend factor, so a weather change grows or thins the clouds. The wind is `windStep(weather.mCloudSpeed, dt)` along `windDirection`, summed in double in `Sky::update` and wrapped by `wrapWind`. `volumeShareTarget(isStorm, fogDepth)` is 0 for storms (ash, blight, blizzard) and for a land fog depth of 1 or more (fog, snow), eased over 3 s: with a share under 1 the vanilla layer of the weather draws on the second cloud dome beneath the volume.
- **How it reaches the screen (a decision, spec D9):** not through the tonemap. The resolved picture is bound as the diffuse texture of the first cloud dome (`Sky::setVolumeClouds`, `Clouds::setTexture`), and `sky/clouds/main.frag` reads it by screen position when the dome's material says so (`Material::setVolumeClouds`, emissive alpha), keeping the dome's horizon fade. So clouds sit exactly where vanilla clouds do in the draw order (behind the sun disc's glare and every opaque thing), the stars show through thin cloud, and there is no new binding for the colour.
- **Order on the GPU:** the cloud graph has submit order -4 (before the shadow cascades -3, light grid -2, fog volume -1 and the scene), because it reads only the scene block that the CPU writes. `View::CloudVolume::setEnabled(false)` stops the march, resolve and history while no volume is drawn (interiors, vanilla weathers, under water) and drops the history.
- **Ground shadow (D6):** `shadowMain` writes a 256 by 256 map of the sun's transmittance through the layer on the layer's middle plane, plus or minus 20 km round the camera, snapped to whole texels so it does not crawl, from the same density, wind and coverage as the march; two more texels of the image hold its placement and strength. View binding 16 (a combined sampler read with `texelFetch`) is the only new view binding: every creator of a view set (`rendermanager.cpp` twice, `map.cpp`, `preview.cpp`, the editor's `scenehost.cpp`) binds `View::dummyCloudShadow()`. `lib/view/volumecloudshadow.glsl` sends a ground point along the sun's ray to that plane and reads it; `shadow()` uses `cloudsShadow`, which mixes the vanilla layers' shadow (task 0038) with the volume's by the volume's share, so the two never add up. The shadow pass runs every frame, also when the clouds are not drawn (it then writes share 0).
- **Look of 2026-11-04 (stage log in `docs/tasks/0042-rendering-volumetric-clouds.md`):** the density reads the detail texture twice (`detailTileMeters` 800 and `detailFineTileMeters` 300, mixed by `combineDetail`: weight 0.4, contrast 1.6), `defaultErosion` is 0.85 and the sun is scaled by `sunPhaseScale` (2 pi, was 4 pi). Every detail tile must divide `shapeTileMeters` (12000), which `wrapWind` wraps by. **The march ray's dither is blue noise** (`bluenoise.hpp`, `Render::BlueNoise`: a 64 by 64 R8 texture made at start-up by void-and-cluster from a fixed seed, about 17 ms, nothing checked in; compute set binding 12 `blueTex`), offset by the golden ratio per frame (`ditherOffset`; the shader repeats it). **The grid of squares in a cloud's body came from the history clamp:** its min/max box was taken round the nearest march texel, so it changed in steps at every march texel edge; it is now the four nearest texels' boxes mixed by the fraction (`resolveMain`). The upscale is bicubic (`catmullRomWeights`, `clampToNearestTaps`).
- **Horizon, curved layer, variety (2026-11-05, all off by default):** `volumetric clouds horizon` lowers the volume's dome (`domeHorizonDrop`, `Sky::applyVolumeClouds`) and `Material::setVolumeClouds(on, true)` (ambient alpha 3) skips the dome's vertex fade: **the clear band above the horizon is the dome (rim 5.7 degrees up, alpha 0 / 0.25 / 1 by row), not the flat slab.** `curved layer` + `planet radius` (km) use the maths of `cloudcurvemath.hpp` (twin in `cloud.slang`; radii in metres, stable roots, planet centre below the camera, `curvedMaxRayMeters`, `farFade` into the haze; the ground shadow map stays flat); `variety` warps the shape lookup and moves the coverage by a lookup of the shape noise over `largeTileMeters` (84 km), and then the wind wraps by that tile (`wrapWind(double, float)`, chosen in `Sky::getVolumeClouds`; every tile must divide it). The parameter block has one extra vec4 after `toPreviousClip` (`curve`, `buildCurveParams`); `paramsVec4s` stays 10 for the old tests. Stage log: `docs/tasks/0042-rendering-volumetric-clouds.md`.
- **Limits and pitfalls:** the images are sized at start from the render target; a window resize keeps the picture correct (the dome samples by screen fraction) but not sharper. The camera is assumed below the layer (the march is for a camera on the ground); a very high camera (levitation above 1500 m) shows the layer from inside, which works only until the camera passes the base. The sun below the horizon casts no shadow and clouds are lit by `scene.lightDiffuse` (the manager's mirrored moon light at night). The march does not fade clouds with the weather's own fog end; the haze length is `hazeLengthMeters(fogEnd)`. A frame check of this pass needs the camera aimed at the sky: the console cannot after `coc`; use a Lua player script (`tools/benchmark_data/scripts/bench_look_up.lua`, the `look` option of `tools/benchmark.sh`).
- **Not built:** a second (cirrus) layer, a precomputed sky table (D10), clouds seen from above, shadows of clouds on other clouds, lightning inside the cloud, the editor (it never takes the setting), the clouds seen in water reflections (the reflection pass draws the vanilla layers).

## The procedural sun (task 0047)

- **`[Rendering] procedural sun`** (off by default; needs `hdr` and a build that has slangc), `procedural sun size` (0.25 to 2.5), `intensity` (1 to 100, default 30), `glow` (0 to 4). Read at start by `MWRender::Sky`'s constructor. Off, nothing below is created and the sun is the textured one exactly.
- **`sunmath.hpp`** (`Render::Sun`) is the maths and `files/shaders/sky/sun/proceduralsun.slang` repeats its constants (a test reads them back: `testproceduralsun.cpp`); change both together. The disc is drawn on the textured sun's quad. Its parameters ride in the sun's own material (`pbr.x` intensity, `pbr.y` glow scale, `pbr.z` disc radius; emissive is the colour and diffuse alpha the weather's alpha, as before).
- **A Slang-only graphics shader:** `Pipeline::Graphics::slangOnlyPaths` lists paths (here `sky/sunproc`) that have only `main.vert.spv` and `main.frag.spv` and no GLSL; `createShaderStage` reads those directly, whatever `slang shaders` says. `hasSlangShader(path)` says whether the files exist. A new Slang graphics shader can do the same.
- **What is not replaced:** the occlusion query, the flash and the glare overlay still use the textured `sky/sun` pipeline and are drawn over the disc. The moons stay textured.
- **Colour hour:** the disc's colour is the weather's sun colour, which follows the colour tables' hour with `atmosphere` and `sun follows colour tables` (task 0034).

## The runtime texture downscaler (task 0049)

- **Settings** (`[Rendering]`, all off by default, read at start by `RenderManager`'s constructor before any model or terrain read): `texture max size`, `texture max size terrain`, `texture max size objects` (0 or 16 to 8192, rounded down to a power of two), `texture memory budget` (`off`, `auto`), `texture downscale report` (one log line at exit). Off, every read returns the very same `vsg::Data` as before (a test checks the pointer).
- **Code:** `vsgutil/texturecap.*` is the decisions (`planLevels`, `capFromBudget`, `effectiveCap`, `bytesOfChain`) and `vsgutil/textureresize.*` the data operations (`dropMipLevels`, `shrinkUncompressed`, `applyCap`, the report). `vsgUtil::readImage` and `readOptionalImage` take an `ImageUse` (category, kind, floor, alpha cutoff); no category means never capped. Opted in: NIF and COLLADA textures and their `_n`, `_rmaos`, specular and `_p` maps (`Object`, `_p` floors at 256) and the terrain's layer, normal, material and height reads (`Terrain`). UI, water, sky, rain, HUD never opt in. `readImageFromMemory` has no caller that opts in, so it has no argument. No shader was added (decision 0009 does not apply).
- **Method:** drop top mip levels where a chain exists (exact, any format); box-filter shrink (stored values, after `removeSrgb`, so no gamma) only for single-level UNORM 8-bit images; a block-compressed image with one level stays full size and is counted as "left big". The `vsgdecompress` fallback (cards without BC) makes single-level RGBA8, so there every texture takes the shrink path.
- **Cache:** `vsg::read` keeps the full image in the shared objects; the capped copy is kept in a weak map in `readimage.cpp` keyed by (full image, cap, kind, cutoff), so users of one file share one capped image and two categories do not collide. CPU memory of the full image is not freed (it stays in `sharedObjects` until pruned); only GPU memory falls.
- **The `auto` table** (`texturecap.cpp`, `budgetBands`) is a first guess from the spec. Bands start at their lower bound. Device memory is `Render::Engine::deviceLocalMiB()`.
- **Terrain arrays stay one size:** the terrain builder reads each array's layers with `vsgUtil::readArrayImages`. If the cap leaves any layer over the cap (a single-level block-compressed image), the whole array is read again uncapped, so capping never turns a uniform array into a mixed one (which draws grey). Chosen over decode, shrink and re-encode (needs a BC encoder) and over padding (wrong texture coordinates).
- **Report:** `applyCapUncounted` returns what it did; only the loader thread whose capped image is kept in the cache records it, so racing threads do not double count.
- **Cutouts:** the NIF reader reads the node's `NiAlphaProperty` first (`handleProperties`) and passes the alpha test threshold as `ImageUse::alphaCutoff` for the base texture; a CPU shrink then keeps the share of texels that pass the test. It only matters for single-level uncompressed images (TGA, PNG); a DDS with a chain just loses levels. The cutoff is part of the cache key.
- **Budget setting:** `texture memory budget = <MiB>` behaves as `auto` on a card with that much device-local memory (`TextureCap::parseBudget`).
- **Known limits:** a map is capped by the same cap as its diffuse rather than by the diffuse's capped size; actors and objects share one cap; COLLADA reads pass no alpha cutoff.
- **Measured** (RTX 4070, Faultier data3, Balmora pose, nvidia-smi memory.used minus baseline, whole system so noisy): none +629 MiB, 1024 +369, 512 +254, 256 +222; `auto` on the 12 GiB card gave objects uncapped (+638). Simulated cards (`texture memory budget = 4096`, `6144`, `8192`): 4096 gives objects 1024, terrain 512 and +366 MiB (413 to 101 MiB of capped texture data); 6144 and 8192 give objects 2048, terrain 1024, which touches only 3 textures of the 2048 pack (+620 to +640 MiB).

## Depth is reversed (task 0066, stage a)

- The whole renderer stores depth as VSG's `perspective` writes it: 1 at the near plane, 0 at the far plane, D32_SFLOAT, compare GREATER, clear 0 (`depth.hpp`: `nearDepth`, `farDepth`). Do not set another compare op or clear value; use `Render::nearDepth` and `farDepth` for frustum corners. `depthmath.hpp` has the maths and the precision numbers (0.01 units out to 590,000 with near 1); the shaders' `depthBufferValueToViewZ` (`lib/view/depthbuffer.glsl`) is its twin. ## Aerial perspective, the haze of the whole-map view (task 0066, stage c)

- **Settings** (`[WorldLod]`, read at start for the shaders): `haze` (true; only has an effect with `map view`, `enabled` and `[Terrain] distant terrain`), `haze visibility` (100000: the distance that keeps 10 percent of the light along the ground in clear weather), `haze height` (4000: the scale height), `haze weather gain` (3; it was 10 until task 0088, which hid all land past about 3,000 units in an ash storm). Off (any of them), the fog is the linear one and the shaders compile the haze out (`cAerialHaze` in `fog.settings` is a constant false).
- **One function:** `applyFog` in `files/shaders/lib/view/fog.glsl` (`aerialActive`, `aerialBeta`, `aerialOpticalDepth`, `aerialFogAmount`, `mixFog`) is where every shader that fogs (objects, clusters, terrain and tiles, water) gets it; the twin is `aerialmath.hpp` (`Render::Aerial`). The three constants the shader repeats (`aerialClearFogDepth`, `aerialMaxWeatherExcess`, `aerialMaxCameraHeightScales`) are read back by a test: change both together. The sky, clouds and sun do not use `applyFog` and keep their colours.
- **The mark:** with the haze on, `Scene::fogScale` is NEGATIVE (`View::Scene::setFogRange(start, end, aerial)` -> `Aerial::sceneFogRange`); its size is the linear fog's, so the weather's fog depth is `1 - start / end` (FogManager: start = range * (1 - depth), end = range). Never test `fogScale > 0` for "there is fog" in a new shader: the volumetric fog and the cloud/volume compute shaders read `fogScale <= 0` as "no fog" and so are off while the haze is on. Set only in the main view, exterior (`Render_Sky` active), above water, not `[Fog] use distant fog`, no Lua `setViewDistance` override, not a bake run, and only if the shaders were built with it (`RenderManager::mAerialShader`: the condition is read once at start, like `fog.settings`).
- **Weather:** `Aerial::weatherBeta` multiplies the base density by `exp(gain * clamp(depth - 0.7, 0, 0.42))`, depth being the weather's `Land_Fog_Day_Depth` (clear 0.69, rain 0.8, storm and fog 1.0, blizzard 2.8). With the gain of 3 (cap 0.42; the distance that keeps 10 percent of the light along the ground, base 100,000): ash storm (depth 1.1) 30,100, storm or fog (1.0) 40,700, rain (0.8) 74,000, blizzard (2.8) and night ash storm (1.2) 28,400. The gain of 10 gave 1,830 for an ash storm (it hid all far land, toddhow 2026-11-05), 5,000 for a storm and 30,000 for rain; vanilla's linear fog ends at the view distance in every weather. A weather with fog depth 0 would be read as depth 1 (an exterior with no fog stores an end of 3.4e38).
- **Pitfall:** a `[Rendering]` or `[WorldLod]` default that a new shader constant reads must also be in the editor's `defaults.cfg`, which `eden-studio` loads: rebuild it (the stale exe fails at start with "Default setting ... is not initialized").
- **Not built:** haze in interiors, a separate sun-side glow beyond the existing sun glow (`cSunGlow` is added to the haze colour in the same way as to the linear fog), height fog that follows terrain (the density follows world z = 0, not the ground), the sky's own aerial scattering, a visibility bound to the loaded world's size.

## Temporal anti-aliasing (task 0075)

- **Settings** (`[Rendering]`, read at start by `MWRender::RenderManager`): `taa` (off), `taa sharpness` (0.25), `taa jitter scale` (1), `taa history` (0.95), `taa clipping` (`minmax` by default; `variance` is an opt-in, patent US10116916B2), `taa clip gamma` (1), `taa debug` (`none`, `weight`, `reject`, `velocity`). It needs `hdr`, `gbuffer` and `[Video] antialiasing = 0`; otherwise a warning and nothing exists (the user's antialiasing is never changed). Off, there is no camera, wrapper, image, descriptor, pass or timer, and the view draws with `mSceneCamera` as before. Research: `docs/research/0037-temporal-anti-aliasing.md`; spec and measurements: `docs/tasks/0075-temporal-anti-aliasing.md`.
- **The jitter is a clip-space shift in front of the projection** (`Render::Taa::jitterMatrix`, `JitteredProjection` in `taa.hpp`). Only the view's own camera (`RenderManager::mRenderCamera`, sharing `mViewMatrix` and `mSceneCamera`'s viewport state) and the first-person projection get it. `mProjectionMatrix` and `mSceneCamera` stay unjittered on purpose, because everything that reconstructs positions needs the true camera: the velocity pass, the fog and cloud volumes, AO, SSS, shadow cascade fitting, picking, post-processing. **A new consumer of the camera's projection must read `mProjectionMatrix`, never `mView->camera`.** `vsg::RelativeProjection` is not used: its `changeExtent` rescales the shift on a resize. `GBUFFER_MOTION` needs no correction (both positions go through the same jittered projection, so the shift cancels): with the camera still, the velocity debug view stays mid-grey.
- **The resolve** is `files/shaders/post/taa.slang`, two compute dispatches in `Render::TaaPass` (`taa.cpp`), loaded whenever `taa` is on (like the clouds: whatever `slang shaders` says; a missing `post/main.taaresolve.spv` or `main.taaoutput.spv` turns TAA off with a log line). Its twin is `taamath.hpp` (`Render::Taa`): constants, `compress`/`expand` (colour squeezed by luma so a lamp cannot dominate), YCoCg, the variance box, `clipToBox`, the history weight, `depthRejectRange`, `catmullRom5`, `sharpenCross`, the sky's reprojection; change both together (`testtaapass.cpp` reads the constants and the push-constant block back from the file). The history alpha holds `log2(1 + the closest depth of the 3 by 3)` (-1: sky).
- **Velocity is the closest pixel's of a 3 by 3; the sky (no depth anywhere in the 3 by 3) is reprojected with the rotation part of `toPreviousClip` applied to `(dir, 0)`,** because `velocity.frag` writes 0 for a pixel with no opaque surface (and is unchanged). Transparent things (water, rain, snow, particles, glows) write no depth or velocity, so they are reprojected as whatever is behind them: **so they are not drawn before the resolve**: with TAA the main view's depth-sorted bin is a `vsgUtil::DeferredBin` (it collects, draws nothing), the rain is added to that bin, and a second render pass (`mOverlayGraph`, between the resolve and the bloom) replays the bin over the resolved picture. Rules of that pass: its render pass is `HdrTarget::createOverlayFramebuffer`'s (same attachments and formats as the scene pass, so the scene's pipelines are compatible; colour 0 is the TAA output, which the resolve leaves in `GENERAL`, loaded not cleared; the G-buffer extras and depth are loaded and stored); blended draws write none of the extras (`writesGBuffer`), so nothing else changes; its view uses the unjittered `mSceneCamera` (the streaks must not move with the jitter) and no `viewDependentState` (the lights were packed by the main view); `BinReplay` is only valid in the same frame and record traversal as the main view, because bin elements hold raw node pointers, so never record the overlay graph from another command graph; **an object that must be drawn before the resolve must not be in `Bin_DepthSorted`**. Edges of blended meshes are not anti-aliased (they are drawn after the resolve, depth-tested against the jittered depth). **Their pipelines (default shader, blended, depth-tested, no bias of their own) carry a slope-scaled depth bias of 1.25 x `taa jitter scale` (`Pipeline::Graphics::overlayDepthBiasSlope`, `Render::Taa::overlayDepthBiasSlope`, `Pipeline::usesOverlayDepthBias`), set only with TAA on: without it a blended sheet lying on the ground (the Red Mountain lava is blended with depth writes) passed or failed the overlay's depth test by the jitter's sub-pixel shift, a different answer in each Halton phase (task 0075, resolution log).** Off (no `taa`), none of this exists. A glow moving fast no longer smears for the same reason. An actor's walk across the ground is also not in the velocity buffer (task 0026, stage c), so a moving actor rests on the clip alone; a frame with a dark actor against bright sky showed no trail (`docs/tasks/0075`, acceptance).
- **The disocclusion test uses a range** (`depthRejectRange`): the closest depth of a 3 by 3 changes with the jitter at a silhouette, so comparing with one stored value rejected edge pixels at random (1% of the foliage flipped by more than 24 levels every frame on a still camera, 0.016% after the fix).
- **AO, SSS and the volumes are not resolved:** the tonemap applies AO and SSS from this frame's jittered images after the resolve, so AO's own silhouette edges are not smoothed and its darkening is not accumulated unless `[Rendering] ao temporal` is on (task 0076, above: it takes `RenderManager::temporalState()`'s frame index and the jitter delta). The fog volume and the clouds have temporal filters of their own and pass through the resolve like any colour.
- **Resets** (`historyReset`, decided in `RenderManager::updateVelocity` from the same previous-camera data): first frame, a camera move over 512 units in a frame, a turn over 60 degrees, a gap over 250 ms, and a rebuild (resize: `TaaPass::setSource`, three frames of warm-up that put the images into their layout). With `taa debug = weight` the weight is black exactly on a reset frame.
- **Cost** (RTX 4070): the `taa` GPU pass takes 0.15 ms at 1280 x 720, 0.24 ms at 1920 x 1080, 0.46 ms at 2560 x 1440 (3 images of 8 bytes a pixel: about 66 MB at 4K, which could be cut to two by writing the sharpened picture only when the sharpness is above 0). CPU frame time did not move beyond the spread.
- **Pitfalls found:** a `vsg::Switch` is a `Node`, not a `Command`: it goes in a `Group` beside the `Commands`, not in `Commands::addChild`. A freeze message in a check run on a fresh user folder (5 s cell load while the navigator builds) is the freeze monitor, not TAA: scenes should set `[Navigator] enable = false`.
- **Not built:** transparent things drawn after the resolve, a per-object previous matrix for rigid moving objects, a motion-adaptive sharpen, TAA with MSAA (refused), the editor and preview (they never take the setting), an upscaler.

## Shadows from point lights (task 0077)

- **`[Shadows] point light shadows`** (off by default; needs `hdr`, `gbuffer` and `pbr`, so the lights are summed per pixel; refused with a warning with `[Shaders] classic falloff`), `point light shadow count` (1 to 8, default 4), `point light shadow resolution` (128 to 2048, default 512), `point light shadow filter taps` (1 to 16, default 8), `point light shadow bias` (0.25 to 6, default 1.5). Off, no image, view, graph or define exists and a frame equals the commit before (second runs of the pair, 0.000 percent). Spec and stage log: `docs/tasks/0077-point-light-shadows.md`; the research is `docs/research/0039-point-light-shadows.md`.
- **The twins:** `pointshadowmath.hpp` (faces, projection, depth, bias, tangent basis, the Poisson taps, the CPU reference `visibility`), `pointshadowselect.hpp` (which lights get a slot), `pointshadowgpu.hpp` (the data buffer's layout) and the shaders `files/shaders/lib/light/pointshadow.slang` and `.glsl`: change them together (`RenderPointShadowShader` compares the tables and constants). A face's projection is its own (`View::PointShadowProjection`, reversed finite depth, `clip.z / w = DepthMath::ndcDepth(4, far, d)`), the faces' axes are the table in `faceAxes` (right = cross(forward, up), what `vsg::LookAt` builds), and the guard band widens the field of view to `tanHalfFov`.
- **Storage:** one `D32_SFLOAT` 2D array, six layers a slot, the face chosen in the shader (no cube map, no `imageCubeArray`); each tap picks its own face, so the filter is continuous across an edge. Faces are drawn with no culling, no depth clamp and the base view's own override states (`View::PointShadow`).
- **A light's own model does not cast in its own pass (decision 0012):** `Anim::Transform::setPointShadowCarrier` (set by `MWAnim::decorate` and `create` for the model that carries a light) skips the subtree when the traversal mask has exactly the bit of the slot that holds the light (`components/animation/pointshadowcarrier.hpp`; face views get `pointShadowSlotMask(slot)`, `PointShadows::update` writes the owner table). A new way to add a light to a model should call `MWAnim::markPointShadowCarrier` with the transform above that model and nothing else (never an actor's body). The slot bit must stay out of every other mask of the renderer (bits 48 to 55).
- **Memory warning:** `memoryWarningText` logs once at start when the maps pass 256 MiB (`memoryWarningBytes`); 8 slots at 2048 texels is 768 MiB.
- **The light index (the review's blocker):** the data buffer is indexed by the light's place in the light buffer, and that list is different in every traversal. So `View::CollectLights::pack` writes the shadow entry of each light in the loop that writes the light, matching the node's address against the slots (`setShadowEntries`), and keeps a snapshot of each light for `MWRender::PointShadows::update`, which therefore never follows a pointer to a node of an earlier frame. The buffer is `DYNAMIC_DATA_TRANSFER_AFTER_RECORD` for that reason.
- **Selection:** by `radius^2 / (distance^2 + 1)` only (the colour flickers; the radius never does: `LightController::apply` in `components/mwanimation/light.cpp` writes `light.color`), hysteresis 1.25, a holder is kept at least 30 frames, a holder whose light is not in the list keeps its slot for 16 frames, a light with a far plane under two near planes (radius below 3.6) casts nothing, the order among equals is the quantised position, never an address.
- **Pitfalls:** a Slang twin of a shadow map that GLSL only compares with must be a `DepthTexture2DArray` (glslang marks it depth 1; `Texture2DArray<float>` is depth unknown, and the interface check refuses the twin); the loops multiply `illumination` by `pointLightShadow(lightIndexList[offset + l], viewPos)` under `POINT_SHADOW`, so any new light loop needs the same line; the stand-in buffer has slot count 0 and the shader returns 1 at once, because the map and preview views bind it with the same pipelines; run-to-run noise of the Arrille's scene is up to 22 percent over 8 grey levels, compare the second runs.
- **Not built:** water, a fade-out, light shafts, a way to look at the maps, excluding the model that carries a light, per-vertex lit surfaces.

- **The cache (stage e, 2026-11-06):** `[Shadows] point light shadow cache` (off), `point light shadow refresh faces` (1 to 48, default 6) and `point light shadow refresh frames` (2 to 600, default 24). `pointshadowcache.hpp`: `FaceCache` (the pure decisions: a new, changed or moved light redraws its whole slot at once and outside the budget; stale faces (world epoch, a moving caster in the wedge, age) are drawn oldest first within the budget), `disturbanceTouchesFace`, `MotionTracker` (the casters that moved, from poses reported once a frame). `MWRender::PointShadows::update` leaves an undrawn face's render graph out of the slot's command graph, which is all a skipped face needs (its depth image stays as it was). `Scene::collectMoving` reports actors and doors, `RenderManager::updateSceneData` the player, `Scene::changeCounter` is the epoch. **Rules for a change here:** a caster that moves without moving its `Anim::Transform` (limb animation) is only caught by the refresh period; a new kind of caster that moves must be reported to the tracker or it lags by up to `refresh frames`; **never put the light's colour into the cache's inputs** (a flicker would redraw all of it); a light that moves every frame costs what it did with the cache off. `ctr_pshadow_faces` (frame counters) and the `point shadow <slot>` timer passes (the first four slots) show the effect; with `[Cells] load trace` and Verbose a line every 120 frames gives the slots drawn whole, the faces waiting and the epoch. Spec: `docs/tasks/0077-point-light-shadows.md`, "Caching the maps".

## Video memory scale-back (task 0080, stages a to c)

- **`[VideoMemory] enabled`** (off by default; read at start by `RenderManager::setupVideoMemory`). Off, no `Scaler` exists, `Engine::deviceLocalMemorySample` is never called and nothing is measured. Spec and stage log: `docs/tasks/0080-vram-scale-back-and-mip-streaming.md`.
- **Pure parts, all header-only** (`vramsource.hpp`, `vramaccount.hpp`, `vramcontroller.hpp`, `vramorder.hpp`) plus `vramscaler.*` (the glue with `std::function` adapters and a source: tested with fakes in `testvram.cpp` and `testvramscaler.cpp`). The controller takes time and samples as arguments (no clock, deterministic) and never changes a level itself: the caller confirms with `applied` or `notApplied`. Keep Vulkan and VSG out of these files so the controller stays testable.
- **The pressure is `max(ledger, driver usage) / budget`, smoothed.** VSG's memory pools keep freed memory, so the driver's usage may not fall after a step (measured: flat at 426 MiB for a whole climb); a step that frees memory the driver does not show makes the controller ratchet through every level. `usage source = ledger` ignores the driver (a diagnostic), VSG's pools are handed back by `Engine::releaseUnusedDeviceMemory()` (`vsg::MemoryBufferPools::releaseUnusedPools`: it frees only entries with nothing reserved or referenced, under the pools' mutex), called from `Scaler::sampleNow` on the main thread by `PoolReleasePlanner` (`vrampoolrelease.hpp`): 1, 3 and 8 s after a reduction, every 10 s while anything is reduced, never closer than 1 s. Never call it per frame: it costs 1 to 4 ms and returns only whole empty 16 MiB entries (a live 3 KiB image keeps one).
- **`OPENEDEN_VRAM_BUDGET_SCRIPT="0:900,30:420,75:900"`** (test aid, `vrambudgetscript.hpp`; only with `[VideoMemory] budget = auto`) replaces the driver's budget by time (seconds since the scale-back started), so a reduce-then-restore cycle can be run on a card with room.
- **A swapped texture needs a new `BindDescriptorSet`** (d0 spike, task 0080): `BindDescriptorSet::compile` returns early once compiled, so changing its `descriptorSet` does nothing; never `vkUpdateDescriptorSets` a set that may be in flight.
- **An adapter must free memory it can show in the ledger**, or its steps are wasted. The registered ones, `far objects` and `far terrain`, change the live residency budgets of the world LOD (`setResidentBudget`), which free memory only for what has a fallback (task 0060): on the `high` tier nothing is freed, on `low` and `minimal` far clusters are evicted. A new adapter writes its own ledger entries in `account` and re-applies its level there when its system was rebuilt.
- **Adding a setting key to `[VideoMemory]`** needs `files/settings-default.cfg` (the editor's `defaults.cfg` too: rebuild `eden-studio`, see the pitfall under "Aerial perspective").
- **Texture mip swaps (task 0080 stage d, first slice):** the `texture mips` system is `MWRender::TextureMipsDriver` over `vsgUtil::TextureMips::Swapper` and the pure `Render::VideoMemory::TextureMips` (`vramtexturemips.hpp`). A swap builds a new Image, DescriptorImage, DescriptorSet and BindDescriptorSet, compiles it, points the groups that held the old bind at it and retires the old one through `CompileContext::detach`; users are found by scanning the scene graph (a `vsg::Visitor` must override `apply(vsg::Object&)` to traverse, the default does nothing), never by a loader hook. `OPENEDEN_TEXTURE_MIPS_TEST="8:1,16:0"` (seconds:level) runs it without the controller. The scan also covers the models the loaders cache (`cachedModels`: `LoadedObject` entries, the templates scene objects are cloned from, which hold the same binds) and every command graph of the viewer; without them 2 of 7 retired binds stayed alive. A swapped texture is handed out reduced to later readers (`activeReduction`, used by `readOptionalImage`). Memory comes back to the driver only when whole pool entries empty (`releaseUnusedPools`): an image of 16 MiB or more owns one; smaller ones share entries with other allocations. The stage log in the task spec has the numbers.
- **Calling the swapper (task 0080 stage d, second slice):** console `texturemips [status|0|1|2|off]` (`TextureMipsDriver::command`; a manual level beats the controller and skips the hysteresis); the adapter `texture mips` is last in the default `order`; the plan's use signal is a camera distance to the `CullNode`/`CullGroup` spheres above a texture's groups (`Swapper::scan(root, camera, frame)`: no frustum, radius not scaled, templates never near). Never write `Log(...) << somethingThatLogs()` (the Log holds the log's lock: "resource deadlock would occur"). Terrain layer arrays are swapped too, see the next bullet.
- **Terrain layer arrays (task 0080 stage d, third slice):** `Swapper` swaps the arrays the terrain Builder makes (`dropArrayLevels`, `shrinkArray`; the reduced array on a worker; binds in steps of 8 and 0.8 ms). To free the old arrays four things must be true, found by evidence: the views built ahead of the player and the pooled map views are emptied (`Preload::releaseViews`, `Map::clearIdleTerrainViews`), then `Builder::pruneCache` (in that order: an entry shared with a view is only the cache's once the view is gone), the Builder hands the new descriptor to later batches (`replaceArrayDescriptor`), and after an array swap the queue waits for `releaseUnusedPools` before the next swap (a new image allocated into a freed block pins it: `Engine::deviceMemoryPoolStats` shows reserved against free inside). The LOD tiles' Builder uses the live Builder's arrays (task 0080, fourth slice: `Builder::setStorageSharingLayers` when `Terrain::layerArraysShareable`: same layer list and map settings; it saves a second set, about 2 GiB with a texture mod, and the swap covers the tiles with the live terrain; a baked albedo tile keeps its own one-layer array). `LodTerrain::pruneCache` runs with the live prune before and after an array swap.

- **Terrain tile fade (task 0087):** `[WorldLod] terrain fade time` (0.4; 0 = the instant swap). The tile fade is `Batch::fade` in the terrain batch uniform (binding 2, now read by both stages: `files/shaders/terrain/data.glsl` and `.slang`, padded to 32 bytes), dropped by `dither8` as the LAST statement of `terrain/main.frag` and `terrain.frag.slang` (no define, so no new permutation sets). Only `LodTerrain`'s builder makes the uniform dynamic (`Builder::setDynamicBatchData`); `Builder::setBatchFade` writes it. The hand-over rules are `Lod::stepTerrainFades` (`components/lod/terrainfade.*`); coverage counts a tile only while solid. A tile new with nothing beneath it dithers in over the sky.

## Terrain layer arrays: re-encoding (task 0089, third round)

- `convertToArrayTexture(images, ArrayConvertOptions, ArrayConvertStats*)` is opt-in (`reencode`): the terrain builder turns it on (`OPENEDEN_TERRAIN_REENCODE=0` turns it off for a comparison). A layer that does not fit is decoded (`detail::decodeToRgba8`: BC1, 2, 3, 7, RGBA, BGRA, RGB, BGR), resized (`RgbaResize`) and, for a BC1 array, encoded (`Bc1Encode`) with a mip chain of its own, on up to 8 threads. Normal, material and height arrays use `encodeToBc1 = false`: only BC1 sources go into a BC1 array there (alpha is data).
- **In a block compressed array `width` and `height` inside `convertToArrayTexture` count blocks;** use `levels[0].width` and `.height` for texels.
- The BC7 decoder's partition tables were read from the D3D11 decoder, not copied from a source; `apps/components_tests/vsgutil/testbc7decode.cpp` holds the hashes. `I:\Projects\OpenEden-work\bc1\d3dbc7.cpp` is the oracle harness (outside the repository).
- Still not covered: BC4 and BC5 layers (one height map in the mod profile), and an array whose reference is BC3 or BC7 (the old rules apply).

## Puddle maths (task 0095, stage W-a)

- `puddlefill.hpp` (where water collects on a height grid: Priority-Flood, basins, catchment) and `puddlelevel.hpp` (level, depth, coverage, quantisers) are header-only, pure, with no engine types, and not wired to anything yet. The shader twin comes in stage W-d.
- **Bake the cap from the pit's floor (`capacityFromFloor`), not per texel:** clamping each texel's capacity turns a deep hollow into a flat 12-unit pond (measured on Morrowind's land in the stage log of task 0095).
- The filled height is independent of the order equal texels are visited; only flow directions on flat ground depend on it (first in, first out). Never rely on a flow direction on a plateau being symmetric.
- **`catchmentRatioBounded` (stage W-b)** is what the baker uses for the catchment: only ground within a bounded WATER PATH of the pond counts (tenths of a texel along the flood tree, 10 per orthogonal step and 14 per diagonal one), and water counts in the first pit it reaches. `catchmentRatio` (unbounded, flows through upstream pits) stays for comparison. The baker, the pack and the window are in `components/puddle/` (its own `CLAUDE.md`).
