# physics/jolt — Jolt backend

The only module allowed to include Jolt headers or link the `Jolt` target.

## Rules
- Link Jolt `PRIVATE`. Public headers in `include/` must never include a Jolt header or expose a Jolt type; callers see only our own types (later: `physics/interface`).
- Include `<Jolt/Jolt.h>` before any other Jolt header (Jolt requirement, see `HelloWorld/HelloWorld.cpp` in the Jolt repo).
- Jolt keeps global state (`JPH::Factory::sInstance`, registered types, allocator hooks). Whoever sets it owns tearing it down; leave globals clean.
- Jolt build options are set in `cmake/OpasDependencies.cmake` and explained in `docs/dependencies.md`. `CROSS_PLATFORM_DETERMINISTIC` is ON — don't turn it off without updating golden replays and that doc.

## Pitfalls
- Jolt compiles with RTTI and exceptions off by default; that only applies inside Jolt's own targets, not ours.
- Jolt's public compile definitions (`JPH_*`) flow to us through the `Jolt` target. Never redefine them by hand, or Jolt's headers and library will disagree on layouts.
- Swing-twist constraint space is X = twist, Y = plane × twist, Z = plane axis (`SwingTwistConstraint.cpp` constructor). Targets passed to `SetTargetOrientationCS` use that frame; M1's interface comment had Y and Z swapped until M3.
- Cone joints are `SwingTwistConstraint`s; pyramid joints (lopsided swing, task 0014) are `SixDOFConstraint`s with fixed translation, because `SwingTwistConstraint::UpdateLimits` always passes symmetric swing limits. `JointSlot::shape` says which type the slot holds; cast on it, never guess. Both use the same constraint space (SixDOF: X = `mAxisX`, Y = `mAxisY`, Z = X × Y, so `mAxisY` = plane × twist gives Z = plane).
- A `SixDOFConstraint` has one motor per rotation axis; `setJointMotor` gives all three the same gains. Like the cone, its `PositionAndVelocity` mode still damps at zero stiffness (`HasStiffnessOrDamping` in `SixDOFConstraint.cpp`).
- Slow test bodies fall asleep: Jolt sleeps a body after 0.5 s below 0.03 m/s at its surface (`mTimeBeforeSleep`, `mPointVelocitySleepThreshold` in `PhysicsSettings.h`), and a sleeping body reads zero velocity.
- Collision groups: one `GroupFilterTable` per group, shared by reference count with its bodies. The Jolt group ID is a serial number that is never reused, so bodies of a destroyed group are never mistaken for members of a new group in a reused slot. `GroupFilterTable::DisableCollision` wants the smaller sub-group first.
- `WorldConfig::subStepsPerStep` (M5, `docs/tasks/0017`) is passed to `PhysicsSystem::Update` as `inCollisionSteps`; listeners still run once per fixed step with the full dt. 1 keeps every M1–M4 result; standing balance needs >= 120 Hz internally.
- `WorldConfig::workerThreads` (task 0018): 1 keeps `JPH::JobSystemSingleThreaded`; more uses `JPH::JobSystemThreadPool` with `workerThreads - 1` threads, because the calling thread also runs jobs while it waits (`JobSystemThreadPool::Init`). Our listeners run before and after `PhysicsSystem::Update` on the calling thread, never on Jolt's workers, so they need no locking. Never use Jolt's `PhysicsStepListener` or contact listeners for core logic: Jolt calls those from several threads in no fixed order (`Docs/Architecture.md`, "Deterministic Simulation").
- Jolt uses at most 32 threads on a step (`PhysicsUpdateContext::cMaxConcurrency`); `workerThreads` above 32 only adds idle threads. Each world owns its `workerThreads - 1` threads for its whole life, so several worlds share the CPU.
- Jolt waits on every job of every sub-step at once, through one array of `cMaxPhysicsJobs` handles and one barrier of `JobSystemWithBarrier::cMaxJobs` (both 2048, `PhysicsSystem.cpp` "Build job barrier"), and 8 job kinds per sub-step grow with the thread count. Too many threads with many sub-steps overflow it (an assert in Debug, `StaticArray.h` `mSize < N`). So the backend starts at most min(`workerThreads`, 32, ⌊(2048 ÷ sub-steps − 11) ÷ 8⌋) threads (`usableThreads` in `JoltWorld.cpp`): all 32 up to 4 sub-steps, 30 at 8, 14 at 16. Found by the task 0018 P2 review and its 32-thread, 16-sub-step test; a larger job pool does not help, because the handle array and the barrier are fixed.
- Floating-point traps differ between threads on MSVC: Jolt's workers unmask divide-by-zero, invalid and overflow (`JobSystemThreadPool.cpp`, `FPExceptionsEnable`; on because `FLOATING_POINT_EXCEPTIONS_ENABLED` defaults to ON), the calling thread does not. A NaN or Inf we feed Jolt can crash the process with more than one thread, and only when a worker runs that job. Results do not change. Jolt also asks for the same denormal (DAZ/FTZ) state on every thread (`Docs/Architecture.md`); check this when OpenMW hosts the world (M8), where `SetThreadInitFunction` could copy the caller's state.
- The thread cap counts only the jobs Jolt waits on through its handle array. Continuous-collision and soft-body jobs come on top and fit only because the backend registers no Jolt step listeners and creates neither kind of body; revisit `usableThreads` before adding any of them (task 0018 P3 review).
