# The world: `apps/openmw/mwworld`

Rules and pitfalls for new OpenEden code here. This folder is mostly OpenMW's (inherited): keep changes small and in its style. Read the root `CLAUDE.md` first.

## Incremental cell build (task 0060, `Scene`, `[Cells] incremental cell build`, off by default)

With the setting off nothing here changes: `Scene::insertCell` builds every object of a cell inside `loadCell`, as OpenMW does.

With it on, a **border crossing** (the `ChangeCell` that `World::moveObject` pushes, `incrementalLoad = true`) loads the new exterior cells as before (land, height field, pathgrid, local scripts registered, window manager, water, `exteriorCellLoaded`) but does not build their objects. `Scene::insertCell` puts each object in `Scene::mBuildQueue` (a `Misc::BuildQueue<Ptr>`, `components/misc/buildqueue.hpp`, unit tested with fakes) and `Game::run` calls `Scene::buildPendingObjects()` once a frame, before the local scripts. It builds objects until `[Cells] incremental build budget ms` is used (at least one object; after 120 calls a share of the queue, so it always empties). Order: nearer cells first; inside a cell the plain objects (statics, doors, containers, lights, items), then the actors, then the navigator pass; inside each, nearer to the player first. The order never depends on time; only how many fit in a frame does.

"Building" an object is exactly what `insertCell` did: `addObject` for rendering, mechanics, physics, Lua and the extension host, then the second `addObject` for the navigator (with one `UpdateGuard` per frame instead of one per load).

### What an unbuilt object is

An object of an active cell that is waiting is in the same state as a **disabled** object, which OpenMW already supports: no model, no physics body, no mechanics entry, no navigator entry, no Lua `onActive`. It differs in that its record says enabled, so:

| Thing | What happens to an unbuilt object |
| --- | --- |
| Local scripts | skipped by `Game::executeLocalScripts` (`Scene::isPendingBuild`) until the object is built (its navigator pass is the last item, so up to a few frames longer) |
| `Disable`, `Delete`, moving to an inactive cell | `Scene::removeObjectFromScene` forgets it from the queue (`cancelKey`) and the usual removal copes with a never-added object |
| `Enable`, `placeatpc`, a new reference, levelled-list spawns | `World::enable` does nothing for an enabled object; new references are added at once by `addObjectToScene`, which also cancels a queued entry for the same reference (never two adds) |
| Moving between two active cells | `World::moveObject` calls `Scene::updatePendingPtr`, which gives the queued entries the new reference |
| Scripted move, rotate, scale | the build reads the record's position, rotation and scale as they are then (`loadTransform`, `makeDirectNodeRotation`); an object whose angle a script set in the inverse order before it was built gets the direct order |
| `mPhysicsPostponed` | `addPostponedPhysicsObjects` skips queued objects; the build clears the flag and adds the body at the current position |
| Cell unload mid-build, `Scene::clear` (load game, new game) | `unloadCell` calls `cancelGroup`; `clear` empties the queue |
| Teleport, interior door, fast travel, first load, `changeToExteriorCell` with `incremental = false` | never incremental; a non-incremental `changeCellGrid` also builds every cell still waiting (`finishCell`) |
| The cell the player stands in | `changeCellGrid` and `changePlayerCell` call `finishCell`: the player is never in a cell that is not built |
| Saving | the save reads records, not the scene, so it does not care; a game loaded from it starts with an empty queue |
| Picking, activation rays, tooltips | `World::getFocusObject` and `castRenderingRay` use the render scene graph, so an unbuilt object is both invisible and unpickable; its body does not exist either, so rays and bumping agree |
| Object paging and LOD clusters | `RenderManager::setCellObjectsPending(x, y, true)` tells `DistantObjects` the cell is unbuilt: its distant chunk keeps drawing even though the cell is in the active grid, and `staticsReady` is false, so a cluster stays solid until `reportBuiltCells` clears the flag |
| Sound, lights | set up by the build like any object (`Class::insertObject*`), at that time |

### Threads and pitfalls

- Everything above runs on the main thread. `Scene::changeCellGrid` can run on a loading-screen worker, but only for loads that are not incremental, which never queue.
- The build budget uses `std::chrono::steady_clock`. It decides only how many objects fit in a frame.
- A build step can run more than the budget: one NPC is 2 to 10 ms, a cold one up to 50 ms. That is why `Npc::defaultPartModels` and `Npc::animationSources` are preloaded (`PreloadCell`).
- Do not call `addObject` for a queued object by another route: `PhysicsSystem::addObject` asserts that a body does not exist yet.

## Weather from plain descriptions and a game pack's weather (task 0127, stage W-S1, `[Game] neutral weather`, off by default)

- `weatherparams.hpp`: `Weather` and `WeatherManager` no longer read `Fallback::Map` themselves. `weatherParamsFromFallback(name)` and `weatherManagerParamsFromFallback()` (weather.cpp) fill `WeatherParams` and `WeatherManagerParams` with exactly the keys and conditions the old constructors read (note: `Weather_<name>_Rain_Loop_Sound_ID` is only read for a weather with precipitation, because `Fallback::Map` throws for a key that is not allowed for that weather); the constructors read the structs. `apps/openmw_tests/mwworld/testweatherparams.cpp` pins every field against hand-written expectations. A new key of the INI that the weather reads goes into the struct and into that test.
- A game pack's weather (`neutralweather.*`): the pack describes weathers, the sun hours and a cell's weather list through the SDK's `WeatherSource` (`sdk/include/openeden/game/weather_source.hpp`, found by `dynamic_cast` on the registered cell source); `makeSessionNeutralWeather()` (called by `World::makeWeatherManager`, at construction and at `startNewGame`) builds a `NeutralWeatherSetup` and `WeatherManager` takes it instead of Morrowind's ten weathers and the store's `ESM::Region`s. A neutral cell has no region: `WeatherManager::regionOf(cell)` asks `NeutralRegionProvider`, which makes one region per distinct weather list (key `<game>:weather:<hex key>`), chances normalised to exactly 100. Only exterior cells have a region (as Morrowind). `World::updateWeather` and `WeatherManager::update` call `regionOf`, never `getCell()->getRegion()` directly.
- **Precipitation, snow and thunder (task 0127, stage W-S2):** `WeatherDescription` (SDK `weather_source.hpp` 0.2) carries `precipitation` (None, Rain, Snow), `precipitationThreshold`, `thunderFrequency` and `thunderThreshold`. `weatherEntryFromDescription` turns them into the same fields Morrowind's INI fills: Rain sets `usingPrecip` (the manager's rain, `raindrop.nif`, and so the wetness) with Morrowind's rain numbers (thunderstorm numbers when there is thunder) and `rainLoopSoundId = "None"`; Snow sets the entry's `particleEffect` to the configured snow model (`[Models] weathersnow`), or the blizzard model when the wind is at least `kBlizzardWind`, which is what the snow cover (`updateCover`) looks at; thunder fills `thunderFrequency`, `thunderThreshold` and `flashDecrement`, and the existing `Weather::calculateThunder` and lightning-as-light path (task 0040) do the rest. The thresholds are kept between 0.1 and 0.9 (the manager treats 0 as unset and divides by one minus the threshold). All numbers are named stand-ins in `NeutralWeatherConstants` because the game's particle data (SPGD) is not decoded. The sounds (rain loop, thunder) are empty on purpose. `OPENEDEN_NEUTRAL_FORCE_WEATHER=<editor id>` (developer aid, `docs/debug-environment-variables.md`) starts every neutral region in a named weather: it sets the region's weather when the region is made and whenever the weather is re-rolled, since `ChangeWeather` cannot reach a neutral region.
- **Limits of this slice:** one cloud picture (the first layer whose texture exists), no sound, aurora or SPGD particle data (an ash storm of Solstheim or the Blackreach spores carry the snow flag and fall as snow); the sun hours and the colour blend are Skyrim's climate times with a plain linear blend (UNVERIFIED against the game); `ChangeWeather` and Lua `core.weather.changeWeather` throw/do nothing for a neutral region (they look the region up in the `ESM::Region` store); a neutral save is still refused. The pack's weather index is built on the main thread inside the World constructor (about 2 s for the five masters).
- **More sky (task 0127, stage W-S3):** `WeatherDescription` (SDK 0.3) also carries `extraCloudLayers` (texture, alpha and tint by time of day, drift) and an image space grade by time of day; `TimeOfDayDescription` carries the climate's sun and sun glare pictures and which moons exist. `weatherEntryFromDescription(w, maxLayers)` keeps the first `[Game] neutral weather cloud layers` (default 4, 0 = the single picture of W-S1) extra layers in `WeatherParams::extraClouds` and always carries the grade in `imageSpace`. `calculateResult` interpolates each layer's alpha and tint over the day (the "Sky" windows) into `WeatherResult::mExtraClouds`; in a transition `blendExtraCloudLayers` fades the old weather's layers out and the new one's in with the first picture's blend (at most `MWRender::kMaxExtraCloudLayers` = 8 together). `MWRender::Sky` draws them with a pool of `Clouds` domes made only when neutral world and neutral weather are on (the same cloud pipeline, no shader change), replaces the sun disc and glare pictures once per name (`Sun::setDiscTexture`, `setGlareTexture`: a compiled descriptor set swapped into the groups' state commands) and draws a moon the climate does not have with alpha 0. The grade reaches the renderer only with `[Game] neutral weather image space` (off): `WeatherManager` hands `log2(brightness)` to `RenderManager::setImageSpaceStops`, added to the tonemap's exposure; saturation, contrast and tint are carried but NOT applied (they need a tonemap shader change). With the volumetric clouds on the extra layers are not drawn. Morrowind weathers have none of this (empty vectors, defaults).
- `tools/neutral_session_check/check.sh ... w1` is the in-game sky check (hours of the day, then a fast clock until the weather changes), `CHECK_TIMEOUT` lengthens the 170 s limit.
