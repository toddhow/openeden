## The three moves (smallest risk first), each with its risks

### Move 1: Morrowind's data conventions out of generic code (into `compat_morrowind`)
- **What:** the places that name Morrowind's skeleton files, units and node rules while living in generic code: `base_anim` in `apps/openmw/mwrender/animcontext.cpp`, `mwrender/npc.cpp`, `components/vsgadapters/nif/nif.cpp`, `apps/opencs/model/prefs/values.hpp`; `Constants::UnitsPerMeter` uses (27 files outside tests mention `UnitsPerMeter`; how many are the Morrowind constant and how many generic: **verify**, the first task of the move is that list); the `bip01` rule via task 0082's `SceneOptions`. They are asked of `openeden.game` (`GameContract`: units, default skeleton; extended with the few other conventions found: **minor version** of the contract, 1.1).
- **Risk:** low per file, wide in count; a missed site silently keeps the Morrowind default for another game. The `Constants` value may be used by tuning and physics values that must not change.
- **Verification:** unit tests; the Lua tests; a frame comparison in a Morrowind interior and exterior with the setting at its default (viewed before commit); `grep` check that no listed file names the Morrowind constant.

### Move 2: crafting rules (alchemy, enchanting, repair, recharge)
- **What:** `apps/openmw/mwmechanics/alchemy.*` (632 lines in the `.cpp`), `enchanting.*` (417), `recharge.*` (110), `repair.*` (115): 1,274 lines of `.cpp`, with no `mwrender`, `mwgui` or `mwphysics` include in `alchemy.cpp` and `enchanting.cpp` (grep at the commit above; the headers and the other two files are **verify**). They are called by `mwclass/apparatus.cpp`, `ingredient.cpp`, `potion.cpp` and `mwgui/alchemywindow.cpp` and the equivalent windows, and from `mwscript`.
- **Contract:** `GameRules` gets `craft(...)` entry points (design doc 5.5), derived by removing Morrowind-only data, not by copying the Morrowind classes; the windows call the contract.
- **Risk:** medium. The windows (`mwgui`) still include the types; the contract must carry enough for the UI without leaking `ESM::` structs, which means a first record-view type (`openeden.records`). GMST-based formulas read the store; they keep their source (root guide: Morrowind values keep their existing source). Random numbers: the existing `Misc::Rng` use must keep the same draw order (determinism).
- **Verification:** the existing tests for these classes if any (**verify**: none were found by name at the commit above, so the task writes characterization tests first, from a fixed-seed scenario, before the move); a recorded scenario that brews, enchants and repairs with a fixed seed gives identical results before and after (numbers in the stage log).

### Move 3: dialogue and journal (with their save state)
- **What:** `apps/openmw/mwdialogue/` (3,340 lines: `filter.*`, `selectwrapper.*`, `dialoguemanagerimp.*`, `journalimp.*`, `quest.*`, `topic.*`, `scripttest.*`, `keywordsearch.*`) and the save records they write: `ESM::DialogueState`, `ESM::JournalEntry`, `ESM::QuestState` (`components/esm3/dialoguestate`, `journalentry`, `queststate`; used in `dialoguemanagerimp.cpp` and `journalimp.cpp`). It is the first move that needs the **save chunk handler**; `MWBase::DialogueManager` and `MWBase::Journal` are the existing interfaces it implements.
- **Includes today:** `mwbase` 26, `esm3` 20, `mwworld` 18, `compiler` 14, `mwmechanics` 7, `mwscript` 6 (research note 0043): the smallest outward web of the rule directories, but it calls the script compiler, so the script host contract (design doc 5.6) must exist in a first form (compile and run a result script) before this move; if it does not, this move waits and the order becomes 2 then 3.
- **Risk:** high of the three. Saves must keep the same bytes; the dialogue UI (`mwgui/dialoguewindow`) and the Lua bindings (`mwlua` `dialogue` and journal types) call it.
- **Verification:** save round trip (load an existing save made at the fork point, save, compare the dialogue/journal/quest records byte for byte; load the result); the 32 Lua tests; a scripted conversation (topics, a persuasion, a journal update) with a fixed seed gives the same results before and after.

## Constraints
- One move per branch; each move ends with the tree building and every test passing; a move is **reverted whole** if its comparison fails.
- No behaviour change, no new setting. If a move cannot keep Morrowind identical it stops and asks.
- The layer rules checker (0081) gains no new exception; each move removes the ones it fixes.
- No file is rewritten for style; the code moves with its history (`git mv`) and its OpenMW notices and AUTHORS entries (root guide guardrails, GPL).
- Namespace: the moved code keeps `MWMechanics`/`MWDialogue` names in this task; renaming is a separate, later change (no drive-by changes).

### Review 4 fixes (2026-11-08, findings 1, 4, 5, 6, 7; same hand wrote tests and code, no fresh reviewer)

- **A game can say "none" (finding 1).** `GameContract::specifiesAllConventions()` is a new virtual with the default `false` (additive, placed before the four conventions; 1.1 had not been released, so no version change). A pack that returns `true` (compat_morrowind and compat_skyrimse do) answers all four conventions itself: `gameConventionsFrom` copies an empty bone name, prefix list, suffix or animation file as it is, so Skyrim no longer gets `.1st` or the `root bone` fallback. A pack that returns `false` (a contract 1.0 pack) keeps the old rule: empty means "not specified" and the engine keeps Morrowind's value. Sites guard the empties: `CreativeMotionPoseDriver` (no lookup of a bone named ""), `MWAnim::Play::addSingleAnimSource` (an empty name never matches a bone with no name), `MWAnim::Actor::assignBones`. Tests first (7 of the 9 new `GameConventionsExplicit`/`GameConventionsValidation` tests failed against the old copy, log `I:/Projects/OpenEden-work/review4/red_gameconv.txt`; two were pins).
- **Pack data is validated (finding 7).** The unit must be finite and positive (else the default stays); bone names and skeleton prefixes are lower-cased (lookups are by lower-cased name); empty prefixes are dropped. The first-person animation file is NOT lower-cased and not rejected: it is a name or a path as the animation context passes it on to the VFS (Morrowind: a bare name resolved by the context; Skyrim: a full VFS path); the field is documented as that.
- **Ordering and lifetime (findings 5 and 6).** The snapshot store is never destroyed (a function-local static released from its `unique_ptr`, so workers that read at exit never see it destroyed). `ExtensionHost::start()` resets the conventions before `initialize()` and installs the pack's only when the session has no error; `stop()` no longer resets them (workers may still read; the values are copies). A pack that faults later leaves the values as they are (resetting mid-session would mix two games' values; the session is marked failed and saving refused). Not done: installing before the first loading screen and before actors are built (the lifecycle has no hook between resolve and start; an actor built before then keeps the bones it resolved), and a single definition of the store across shared libraries (it is an inline static; the header says only the host executable may call `setGameConventions`, and `CI/check_game_conventions.sh` now runs in CI).
- **Registration (finding 4).** The two test files of move 1 are in `apps/components_tests/CMakeLists.txt`, and `CI/check_tests_registered.sh` keeps every test file registered.

**What leaks through the interfaces the UI needs** (the reasons the contract is not a quick sketch):
1. `MWWorld::Ptr` is in every public signature: ingredient and apparatus slots, `getOldItem`, `getGem`, `getTool`, `setAlchemist`, `rechargeItem`. `Ptr` lives in `apps/openmw/mwworld` (the `rules` layer), not in the SDK. The SDK has an `EntityId` (`sdk/include/openeden/entity.hpp`, index and generation) but nothing maps a `Ptr` to it for an item inside an inventory (a stack in a `ContainerStore` is not a world entity).
2. `ESM::EffectList` / `ESM::ENAMstruct` (enchanting input, alchemy's effect list), `ESM::Enchantment::Type` (cast style), `MWMechanics::EffectKey`, `ESM::Apparatus::AppaType` (the window switches on it) and skill ids are in the headers and read by the windows.
3. The windows read records themselves (`ESM::Repair` quality and uses, `ESM::Apparatus`, `ESM::Ingredient`, `ESM::MagicEffect` flags), so the contract must also carry a **record view** for them.
4. `sdk/include/openeden/game/records.hpp` has only `RecordTypeInfo` and `RecordService` (type registration). The "first record-view type" the spec names, `record_cast<T>`, does not exist (design doc 5.1 puts it at stages c and e). `GameRules` does not exist either (the Skyrim pack of task 0086 fails `start()` on the null `GameRules`).
5. Three of the classes hold **state** across calls (slots, chosen cast style, the tool), so the contract is a session, not a set of functions.

**Risks and what stage 2c needs decided (the stop condition of the task).**
- **(a) The item handle.** A contract that carries no `Ptr` needs a handle for "an item in an inventory or the world" and a core-side table from handle to `Ptr`, with a lifetime rule (a handle outlives its stack when the stack is removed and added again, as `Repair` does when a tool is used up and replaced by another of the same id). `EntityId` is the only candidate in the SDK; a new opaque `ItemHandle` is the other. Every window site that holds a `Ptr` next to an `Alchemy`, `Enchanting` or `Repair` would hold a handle and ask the core for the `Ptr` for icons and tooltips.
- **(b) A record view.** The windows read `ESM::Repair`, `ESM::Apparatus`, `ESM::Ingredient` and `ESM::MagicEffect` fields. Either design doc 5.1's record view (`openeden.records`, stage c) exists first, or the crafting contract returns the few plain values the windows need (tool quality and uses, apparatus type and quality, effect names), or `game_morrowind` and the windows keep including `mwworld` headers for this move. The design doc (9, question 2, and note 0043) expects a **static** `game_morrowind` whose rule code calls the world model constantly, which answers whether the pack may include `apps/openmw/mwworld`: yes in a static pack; it does not say where those includes are checked (see d).
- **(c) The per-frame recharge path.** `rechargeItem(Ptr, float, float)` runs for every enchanted item of the player and the active cells on the main thread each frame (`ContainerStore::rechargeItems`, `CellStore::rechargeItems`) and caches one GMST in a function-local static. Putting it behind a virtual costs one call per enchanted item per frame. Alternative: a non-virtual helper that the pack exports (a function pointer registered at start).
- **(d) Build and checks.** A static `game_morrowind` that includes `apps/openmw` headers and is linked into `openmw` makes the library dependency circular (`openmw-lib` calls `rechargeItem` and the sessions; the pack calls `mwworld`, `mwbase`, `mwclass`): CMake expresses it for static libraries only with a repeated or grouped link line (GCC), and the pack needs `openmw-lib`'s include directories and precompiled header. `CI/check_layer_rules.sh` does not look at `game_packs/`: it would need a `game_packs/morrowind` layer line (above `rules`, allowed to include `engine`, `rules`, `formats`), or the classes stay where the checker sees them. `CI/check_extension_sdk.sh` forbids Lua words in `sdk/include`.
- **(e) Static caches.** `fWortChanceValue`, `fMagicItemRechargePerSecond` (and in the character code the tests reach, `fFatigueBase`, `fFatigueMult`) are read once into function-local statics. They keep their source (root guide), but a pack started twice in one process (the tests) sees the first value; the 2b tests therefore fix those values for the whole process.

**Recommendation.** Decide (a) a new opaque `ItemHandle` with a core table, (b) plain values in the contract for this move (the record view later), (c) the non-virtual exported helper for the per-frame path, and (d) a `game_packs/morrowind` layer line; then 2c is mechanical but wide (about 25 call sites in `mwgui`, `mwclass`, `mwworld`). Until then **2c is not started and no file has moved.**

**What the code itself needs from the core** (so what a moved copy still includes): the compiler, the interpreter and `MWScript::installOpcodes` (result scripts are compiled per call in `DialogueManager::compile` and run in `executeScript`); `MWBase::World` (`updateDialogueGlobals`, globals, `isSwimming`, `getCellName`, weather), `MechanicsManager` (`getDerivedDisposition`, `getPersuasionDispositionChange`, `countDeaths`, `awarenessCheck`, `isAggressive`), `LuaManager` (`onDialogueResponse`, `questUpdated`), `SoundManager` (`sayActive`, `say`), `WindowManager` (`messageBox`), the ESM store (Dialogue, Faction, GMSTs) and the NPC and creature classes through `Ptr`. `Quest`, `Topic` and `Entry` also read the ESM store inside their constructors and `getName()`.

**Save records (bytes).** `DialogueManager::write` writes ONE `REC_DIAS` (`ESM::DialogueState`: `TOPI` known topics, `FACT`/`REA2`/`INTV` faction reactions). `Journal::write` writes, in this order: for each quest in `RefId` order a `REC_QUES` followed by its entries as `REC_JOUR` (type 2); then the journal entries as `REC_JOUR` (type 0); then each topic's entries as `REC_JOUR` (type 1). `MWState` writes them after the saved-game header and counts them first (`countSavedGameRecords`). The structs `ESM::DialogueState`, `QuestState` and `JournalEntry` live in `components/esm3` (formats layer) and are used by nothing else but `apps/essimporter` (a separate import path) and the two classes. `SaveChunkService` (task 0084) is **not hooked into `.omwsave`** and a chunk is a different container (`{pack id, name, version}` framing, a checksum, the `GPCK` header), so a chunk written by the pack could not have the same bytes, and a save made before could not load without a converter. The task text allows the other route ("otherwise keep records in the engine save stream and say so"): **the records stay in the engine save stream**.

**The decision this move cannot take alone.** Move 2 moved code behind a new SDK contract of plain values (`crafting.hpp`: `ItemHandle`, sessions, no `ESM::` and no `Ptr`). The same shape for dialogue would be a contract that re-expresses about 30 functions and four data types, an actor handle for `say`, `startDialogue` and `clearInfoActor`, plain views of quests, topics and journal entries for the window (about 40 sites) and for Lua (about 35 sites, where the types are sol2 usertypes), the execution of result scripts (a script host contract that does not exist: `ScriptHostService` only declares a language), response callbacks, and a plain-value save state that the engine would convert to the three ESM records. That is the largest piece of the project so far. The spec itself says the move implements "the existing interfaces" (`MWBase::DialogueManager`, `MWBase::Journal`). Two shapes:

- **Shape A (recommended): move the implementation, keep the engine's interfaces.** `git mv` `filter.*`, `selectwrapper.*`, `dialoguemanagerimp.*` and `journalimp.*` into `game_packs/morrowind` (`src/dialogue/`, in the static target `game_morrowind`, as the crafting rules); the pack implements `MWBase::DialogueManager` and `MWBase::Journal`; `openmw` asks the pack for them (`game_morrowind::makeDialogueManager(extensions, translation)` and `makeJournal()`) instead of `new MWDialogue::...` in `game.hpp`, the same "installed by the executable" shape as the crafting rules. The interfaces, `KeywordSearch` (a text utility the window uses; it has its own tests), the data types `Entry`, `Quest`, `Topic`, `StampedJournalEntry` (they sit in the `MWBase::Journal` signature and in Lua and window code) and `ScriptTest` stay in `apps/openmw/mwdialogue`. No call site outside `game.hpp` changes; the records stay in the engine save stream through the existing `write` and `readRecord`, so the bytes are the same by construction (and the 13 save tests of stage 3b pin them). Cost: the SDK gets no dialogue contract, so the pack holds the code but a second game pack could not use the slot yet.
- **Shape B: a full SDK contract as in move 2.** Correct in the end and large; it needs three more decisions (an actor handle, plain views for the Lua usertypes, a script-host contract). Recommend it as a later task, after the script host contract exists and after Lua descriptors (decision 0014).

Other choices, each with a recommendation: (1) save stays in the engine stream (above); (2) which files move: the Shape A list; (3) `KeywordSearch` stays in the core; (4) layer rules: the `game_packs/morrowind` line from move 2 covers the pack, `mwdialogue` keeps its `rules` line, exceptions stay 104 (nothing removed or added); (5) `MWDialogue` names and `m` prefixes are kept (no rename in this task); (6) the pack is installed by the executable, not by `game=` (as in move 2). *(Stage 3b state, kept for the record: stage 3c was not started when this was written.
