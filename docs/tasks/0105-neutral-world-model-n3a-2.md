# Task: The neutral world model, stage N3a-2 (the base record, its store, the RefId scheme and the stub player)

Design doc section: `docs/design/neutral-world-model.md` sections 10.1, 10.3, 10.4 (R4) and 10.6 (row N3a-2), decision 0016
Goal: the engine can hold the facts of a neutral object's base (kind, model, collision hint, payload) as a record in `ESMStore`, under a stable `RefId`, and a session whose game defines no player gets a stub `Player` NPC so the World's player lookups succeed; nothing consumes either yet, and with `[Game] neutral world` off (the default) the engine is exactly as before.

**What stage N3a-2 is (the order, recorded).** Section 10.6 defines N3a-2 as `NeutralBase`, its `Store`, the `RefId` scheme and the stub player (R4). It is NOT the delivery of the plugin list to the Skyrim pack (R5, second half), which the N3a-1 stage log (caveat 2) flagged as "the next stage that needs cells must settle where the plugin list comes from". Section 10.6 gives that to no stage by name: N3a-3 (cells, `loadRefs`, boxes) is the first that needs real Skyrim cells. So the order is: N3a-2 (this) -> a plugin-list/content delivery decision and piece before or inside N3a-3 -> N3a-3. This stage does not do it; see "Open for toddhow".

Inherited code touched (at commit `846dbb8849`): `apps/openmw/mwworld/esmstore.hpp` (`StoreTuple` gets `Store<NeutralBase>` as its LAST element; a `bool mNeutralStubs` with `hasNeutralStubs()` / `markNeutralStubs()`; includes `neutralstore.hpp`), `apps/openmw/mwworld/esmstore.cpp` (`ESMStore::write`: refuses while `mNeutralStubs`), `apps/openmw/mwworld/worldimp.cpp` (`World::World`: calls `insertNeutralStubPlayer` before `mStore.setUp()` when `[Game] neutral world` is on), `apps/openmw/CMakeLists.txt`, `apps/openmw_tests/CMakeLists.txt`. New: `apps/openmw/mwworld/neutralstore.{hpp,cpp}`, `neutralstub.{hpp,cpp}`. **Not touched:** `store.hpp` / `store.cpp`, `components/esm*` (no `RecNameInts` value yet: nothing here needs one; it arrives with `LiveCellRef<NeutralBase>` in N3a-3), `Ptr`, `Class`, `CellStore`, `Scene`, `MWRender`, `MWPhysics`, the SDK.
Inputs / outputs: `openeden::sdk::game::WorldObject` and its parts (read only); `ESM::NPC`, `ESM::Race`, `ESM::Class` (the stub records, `blank()` plus names).
Constraints: main thread only; no heap allocation per frame (nothing runs per frame); `Store<NeutralBase>` is not a `DynamicStore`, so `ESMStore::begin()/end()`, `countSavedGameRecords`, the id index and the record decoders do not see it; the stub is made only when the store has no NPC `Player` (Morrowind is never touched); the setting is read once, in `World::World`; layer exceptions stay 104; no SDK change.
Acceptance criteria:
- [x] `neutralBaseId` gives `"<gameId>:b<base>"` for an object with a base and `"<gameId>:o<placement>"` for one without; the same input gives the same `RefId`, other games, other kinds of key and other numbers give other ones; a game id that is empty or holds `:` or a control character, or an object with neither a base nor a placement id, is refused with a message.
- [x] `Store<NeutralBase>::addFromObject` adds a record with the object's base facts (game, ids, kind, editor id, model, collision, payload), finds it again for later placements of the same base whatever their transform, flags or placement id (`Existing`), keeps the first record and reports a `Conflict` (counted, named by game and id) when the same id arrives with other facts, refuses past its cap and for an unusable object without changing anything; `search`/`find` (the latter throws naming the id), `all()` in first-add order, `removeGame` and `clear`; pointers stay valid while more records are added.
- [x] `Store<NeutralBase>` is part of `ESMStore::StoreTuple` and is not convertible to `DynamicStore`; a fresh `ESMStore` iterates exactly the dynamic stores it iterated before (the count is derived from the tuple in a test); `find(id)` and `countSavedGameRecords()` know nothing of it.
- [x] `insertNeutralStubPlayer` adds an NPC `Player` (blank stats), a stub race and a stub class as static records to a store that has no `Player`, marks the store and returns true; it returns false and changes nothing when a `Player` exists or when called twice; `validateRecords`, `movePlayerRecord`, `checkPlayer` and `clearDynamic` accept the stub.
- [x] `ESMStore::write` throws (`std::runtime_error` naming the stub) while the store holds the stub, before it writes anything; a store with a real player writes the same bytes as before.
- [x] With `[Game] neutral world` off, and on, a Morrowind session is exactly as before: `tools/worldobjects_check` dump byte-identical to the parent executable, a fixed-time frame with the same SHA-256, and `testesmstorecounts` output on the user's Morrowind data identical (setting off and on).
Out of scope: anything that reads the base store (cells, class, `LiveCellRef`: N3a-3), a `RecNameInts` value, the plugin list reaching the pack (R5), saves (N6), the session's real player (the stub is a dummy), lights (`LightComponent`: N3a-5), the quaternion inverse (N3a-3).

## Design choices made here (toddhow may overturn)

1. **`Store<NeutralBase>` derives `StoreBase`, not `TypedDynamicStore`.** The usual route (a `TypedDynamicStore<T>` with `T::load`/`save` and `sRecordId`) would make it a `DynamicStore`, so it would appear in `ESMStore::begin()` (the counts test lists stores by index), in the id index and in the record-name map, and would invite a save path. A neutral base has no file form and never gets one. The cost: it is a small store of its own (a `std::unordered_map` and an ordered vector), not the generic one.
2. **No `RecNameInts` value in this stage.** Design 10.2 lists it for the third cell kind and `LiveCellRef`; the store needs none. It is added when N3a-3 needs it, so inherited `components/esm/defs.hpp` is not edited here.
3. **The key is the pack's base id, not the editor id.** An editor id can be empty or repeated (Skyrim SE); the pack's `WorldId` is session-unique. A placement that names no base is keyed by the placement (`:o`) so its inline facts have a home. The editor id stays a field.
4. **One record per id, first wins, conflicts counted.** Many placements share a base; if a pack ever hands two different descriptions of one base, the engine keeps the first and reports, rather than drawing the same base two ways.
5. **The stub is made in `World::World`, before `mStore.setUp()`,** because `movePlayerRecord()` dereferences the lookup (a missing `Player` crashes) and the shared lists and id index are built in `setUp()`. It is made only when no `Player` exists, so with the setting on Morrowind is untouched.
6. **The save backstop is a throw in `ESMStore::write`, not a skipped record.** The game state already refuses to save a neutral session (`ExtensionHost::savingRefusal`); a store that quietly dropped the stub would produce a save that loads as a different game. A throw cannot be missed.

## Open for toddhow

1. **Where does the pack get its plugin list (R5, second half)?** Needed before N3a-3 can show a real Skyrim cell; section 10.6 gives it to no stage. Options: (a) a field on the world source service (`registerSource` or a new function) through which the engine hands the pack the `content=` list and the data folders, called from `ExtensionHost` after the pack starts; (b) the pack reads the engine's `openmw.cfg` content list itself (needs a path and the same parsing the engine does, two readers of one file); (c) a Skyrim-only setting in the pack's own namespace. Recommendation: (a), as its own small stage "N3a-2b" before N3a-3 (an additive SDK function at the end of `WorldSourceService`, 1.1).
2. The stub player makes a saving-refusal backstop that throws; `StateManager::saveGame` already refuses earlier, so a user sees the message box, not the exception.
3. `Store<NeutralBase>` is not generic-store shaped (design choice 1); if you prefer it as a `TypedDynamicStore` the cost is an ESM-flavoured `load`/`save` that throw and a `DynamicStore` that shows in `begin()`.

## Decisions recorded (2026-11-10, toddhow's blanket approval of recommendations)

1. The save backstop throw in `ESMStore::write` while the stub player is present **stays** (open point 2).
2. `Store<NeutralBase>` **stays deliberately not a `TypedDynamicStore`** (design choice 1, open point 3).
3. The plugin-list delivery (open point 1, recommendation (a)) becomes its own small stage **N3a-2b** before N3a-3: `docs/tasks/0107-neutral-world-model-n3a-2b.md`.
