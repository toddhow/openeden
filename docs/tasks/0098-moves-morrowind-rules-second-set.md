# Task: Moving Morrowind's rules into the Morrowind pack, second set of moves (moves 4 to 9)
Design doc section: `docs/design/game-packs.md` sections 5.5, 5.6, 10 (stage e) and 11; decision 0013; decision 0014 (script runtimes); `docs/research/0043-separating-formats-from-game-rules.md` section 3; task 0085 (moves 1 to 3, the method and the stage logs this spec continues).
Goal: take the next Morrowind-only rule code out of `openmw-lib` into the static target `game_morrowind` (`game_packs/morrowind/`), one move at a time, with Morrowind provably playing the same after each, and say honestly how far each move gets a second game.
Inherited code touched, at commit `b9f91834a8`: per move, below. Common to all: `apps/openmw/CMakeLists.txt`, `game_packs/morrowind/CMakeLists.txt`, `apps/openmw/main.cpp` and `apps/openmw/game.hpp` (where the core is wired), the `apps/openmw/mwbase/` interfaces each move crosses.
Inputs / outputs: files moved by `git mv` into `game_packs/morrowind/{src,include/game_morrowind}`; new core-side interfaces only where a move needs one (named per move); no SDK header unless a move says so (move 9 only).
Constraints: determinism (Rng draw order kept), no allocation added to per-frame paths, threading stated per move, every setting unchanged, Morrowind default behaviour identical (the rule of task 0085 stands: a move is reverted whole if its comparison fails).
Status: DRAFT, docs only, written 2026-11-09 for toddhow's approval. Nothing is built or moved by this spec. Measured by `grep`, `wc -l` and reading only; no build, no game run.

## 1. Where the project stands, and what the survey found

Moves 1 to 3 are done (task 0085): data conventions (generic code reads `Misc::GameConventions`), crafting (behind `sdk/include/openeden/game/crafting.hpp`, a contract of plain values: Shape B), and dialogue and journal (Shape A: the pack implements `MWBase::DialogueManager` and `MWBase::Journal`, installed by the executable; provisional pending toddhow). The rest of the rule directories is **74,769 lines** (`.cpp` and `.hpp`, `wc -l`): `mwmechanics` 27,587, `mwworld` 25,364, `mwscript` 9,575, `mwclass` 8,661, `mwstate` 2,694, `mwdialogue` 888 (the data types left behind). Outside them: `mwgui` 41,425 (the UI system, decision 0015), `mwrender` 27,582, `mwlua` 12,055.

Four findings change how this spec is written:

1. **The layer checker cannot count these moves.** None of the 104 exceptions in `CI/layer_rules.txt` names a file under `apps/openmw` (`grep '^except' | grep -c apps/` finds 0 in the source column and 0 as target); 42 of them are `esm`/`esm3`/`esm4`/`esmbridge` seams and 17 are `vsgadapters -> nif`, which belong to the record-store and format work of task 0083, not to rule moves. Also `allow rules` lists `ui host tools`, so a file in `game_packs/` may include `mwgui` and `mwrender` without the checker noticing. **Every move below therefore removes 0 exceptions**, and the honest metrics are (a) lines that left `openmw-lib` and (b) the per-move count of `mwrender`, `mwgui` and `mwphysics` includes in the moved code (the coupling the checker cannot see). Open question 4 proposes a small `CI/` script that prints both and fails if they grow.
2. **Shape A buys isolation, not a second game.** Shape A (move the implementation, keep the `MWBase` interface with `Ptr` and `ESM::` types in its signature) takes Morrowind code out of the core library. It does not give a Skyrim pack anything to implement: move 3's own note 4 says it. Shape B (a contract of plain values in `sdk/include/openeden/game/`) is what a second game needs, and it is far larger per move (move 2's `crafting.hpp` took a handle table and about 25 call-site changes). This spec ranks each move on **two separate axes** and does not blend them: **isolation value** (lines leaving the core, how clean the cut) and **second-game value** (what a Skyrim SE pack could use, and what the Shape B follow-up would be). Nothing here is Skyrim progress unless the second axis says so.
3. **Most of `mwmechanics` is not movable yet, and the reason is measurable.** Files of `mwmechanics` that include `mwrender`, `mwphysics` or `mwsound`: `activespells`, `actors`, `aicombat`, `aipackage`, `aiwander`, `character`, `mechanicsmanagerimp`, `pathfinding`, `spellcasting`, `spelleffects`, `summoning` (11 files; `mwrender` is included 14 times and `mwphysics` 6 times across the directory). `character.cpp` (4,030 lines) is the animation state machine, `actors.cpp` (2,492) the per-frame actor scheduler, `mechanicsmanagerimp.cpp` (2,083) mixes crime, barter and persuasion with animation and AI forwarding (83 virtual functions in `MWBase::MechanicsManager`). They need a design decision before any move (section 5), not a `git mv`.
4. **There are three install hooks already and a fourth is coming.** Crafting is installed through `GameRules` (`MWWorld::installGameRules`), dialogue through `MWDialogue::installFactories`, and the pack lifecycle starts after some of the objects exist (task 0084 log). Moves 4 to 8 would each add another. Move 5 starts with a single registry (below) so the count stops growing.

## 4. Per-move plan

All moves follow task 0085's loop: survey stage (a), characterization tests that pass on the OLD code (b), the move (c), a fresh review before toddhow. The full loop is required for every move here (each touches `apps/openmw` and crosses a seam; move 7 writes saves). Tests are written from the survey, not from the implementation, as in moves 2 and 3: real classes with throwing doubles of the `MWBase` interfaces (`tools/mwbase_fakes/gen.py`, checked by `CI/check_mwbase_fakes.sh`), an in-memory TES3 plugin for the ESM store, fixed-seed `Rng`, and "mutations": five single-line changes to the old code, each of which must make a named test fail, rerun against the moved files.

### Move 4: the script command set

- **What moves:** `mwscript/{ai,animation,cell,container,control,dialogue,gui,misc,sky,sound,stats,transformation,user}extensions.*` and `extensions.*` (7,328 `.cpp` lines), and the compile-side table `components/compiler/extensions0.*` with `opcodes.hpp` (557 + 568 lines). **Stays in the core:** `interpretercontext`, `compilercontext`, `globalscripts`, `locals`, `scriptmanagerimp`, `ref` (1,905 lines; `Locals` is part of `RefData`, `GlobalScripts` is used by state, Lua and the world), the `Compiler::` and `Interpreter::` machinery.
- **The seam:** `components` may not include `game_packs/` (`deny components/ game_packs/`), so the table is registered by an installed function: `Compiler::registerExtensions` and `MWScript::installOpcodes` call hooks the executable fills (`game_morrowind::registerCompileExtensions`, `game_morrowind::installOpcodes`). `Compiler::registerExtensions` has 7 callers (`game.hpp`, `console.cpp`, the three Eden Studio files, two tests); the editor is a `tools` program and links `game_morrowind`. The 13 command files include `mwbase` and `mwworld` freely (allowed for a static pack).
- **Characterization tests first:** (1) the existing golden compile recording `apps/components_tests/compiler/testmorrowindprogramgolden.cpp` (512 commands plus hand-written scripts) must stay byte-identical and **unedited except for the registration call it makes** (one line: toddhow approves, listed in `docs/toddhow-checks.md` section 3 by whoever builds it); (2) a new test dumps the registered table (name, signature string, segment and code) before and after and compares them; the same for the installed opcode set of `installOpcodes`, with and without `consoleOnly`; (3) mutations: drop one `Stats::installOpcodes` call, change one signature letter, swap two opcode codes.
- **Save:** none (scripts' locals and globals are written by the kept `Locals` and `GlobalScripts`). **RECALLED-VERIFY:** what `GlobalScripts` writes as its record, not read for this spec; the move does not touch it.
- **Off means unchanged:** the same golden programs; a compile of every installed script (`--script-all`, the existing mode) gives the same count of compiled and failed scripts before and after (record the numbers in the stage log); the 32 Lua integration tests (several drive `mwscript`).
- **Layer exceptions removed:** 0. Metric: `mwscript` includes of `mwrender` 1 and `mwstate` 1 leave the core's count; the pack then holds 7,330 lines of `mwbase`/`mwworld`/`mwmechanics` includers.
- **Acceptance:** the table and opcode comparisons identical; `openmw-lib` no longer contains the command files (`nm` or a link check); `game=morrowind` runs a scripted quest (Seyda Neen start) through the script manager; the console runs `player->additem gold_001 5`; Eden Studio's script checker still highlights a script.
- **Risks:** (a) a pack that registers the compile table AFTER something compiles (the order at `game.hpp` where `Compiler::registerExtensions(mExtensions)` runs at line 84, before the pack lifecycle: see task 0084's start-order log); (b) the editor must link the pack (`opencs` `scriptcheck` etc.), which makes Eden Studio depend on `game_morrowind` for Morrowind scripts; (c) Task 0092/0093's runtimes reuse the compiler and interpreter: nothing in this move touches those directories (the `rules` layer line for `components/compiler` stays); (d) a missed registration silently drops a command: the table dump catches it.

### Move 5: the rules registry and the small free-function rules

- **Stage 5.0, the registry (core only, no move):** one core-side `MWBase::RulesRegistry` (header `apps/openmw/mwbase/rulesregistry.hpp`) that holds the rule interfaces the pack provides (move 5 adds `ThiefRules` and `ProgressionRules`; later moves add theirs), installed once by the executable (`main.cpp`) and, when `game=` starts the pack early enough, by the pack lifecycle. It absorbs the existing `MWWorld::installGameRules` use for crafting and `MWDialogue::installFactories` so there is **one** hook (their behaviour unchanged; characterization tests of moves 2 and 3 unedited and passing). A missing rule set throws a runtime error naming the missing piece, as the dialogue factories do.
- **What moves (5.1):** `security.*`, `pickpocket.*`, `difficultyscaling.*`, `levelledlist.*`, `autocalcspell.*` (656 `.cpp` lines). New core-side seam interfaces: `MWMechanics::ThiefRules` (`pickLock`, `probeTrap`, the pickpocket chance and result) and `MWMechanics::ProgressionRules` (`autoCalcSpells`, `scaledByDifficulty`, `levelledListChoice`). Callers change from a direct include to the registry's accessor: `character.cpp:1847,1849`, `mwgui/pickpocketitemmodel.*`, `mwgui` and `mwclass` for autocalc, `mwclass` x2 for difficulty, 5 files for levelled lists (about 15 sites).
- **Characterization tests first:** for each function, results over a grid of inputs (stats, skills, fatigue, seeds) and GMST values, compared with the old code's results; the `Rng` draw ORDER pinned (a sibling generator, as move 2 did). `Security::pickLock` and `probeTrap` are class methods taking `Ptr`s and returning a message and sound: tested through real `Ptr`s on an in-memory store.
- **Save:** none. **Off means unchanged:** the grid results; an in-game lockpick, probe and pickpocket scene (`tools/thief_check`, a new quiet-window check in the style of `tools/crafting_check`) with fixed seed gives the same messages.
- **Layer exceptions removed:** 0. **Risks:** a hook that is hit every frame (`levelledlist` runs on cell load, not per frame: **verify** `levelledlist` call frequency); `autocalcspell` is called from the window while an NPC is built.

### Move 6: disposition, barter, persuasion

- **What moves:** `MechanicsManager::getDerivedDisposition`, `getBarterOffer`, `getPersuasionDispositionChange`, `countDeaths` (lines 491 to 762, 272 lines). **How:** first split them out of `mechanicsmanagerimp.cpp` into a core-side `MWMechanics::SocialRules` interface (a pure refactor in the core, tests first), `MechanicsManager` keeps its `MWBase::MechanicsManager` overrides as one-line forwarders so the 12 call-site files and the moved dialogue pack code do not change; then Shape A: the pack implements `SocialRules`.
- **Second-game follow-up:** the pure arithmetic (disposition from personality, speechcraft, faction reaction and a fight bonus; price from skill and disposition) can be re-expressed as numbers in, number out in `sdk/include/openeden/game/social.hpp` (Shape B), kept as a later task; not part of this move.
- **Tests first:** a table of (actor stats, faction rank, GMSTs) to disposition, barter price and persuasion outcomes recorded from the OLD code through real `NpcStats`/`CreatureStats`; `Rng` order for persuasion; three mutations.
- **Save:** none (disposition and crime modifier live in `NpcStats`, which stays). **Layer exceptions removed:** 0.
- **Risk:** `getDerivedDisposition` reads `mActors`/the player and the faction code: 1 `mActors` reference in the range. Persuasion is called from the moved dialogue code, which already lives in the pack, so the call becomes intra-pack.

### Move 7: crime, theft, stolen items (full loop, saves)

- **What moves:** 724 lines of `mechanicsmanagerimp.cpp` (lines 904 to 1627, the functions in the table of section 2). **How:** stage 7.0 extracts them (and the `mStolenItems` map and its `Owner`/`OwnerMap` types, which stay core-OWNED data) into a core-side class behind a new `MWBase::JusticeRules`-style interface with the old `MechanicsManager` overrides forwarding to it; stage 7.1 moves the implementation to the pack. The witness search needs the actor list: the interface takes it as a callback (`getActorsInRange`), so the pack does not include `actors.hpp`.
- **Save:** `ESM::REC_STLN` is written and read by `MechanicsManager::write`/`readRecord` and **stays in the engine stream, written by the core from the map the core owns**, so the bytes are identical by construction. Test: a golden stream of a small `StolenItems` state taken from the old code (as the 351-byte golden of move 3), a read-then-write round trip, and a load of a save made before the move. **RECALLED-VERIFY:** `Actors::write` (`mActors.write`) was not read; whether it writes crime state (witness lists, `AiSequence` crime flags) decides if the stage log needs a second golden.
- **Threads:** **RECALLED-VERIFY** — which of `actorAttacked`, `itemTaken`, `commitCrime` run on the main thread and which on an actor-update worker; the stage 7.a survey states it per function before any code moves, and the pull request says it.

An in-game check, `tools/crime_check` (steal an item in front of an NPC in a quiet-window game; frames viewed; the bounty value read through a Lua script).
- **Layer exceptions removed:** 0. **Risks:** the highest of this set: 19 call-site files (`mwgui` x8, `mwclass` x3, `mwscript` x3, `mwworld` x3, `mwlua` x1, `mwmechanics` x1), a mixed class, the save record, threads. ### Move 8: `MWClass`

- **What moves:** in three stages, each its own review. **8a** world objects: `door`, `container`, `activator`, `static`, `bodypart` (1,043 `.cpp` lines). **8b** items: `armor`, `weapon`, `clothing`, `book`, `ingredient`, `potion`, `misc`, `light`, `lockpick`, `probe`, `repair`, `apparatus` (2,682). **8c** actors: `npc`, `creature`, `actor`, `creaturelevlist`, `itemlevlist` (2,658, after moves 5 to 7 so `npc.cpp` and `creature.cpp` call the registry rather than the core headers). **Never:** `esm4base`, `esm4npc`, `light4` (257 lines).
