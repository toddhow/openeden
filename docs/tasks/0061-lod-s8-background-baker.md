## What exists today (read from the code)

- **Two bakers, both inside a running game.** `openmw --bake-lod-terrain` and `--bake-lod-objects` start a new game without the menu, and a `LodTerrainBaker` or `LodObjectBaker` is called once per running frame from the frame callback in `vsgengine.cpp` (lines near 497 to 511), on the **main thread**, about 10 ms of work per call (`lodobjectbaker.hpp` class comment), then the engine is asked to quit. So today a bake **opens the game's window and renders frames** while baking, and it takes the ESM store, VFS and resource system from the running engine (`MWBase::Environment::get().getESMStore()` in `lodterrainbaker.cpp`). Neither needs the GPU for its result: the terrain baker reads land through `Terrain::Storage::getVertexData` and decodes layer pictures on the CPU (`components/lod/texturedecode.*`); the object baker reads `Nif::` records directly (`components/lod/nifflatten.*`).
- **Both write one pack, whole.** Terrain: `<user data>/openeden/lod/terrain.edenpak`, 571 tiles (levels 1 to 3), 46,016,992 bytes stored uncompressed, 4.65 s (task 0055). Objects: `<user data>/openeden/lod/objects.edenpak`, levels 1 and 2 (level 3 is not baked by default), 156 MB (149 MiB), about 25 s (task 0059 stage c; 458 clusters). If the digest of a rebuilt pack equals the one on disk nothing is written ("already up to date"), otherwise the whole pack is rewritten and `generation` goes up by one. There is no resume inside a bake, no per-unit reuse, no generation folder, no `current` pointer, no status file.
- **A digest-only pass exists for staleness.** `TileBakeSettings::mDigestOnly` computes a terrain tile's digest without blending; the cluster side recomputes tile digests without building meshes (task 0059 "Cache key and staleness"). The runtime (`LodTerrain`, `LodClusters`) already ignores a pack whose digest does not match the loaded content, with a warning.
- **Digests are per unit and independent.** A terrain tile's digest hashes its id, the settings, the full-detail samples and `albedoInputsDigest` (blend map bytes, vertex colours, a BLAKE3 of every used layer file); a cluster's hashes its objects' (cell, reference, record id, model path, transform) and the model file's hash. A tile's digest does **not** depend on its children's keys (the design doc 4.5 idea of "a coarse tile lists its children's keys" was not built). That is good for this task: units can be compared and rebuilt independently.
- **The game opens pack files with a handle per read.** `VFS::readFileRange` (`rangeread.hpp`) opens the file for each call; whether `EdenArchive::Archive::open` keeps a handle between reads is **verify**. On Windows a file that is opened for a read and not shared for delete cannot be removed, and a file that is removed between two reads makes the second read fail. So "the baker never deletes a file the game may read" must be a rule enforced with a lock, not luck (below).
- **The cell numbers.** Morrowind with its two expansions: 1559 exterior cells with data, 119,122 statics with a model, 1,175 distinct models (task 0059). **The whole bake takes about 30 s on this machine for this data.** So the machinery below is not needed for vanilla Morrowind's time; it is needed because (a) a long mod list (Tamriel Rebuilt style land and object counts: how much longer is **not measured**; I will not guess a multiple) multiplies every number and makes a bake a quarter-hour or more of one core, and the player should not wait, (b) a changed load order should redo only what changed, (c) the impostor atlases of S10 need a GPU and are slow, and (d) a game that is playing must not hitch because a bake runs beside it. State this honestly in the launcher text: for vanilla Morrowind "Build now" is a half-minute.

## Design, in plain language

**The baker is the game executable in a bake mode, not a second program.** The bakers need the game's content loading (the ESM store of the load order, the VFS with its archives and data folders, the resource system, the settings), and that code lives in `OMW::Engine::prepareEngine` and the World constructor, not in a library. A separate `openeden-bake` executable would have to reproduce it and could drift from what the game loads, which is exactly how a bake becomes stale-by-bug. So: **`openmw --bake-lod-all`** starts the same engine in a mode with no menu (as the existing bake modes), no game window shown if it can be avoided (see the risks), low priority, and N worker threads, runs the unit plan, writes the generation and exits. The two old switches stay as aliases that run only their part. A shipped small front-end executable with its own name (so Task Manager and the launcher say "OpenEden LOD baker") is a later cosmetic, and is only a copy or a launcher that runs the same binary with the switch. This is a change from the design doc's wording only in detail: D2 said "the same executable started in a bake mode" (4.2), which this is.

**Work units.** One unit is "the payload of one key in one pack":

| Kind | Key (existing code) | Input digest (existing code) | Output |
| --- | --- | --- | --- |
| terrain tile | `Lod::packTileKey` (tag `0x10`) | the tile digest (`TileBakeSettings`) | one `terrain tile` payload (task 0055 layout 1) |
| object cluster | `Lod::packClusterKey` (tag `0x11`) | the cluster digest | one cluster payload (task 0059 layout, version 0 draft until approved) |
| impostor atlas (later, S10) | tag `0x12` | digest of the model, views, settings | an atlas payload, needs a GPU |
| model LOD chain (task 0062) | tag to be reserved, see that spec | digest of model file and settings | an index-buffer set |
| grass coverage (S7) | tag `0x13` | digest of the land textures | a coverage map |

A unit is identified by **(kind, key, parameter digest)**: the key says what, the **parameter digest** (baker tool version, layout version, the settings that change bytes: grid size, albedo size, level errors, drop factor, cell size, worldspace) says how, and the **input digest** says from what. The unit's **cache name** is `<kind>-<key hex>-<first 16 hex of BLAKE3(parameter digest ‖ input digest)>`. Two bakers given the same load order produce the same cache names; a change in any input or parameter gives a new name, so "is this unit already done" is a file-exists test in the unit store.

**Two layers on disk: a unit store and generations.** The container is immutable once written and holds many entries, so rewriting 149 MiB because one mod moved one rock would waste time and disk. So:

```
<lod cache>/                         (default <getCachePath()>/openeden/lod/, task 0058 D8)
  status.json  command.json  lock    (the contract, below)
  units/<kind>-<key>-<digest16>.unit (raw payload bytes of finished units; written to a temp name, renamed)
  gen-000007/                        (one generation: finished, immutable, never edited)
    terrain.edenpak  objects.edenpak (derived packs, `packFlagDerived`, `mGeneration` = 7)
    generation.json                  (canonical manifest: table of unit cache names, load-order fingerprint, tool version, complete or partial)
  current                            (one line: "gen-000007"; rewritten by atomic rename)
  in-use/<pid>-<token>.json          (written by a running game: which generation it opened)
```

A **generation** is assembled from unit files in key order by the container's deterministic writer (`TilePack`/`ClusterPack` writers; store-only for terrain so bytes do not depend on the zstd version, zstd for clusters as now). The units are kept so that the next generation reuses them; a pack can always be rebuilt from units. **Whether unit files should be kept at all** (about 200 MiB for Morrowind, double the disk of the packs) or the previous generation's packs should be read for reuse (copy the entry's stored chunks without decoding if the writer allows it, **verify** in `edenarchive/writer.hpp`) is decision D3; the recommendation is **units**, because a killed baker leaves only complete unit files (resume with no pack to re-open) and because partial progress is a set of files, not a half-written pack.

**Stale means: its cache name is not in the unit table of the plan.** At start the baker (or the game, for the "is my generation current" test, with the digest-only function) computes the **plan**: every unit the load order needs with its input digest, **without building meshes** (the digest-only passes above). Then: units whose cache name is in `units/` are done; the rest are the work; units in the current generation that are not in the plan are dropped when the next generation is written. A load-order change therefore rebakes **only the changed units**: a new mod's placements change the clusters of the tiles it touches; a retextured land cell changes its terrain tiles and the tiles above it that sample it (the digest covers the sampled data, so the coarse tiles' digests change exactly when their samples do). Cost of the plan pass is the cost of the digest-only functions: seconds for Morrowind (collecting 123,576 references took about 1 s, task 0059); for a large mod list, the hashing of model files dominates (`BLAKE3` of each used model and layer file, read through the VFS) and is the thing to measure first (stage a).

**Order of work** (design doc 4.3): coarse levels first (the whole map at low detail within the first minutes), then refinement toward where the player last was (`lastCell` from the status file or the save), then the rest. With 3 baked levels the order is: terrain level 3, level 2, objects level 2, terrain level 1, objects level 1, each sorted by distance to `lastCell` (ties by key), so a stopped bake is already a usable partial generation.

**Running beside the game without hurting it.** What the bake takes from the game: CPU time, memory bandwidth, disk, and RAM (the bakers' peak memory is **not measured** and the object baker copies a model's pieces for every placed object and level, task 0059 "Known approximations"). What the baker does about it:

- **Priority.** Windows: `SetPriorityClass(BELOW_NORMAL_PRIORITY_CLASS)`, or `PROCESS_MODE_BACKGROUND_BEGIN` for the lowest CPU, I/O and memory priority (a process can only set this on itself; the mode lowers IO priority too; **verify** its effect on the work threads of the process and the 0.25-core fairness). Linux: `setpriority(PRIO_PROCESS, 0, 10)` and `SCHED_IDLE` for the worker threads, `ioprio_set` idle class for IO (**verify** support in the container and the kernel). Both through one `Platform::lowerProcessPriority()` function in a small platform file with a unit test that only calls it (it cannot assert the OS's choice).
- **Threads.** `bake threads` default is a quarter of the cores (at least 1) while the game is running (the design doc 4.2) and half when no game is running (a lock check, below). Units run one per worker, never split across threads, so bytes do not depend on the count (design doc 4.4).
- **Pause when the game is busy.** The baker can only know the game's frame health if the game tells it. Proposal: while a game is running with `[WorldLod] background bake = true` it writes `<lod cache>/game.json` every 5 s with its 95th percentile frame time of the last 10 s (a field the frame counters already compute from, **verify**) and its process token. The baker pauses its workers when the number is over `1.5 x` the game's median in the last minute for two samples in a row and resumes after ten calm seconds. Without a game file (no game running) it never pauses for this reason. A baker pausing itself is `state: paused` with `pauseReason: "game busy"`.
- **Battery.** Windows `GetSystemPowerStatus` (ACLineStatus), Linux `/sys/class/power_supply/*/online` (**verify**; not every machine has them). Default: do not start on battery, pause on battery, shown as `pauseReason: "battery"`; a setting `bake on battery` (false) turns it off. A desktop with no battery reports "line power".
- **Memory.** The baker refuses to start a unit batch if the free physical memory is under a floor (starting value 1 GiB, **to be measured**; Windows `GlobalMemoryStatusEx`, Linux `/proc/meminfo`, both **verify**) and drops to one thread.
- **Disk.** Before the plan runs: free space on the cache volume must be at least `2 x` the estimated size of one generation (the previous generation's size, or a table by cell count for a first bake: Morrowind 200 MB) plus 100 MiB; otherwise `failed` with a clear message, nothing written. The cache size limit (`cache size limit`, default 4 GiB, a guess) is checked after each publish.

**Resume after a kill.** The only state is files. A unit file is written to `units/.tmp-<name>`, flushed, and renamed; a killed baker leaves complete units and stray `.tmp-*` files that the next run deletes after it holds the lock. The plan is recomputed at every start. A kill during publish: the generation folder is built as `gen-N.tmp`, renamed to `gen-N` when complete, and only then `current` is rewritten (atomic rename; `std::filesystem::rename` over an existing file replaces it on POSIX, and on Windows the standard says the result is implementation-defined, so use `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)` there, **verify**). A reader that finds `current` naming a missing folder, or a folder without `generation.json`, uses nothing (the live path stays) and logs once.

**Determinism.** As the existing bakers: no clock, no unseeded randomness, objects and tiles in key order, one thread per unit, thread count and order of completion do not change a unit's bytes, generation assembly reads units in key order. Verified by baking a small generated world twice with 1 and 4 threads and comparing SHA-256 of the generation's files, and by baking it with a different unit completion order (a test hook that delays units). The status file and log carry wall-clock times (they are not simulation output; design doc 4.4 and task 0058 say the same); the pack bytes carry none. Cross-machine byte equality is not promised (design doc 4.4).

**Atomic publish and hand-over at restart** (design doc 4.7, the toddhow rule). The baker never edits or removes a file inside a published `gen-N` folder. The game reads `current` **once, at start**, and opens that generation; a bake that finishes while the game plays only adds `gen-(N+1)` and moves `current`, and the game ignores it until the next start. Hot-swapping a running game is not a goal (root `CLAUDE.md`, hot reload is "Not yet"). In-game text: the options window shows "a newer world LOD set is ready; it is used after you restart" (a status line only; the strings go through YAML localisation, a later UI task).

**Cleaning up old generations.** Keep `current` and the **one before it** (rollback if a generation turns out bad) and delete older ones, plus unit files not in the current plan, **only when no live process uses them**: a running game writes `in-use/<pid>-<token>.json` naming the generation it opened (and deletes it on exit); a file is "live" if its `pid` exists **and** its process start time matches the token (so a recycled pid is not mistaken; Windows `GetProcessTimes`, Linux `/proc/<pid>/stat` field 22, **verify**). A stale in-use file (dead process) is ignored and removed. On Windows the game opens pack files without delete sharing for the call duration only, so removal could in principle fail with "in use"; the baker treats a failed removal as "try next time", never as an error. This also covers the file-locking pitfall of the archive spec section 18.

**What happens when the load order changes.** The launcher (task 0058) and the game compute the **fingerprint** (design doc 4.6 step 1: names, sizes and modified times of content files, data folders and archives; one shared function) and compare it with `generation.json`'s. A different fingerprint means "out of date", not "unusable": the game at start runs the digest-only plan for the **current** generation (units it has whose names are still in the plan are valid; the others are missing), draws the valid units, and uses the live path for the rest, **never a stale unit** (design doc 4.6 step 4). This partial use needs the runtime to accept a generation with a subset valid: today `LodTerrain` and `LodClusters` refuse the whole pack on a digest mismatch ("stale"), because the pack digest covers every tile. Stage e changes that to a per-unit check. Until then the behaviour is all-or-nothing, as now; this is stated so that nobody believes the partial use already exists.

**Failure handling.** Every unit is run in a `try`; an exception or a refused input (the NIF reader failing on a model, a land record that does not parse) marks the unit failed with its key and a located message, the bake goes on, and `unitsFailed` and the first 20 messages go in the status file. A generation is published when every plan unit is either done or failed, with `complete: false` if any failed; the game treats a failed unit as missing (live path). A crash of the baker process leaves no published state; `status.json` stays at `building` with a stale heartbeat and the launcher shows "failed (the baker stopped without finishing)" (task 0058). Out of memory, disk full, a read-only cache folder, a cache folder on a removed drive, a cancelled `command.json` stop: each ends in a terminal state written if it still can be, never a partial publish. A second baker for one cache is refused by the lock.

**The lock.** `<lod cache>/lock` is created exclusively at start (`CreateFileW` with share mode 0 on Windows, `flock(LOCK_EX|LOCK_NB)` on Linux; the OS drops it when the process dies, which also answers the "a lock left by a crash must expire" question of design doc 4.7 for the baker lock; the game's `in-use` files are the other mechanism and need the token check above). A baker that cannot take it logs "another baker is running" and exits with code 3.

## The status file (the authority for task 0058; a proposal for toddhow to approve)

Task 0058 drafted this contract from the design doc before a baker existed. This spec keeps its shape and adds what the baker needs; where they differ, this text wins and 0058 is edited when this is approved. Differences: `mode` (`background` or `ahead`), integer `generationNumber` besides the hex `generation`, `phase`, `units` per kind, `unitsReused`, `bytesWritten`, `diskFreeBytes`, `lastCommandId` in the file (0058's text mentions it but its example omits it), `gameRunning`, `threads`. Written to `<lod cache>/status.json` by writing `status.json.tmp`, flushing and renaming, at least every 5 s while working and on every state change; the baker is the only writer; the format string and `version` let readers refuse a newer major version.

```json
{
  "format": "openeden.lod.status",
  "version": 1,
  "toolVersion": "<baker version string>",
  "pid": 12345,
  "processStartToken": "<OS token of the baker process>",
  "mode": "background",
  "state": "building",
  "phase": "terrain level 3",
  "pauseReason": "",
  "heartbeat": 1730000000,
  "profile": "<name or empty>",
  "fingerprint": "<64 hex>",
  "generationNumber": 7,
  "generation": "<64 hex: BLAKE3 of generation.json once complete, else empty>",
  "units": [ { "kind": "terrain", "total": 571, "done": 300, "reused": 250, "failed": 0 },
             { "kind": "cluster", "total": 458, "done": 0, "reused": 0, "failed": 0 } ],
  "unitsTotal": 1029, "unitsDone": 300, "unitsReused": 250, "unitsFailed": 0,
  "threads": 2,
  "gameRunning": true,
  "lastCell": { "worldspace": "", "x": 0, "y": 0 },
  "etaSeconds": -1,
  "bytesWritten": 0,
  "cacheBytes": 0,
  "diskFreeBytes": 0,
  "lastCommandId": 0,
  "errors": [ { "unit": "cluster-1100000000000a0b", "message": "located message" } ],
  "logPath": ""
}
```

States: `idle`, `planning`, `building`, `paused`, `publishing`, `done`, `failed`, `stopped`. Rules (from 0058, repeated because they are the contract): `heartbeat` older than 30 s while `building` or `publishing` means the baker died; `errors` holds at most 20 entries; the reader treats every string as untrusted text (shown, never opened or executed), caps the file at 256 KiB, caps field lengths, and never recurses on file data. The file contains no mod content, only keys, counts and short messages. `command.json` (`pause`, `resume`, `stop`, with an increasing id) is checked between units; `stop` finishes the running units, publishes a **partial** generation if every unit of the coarse levels is done (otherwise none), and sets `state: stopped`.

## Ahead-of-time mode and what may be shipped

`openmw --bake-lod-all --lod-out <folder>` writes the same units and a generation into `<folder>` instead of the cache, at normal priority, all cores, no status pause rules, and exits when done (exit code 0 done, 1 some units failed, 2 failed, 3 locked). It is for people who want to bake once on a fast machine and copy the cache folder, and for tests. Nothing in it is special: a copied folder is a cache folder.

**The licensing rule.** A bake of Morrowind is geometry simplified from Bethesda models, ground pictures made from Bethesda textures, and tile data from Bethesda land records. It is derived from the user's own data; the guardrails in the root guide forbid game assets in the repository, and it must not be **redistributed** (by us, in a release, an installer, a test corpus or a mod). The baker therefore (a) writes `derivedFrom` provenance in the manifest, (b) prints the notice "derived from your game data; do not share" at the end of an ahead-of-time run, and (c) never writes a bake into the repository tree (it refuses an output folder that is inside a git working tree whose root contains a `CLAUDE.md` of this project, **verify** the test, or simply inside the source checkout path the executable was built from).

**A mod may ship a bake of its own content** (decision D5): a **mod-scoped** run, `--lod-scope mod:<data folder or archive>`, bakes only units whose every input file is provided by that mod's own folder or pack. The VFS knows which archive provides a path (`VFS::Manager::getArchiveDescription`, `getOverrides`, `mProviders`, `components/vfs/CLAUDE.md`, "Overrides"); a unit with any input from another provider is skipped (counted `mixed`). The result is a pack whose units validate by their own input digests. Whether a mod's *terrain tile* can be scoped (a tile samples neighbouring cells that other plugins also edit) and whether the game should accept a shipped unit pack beside its own generation are open questions (D5, risk 3); this task builds the scope filter and the manifest field, not the loading of shipped bakes by the game.

## Decisions (recommendation first; toddhow decides)

| # | Decision | Recommended | Alternative |
| --- | --- | --- | --- |
| D1 | Which executable | The game binary in a bake mode (`openmw --bake-lod-all`), sharing the engine's content loading; a differently named front-end later, cosmetic | A separate `openeden-bake` that reimplements content loading (drift, large, no benefit now) |
| D2 | Window | The first version still creates the engine's window (as the existing bakers do), hidden if the platform allows (**verify** `Render::Engine` window traits for a hidden window); stage f makes a content-only start (no window, no Vulkan device) for the bake mode, since neither baker needs the GPU | Require a window forever (an extra Vulkan device on the user's machine while they play) |
| D3 | What is the unit store | `units/` of raw payloads, packs assembled from them per generation | Re-read the previous generation's packs and copy entries (no second copy on disk, but resume needs a half-built pack) |
| D4 | Generations kept | `current` and one before; older removed when no process uses them | Keep all until the size limit |
| D5 | Shipping bakes | Never redistribute our bakes of base game data; a mod-scoped mode exists for a mod's own content, loaded by the game in a later task | No shipping at all (simplest; mods lose a startup win) |
| D6 | When to publish a partial generation | On stop, or at the end with failures, only if the coarse levels are complete | Only complete generations |
| D7 | The status contract | This spec's JSON, shared reader/writer in `components/worldlod/` (task 0058 D5) | Three parsers |
| D8 | Default for `background bake` | false; the launcher offers it; "Build now" is the explicit action | On when `enabled` |
| D9 | Pause policy | Game busy and battery pause by default; memory floor and disk check always | Never pause (simpler, worse neighbour) |

## Stages (each committed working and tested)

- **a. Plan and units, GPU-free, no behaviour change.** `components/worldlod/` (new): the unit model (kind, key, parameter digest, input digest, cache name), the plan builder that wraps the existing digest-only functions of `tilebake` and the cluster side, and `generation.json` (canonical JSON, byte-for-byte round trip, located errors, the project's rule for new formats). Tests on generated worlds: names are stable, any input or parameter change renames exactly the affected units, coarse tile digests change when and only when their samples change, plan order is coarse first then by distance to `lastCell` with ties by key. Measure the plan pass on the real data (the time of collecting and hashing for Morrowind) and record it.
- **b. Unit runner and unit store.** Worker threads running one unit each over the existing pure pipelines (the bakers' main-thread slices are replaced by workers; the pure functions are unchanged), the `units/` store with temp-name-then-rename, resume (kill the process mid-run in a test with a hook and run again: no unit is redone, none is half), thread-count and completion-order independence (SHA-256 of units and of the assembled generation equal for 1 and 4 threads), failure of one unit (a corrupted model in the generated input) recorded and the run goes on.
- **c. Generations and publish.** Assemble packs from units in key order, `gen-N.tmp` -> `gen-N`, `current` by atomic rename, `in-use` files written by the game at start (a tiny addition to `LodTerrain`/`LodClusters` start-up, off unless `[WorldLod] enabled`), the clean-up rules with the process token check, the disk and memory checks, the lock. Windows and Linux paths for rename, lock and process tokens, each tested where it can be (the token and lock logic behind an interface with a fake in the tests, the real ones run by a smoke test on each OS).
- **d. Status file, command file, priority, pause rules.** The shared reader/writer (also used by task 0058's stage a), the writer thread (heartbeat every 5 s), `command.json` handling between units, `Platform::lowerProcessPriority`, the battery and game-busy pause (with a fake game file), the `game.json` writer in the game (a counter read already present, off unless `background bake`). A **fake baker** for the launcher's tests is a few lines on top of the writer.
- **e. Runtime reads a generation.** `LodTerrain` and `LodClusters` read `current`, open the named generation, and apply the per-unit validity check instead of refusing a whole pack; a stale unit is never drawn; a missing or damaged unit falls to the live path; the old single-pack location is read as a legacy fallback for one release so toddhow's present bakes keep working (or are simply re-baked: decision at the stage). Off means unchanged is re-checked.
- **f. Content-only bake start (no window).** The bake mode starts the content loading without a window or a Vulkan device (if the code allows it; **verify** how much of `prepareEngine` assumes a renderer). If it does not, the stage is a report and the window stays hidden. This is also what makes a launcher-started bake invisible.
- **g. The ahead-of-time mode and the scope filter.** `--lod-out`, exit codes, the notice, the refusal of an output inside the checkout, `--lod-scope mod:...` with the `mixed` count. Documentation in the launcher text of task 0058 (a later UI task).

## Constraints

- **Determinism.** Written above; the pack and unit bytes are a function of the inputs and parameters only (unit tests with 1 and 4 threads, shuffled completion, and a clean tree versus a resumed run).
- **Threading.** The unit runner's workers call the pure pipelines only; the status writer is its own thread; the main thread of the baker process does I/O and supervision. In the **game**, the only new code is the `in-use` and `game.json` writers (a file write every 5 s, off the main thread) and the generation reading in `LodTerrain`/`LodClusters`, which already read packs on a worker.
- **Allocation.** None in the game's per-frame path; the baker's allocations are its own (it is a tool), but the plan pass must not hold every model in memory at once (stage a records the peak).
- **Untrusted input.** Everything the game reads from the cache is checked: `current` (at most 64 bytes, must match `gen-[0-9]{6}`, no separators, no `..`), `generation.json` (size cap 1 MiB, strict canonical parse), each pack by the container reader, each unit payload by its layout reader; any failure means "no data, live path, one log line" and never a crash. The baker's own output safety: file names are built only from fixed prefixes, integers and hex digests (never from a texture path, model name or any string out of game data); every path is joined under the cache root and checked to be inside it after resolving (no symbolic links or Windows junctions followed out of the folder: `std::filesystem::weakly_canonical` and a prefix test, plus a refusal when the root itself is a reparse point whose target is outside the user's data and cache areas, **verify**); the cache folder setting is validated before use (not a drive root, not the game's `Data Files`, not a mod folder: the baker refuses a folder that contains an `.esm`, `.esp` or `.bsa`).
- **Off means unchanged.** With `[WorldLod] enabled = false` the game starts no baker, writes no `in-use` or `game.json`, reads no `current`; `background bake` is inert unless `enabled`; the 32 Lua tests and a frame of the Balmora pose are unchanged (as in tasks 0055 and 0059).
- **Windows and Linux.** Both are targets. File names, rename-over-existing, process priority, locks and process tokens are the platform-specific points (each marked **verify** above) and live in one small `components/platform` addition per call; macOS is not a target (root guide).
- **No game assets in the repository.** Bakes live in the user's cache folder; tests use generated worlds; the ahead-of-time mode refuses to write into the source tree.
- **Disk use.** Morrowind estimate: units 200 MB, two generations 400 MB, so about 600 MB; stated in the launcher page.
- New files under `components/` use lowercase letters and digits only.

## Risks and open questions

1. **A baker with a window is a poor background process.** It opens a Vulkan device and a window beside the player's game (D2). Stage f may find that engine start-up cannot run without a renderer; then the background mode ships with a hidden window and its GPU memory cost, or waits.
2. **The runtime's all-or-nothing staleness** (stage e) is a change to inherited-by-us code under full loop, and the hand-over state machines (`Lod::stepTileFade`, `stepCoverage`) assume the set of cluster tiles is fixed for a session; per-unit validity only changes which tiles exist, not the machine, but it must be checked.
3. **Terrain tiles and mod scope.** A tile's digest covers its samples, which include neighbours; a mod that edits one cell changes up to the tiles above it. Whether a shipped scoped bake can ever be valid beside other mods is unresolved; the scope filter is built, loading shipped units is not promised.
4. **Peak memory and the plan pass** are not measured; the object baker's copies are listed as an approximation in task 0059.
5. **Pause by frame time** needs the game to publish its health; a game that does not (older build) leaves the baker on its fixed low priority only.
6. **Cache-limit eviction policy** (what goes first when the limit is hit: old generations, then units not in the plan; never the current) is stated, but the default size is a guess.
7. **Clock jumps and heartbeat.** The status file uses wall time (task 0058); a clock change can make a live baker look dead for 30 s; acceptable.

## Acceptance criteria

- [ ] Stage a: plan tests pass; the plan pass for the real Morrowind data is timed and recorded (seconds, peak memory), and renaming behaves as specified on a generated world with one changed placement.
- [ ] Stage b: **kill test**: a baker killed at three points in a generated world leaves only complete unit files, a second run finishes with the same final SHA-256 as an uninterrupted run; 1 thread and 4 threads give the same SHA-256 for every unit and the generation; a deliberately corrupted model fails one unit, not the run.
- [ ] Stage c: a generation is published atomically (a reader polling `current` during a publish only ever sees the old or the new complete generation, tested with a hook that sleeps between steps); clean-up keeps `current` and the one before and never removes a generation named by a live `in-use` file; a stale `in-use` file (dead pid, mismatching token) does not block clean-up; the disk-space check refuses before writing.
- [ ] Stage d: the status file is valid against the proposed schema in every state, rewritten atomically (a reader loop for 10 s never sees a partial file), the launcher-side reader (stage a of task 0058) accepts what the writer writes and refuses a truncated, oversized or higher-version file; `pause`, `resume`, `stop` act within the running units; pausing for a busy game works against a fake game file.
- [ ] **Real data, Morrowind + Tribunal + Bloodmoon (the S0 machine):** a full bake through `--bake-lod-all` yields terrain 571 tiles and 458 clusters, a generation that the present runtime renders as the earlier packs did (the Balmora far pose frames differ from the pre-change frames by at most the noise of tasks 0055 and 0059: 0.1 to 0.2 points), in no more than twice the time of the two old bakers added together (about 30 s; 60 s limit), and a second run says "already up to date" and writes no unit.
- [ ] **Beside a playing game** (the S0 Balmora pose, 30000 view, distant terrain and clusters on, 1280 x 720): with the baker running at `bake threads` = 2 for the length of a full bake, the game's frame time median is within 10 percent of the same run with no baker and its p99 within 25 percent (S0 baselines: 3.74 to 4.04 ms median, p95 4.47 to 4.67 at this pose; run-to-run noise on this machine up to 0.7 ms between identical runs, so the criterion is judged on three runs each). If it is not met, the thread default drops to 1 and the criterion is judged again.
- [ ] A load-order change test on generated data (one placement moved, one land texture changed): only the units whose digests changed are rebuilt (counted in the status file), the result equals a clean bake.
- [ ] The ahead-of-time mode writes a complete cache folder that, copied to another user data folder on the same machine, is used by the game; it refuses an output inside the source tree; `--lod-scope` skips and counts `mixed` units on a generated two-provider VFS.
- [ ] Windows and Linux: the smoke tests for lock, rename-over-existing, process priority and process token pass on both; the Linux run is on the CI image (as the earlier stages' Linux runs).
- [ ] With `[WorldLod] enabled = false`: no process, file or thread of this system; the 32 Lua tests pass; a frame of the Balmora pose is unchanged.
- [ ] A fresh reviewer read each stage's code (file safety, threading, determinism first); unit tests, clang-format 14 and the check scripts pass.

Out of scope: the launcher page (task 0058; its stage a shares this task's reader), impostor atlases and their GPU bake (S10), grass coverage (S7), the streaming core (task 0060), hot-swapping a generation in a running game, DirectStorage, network or shared caches between machines, loading a mod's shipped bake in the game (a later task after D5), Fallout: New Vegas world source (S12), changing the terrain or cluster layouts, and macOS.
