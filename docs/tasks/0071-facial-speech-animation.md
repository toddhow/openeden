### Is "any GPU" true?

- **NVIDIA's shipped runtime: no.** The SDK needs an NVIDIA GPU, CUDA 12.8 to below 13.0 and TensorRT 10.13 to below 11.0 **[V: github.com/NVIDIA/Audio2Face-3D-SDK README]**; the model cards name TensorRT as the acceleration engine and say the models are "designed and/or optimized to run on NVIDIA GPU-accelerated systems" **[V: huggingface.co/nvidia/Audio2Face-3D-v3.0]**.
- **The weights themselves are portable: yes, in a vendor-neutral file.** Both model repositories publish an ONNX file: v3.0 has `network.onnx` (725 MB; repository 777 MB; about 180 million parameters) and v2.3 Mark has `network.onnx` (75.8 MB; repository 321 MB; about 18.6 million parameters), downloadable without a gate **[V: the Hugging Face file listings, 2026-11-03]**. Audio2Emotion v2.2 has `network.onnx` (1.27 GB) but is gated (log in, accept its own licence) **[V]**.
- **"Uses ONNX" is confirmed in this sense:** the SDK's own scripts take the ONNX file and build TensorRT engines from it with `trtexec --onnx=...`, with no plugin libraries and no custom-operator handling in the script (`audio2x-common/scripts/audio2x/trt.py`) **[V]**. So the network is, at the file level, standard ONNX that TensorRT's parser accepts. That is evidence for, not proof of, support in other runtimes (operator and opset support in ONNX Runtime execution providers, in particular DirectML, is **[A]**).
- **Third-party evidence that the ONNX route works elsewhere:** the community `a2f-rs` project (crate `a2f-mlx` 0.2.0) runs the v2.3.1 "James" network from NVIDIA's official ONNX file through ONNX Runtime's CPU execution provider as its reference path and through a hand-written Apple MLX graph; it reports 8.03 s of speech taking 18.8 s on the CPU provider (2.34 times slower than real time) and 2.8 s on Metal (about 0.35, i.e. 2.8 times faster than real time) on an M1 Max **[S: docs.rs/crate/a2f-mlx/0.2.0, one sample, not reproduced; its own licence is not stated on the page]**. It shows the small regression network runs off NVIDIA hardware; it says nothing about v3.0 (diffusion, HuBERT encoder) or about AMD/Intel GPUs.
- **Conclusion:** "any GPU" is **not true of NVIDIA's runtime** and **may be made true by our own ONNX Runtime front end** (CPU, DirectML on Windows for AMD/Intel/NVIDIA, OpenVINO, ROCm or MIGraphX on Linux; CUDA/TensorRT optional on NVIDIA for speed). That is engineering we would own, and it is **unverified** for both models. This task therefore makes it the gate of stage a.

### Finding: what needs an NVIDIA GPU (toddhow's lead "you only need an NVIDIA GPU to build the model")

- **What needs one:** (1) running NVIDIA's SDK at all (CUDA and TensorRT) **[V]**; (2) the install-time step that converts ONNX into a TensorRT engine for the user's GPU: `trt.py` calls `trtexec` per GPU (`--device=`, optional `--hardwareCompatibilityLevel=ampere+`), and the SDK's `gen_test_data` scripts "convert downloaded models to TensorRT format" **[V]**; TensorRT engines are tied to a GPU architecture and TensorRT version by design **[A: general TensorRT knowledge; the script flags are consistent with it]**. So the engine files are the non-portable artefact; they are built locally, are not what NVIDIA publishes, and are not what we need.
- **What does not need one:** obtaining the ONNX weights (a plain download from Hugging Face, v3.0 and v2.3 ungated) **[V]**, and running that ONNX in a neutral runtime **[A, the part to test]**. Training and fine-tuning are not needed: NVIDIA says it open-sourced a training framework and an example dataset **[V: arXiv 2508.16401 statement; framework licence seen only in a third-party summary [S]]**, but we do not train.
- **So the lead is right in this form:** an NVIDIA GPU is needed for NVIDIA's own runtime and engine build; the deployable weights exist as ONNX without it. Whether the ONNX gives the same result on other runtimes must be tested (stage a).

### Licence and redistribution of the neutral form

- NVIDIA Open Model License (text dated 2025-10-24, read 2026-11-03 **[V]**): grants a perpetual, worldwide, non-exclusive, no-charge, royalty-free, revocable right to "reproduce, use, create derivative works of, make, have made, sell, offer for sale" the Model; "Model" includes checkpoints and learnt weights; "Derivative Model" covers modifications and works based on the Model; "An output is not a Derivative Model"; "NVIDIA claims no ownership rights in outputs"; "You are and will be the owner of Your Derivative Models"; if you distribute the Model you must give recipients a copy of the Agreement. The text does **not** mention hardware, platforms, conversion between formats or other vendors' systems **[V: as read; a lawyer should read the whole text]**. Termination applies if you "bypass, disable, reduce the efficacy of, or circumvent any technical limitation, safety guardrail" (whether a different runtime or quantisation counts is a lawyer question **[A]**), and NVIDIA may update the Agreement.
- Consequences (plain words, not legal advice): converting to another runtime, running on non-NVIDIA hardware and quantising are not prohibited by the text as read; a quantised or re-exported file is a Derivative Model we would own subject to NVIDIA's underlying rights; redistribution needs the Agreement text and notice; **Audio2Emotion has its own gated licence (only with Audio2Face, not for emotion recognition) and must not be redistributed or relied on.**
- **Recommended acquisition flow (no redistribution by us):** the user, or Eden Studio on the user's behalf after a licence dialog showing NVIDIA's Agreement and the user's consent, downloads the ONNX file straight from NVIDIA's Hugging Face repository into the user data folder (`openeden/models/`). Nothing from NVIDIA is stored in this repository or shipped in an installer; the notice is shown and kept beside the file; the file's SHA-256 is pinned in our code so a changed or tampered file is refused. This sidesteps the redistribution obligations and the updates clause (we do not host the model). If a lawyer later says redistribution is fine, a bundled download becomes possible; not needed now.

### Architecture D (the one that conforms to the decision), gated by stage a

1. **Inference:** a small OpenEden library/tool (`components/face`, tool `edenface`) loads NVIDIA's ONNX with ONNX Runtime (MIT **[A: verify before adding to `docs/dependencies.md`]**), chooses an execution provider per machine (DirectML, OpenVINO, ROCm/MIGraphX, CPU; CUDA/TensorRT optional), runs the published window scheme (v3.0: 16 kHz audio, 1 s buffer with 1 s padding each side, 30 output frames of 30 fps per window, 2 diffusion steps, GRU latent 256, emotion input of 10 labels, explicit `noise` and `input_latents` inputs **[V: network_info.json and trt_info.json of the v3.0 repository]**; v2.3: 8,320-sample windows at 50 percent overlap, 10 emotion labels plus a 16-value implicit emotion **[V]**).
2. **Post-processing:** the networks output geometry (skin 72,006 floats = 24,002 vertices for v3.0; tongue, jaw, eyes) **[V]**, not blendshape weights; NVIDIA's SDK then solves 52 blendshape poses with regularised least squares, temporal smoothing and symmetry terms (config values in `bs_skin_config_*.json`: L2 0.1, L1 0.1, temporal 0.05, symmetry 100 **[V]**; pose names are not in the config **[V]**; the solve data are `bs_skin_*.npz`, 15.3 MB per identity **[V]**). We re-implement the solve in our own code, porting from the MIT-licensed SDK source with its notice kept (GPL-3.0-or-later compatible), or we decide to drive our heads directly from a smaller set of channels (stage a). The 52 channels map to our head's channels through the face rig contract; **Morrowind's stock heads have no morph targets** (only a mouth animation range driven by loudness today), so the large quality gain applies to heads that have morphs or bones: replacer heads, later-game heads (Skyrim `.tri`, Fallout), and Morrowind heads after the AdvancedBodies face-morph work. For stock Morrowind heads the useful output is mainly jaw and a few mouth channels.
3. **Output:** `openeden.facecurves` curves (stage b), stored as derived data in `openeden/face/`, never regenerated at run time.
4. **No NVIDIA code in the repository except what is deliberately ported (MIT, notices kept); no CUDA or TensorRT dependency; no weights stored by us.**

### "Build in the background while the player plays" (design, nothing built)

- **Derived data like the LOD and body bakes:** cache `openeden/face/` (one `.facecurves` per voice line, packed into an Eden Archive per voice folder), status file, staleness digest = hash of the audio file bytes + model file SHA-256 + runtime/provider + our post-processing version + seed + emotion setting. Re-run determinism: v3.0 takes explicit `noise` and `input_latents` inputs **[V]**, so a seeded run is repeatable on the same machine and runtime **[A]**; bit-identical results across providers, drivers or GPUs are **not** expected **[A]**, so the cache is authoritative once built (curves never rebuilt unless the digest changes) and the "byte-identical rebuild" criterion applies only to the same machine and provider.
- **What the player's install has (counted on toddhow's Morrowind data folder, 2026-11-03, read-only):** 6,447 voice files `Sound/Vo/**/*.mp3` loose in the data folder, 128.4 MiB, mean 20,883 bytes; the sampled files are 44.1 kHz mono, 64 kbit/s, 0.9 to 7.1 s long (14 sampled), so about 16,800 s (about 4.7 hours) of speech in total **[V for the file count and bytes; the duration is derived from the 64 kbit/s sample: [A]]**. `Morrowind.bsa`, `Tribunal.bsa` and `Bloodmoon.bsa` contain no sound files **[V: `bsatool list`]**. His data folder includes some mod plugins; the count may include their voices.
- **Cache size estimate [A]:** 52 channels at 30 frames per second at 1 byte is 1,560 bytes per second of speech, so 4.7 hours is about 26 MB uncompressed, much less after delta coding and zstd; with tongue, jaw, eye and viseme channels still well under 100 MB.
- **Time estimate [A]:** at the one published CPU figure (2.34 times real time for the 18.6 million-parameter network on an M1 Max), the whole set would take about 11 hours of CPU; the 180 million-parameter v3.0 would be much slower. Therefore: **never build the whole set eagerly.** Build lazily by priority.
- **Queue order:** (1) the line being spoken is never waited for (it plays with the fallback and the curve is used the next time); (2) lines of NPCs in the player's cell and the neighbouring cells, nearest first; (3) lines of the topics the player has open or the quests in progress (INFO records name the voice file: `DialogueManager::say` reads `info->mSound`, `correctSoundPath`); (4) the rest by a background sweep, off by default. A line is built from `DialogueManager`'s sound path through the VFS, never from a path we invent.
- **Fallback while a line is not built:** exactly today's behaviour: the loudness-driven mouth (`MWSound` loudness, `Npc::setFacialState`, `MWAnim::Face`) and random blinks, so the setting is safe to leave on.
- **Contention with the game:** a worker thread at idle priority; a per-frame CPU budget; pause in combat, during loading and while the frame time exceeds a threshold; GPU inference only in menus and loading screens or by an explicit setting (the game needs the GPU: running a 180 million-parameter network concurrently would cost frame time; **measure**); `incremental build budget`-style setting names to follow the existing `[Cells]` pattern.
- **First-run prompt:** one of the choices of toddhow's planned first-time configuration prompt: face animation "off / background, low priority / when idle / ahead of time (bake command)".
- **Ahead-of-time bake command:** `openmw --bake-face` (build the set or a chosen NPC/topic list; resumable; status file), and an Eden Studio button for mod authors.
- **Shipping rule (unchanged):** curves generated on the player's machine from the player's own Bethesda audio are derived data from game assets: never committed, never shipped, never uploaded (same rule as the LOD and body bakes and decision "bakes of game data are never redistributed"); curves for audio we have the rights to may ship in a compatibility pack. The idea of shipping Bethesda-line curves "because they are original" stays blocked on the lawyer questions of note 0034 section 4.

### Gate of stage a (what must be true before architecture D is built)

A hands-on test on toddhow's machine with the real downloaded ONNX files (no code in the repository; a scratch script is fine and stays out of the repo): (1) `onnxruntime` loads v2.3 Mark and v3.0 `network.onnx` on the CPU provider and on DirectML without unsupported-operator errors; (2) the outputs match NVIDIA's reference (toddhow's RTX 4070 can run NVIDIA's SDK once to produce reference output; compare vertex positions or solved weights within a stated tolerance); (3) time per second of audio on CPU and on DirectML (and the extra cost at different thread priorities), and peak memory; (4) the 52-weight solve reproduced from `bs_skin_*.npz` and the config values. **If the gate fails** (unsupported operators, a wrong result, or too slow on non-NVIDIA hardware): my recommendation, not a silent change of toddhow's decision, is a tiered design: Tier 1 everywhere: the free baseline (the existing loudness drive, plus visemes from a permissive aligner such as Rhubarb Lip Sync, MIT); Tier 2: NVIDIA's SDK as an external tool on machines with an NVIDIA GPU, producing the same `openeden.facecurves`. The format, face rig contract, playback and background queue are the same in every case; only the producer changes.

## Shipping rule (proposal, awaiting toddhow)

1. Curves for audio we have the rights to ship (our own recordings, text-to-speech from a permissively licensed engine, volunteer or mod-author lines under a permissive licence): may ship in a compatibility pack or a mod.

### 2026-11-11: engine wiring stage (stage e, engine half) - SPEC (written before the code)

Goal: with `[Face] speech curves = true` (off by default) an NPC that speaks a voice line for which a curves file exists drives its stock head from the curves at the sound's playback position; otherwise today's loudness drive runs unchanged.

- **Path convention (decided here, recorded for toddhow).** The curves of a voice line sit beside it in the VFS: the path the engine passes to `SoundManager::say` (for example `sound/vo/a/f/hlo_af001.wav`, normalised, lower case) with its last extension replaced by `.facecurves` (packed `OPFC` binary, tried first) or `.facecurves.json` (canonical JSON). A loose file in a data folder and an Eden Archive entry with the same path both work (the pack is read through the same VFS). The format's own `audio.name` stays informational.
- **Eden Archive entry type for the binary form: `0x0100` "face curves"** (first id of the unallocated range `0x0100` to `0xEFFF`; the types `0x0005` to `0x00FF` are reserved for core and tile-family types). Added to the entry type table of `docs/spec/eden-archive-format-v0.1.md` as draft and to `Face::sEntryTypeFaceCurves`. - **Sync.** `curve time = stream playback position in seconds` (OpenAL's sample offset minus the queued samples, `OpenAL_SoundStream::getStreamOffset`), clamped at 0; no fixed offset. Past the last curve frame the mouth is closed (talk 0) for as long as the sound still plays; the curves are not looped. The curve file's audio hash is NOT checked at run time (it would mean reading the audio again); the generator side checks it (`audioMatches`).
- **Drive.** `Face::Driver` reduces curves to talk and blink (a stock head has one "talk" range and one "blink" range in a single time-keyed animation). New: Rhubarb curves (viseme channels only) reduce to talk by a named openness table. When speech is active a blink of 0.1 or more takes the head's animation time over from talk (one animation, one value, so they cannot both show); blink amount 0..1 maps to the first half of the blink range (open to closed; the head's blink key frames are assumed to close at the middle, NOT verified on a real head).
- **Threads.** Lookup, parse and cache run on the main thread inside `CharacterController::update` (the same place that sets the loudness today); the result is two floats written to `MWAnim::Face`, which `Npc::update` (an update-thread worker for non-player actors) only reads, exactly like the existing `loudness` float. ### Item 4: the solve, inferred (RECALLED-VERIFY)

Implemented in `bssolve.py` (numpy only). Over the frontal-mask vertices, with B_i the pose deltas and t the target displacement from neutral, minimise
`||sum_i w_i B_i - t||^2 + l2 ||w||^2 + lt ||w - w_prev||^2 + ls * sum_pairs (w_a - w_b)^2 + l1 * sum w`, with 0 <= w <= 1 and inactive poses fixed at 0, by coordinate descent on the 52x52 normal matrix. This is my reading of the parameter names; the exact scaling of each term and the role of `templateBBSize` are NOT in the published files.
Synthetic check (random sparse true weights, target built from the same poses, Mark): with geometry in native units the weights are recovered to a maximum error of 0.015 to 0.027 (mean about 0.001), reconstruction error 0.2 to 0.4 percent, jawOpen 0.8 recovered as 0.8, 14 to 17 ms per frame in a pure-numpy loop. Dividing the geometry by `templateBBSize` (53.45) makes the regularisation swamp the data (maximum error up to 0.99). So native units give sensible strengths, but only a comparison with NVIDIA's weights on real network output can confirm the formulation (item 2, pending).
