## What exists today (read from the code at this commit)

- **The launcher has pages, not a mod manager.** `Launcher::MainDialog::createPages` creates five pages: `DataFilesPage`, `GraphicsPage`, `ImportPage`, `SettingsPage`, `ExtensionsPage` (`apps/launcher/maindialog.cpp`), each with `loadSettings`/`saveSettings`, and `MainDialog::writeSettings` calls every page's `saveSettings` then writes the user `openmw.cfg`, `settings.cfg` and the launcher file. `ExtensionsPage` is the newest and smallest page (144 lines), written in code without a `.ui` file.
- **The launcher already has "profiles", but only content lists.** `Config::LauncherSettings::Profile` holds three string lists (`mArchives`, `mData`, `mContent`) and `Profiles` holds the current profile name and a map (`components/config/launchersettings.hpp`); `DataFilesPage` shows them in a combo box (`apps/launcher/utils/profilescombobox.*`). They are stored in the launcher's own config file, not in `openmw.cfg`. A mod profile in this task is the same idea made larger, so the two must be reconciled (decision D3).
- **`openmw.cfg` is written by the launcher, carefully.** `GameSettings::writeFileWithComments` keeps comments and untouched lines, rewrites only the "ordered" lines, and returns without writing if the file already holds the wanted settings (`components/config/gamesettings.cpp`, line 287 onwards). Lines that come from the global `openmw.cfg` are not the user's: `removeDataDir` says that "non-user settings can't be removed as we can't edit the openmw.cfg they're in" (`gamesettings.hpp`). The Extensions page uses `replace=extension` so that a user line can switch off something enabled globally (`extensionspage.cpp`, `saveSettings`).
- **What the engine reads.** `Engine::prepareEngine` builds `Files::Collections(mDataDirs)` (`apps/openmw/vsgengine.cpp`, around line 324), calls `VFS::registerArchives` with the `fallback-archive=` list, and uses the same collections to find content files and translation data (line 418). So a plugin (`content=`) is found by name in the **data folders on disk**, not through the VFS, and every data folder is also a VFS source (a `FileSystemArchive`). Priority is: archives first, then data folders, later wins, **every loose folder beats every archive and every pack** (task 0050, "Priority order"; `components/vfs/registerarchives.cpp`).
- **The VFS can already say who overrides whom** (task 0050, stage c): `Manager::getOverrides()` returns winner and losers per path, `getConflicts()` drops content-identical ones, `getOverrideCounts()` summarises per source, `getArchiveDescription(i)` names a source. Legacy sources (loose files, BSA) have no stored hash, so identical duplicates among them are listed as conflicts until a tool hashes them (0050 notes, "Content hashes and legacy duplicates").
- **The Eden Archive tools exist** (task 0052): `edenpack [--store|--optimise] [--level N] [--chunk-size N] [--threads N] [--force] [--normalize-names] <input-folder> <output.edenpak>` packs every regular file below a folder, never changes the inputs, writes next to a `<output>.tmp` name, and exits 0 (done), 1 (refused or invalid input) or 2 (usage or I/O error) (`apps/edenarchive/edenpack.cpp`, `toolcommon.hpp`). `edenlist` prints `<size> <64 hex content hash> <path>` per entry; `edenvalidate` checks a pack; the library is Apache-2.0 and is built on BLAKE3 and zstd (`edenarchive/CLAUDE.md`). Names must be normalized (lower case, `/`) unless `--normalize-names` is given; two files that would get one name are refused. A small file costs up to 4095 bytes of padding in a pack (`edenarchive/CLAUDE.md`, "Pitfalls"; spec 8.1), so a mod of hundreds of thousands of tiny files gets bigger, not smaller. `edenpack` prints no progress, only a final line.
- **Packs ride on `fallback-archive=`** (task 0050 D6), recognised by magic bytes, so a pack sits **below every loose data folder**, like a BSA. The launcher's archive file filter (`addArchivesFromDir`: `*.bsa`, `*.ba2` plus `BSAFile::detectVersion`) does not yet know packs (0050 stage g note b).
- **The launcher can start a program with arguments** (`Process::ProcessInvoker::startProcess(name, arguments, detached)`, `components/process/processinvoker.cpp`); `MainDialog::play` currently starts `openmw` with none.
- **Plugin headers are read already.** The content selector model reads each plugin file's header to show its masters and flags (`components/contentselector/model/contentmodel.cpp`; the master list comes from `ESM::ESMReader::getGameFiles`, `components/esm3/esmreader.hpp`). Which of Morrowind's and New Vegas's plugin kinds it reads, and what it does for a missing master, is **verify** by reading the model before stage b.
- **No archive extraction library is linked by the launcher.** `docs/dependencies.md` lists minizip only as something assimp uses (Windows vcpkg set; Linux system or bundled copy); the wizard unpacks installers with unshield. Nothing reads zip, 7z or rar for mods.
- **There is no `apps/launcher/CLAUDE.md`.** This task creates it.

## Design, in plain language

### What a "mod" is in this project

A mod is a **place on disk that adds files to the game**. It is one of:

1. a **folder** that the game would use as a `data=` folder: it may hold loose assets (`meshes/`, `textures/`, `sound/`, ...), plugin files (`.esp`, `.esm`, `.omwaddon`, `.omwgame`, `.omwscripts`) and archives (`.bsa`, `.ba2`); some mods wrap all of this in one more folder (for example `Data Files/`), which the organizer lets the user point at;
2. an **`.edenpak` file** (an Eden Archive pack, for example one the user made by repacking, or one a mod author published);
3. later, a **group** of the above chosen by the user (not in this task).

The organizer never calls the game's own `Data Files`/`Morrowind` data folder a mod: the base game is a fixed, first layer of every profile that cannot be disabled or edited (what the launcher calls the game's `data=` line), shown but locked.

A mod is stored as a small record in the **mod library**: a stable id, a name, the path of its root (the user's original, never copied by default), the sub-path of its data root, the list of plugin files and archives it contains (found by scanning), and notes. The record points at the files; the files stay where the user put them.

### Profiles

A **profile** is a named setup, and it is the only thing that decides what the game sees:

- the ordered list of mods and which are enabled;
- the order of plugin files (the load order), including which are active;
- the order of archives;
- the groundcover list and the extension list (the same lines the Data Files and Extensions pages edit today);
- an optional **settings overlay**: a few `settings.cfg` keys that differ per profile (decision D8: recommend none in the first version, and add it when asked).

Switching profiles is a launcher action. Nothing else changes: the user's mods are not moved, and no file is copied.

### The virtual-folder model

Mod Organizer 2 shows the game one merged "virtual" Data folder built from the mods of the active profile without installing them into the game folder; I read a summary of this (web search 2026-11-02; community descriptions only: stepmodifications.org "Guide:Mod Organizer/Advanced", forums.nexusmods.com topic 7822593 "Mod Organizer 2 overwrite", geckwiki.com "MO": MO2 is built on a virtual file system called USVFS, each profile has its own mod list and load order, and a shared "overwrite" folder collects files that tools write while running) and did not read MO2's source, so any further MO2 behaviour is **verify**. Vortex works differently as far as I recall (a staging folder per mod, then files linked or copied into the game folder on "deploy"), which I did not re-check here (**verify**). OpenEden does not need a virtual file system driver, because **OpenMW already works this way**: the engine takes a list of `data=` folders and merges them in order, later wins (`registerArchives`). So the organizer's virtual folder is nothing more than **the right `data=`, `content=` and `fallback-archive=` lines**, generated from the profile. That is also why it is safe: no game-folder copy, no drivers, nothing running while the game plays.

How the lines reach the engine, honestly:

- The launcher already rewrites the **user** `openmw.cfg` (the file in `getUserConfigPath()`), keeps its comments and the lines it does not own, and writes nothing if nothing changed. The organizer reuses exactly that path: on Play (and on an explicit "Apply") it writes the lines of the active profile into the user `openmw.cfg`, **after saving a backup copy** of the file (`openmw.cfg.bak-<n>`, the last five kept). It touches only the keys it owns: `data=`, `content=`, `groundcover=`, `fallback-archive=` and `extension=` (the same set the existing pages write), and leaves every other line and comment alone. The **global** `openmw.cfg` (the install's) is never written; lines that come from it cannot be removed, only overridden with `replace=` as the Extensions page does.
- The profile is the source of truth; `openmw.cfg` is its **rendering**. If the user edits `openmw.cfg` by hand, the launcher notices at start (the rendered lines no longer match the active profile) and asks: keep the file's version as a new profile, or re-apply the profile. It never silently overwrites a hand edit without the backup.
- Alternative the design doc did not weigh (decision D4): do not touch `openmw.cfg` at all; write a **generated config folder** and start the game with `--config=<folder>` (the engine reads extra config directories, `ConfigurationManager::addExtraConfigDirs`). It leaves the user's file untouched, but then the game started from a shortcut or a terminal does not see the profile, and the existing pages would show a different state from the game. Recommended only if toddhow wants "never edit openmw.cfg" as a hard rule.

### Conflicts

The conflict view answers "which mod provides this file, and what does it hide?". It is **built without starting the game**: the organizer builds a throw-away `VFS::Manager` from the profile's layout (the same call sequence as `registerArchives`, in the same order; `Engine::prepareEngine` already builds a second throw-away manager for its override report) and asks `getOverrides()`. Each provider maps back to a mod through `getArchiveDescription`, which the organizer fills with the mod's id. The page shows:

- per mod: how many files it overrides and how many files of it are hidden by later mods (from `getOverrideCounts()`), as columns in the mod list;
- per file (a table with filter by mod and by folder): the winner and the losers in order; when both hashes are known and equal, "same content, no real conflict" (packs have stored hashes; for loose files and BSA entries a **Compare content** button hashes **only the files in conflict**, on demand, with BLAKE3 from the Eden library, in a worker thread, with a cancel);
- two mods that both ship a file whose names differ only in letter case count as the same file, because the engine compares names after ASCII lower-casing (task 0050, "Path normalization"); the view shows the original spelling of each.

Record-level conflicts (two plugins changing one record) are a **later spec**, not this task: they need a full plugin reader and a record diff, which is a project of its own.

### Repack into the Eden Archive

The player picks a mod and chooses **Repack for faster loading**. The organizer:

1. does a **dry run**: lists the files, the total size, the estimated pack size (an upper bound that counts the 4096-byte block padding of every file, with a warning when it is clearly larger than the source), the free space on the target drive, and the files it will **not** pack (plugin files, see below) and names that cannot be stored (two names that collide after lower-casing: shown with both original paths);
2. runs `edenpack --store --normalize-names <mod data root> <cache>/<mod-id>-<key>.edenpak` as a **child process** (decision D6), so a pack bug cannot take the launcher down; the output goes to a temporary name first, which `edenpack` already does;
3. **verifies** the result: `edenvalidate` on the pack, then a compare of every packed entry's size and BLAKE3 hash with the source file's (read back from the source, not trusted from the packer);
4. only then marks the repack as available, and offers **Use repacked**, which changes the profile (never the mod): in the profile that mod now contributes its pack instead of its loose files.

"Restore" is trivial and safe because nothing original was touched: switch the mod back to **Use original** (one click), and optionally delete the pack from the cache.

Two facts from the code make this harder than it sounds, and the spec has to say so:

- **Plugins are found in data folders on disk, not in the VFS** (`vsgengine.cpp`, `Files::Collections`; see above). A mod that has an `.esp` must still have a `data=` folder holding it. If the original folder stays in the profile, its loose files keep winning over the pack and nothing is gained. So the organizer builds a small **shim folder** in the cache per repacked mod that contains only the mod's plugin files and other files the engine reads from disk (hard links where the file system allows, otherwise copies; a derived copy of the user's own file, never a modification, removed with the repack). The profile then has `data=<shim>` and, since task 0064, `data=<pack>` on the next line, both at the position of the original folder (before 0064 it was `fallback-archive=<pack>`, which sat below all folders). A pack provides no plugins to the engine (0064 D4), so the shim stays needed. Which file kinds the engine reads from disk and not through the VFS (plugins, `.omwscripts`, translation data are the cases seen; others are **verify** by a grep of `Files::Collections` users before stage d) decides the shim's content.
- **A pack in `fallback-archive=` sits below all loose folders** (0050 D6), so repacking a loose-file mod moves it from "among the loose mods" to "below every loose mod". If that mod overrides, or is overridden by, another loose mod, the result changes silently. The organizer therefore **proves the swap is harmless before offering it**: it builds the layout both ways with the throw-away manager and compares the winner of every path; if any winner differs, **Use repacked** is disabled and the page lists the paths (the player may still repack, to keep it for later, or the player decides to give the pack a place, decision D5). A proper fix is an engine change that lets a pack take a place in the data-folder order; that is outside this task and would be its own full-loop spec. **Done in task 0064 (2026-11-02):** a `data=` line may name an `.edenpak` file, and the pack then stands at the position of its line. The organizer writes the pack as a `data=` line at the mod's old place (never in `fallback-archive=`), so the swap cannot change a winner; the dry-run proof remains useful only for a pack the player puts in `fallback-archive=`. The launcher side is still to do here: `Config::GameSettings::validatePaths` keeps only `data=` lines for which `QDir(path).exists()` is true, which drops a pack line, so it must learn `.edenpak` before this task writes one (and the Data Files page must show it).

Packs of BSA archives (converting `.bsa` to `.edenpak`) are not in the first version: `edenpack` takes a folder, and unpacking a BSA to a folder first is a copy of the mod's data (decision D7).

The repack key is `BLAKE3(mod content fingerprint, packer version, mode, chunk size, level)`, so an unchanged mod never repacks twice and a changed one gets a new pack; the content fingerprint is the sorted list of (normalized path, size, content hash) of the mod's files, which the verify step has already computed. Old packs of a mod that are no longer the current key are shown as **stale** and can be cleared (the same idea as the derived-pack digest in spec section 18; this one is a user-level pack, not a `DERIVED` pack, because it is a faithful copy of what the user owns, not generated data, decision D9).

### Where derived files live, and cleaning up

Packs, shims and hash caches go under **`<getCachePath()>/openeden/repack/`** (the same root that task 0058's LOD cache and the baker use, in a sibling folder; `ConfigurationManager::getCachePath`, `components/files/configurationmanager.hpp`), with a setting to move it to another drive. The profile and mod library JSON live in the user config area (`getUserConfigPath()/openeden/`), because they are the player's own data and should be backed up with the config. The Mods page has a **Disk use** panel: total size of the repack cache, per mod, stale entries, a **Clear stale** and a **Clear all** button (each shows what it will delete and asks first). The launcher never deletes anything outside this folder, and it refuses to start deleting if the folder path does not end in the expected names (a guard against a mistyped setting pointing at the user's documents).

### Safety and privacy

- No network access of any kind: no update checks, no downloads, no telemetry, no account. (Nexus lookups exist as a separate tool elsewhere and are not part of this.)
- The launcher writes only: its own JSON files, the user `openmw.cfg` (with backup), and the cache folder. It never writes inside a mod folder or the game's data folder, and every write is by temporary name and atomic rename.
- Mods are third-party works with their own licences (**unknown** per mod). A repack is a local derived copy for the owner's own use; the page says so, the organizer has no export or share function, and nothing is uploaded. The pack's provenance records are not used for user repacks (decision D9) and no mod content enters the repository, tests or CI.
- It refuses to change `openmw.cfg` or run a repack while the game is running (it checks for the `openmw` process by name, **verify** a portable check), because the engine opens packs and archives at start and a replaced file would be a surprise.
- Imported mod folders are untrusted: names are checked with `Path::checkExtractionSafe` (task 0050, `components/vfs/entryname.hpp`) before any file is copied or extracted, links inside a mod folder are not followed, and a mod with a path that fails the check is shown with the problem and cannot be repacked.

### Windows paths and case

Mod folders are often deep; a Windows path over 260 characters fails in older APIs. The organizer uses `std::filesystem` paths (wide on Windows) and shows a clear error naming the file instead of failing silently; whether the launcher's executable has the long-path manifest setting turned on is **verify** (nothing found in `CMakeLists.txt` or `apps/launcher`). Comparisons of mod paths for "is this mod already in the library" are case-insensitive on Windows and case-sensitive on Linux. Names inside mods follow the engine's rule (ASCII lower-casing, no Unicode normalization). Two mod roots that differ only in case on a case-sensitive file system are two mods.

### Translations and accessibility

Every user-visible string uses `tr()`; the `.ts` files must be regenerated with `lupdate` or `CI/check_qt_translations.sh` fails (root `CLAUDE.md`). Accessibility: everything reachable by keyboard (tab order, Space toggles enabled, Alt+Up/Down moves a mod, Delete removes after a confirmation), accessible names on the table, drag and drop is never the only way to reorder, status is never colour only (conflict state has a text/icon), progress is announced through a status label, and nothing relies on a timeout.

## Data model (proposed; the library fixes the exact names)

Two files, JSON written by a canonical writer (sorted keys, fixed number format, trailing newline, round-trips byte for byte, the project's rule for new formats), each with a `format` string and a `version` number; an unknown higher version is read-only and never overwritten.

- `mods.json`: `{ "format": "openeden.mods", "version": 1, "mods": [ { "id": "<slug>", "name": "...", "kind": "folder"|"pack", "root": "<absolute path as the user gave it>", "dataPath": "<relative sub-path or empty>", "notes": "..." } ] }`. The scanned file lists (plugins, archives, counts, sizes) are **not** stored here; they are rescanned (cached by path, size and modified time in the cache folder), so the file stays small and cannot go stale.
- `profiles/<name>.json`: `{ "format": "openeden.profile", "version": 1, "name": "...", "mods": [ { "id": "...", "enabled": true, "useRepack": false } ], "plugins": [ { "name": "foo.esp", "active": true } ], "archives": [ "..." ], "groundcover": [ ... ], "extensions": [ ... ] }`. Order in the arrays is the order of priority (later wins), the same convention as `openmw.cfg`.
- Paths are stored as UTF-8 with `/`; a path under the user's home or the game folder is stored as given (no environment tokens), and a mod whose root no longer exists is kept and shown as missing (a drive may be away), never dropped.

## Stages

Each stage commits working, with a fresh reviewer, and the test-writer's tests for a stage exist before its implementation (full loop). Dependencies: a, then b, then c; d needs b and c (the swap proof uses the layout builder and the conflict scan); e needs a and b (and d for packed-mod import); f last. Stage c can start after a if the layout builder of b is split out first.

- **a. Profiles and the data list.** `components/modorganizer/`: the JSON reader and canonical writer for `mods.json` and profiles, the scanner (finds plugin files, archives, packs and a data root in a folder), the import of the launcher's existing content lists as profiles (D3), the `ModsPage` showing the mod list (name, path, kind, plugin count, archive count, problems) with **Add folder**, **Add pack**, **Remove from list** (never deletes files) and the profile selector. Read-only for `openmw.cfg`: nothing is written to the game's config yet. Unit tests on generated folders (no game files). Creates `apps/launcher/CLAUDE.md`.
- **b. Enable, disable and load order.** Checkboxes, drag and drop and keyboard reordering of mods and of plugins, master-dependency hints from plugin headers (missing master, master after dependant; the read reuses `ESM::ESMReader`/the content model's header reading), the explicit **Sort by masters** (D16), the layout builder (profile to ordered `data=`, `content=`, `fallback-archive=`, `groundcover=`, `extension=` lines), the rendering into the user `openmw.cfg` with backup, owned-keys-only and hand-edit detection (D4), and refusal while the game runs. ## Constraints

- **Original files are never modified, moved or deleted.** The launcher writes only its JSON files, the user `openmw.cfg` (with backup) and the cache folder. Tests include a check that every file of a generated mod is byte-identical and keeps its modified time after a full repack-and-swap cycle.
- **Off means unchanged.** A launcher without any profile, or a player who never opens the Mods page, gets today's behaviour: the Data Files page and `openmw.cfg` handling are unchanged until a profile is applied. The engine is not touched by any stage; the game started with no pack behaves as before.
- No network, no telemetry, no account, no download (D10 may add a library, never a fetch at run time).
- No game or mod asset in the repository, tests or CI: tests generate their mods and archives (the BSA test writers in `components/bsa` and `edenarchive/testsupport` are the precedent).
- Threading: scanning, hashing and repack supervision run off the GUI thread; the GUI thread only reads finished results through signals (`Qt::QueuedConnection`, as `DataFilesPage` already does for loaded cells). Say in the pull request which thread each public function of the library may be called from.
- Determinism: the layout, the conflict list, the repack key and the JSON bytes depend only on the profile and the mod contents, never on directory enumeration order, time or locale.
- Hot paths: not applicable to the game; the scanner and conflict scan are bounded by the number of files and may allocate, but must not hold the whole file list in memory more than once.
- `components/` must not include `apps/`; the library does not depend on Qt widgets (Qt Core types only where the existing config classes force them, `GameSettings` being one).
- Strings: all through `tr()`; regenerate the `.ts` files (`CI/check_qt_translations.sh`).
- A new dependency (D10 only) is licence-checked and recorded in `docs/dependencies.md` before it is used. No code from Mod Organizer 2, Vortex or any other manager is copied; only ideas.
- The Extensions page is untouched except that its `extension=` lines are part of the profile's rendering; the launcher never loads extension code.

## Acceptance criteria

- [ ] Mods can be added from a folder or an `.edenpak`, listed with their plugins and archives, and removed from the list, with no change to any mod file (byte and time comparison test).
- [ ] Profiles can be created, copied, renamed, deleted and switched; the launcher's existing content lists appear as profiles after the first run; JSON files round-trip byte for byte.
- [ ] Enabling, disabling and reordering mods and plugins is possible by mouse and by keyboard; master hints show missing and misordered masters; **Sort by masters** changes nothing until accepted.
- [ ] Applying a profile rewrites only `data=`, `content=`, `groundcover=`, `fallback-archive=` and `extension=` lines of the user `openmw.cfg`, keeps all other lines and comments, writes a backup first, writes nothing if nothing changed, detects a hand edit, never writes the global file, and refuses while the game runs.
- [ ] With the generated example mods, the conflict view's winner for every path equals the winner the real VFS gives when the game is started with the same profile (compared by building the real manager from the written `openmw.cfg` lines).
- [ ] Repack: the dry run reports sizes, padding estimate, free space and exclusions before anything is written; the pack passes `edenvalidate` and the read-back compare of every entry; cancel leaves nothing behind; **Use original** restores the previous behaviour exactly; the cache panel lists and clears packs.
- [ ] **Use repacked** is offered only when every path's winner is unchanged, or the page lists the changed paths and disables it (D5; with the pack written as a `data=` line, task 0064, no path changes, and this is the check that proves it).
- [ ] A repacked mod with a plugin still works: the plugin is found through the shim folder and its assets are served from the pack (checked with a generated mod and the real manager; the in-game check with the player's own Morrowind is toddhow's, written as steps in the pull request).
- [ ] No network access is made by the organizer (checked by reading its call sites and by a run with networking blocked); no telemetry.
- [ ] Long paths, case-only differences and names that fail `checkExtractionSafe` give located errors, not crashes.
- [ ] Unit tests, the 32 Lua tests, the Linux gate, clang-format 14, `CI/check_qt_translations.sh` and the CI check scripts pass; a fresh reviewer read each stage; `apps/launcher/CLAUDE.md` exists.
Out of scope: record-level (ESP/ESM) conflict analysis and patch building, built-in zip/7z/rar extraction (unless D10 is changed), downloading or updating mods, importing profiles from other managers, converting BSA archives, any engine change (a pack taking a place in the data-folder order is done, task 0064), a virtual file system driver, per-profile `settings.cfg` overlays (D8), mod groups, sharing or exporting profiles and repacks, save-game awareness (which profile a save was made with), the World LOD page (task 0058), Eden Studio integration.
