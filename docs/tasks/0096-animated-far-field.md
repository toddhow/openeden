# Task: animated far field (moving effects on far objects, moving distant creatures)
Status: DRAFT 2026-11-09, awaiting toddhow's approval. Docs only so far. Full loop required (touches the LOD cluster layout, `apps/openmw/mwrender/`, `mwmechanics/actors.cpp`).
Design doc section: research note `docs/research/0050-animated-far-field.md` (findings, options, RECALLED-VERIFY list); `docs/tasks/0059-*` (clusters, layout version 1 frozen).
Goal: far objects keep their moving effects (scrolling or flipping textures, alpha pulses, sway) and creatures in the loaded but out-of-processing-range ring keep animating, as opt-in settings that change nothing when off.
Inherited code touched (at the current tree; confirm hashes when work starts): `components/lod/nifflatten.cpp` (`NifFlattener::visit`, `applyProperty`, `addGeometry`), `components/lod/clusterbuild.*` (`ObjectTraits`, `classifyObject`), `components/lod/objectcluster.*` and `clusterpack.*` (layout), `apps/openmw/mwrender/lodclusters.*`, `apps/openmw/mwrender/distantobjects.cpp` (`buildChunk`), `files/shaders/default/main.frag`/`main.vert` (cluster mode `LOD_FADE`), `apps/openmw/mwmechanics/actors.cpp` (`Actors::update`, the `inRange` gate near lines 1696-1710), `apps/openmw/mwmechanics/character.cpp` (`CharacterController`), `components/mwanimation/object.hpp` (`autoPlay`), `components/vsgadapters/nif/nif.cpp` (controller handlers, as the reference for what each controller means).
Inputs / outputs: new settings (all off); layout 2 of `objects.edenpak` (stage b, needs toddhow's approval); a survey report outside the repository.
Constraints:
- Off by default; with every new setting at its default the cluster draws, paging chunks, actors and saves equal the commit before (compared as in the Test plan).
- Determinism: time comes from game or simulation time or a frame counter fed by it, never a wall clock; no unseeded randomness; phases from stable ids.
- Far animation is visual only: no AI, physics, stats, script, sound, text-key or save effect; saves unchanged.
- Derived data (baked packs) lives in the user data folder, is never committed; no game assets in the repository; survey output is aggregate numbers only, names stay local.
- Threads: say in the PR which thread each new update runs on (actor animation runs on update threads; compile on the main thread only).
- Hot paths: no per-frame allocation in the new updates.
- Every engine fact cited by file and function; unverified ones stay RECALLED-VERIFY until a stage settles them.
Acceptance criteria:
- [ ] Every stage below met, each shippable alone.
- [ ] With all new settings off, Morrowind and the world LOD look and run as before (frame comparison, `taa`/`hdr` off for exactness, same cell and camera; census draws equal).
- [ ] Each new setting is in `tools/testprofile/profile.cfg` (or a variant, or `exclude.txt` with a reason) and `tools/testprofile/README.md`; `tools/testprofile/coverage.sh` passes.
Out of scope: far actor proxies beyond the active grid (no actors exist there), impostors with baked animation, raising `CellGridRadius`, skeletal animation inside clusters, particles in far objects, changes to AI or processing range semantics.

## Findings that shape the stages (details in the note)

- Paging chunks (`DistantObjects::buildChunk`) link no controllers: every object there is a frozen rest pose.
- The flattener excludes models whose node or geometry has `mController`, `NiBSAnimationNode`, billboards, particles, skins and non-cutout blends, but never looks at controllers on properties (flip texture, alpha, material colour): those models are baked static into clusters.
- Actors outside `actors processing range` (default 7168) are skipped by `Actors::update` before their animation is advanced; the active grid reaches about 12,000 units, so loaded actors in that ring freeze.

## Stages

Each stage: tests first (a separate writer where the loop calls for it), off by default, frame criteria with frames viewed. Sizes and risk are estimates.

### Stage a: survey (size S, 2 days; risk low; read-only)
A tool (`edensurvey`-style, outside the game loop, reading the user's data through the VFS and the NIF reader) that lists, in aggregate only, for every static, activator and door model: controller kinds on nodes, geometry and properties (UV, flip, alpha, material colour, keyframe, morph, visibility, texture transform), billboard, particle, skin, blend type; and how many cluster pieces (by level) and paging objects would need each kind, per region. Names go to a local report outside the repository, never committed. Also settles: which models are the Ald-ruhn wall panels and the Ghostgate barrier; whether panels are excluded (paging) or baked (cluster); the count of animated vs plain far objects.
Criteria: report byte-identical over two runs; counts reconcile with `--bake-lod-objects`' excluded-by-reason totals (`Animated`, `AlphaBlended`) for the classes it already knows; the property-controller hole of the research note section 3 is confirmed or refuted with a number.
Out: nothing changes in the game.

### Stage a2: flattener sees property controllers (size S, 1 day; risk low-medium)
`NifFlattener` marks `mAnimated` for property-level controllers (`NiFlipController`, `NiAlphaController`, `NiMaterialColorController`, and any other the survey finds), so such models are excluded from clusters instead of baked static. Needs a re-bake and a bumped `bakerVersion` (staleness warning). Behaviour change of the bake only (live paging then draws them, still frozen until stage d). Criteria: unit tests on generated NIFs (red first against the old flattener); a bake before and after differs exactly by the models the survey lists; the cluster count and excluded totals reported.

### Stage b: time-driven UV, alpha and flip in clusters (size M-L, 5 days; risk medium-high: layout 2)
Layout 2: per piece group an effect record (kind, UV scroll velocity, alpha pulse amplitude/frequency/phase, flip strip count and rate); version 1 packs still read as "no effect". Baker maps `NiUVController` and the property controllers to effect records where the controller is linear or periodic, and otherwise leaves the model excluded (live). Shader: a time uniform (game time) and a small parameter block per group in the cluster pipeline only (`LOD_FADE` mode); `[WorldLod] object cluster effects` (off). Needs toddhow's approval of layout 2 before the freeze (decision 0010 rule).
Criteria: payload and reader tests (golden, round trip, version 1 and 2 coexist, strict reader hostile-input cases); two bakes byte-identical; pure CPU twin of the effect maths with tests (wraparound, large times, precision at hours of play: use fractional time); frame: the wall panels move in the distance by the same velocity as the near ones (compare two frames a second apart, difference present with the setting, none without); off: cluster draws byte-identical to the build before (0 pixels); GPU cost measured (estimate under 0.05 ms).

### Stage c: sway for foliage, flags and banners (size M, 4 days; risk medium)
Per piece sway amplitude and phase (from position hash) in the same effect record; vertex displacement in the cluster vertex stage by wind from `Render::WeatherState` when the weather plan (0094) is in, else a fixed default; capped amplitude, anchored base (displacement scaled by height above the piece's base) so cracks do not open. `[WorldLod] object cluster sway` (off). Only models the survey classes as sway-capable (flag/banner meshes by name list in settings data, vanilla has few vertex sway models: RECALLED-VERIFY).
Criteria: pure maths tests; frames at two wind strengths; no silhouette crack in a still frame; off identical.

### Stage d: animated models kept live beyond range with animation LOD (size L, 5 days; risk medium)
`DistantObjects::buildChunk` links the controllers of the models stage a2 excluded (UV, flip, alpha, keyframe) into a per-chunk `Anim::AutoPlay`-style group, updated at a rate that falls with distance (full rate near, 1/4 mid, 1/16 far, by chunk centre distance, steps use accumulated game dt), with a count and distance budget (`[WorldLod] animated object budget`, `animated object distance`); animated objects get their own StateGroups, others stay merged. Settings off.
Criteria: tests for the rate schedule and budget (pure); the paging chunk of a cell with the wall draws moving panels; the census shows draws +N for N animated objects, frame time delta measured and reported (CPU and GPU, three interleaved runs); hot-path allocation test; chunks freed cleanly (no controller outlives its node: lifetime test); off identical.

### Stage e: distant actor animation (size L, 5 days; risk medium-high: mechanics code)
In `Actors::update`, behind `[Game] far animation range` (0 = off, path identical), actors beyond `actors processing range` and within that range get an animation-only update: idle loop, no AI, no movement or physics, text keys ignored, time stepped by accumulated dt at a rate falling with distance, no skin update when culled. Dead, paralysed or scripted-animation (`PlayGroup`) actors keep their current pose rules. Whether far animals may also wander idly (AI) is NOT part of this stage (open question 3).
Criteria: tests with a fake `CharacterController`/seam proving no AI, stat, sound or script call happens in the tier (red first); determinism: a scripted scene run twice, with and without a save/load, yields the same poses and the same game state hash; a creature 9,000 units away animates in frames viewed; CPU cost measured with N actors (estimate 0.1 to 0.5 ms for a few dozen); off: the `inRange` branch compared by trace to be identical.

### Stage f: test profile, tuning, debug views (size S-M, 3 days; risk low)
Settings added to `tools/testprofile/profile.cfg` with `# task 0096:` comments and README lines; `coverage.sh` clean; a debug view colouring pieces by effect kind and animated chunk objects (exclude.txt with reason); budget tuning; docs (`apps/openmw/mwrender/CLAUDE.md`, `components/lod/` notes), the changelog. Linux gate run before any push.

## Answers from toddhow (2026-11-09)

- **Which effects matter most:** "the most obvious ones" (the effects a player notices first at distance: for example the Ald-ruhn wall panels, banners and flags, fires, water wheels, sway of large foliage, and creatures that stand still). Stage a (the survey) should therefore rank the controller kinds by how many far-cluster pieces and how large on screen they are, so the obvious ones go first.
- **Performance budget:** dynamic, not a fixed number. It goes into the scale-back system (task 0080, `[VideoMemory]`: `Render::VideoMemory` controller, `Scaler`, adapters named in `order`, such as `far objects`, `far terrain` and `texture mips`). Design consequence for this task: stages d and e register their own adapters (for example `far animation` that shortens the animation range and lowers the animation update rate in steps, and `distant actors` that reduces the animation-only tier) so the controller can reduce and restore them in the user-ordered ladder. **Open point for the spec:** the controller today reacts to VIDEO MEMORY pressure; the cost of far animation is mostly CPU time, so the scale-back needs a second pressure source (a smoothed frame-time or main-thread-time signal against a target) or these adapters must be driven by the existing memory signal only; decide in stage d (note 0042 and the 0080 stage log describe the memory source and the hysteresis rules to reuse).
- **Far creatures run idle AI too: YES (toddhow).** So stage e is not animation-only: actors in the loaded grid but beyond `actors processing range` also run their idle behaviour (idle animations and, as the spec must decide, wandering), not just a frozen pose that animates. Consequences to settle in stage e before code: (1) it changes vanilla behaviour (AI is not processed beyond the range today), so it is behind a setting, off by default, with a documented list of what runs (idle animation groups, AiWander movement along the pathgrid or navmesh, sleeping/sitting packages) and what never runs far away (combat, scripts, dialogue, hits and spell effects, anything that changes saved state); (2) saves and determinism: far idle AI must not advance anything that is saved differently from vanilla, or must advance it deterministically from game time and the shared PRNG order must not change (no extra draws); (3) physics and navmesh cost for far movers (kinematic only, navmesh or pathgrid lookup, no collision with the player), and the scale-back adapter `distant actors` lowers their update rate and finally freezes them again; (4) actors beyond the 3x3 loaded grid still do not exist (a separate decision).
- **Creatures beyond the active grid are wanted: YES (toddhow).** So the plan needs a far-actor proxy tier (stage e2): drawn, animated, idle-behaving stand-ins for the creatures and NPCs placed in cells that are not loaded. Design constraints to resolve in the spec before code: (1) source of truth: the placed references of each unloaded cell (CREA and NPC_ references in the cell records, already read by the baker for the clusters), plus the SAVE: a creature the player killed, an NPC that moved, was disabled or deleted, or a cell whose state a script changed must not appear as it was in the ESM (read the same per-cell state the game would use when it loads the cell: changed cell records, deleted/disabled flags, moved references; where that state is not available without loading the cell, the proxy tier shows only what is provably unchanged and says so); (2) a proxy is NOT an actor: no AI package, no mechanics, no script, no physics body, no persistence, never targetable, never counted; it must disappear the moment the real cell loads, handing over cleanly to the real actor (same position and pose where possible, with the fade of task 0087/0088 style); (3) idle behaviour is cosmetic: looping idle and a bounded wander around the placed position, deterministic from game time and the reference id (no PRNG draws from the shared stream); (4) cost: a hard cap on proxies, nearest first, models and animations loaded lazily and shared (skinning cost), update rate falls with distance, driven by the scale-back adapter `distant actors` which can reduce to nothing; (5) bake: a per-cell list of proxies (reference id, base record, position, rotation, scale, spawn kind) in the baked far data (layout 2 or a sibling pack), derived from the user's own data and never committed; leveled creature lists and spawners (LVLC) must be resolved deterministically or left out; (6) interplay with the weather and puddle plans: none beyond lighting.
- **Cluster layout 2 APPROVED (toddhow, 2026-11-09), with a re-bake.** The frozen version 1 layout may be succeeded by a version 2 for the effects of stage b (and the proxy data of stage e2 if it lives in the cluster pack). Rules that stay: version 1 packs are still read and draw with no effects (no forced re-bake to keep playing); a version 2 pack is never written by a version 1 reader; the baker writes version 2 only when the effects setting asks for it or always after stage b lands (decide in stage b); `bakerVersion` and the staleness digest change so old packs report stale with a message that says to re-bake; the pinned layout tests are updated in the same change and listed for toddhow. The existing-test edits that this forces fall under his blanket approval of 2026-11-09 but are still listed in the stage log.
- **Stage a2 accepted on its own (toddhow, 2026-11-09): yes.** The flattener may start excluding models with controllers on their properties (flip, alpha, material colour) from the clusters even before stage b exists, moving them to the live (object paging) path, accepting that they then pop in at the live range until stage b brings them back as animated cluster pieces; it needs a re-bake and is behind the baker version bump.
- **Default animation range: the vanilla range (toddhow, 2026-11-09: "Go with the vanilla range then").** `[Game] far animation range` defaults to the vanilla `actors processing range` (7168), so the far tier adds NO extra reach until the player raises it; with the default the feature is a no-op and the game plays as vanilla (this also keeps "off means unchanged" trivially true). Raising it (up to the active grid reach of about 12,000) turns the far tier on, and the scale-back adapters `far animation` and `distant actors` shrink it again under load, never below the vanilla range. The test profile sets a larger value to show the feature. Reading to confirm with toddhow if it matters: "vanilla range" = 7168, not "off".

## Stage a2 and b log, 2026-11-10: property controllers, layout version 2, scrolling cluster groups (built on Windows, local commits, not pushed)

**Decisions taken (toddhow, 2026-11-10 and the blanket approval of 2026-11-09):** stage b is WIDENED to non-scripted, non-activatable scenery activators, not statics only; layout 2 is approved; a2 stands on its own.

**What was built**
- **a2 (`components/lod/nifflatten.cpp`):** a controller on a property (alpha, material colour, flip; `applyProperty`) now marks the model animated; before, such a model was baked as a rest pose. Unconditional, with `bakerVersion` 14. On vanilla data this changes nothing: the bake's `animated` count is 7, as before (survey finding 1 confirmed by the bake itself).
- **Layout version 2 (`components/lod/objectcluster.*`, `clustereffect.hpp`):** version 1 plus one 16-byte effect record per group after the string table (kind bits, u and v speed in texture repeats per second, 4 reserved zero bytes). **The writer writes version 2 only when a group carries an effect; a cluster with none is written as version 1, byte for byte as before. The reader accepts versions 1 and 2** (version 1 means "no effects", as the 2026-11-09 answer says: no forced re-bake; the coordinator's brief said "refuse old packs", the recorded answer was followed). Groups are sorted and distinct by (texture, flags, cutoff, effect kind, speed). Strict reader: unknown kind, non-finite or over-cap (64 repeats a second) speed, a velocity on a kind that does not use it, a scroll that does not move, a version 2 cluster with no effect, non-zero reserved bytes and padding, trailing bytes, every truncation: all refused with the byte's offset. The manifest's `layoutVersion` stays 1 (entries carry their own version).
- **Flattener (`flattenNifModel(root, blendAsCutout, uvEffects)`):** with `uvEffects`, a NiUVController on a shape that is a constant scroll becomes the effect of that shape's pieces and does not mark the model animated, and an `NiBSAnimationNode` with no controller no longer marks it. A scroll is: active, cycling, first UV set, tiling not animated, offset keys on a straight line (linear keys, or Morrowind's two "quadratic" keys per axis whose tangents equal the segment's change: that is what the installed lava, waterfall and fence meshes have; found by reading them), speed within the cap. Any other controller (keyframe, morph, visibility, alpha, a second scroll, a controller on a group node) still marks the model animated. A jump at the end of a cycle when the keys do not add up to whole repeats is not reproduced (smooth scroll).
- **Scenery (`apps/openmw/lodobjectbaker.cpp`, `components/lod/sceneryscript.hpp`):** with `[WorldLod] object cluster scenery` the bake also takes ACTI references whose base record has no name and no script, or a script that never enables, disables, moves, turns, scales or removes its object or starts another script (`Lod::scriptChangesItsObject`, a text scan, case-insensitive, comments and strings skipped). **Found by reading the installed scripts: nearly all moving scenery is scripted.** `in_lava_*` runs the `lava` script (a sound loop and `HurtStandingActor`), the Vivec waterfalls `Sound_Water_Spout`, `Terrain_ashmire` `Sound_mud_bubbles`, vents `Sound_Steam`; the Ghostgate fence runs `GhostfenceScript`, which **disables itself when the journal passes `C3_DestroyDagoth` 20**, so it correctly stays live (a far cluster could not know the fence was gone in an unloaded cell). With "no script" alone the bake takes 276 of the 3,224 activator references and none of the moving ones; the text rule takes 1,049. This heuristic is a decision for toddhow (below).
- **Runtime (`apps/openmw/mwrender/lodclusters.*`, `rendermanager.cpp`):** with `[WorldLod] object cluster effects` a group with a scroll gets `Pipeline::Mode::TEXMAT` and a texture-matrix descriptor (the one the NIF loader makes for a NiUVController; same vertex code in GLSL and Slang), written each frame from `Lod::clusterUvOffset(effect, clock)`: the speed times the clock with the whole repeats removed in double precision. **No shader file changed** (a deviation from the plan's "time uniform and a parameter block in `main.vert`/`main.frag`": reusing the live path's texture matrix needs none, and leaves the shaders, their Slang twins and their interface records untouched). The clock is the sum of the frame times `LodClusters::update` receives (starts at 0 with each `LodClusters`; no wall clock). With the setting off, a version 2 pack's groups draw as still as version 1 groups, with no `TEXMAT` mode, so the pipelines and draws are the old ones. ## Stage c log, 2026-11-10, second slice: sway in the clusters (layout carrier, baker, shader pair, setting; built on Windows, local commits, not pushed)

**Decision taken (toddhow's blanket approval of the layout decision): no new layout version.** Sway is the second kind bit of the version 2 effect record (`clusterEffectSway`, bit 1). The record's last four bytes, reserved and zero until now, hold the lean (a float in (0, 0.1], `maxClusterSwayLean`, equal to `Lod::maxSwayLean`); a record without the sway bit must still keep them zero (the reader still refuses a non-zero byte there, at its offset). So: old version 1 and 2 packs read as before; an older reader refuses a sway record by its reserved bytes (it does not misread it); the writer still writes the lowest version that is needed (a cluster with no effect is version 1, one with only a scroll or a sway is version 2, byte for byte), so a bake with sway off is byte-identical to the build before. A group never has both a scroll and a sway (`isValidClusterEffect` refuses it: both would need the group's one `TEXMAT_BINDING` uniform, which is the carrier of the sway parameters, see below). The group key (builder and validator) gained the lean, so objects with different leans are different groups.

**Per-vertex data without a new vertex attribute:** the vertex format has no room, so each vertex of a sway group carries its weight in its colour ALPHA byte: `Lod::swayEncodeWeight(height above the object's base, object height)` = sqrt(min(1, H t^2 / 2048)) * 255 with t = min(height / H, 1), so the displacement is `lean * wind * 2048 * byte^2 * wave` (the maths of `swayDisplacement` to within a byte step; a test pins the two against each other). The object's base and height come from the z range of the whole object after its transform (`SourceObject::mSwayLean` above 0 makes the builder do it; pieces that already have an effect, a scroll, are left as they are). **The model's own vertex alpha is lost** in a sway group (documented in the setting's comment and the test profile README); the renderer writes alpha 1 into the colour attribute when the sway is not played (`[WorldLod] object cluster sway` off against a pack baked with it on), and the vertex shader outputs alpha 1 in a sway group. Without that, tree bases (weight 0) would be alpha-tested away.

**Baker:** `[WorldLod] object cluster sway` (off), `object cluster sway models` (a comma separated word list matched anywhere in the model path, default `tree, bush, reed, weed, fern, palm, kelp, grass`), `object cluster sway lean` (0 to 0.1, default 0.04). The sway words join the staleness digest only when sway is on, so a pack baked with it off keeps its digest (`bakerVersion` stays 14). With sway on the real Morrowind bake has 2,437 groups with an effect at level 1 (3.34 M triangles), 672 at level 2, 173 at level 3 and 2 at level 4 (scrolls included); 191,301,544 bytes against 186,685,856.

**Renderer:** `Pipeline::Mode::LOD_SWAY` (a vertex mode; `#pragma import_defines` of `default/main.vert` and its Slang twin). The group's `TEXMAT_BINDING` uniform (`vsg::mat4Value`, dynamic) carries the parameters, so no descriptor layout, push constant or scene block changed: column 0 is the wind push along a fixed (1, 1) direction in world units at full weight (`lean * wind * 2048`) and, in z, the clock's angle (`Lod::swayClockAngle`: the effect clock reduced to one 3 s period in double precision), written every frame for the tiles that are drawn. The vertex shader adds a spatial phase of the world position (2,400 and 3,000 units a radian), computes the wave of `Lod::swayWave` (a lean, a swing and a gust), adds a cross motion of a quarter of it, multiplies by the weight and moves the view position (the groundcover's way of turning a world displacement into view space). Wind is `sway wind * (0.3 + 0.7 * Sky::getBaseWindSpeed())` at most 1 (`LodClusters::setWindSpeed`; the weather's wind is read each frame). Settings added: `object cluster sway wind` (0 to 1, the share of the weather's wind), plus the three above. `tools/testprofile/profile.cfg` has `object cluster sway = true`, the README a line, `exclude.txt` the three tuning keys; `coverage.sh` is OK.

## Stage d log, 2026-11-10: animated objects kept live in the object paging chunks, with an animation LOD (built on Windows, local commit, not pushed)

**What was built.** `[WorldLod] animated objects` (off by default; `animated object distance` 24,576 and `animated object budget` 512 tune it). `DistantObjects::buildChunk` (an operation thread) gives each object whose model has auto-play controllers a clone of its model (`MWAnim::cloneIfRequired`, as a placed object gets) and records the controllers and their targets in an `MWRender::AnimatedChunk` that hangs on the chunk node (user object `openeden.animatedchunk`), at most 128 objects a chunk. `DistantObjects::updateAnimation(camera, dt)` (main thread, once a frame, called from `RenderManager::updateDistantObjects` after `update`) runs them. The pure part is `components/lod/animlod.hpp`: `chooseAnimTier` (Full to a quarter of the stop distance, every 4th frame to 60 percent, every 16th to the stop distance, then stopped; 10 percent hysteresis), `animPhaseOf` (a stable 0 to 15 per reference, so objects of one tier do not run on the same frame), `animStartTime` (the start of a phase group other than 0 comes from the reference number, where `Anim::AutoPlay` uses `std::rand()`), and `planAnimFrame` (adds the frame time to each object, chooses its tier, picks the objects due this frame within a budget of controllers, starting at a point that moves with the frame so a budget that cannot run everyone leaves out a different object each time; an object that cost more than the whole budget still runs when it is the first). **The animation keeps its phase:** the time of the frames an object skipped waits in `AnimItem::pendingDt` and is given whole at its next run, so a far object shows the pose a copy running every frame would; a stopped object keeps accumulating and jumps to the right phase when it comes back (tests).

**Not animated (they stay frozen, as before this stage), and why.** (1) Models with a skin (`Anim::Skin` among the cloned controllers): the skin needs the actor's bones; this is the survey's 255 skinned banners and flags, so **the banners and flags of finding 3 are NOT covered by this stage**. (2) Models with a particle system (a compute dispatch under a switch, found by the same `FindDispatch` that `HideParticles` uses): their particles stay switched off as before. The task also asked for "particles optionally culled or paused by distance"; with no particles drawn at all there is nothing to cull, so that part is NOT built (drawing them is a separate stage: the particle controller needs its own link and a world attachment path). (3) Controllers without the auto-play hint (the ones `.kf` files drive): nothing plays them in a chunk.

**Threads and ownership.** `makeAnimatedCopy` and `AnimatedChunk::addObject` run on `DistantObjects`' own build thread, reading only the cached prototype; `AnimatedChunk::update` and `DistantObjects::updateAnimation` run on the main thread only. The `AnimatedChunk` holds a `vsg::ref_ptr` to every controller and every target it runs, so no controller can outlive its nodes; the chunk node holds the `AnimatedChunk`, which dies with the node (tests: `a_chunk_hung_on_a_node_dies_with_the_node`, `the_chunk_keeps_its_controllers_and_targets_alive_and_frees_them_with_it`). `DistantObjects` keeps a reference list of the shown chunks' `AnimatedChunk`s, rebuilt in `setShownChunks` (so the per-frame update does no map or string lookup).
