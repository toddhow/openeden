## What the images are (the contract later passes can rely on)

Three images exist with `gbuffer` on, all the size of the scene (the swapchain's), all single-sample (multisampled targets are resolved), all kept for the whole frame and valid from the end of the main scene pass until the next frame's main pass begins (the same lifetime as `HdrTarget::colorView()`):

| Image | Format | Contents | Where there is no opaque surface |
| --- | --- | --- | --- |
| `normal` | `VK_FORMAT_R16G16B16A16_SFLOAT` | `xyz`: the shading normal in **view space** (unit length before multisample resolve; normal maps applied), `w`: 1 | all zero |
| `linearDepth` | `VK_FORMAT_R32_SFLOAT` | the view-space distance along the camera's view axis, in game units, positive in front of the camera (view space looks down -Z, so this is `-viewPos.z`) | 0 |
| `velocity` (stage b) | `VK_FORMAT_R16G16_SFLOAT` | `currentUV - previousUV`, in texture coordinates (0..1 across the image, y down as the image's rows), of the opaque surface under the pixel; camera motion plus, from stage c, skinned actors' own motion | 0 |

- **View to world:** `scene.invView` (already in the scene uniform) turns a view-space normal into a world-space one. Nothing else is stored in world space.
- **Hardware depth:** the HDR target's resolved `D32_SFLOAT` depth (`HdrTarget::depthView()`) stays as it is, in `DEPTH_STENCIL_ATTACHMENT_OPTIMAL`, where a shader cannot sample it (and where `Reflect`'s copy expects it). That is why `linearDepth` is a colour output and not "the depth buffer again": it is sampleable without a layout change, and a consumer reconstructs a view-space position from it and the projection (`viewPos.xy = ndc.xy * depth / (projection[0][0], projection[1][1])`, `viewPos.z = -depth`).
- **Multisampling (stated compromise):** colour outputs resolve by averaging the samples of a pixel, so on an object's silhouette `normal` is an average of two surfaces' normals (not unit length: renormalise, and treat a length below 0.5 as an edge) and `linearDepth` is an average of two distances (a point between the surfaces). The hardware depth resolves sample zero. A consumer that needs exact edges reads the hardware depth through a copy (as `Reflect` does) or runs without antialiasing. Velocity is computed after the resolve, from the resolved `linearDepth`, so it carries the same edge compromise.
- **What writes the images (the transparency rule):** only opaque, depth-writing draws of the default shader (everything the scene draws with `Pipeline::Graphics` and an empty shader path that is not blended, not a particle and writes colour and depth) and the terrain. Alpha-tested and alpha-to-coverage draws write where they are not discarded (the sample mask applies to every output). Everything else leaves the images as the opaque scene left them: alpha-blended objects and particles (rain, snow, effects, spell glow), the sky and its sun, moon, clouds and stars (own shaders), the water surface and its ripples, debug geometry, the occlusion probe. So under water, behind rain and in front of the sky the images describe what is behind, not the transparent layer. The GUI never touches them (its own pass on the window).
- **Clear values:** the images start every frame as "no surface" (all zero), not at the scene's clear colour.

## Design

**One setting, chosen once at start.** `[Rendering] gbuffer = false` (default). `true` takes effect only when the HDR path is on; otherwise the game logs a warning and runs without it. **Why it needs `hdr`:** the default path draws into the window's render pass, whose attachments are fixed by the swapchain, and adding outputs to it would change the default path (more attachments, different compatibility, more bandwidth). The HDR path already owns its render pass (`HdrTarget`), built for this ("`extraColorFormats`"), so F3 lives there and the default path is not touched. `useGBuffer(gbufferSetting, hdrPath)` is true only when both are true.

**Outputs from the main pass, no prepass** (research 0008's recommendation). The extra colour outputs are added to `HdrTarget`'s render pass at its construction (`extraColorFormats`), before any pipeline of the scene is compiled, since pipelines are compiled against that pass and cannot be changed afterwards.

**The blend-state problem and its solution.** A Vulkan pipeline must have exactly one colour-blend entry per colour attachment of its subpass, and the scene's pipelines are shared between views: the main view (the HDR target's pass, 3 attachments with the G-buffer), the preview and the local map (one attachment) all use the same loaded pipeline objects, and VSG keeps one compiled implementation per view id and reuses it for any view whose merged pipeline states compare equal; the main view, the preview and the map share one view id. VSG's only per-view knob, `overridePipelineStates`, replaces a whole state by type and would destroy each pipeline's own blending. So when the setting is on, `Pipeline::Graphics` and `Pipeline::terrain` use `Pipeline::GBufferBlendState`, a `vsg::ColorBlendState` that always writes `1 + outputs` entries (entry 0 is the pipeline's own; entries 1.. are the G-buffer's). That is always right for the main pass; the preview's and the map's one-attachment passes get entries for attachments they do not have, which drivers ignore and the validation layer would warn about. A first version wrote as many entries as the pass being compiled for had, but then whichever view compiled a shared pipeline first decided the count for all. Giving the main view, or the preview and the map, another view id to avoid this hung the game at start (stage a log), so the fixed count stands; making the preview's and the map's passes carry dummy attachments would make it exact and is left for later. For the G-buffer entries, `colorWriteMask` is all channels for a pipeline that qualifies (see the rule above, `Pipeline::writesGBuffer(options)`, a pure function) and 0 for every other, with blending off. The shader define `GBUFFER` is added only to the pipelines that qualify. A pipeline that does not qualify may still be drawn into a pass that has the attachments: its mask of 0 leaves them alone, and it declares no output for them. With `gbuffer` off none of this code runs: pipelines get the plain `vsg::ColorBlendState` as before, and shaders are compiled without the define (so the SPIR-V is the same).

**The setting is applied from `RenderManager`, not from `ResourceSystem`.** The editor and headless engines build a `ResourceSystem` too and must never see it (F2 read `hdr` only in `RenderManager` for the same reason): `RenderManager` sets `Pipeline::Graphics::gbufferOutputs` and passes the count to the terrain builder, before the first scene object is loaded.

**Debug view.** `[Rendering] gbuffer debug view = none | normals | depth | velocity` (default `none`; read at start; ignored, with a log line, when `gbuffer` is off). The tonemap pass draws the chosen image in place of the scene: normals as `n * 0.5 + 0.5` (black where there is no surface), depth as a grey ramp (`1 - exp(-d / R)`, `R` the view distance setting divided by 8, black where there is none), velocity as `0.5 + v * 200` in red and green (mid-grey where nothing moves). It is a picture for people to look at: it does not feed anything. It is how the result is checked by eye, and the screenshot and the post-processing chain see it as they would the scene.

**Velocity (stage b): camera motion from the stored depth, no new vertex work.** Per-draw previous matrices have no home on this renderer: push constants are full (two `mat4`, the 128-byte minimum), and `Pipeline::Data::Scene` is at the 640 bytes that earlier made interiors brighten when exceeded (`apps/openmw/mwrender/CLAUDE.md`). A fullscreen pass reads `linearDepth`, rebuilds each pixel's world position with this frame's view and projection, projects it with the previous frame's, and writes the screen motion. It treats every pixel as static scenery, so camera motion is exact for the world and wrong for anything that moves on its own. `RenderManager` keeps the previous frame's view and projection (`mPostProcessLastView` already keeps the view for the `.omwfx` chain; the projection can change with the field of view and is kept separately) and resets them to the current ones on the first frame and whenever the camera jumps (a cell change or a teleport), so one frame of nonsense velocity does not reach a consumer. The pass costs one fullscreen triangle in a render graph of its own, timed as `velocity`.

**Object motion (stage c): skinned actors only.** An actor's articulation (limbs, head, weapon arm) is the motion that matters for temporal effects and the only one that has data: the bone matrices of the skin (`Anim::Skin`, `components/animation/skin.hpp`), which today are overwritten each update. Stage c keeps the previous frame's matrices in the second half of the bone matrix array (an array twice as long as the skin has bones, only when the setting is on: `Anim::Skin::keepPreviousMatrices`, read by the NIF and COLLADA loaders; `Skin::apply` copies the first half to the second before writing, so the existing descriptor, cloning and software skinning keep working unchanged), and the vertex shader (with `GBUFFER` and `SKIN`) skins each vertex twice, with the current and the previous bones, both through the current model-view and projection, and passes the difference of the two screen positions on. The default shader writes it to a third G-buffer output (colour output 3), `objectMotion` (`RG16F`, 0 for everything that is not skinned), and the velocity pass adds it to the camera motion. **Not covered, stated:** objects that move as a whole (a swinging door, a thrown item, a creature's root motion and the whole of any actor's walk across the ground, which is a model-view change and not a bone change) get camera motion only, so a temporal effect would ghost on them; fixing that needs the previous model-view matrix of every moving draw (a per-object uniform updated every frame), which is a larger change than this task and costs CPU time on a renderer that is already over its CPU budget (research 0009).

**GPU cost, measured.** `tools/benchmark.sh` (task 0023) over the `heavy_*` scenes with `gpu timing`: `hdr` against `hdr` + `gbuffer` per stage, and the default path against the commit before this task (unchanged). Recorded in `docs/research/0009-render-baseline.md`, new section "F3 cost". The timer's table holds 16 passes; the game registers about 14 with everything on, so stage b's `velocity` pass fits.

**Room for F4 and later.** `normal.w` is written as 1 and reserved: F4's material model can store a second quantity there (roughness) without a new image. The G-buffer outputs are declared in `HdrTarget` by name (`normalView()`, `linearDepthView()`, `objectMotionView()`), the way `colorView()` is, so a consumer is fed the resolved images each frame like `Reflect::setSource` and survives a resize. Baked GI and a ray-traced tier: nothing here requires either; a ray-query pass would read the same images.

## Constraints
Determinism: no change. Allocation: nothing per frame; images are made at start and on resize; the previous-bone array of stage c is allocated when a skin is created, not per frame. Threading: all new code runs on the main thread; the velocity pass's matrices are written on the main thread between frames and read when recording, as `Tonemap`'s push constant is. `Pipeline::GBufferBlendState::apply` runs while a pipeline is compiled (on whichever thread compiles it) and reads only its own members. Off by default and unchanged when off: with `gbuffer = false` no extra attachment, pass, image, descriptor or define exists, the pipelines get the plain colour-blend state, and a frame of the default path is identical to the commit before this task (diffmap, below). With `hdr` on and `gbuffer` off, the HDR path is identical to the commit before this task. Ownership: `HdrTarget` owns the images; `RenderManager` owns the `Velocity` pass by `std::unique_ptr`. Resize: the images and framebuffer are replaced by `HdrTarget::resize`, the velocity image and draw by `Velocity::setSource`, in `syncExtents`.

```
`reprojectVelocity` is the CPU twin of the velocity shader: the pixel's view-space position is `((uv.x*2-1) * depth / projection[0][0], (uv.y*2-1) * depth / projection[1][1], -depth)`, its world position `invView * viewPos`, its previous clip position `prevProjection * prevView * world`, previous UV `prevClip.xy / prevClip.w * 0.5 + 0.5`. With the same matrices both frames the result is `(0,0)`.

```

### 2026-11-01, stage F3b: velocity from camera motion

**What was built, in plain language.** A small extra pass (`Render::Velocity`, `components/render/velocity.*`) runs after the scene when `gbuffer` is on. For every pixel it reads the stored linear depth, rebuilds where that point is in front of the camera, moves it into the previous frame's camera with one matrix and writes how far it moved on screen (`currentUV - previousUV`, RG16F). The matrix (`prevProjection * prevView * currentInvView`) is multiplied in double precision on the CPU, because world positions are large and the product is small. `RenderManager::updateVelocity` keeps the previous frame's view and projection, and compares the camera with itself on the first frame, after a jump of more than 4096 units (a teleport) and after a quarter of a second without a scene frame (a menu or loading screen, where the camera may have been replaced), so no frame of nonsense motion reaches a consumer. The velocity debug view and a `velocity` GPU timer pass exist. The default scale of the velocity view is 200 (the spec first said 40; at 60 frames a second a walking camera moves too little to show at 40).

**Verified.**
- Viewed: with the camera still (`coc` into Seyda Neen at noon, camera held by `camera sensitivity = 0.01`) the velocity view is exactly mid-grey (127, 127, 127 at two sample pixels). Flying forward over Balmora (the benchmark's Lua walk, 60 frames a second) it shows a coherent flow: green growing towards the bottom (near ground moves down the screen), blue on the left and red on the right (surfaces move outwards), grey in the far sky (`scratchpad/gb/v_walk2.png`, `v_walk3.png`).
- `components-tests` pass: 2488, new `RenderVelocityTest` (the matrix and its agreement with the CPU twin, the camera-jump rule, a point behind the previous camera) and the twin's tests from the spec.
- GPU cost of the pass: `gpu_velocity` 0.019 ms median at 1280x720 (`heavy_balmora_walk`).

### 2026-11-01, stage F3c: skinned actors' own motion

**What was built, in plain language.** With `gbuffer` on, every skinned model's bone matrix array is twice as long: the first half is this frame's matrices (as before), the second half the previous frame's. `Anim::Skin::apply` copies the first half into the second just before it writes the new matrices (the first time it writes both halves the same, so the first frame has no motion). One array was chosen over a second one because the descriptor, the cloning of actors and the software skinning (used for picking, which reads only the first half) then needed no change. The vertex shader of a skinned draw that writes the G-buffer (define `GBUFFER_MOTION`, added by `Pipeline::Graphics` to both stages) skins each vertex a second time with the previous bones, through this frame's camera and model, and passes on how far it moved on screen. The fragment shader writes it to colour output 3 (`objectMotion`, RG16F; zero for everything that is not skinned, and for the terrain), and the velocity pass adds it to the camera motion. The G-buffer now always has three extra outputs.
