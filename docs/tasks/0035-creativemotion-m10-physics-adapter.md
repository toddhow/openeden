## What I read (facts the design stands on)

- **The interface to implement:** `components/creativemotion/physics/interface/include/opas/physics/PhysicsWorld.hpp` (`opas::physics::PhysicsWorld`: `createBody`, `destroyBody`, `createJoint`, `destroyJoint`, `createCollisionGroup`, `setSubGroupsCollide`, `destroyCollisionGroup`, `setJointMotor`, `setJointPositionSteps`, `setJointTarget` (two overloads), `applyImpulse`, `setVelocity`, `setBodyDamping`, `setKinematicTarget`, `setMotionType`, `getMotionType`, `readBody`, `readBodies`, `castRay`, `step`, `fixedStepSeconds`, `addStepListener`, `removeStepListener`), with `Descriptions.hpp` (`BodyDesc`, `JointDesc`, `JointMotor`, `Shape`) and `Types.hpp` (`Vec3`, `Quat`, generation-checked `Handle`, `CreateResult`, `ErrorCode`). Meters, kilograms, seconds, radians, right-handed, Z up; floats; "a world is used from one thread at a time, and step callbacks run on the thread that called step()".
- **The reference behaviour:** `components/creativemotion/physics/jolt/src/JoltWorld.cpp` (`JoltWorld`, in `opas::physics::jolt`) is CreativeMotion's own implementation over its own `PhysicsSystem`. Its tests (2,887 in CreativeMotion's repository) pin the meaning of each call. The adapter reproduces that behaviour call by call (validation messages, joint construction: a cone is a `SwingTwistConstraint`, a pyramid a `SixDOFConstraint` with fixed translation; motors as `PositionAndVelocity` with zero target velocity; `kJointPositionSteps` 10; capsules along local Z by rotating Jolt's Y capsule; one `GroupFilterTable` per collision group with a never-reused Jolt group ID; kinematic bodies stopped at their target after the step). It is not reused as code, because it creates and owns a `PhysicsSystem`, a job system and the Jolt global state (`JoltRuntime`) itself, and the vendored copy is never patched (decision 0001; CMake builds it with `OPAS_BUILD_PHYSICS OFF`, root `CMakeLists.txt` around line 596). A CreativeMotion task that splits `JoltWorld` into "body and joint operations over any `PhysicsSystem`" would let both share one implementation: see open question 6.
- **The game's world:** `apps/openmw/mwphysics/physicssystem.cpp`, `PhysicsSystem::PhysicsSystem` (Jolt `Init` with 65536 bodies, the layer interfaces from `joltlayers.hpp`, `SetContactListener(&mContactListener)`, gravity, a `JPH::TempAllocatorImpl` of 25 MiB and a job system), `PhysicsSystem::stepSimulation` (calls `mPhysicsSystem.Update(mPhysicsDt, cCollisionSteps, ...)` in a `while (mTimeAccumJolt >= mPhysicsDt)` loop, on the thread that calls `stepSimulation` (`mwworld/worldimp.cpp:1381`, the main thread). `mPhysicsDt` is 1/60 s unless the `physics framerate` setting changes it; `cCollisionSteps` is 1. `PhysicsSystem::getJoltWorld()` already returns the world (used by the read-only `PhysicsServiceImpl`).
- **Units:** the game's world is in Morrowind units, gravity included (`Misc::Constants::UnitsPerMeter` = 69.99125109, `GravityConst` 8.96, `components/misc/constants.hpp`; `apps/openmw/mwphysics/CLAUDE.md`). `StudioWorld` (task 0030) is in Morrowind units as well, with its own `PhysicsSystem`.
- **Layers:** `joltlayers.hpp` has object layers as bit values (`WORLD` 1<<0 to `SENSOR` 1<<10; 11 is free, and `JPH::ObjectLayer` has at least 16 bits), four broad-phase layers (`WORLD`, `MOVING`, `DEBRIS`, `SENSOR`), and the two filter classes. `DYNAMIC_WORLD` collides with `ACTOR` and `PROJECTILE`; `DEBRIS` collides only with `WORLD` and `HEIGHTMAP`; a dead actor's capsule is moved to `DEBRIS` by `Actor::setCollisionMode(false)` (`actor.cpp` near line 274). The actor movement queries use `CollisionMask_Default` (`WORLD | HEIGHTMAP | ACTOR | DOOR`), so a layer outside it is invisible to them.
- **User data:** `JoltContactListener::OnContactValidate` and `OnContactAdded` (`joltlisteners.hpp`) read `Body::GetUserData()` as a `PtrHolder*` (`Misc::Convert::toPointerFromUserData`, which treats 0 as no pointer), and `PhysicsTaskScheduler::getUserPointer` (`mtphysics.cpp`) does the same. CreativeMotion's `JoltWorld` stores a slot index in the user data. In the game that would be read as a pointer and crash, so **the adapter's bodies carry user data 0** and the adapter finds its own handle from the `JPH::BodyID` (a table indexed by `BodyID::GetIndex()`).
- **Gravity:** `PhysicsSystem::PhysicsSystem` calls `SetGravity(JPH::Vec3(0, 0, +GravityConst * UnitsPerMeter))`, positive Z, which is up. Today nothing is affected: the only dynamic bodies are projectiles, with `mGravityFactor = 0` (`projectile.cpp`), and actors are kinematic (`actor.cpp`). A ragdoll would float upwards. See open question 2.
- **Threads in the game:** `PhysicsTaskScheduler::applyQueuedMovements` first calls `syncSimulation` (waits for the previous frame's actor job) and ends by dispatching a new `MWSimulation` job (`doSimulation`) on the job system; `PhysicsSystem::stepSimulation` then runs `Update` on the main thread, so the actor job and `Update` can run at the same time. Jolt's own queries are thread safe, and the actor job reaches ragdoll bodies only if its layer masks include them (they will not).
- **Other hosts:** `StudioWorld::stepOnce` (task 0030, `apps/opencs/model/physics/studioworld.*`) calls `Update` itself on the main thread, once per 1/60 s step.
- **CreativeMotion's use:** `opas::motor::buildRagdoll(world, rig, profile, rootWorld, options)` and `destroyRagdoll`, `makeLimp` (`core/motor/include/opas/motor/Ragdoll.hpp`) call the interface only through `PhysicsWorld&`. Collision groups with sub-groups are how the neighbouring parts of one ragdoll skip each other.

## Design

### The class (stage a, `components/cmphysics/`)

`namespace CMPhysics`; `class HostedJoltWorld final : public opas::physics::PhysicsWorld`.

**Ownership.** The host owns the `JPH::PhysicsSystem`, the temp allocator, the job system, the Jolt global state (factory, `RegisterTypes`) and the layer interfaces. `HostedJoltWorld` owns only its own bookkeeping and the Jolt bodies, constraints and group filter tables it creates. It is created and destroyed on the main thread. Its destructor removes its constraints and destroys its bodies (bodies first removed from the system, constraints before bodies), so the host's world is left as it was found. The host must destroy the adapter **before** the `PhysicsSystem`, and must not call `Update` while the adapter is being constructed or destroyed. The adapter keeps a reference to the system, so it is not copyable or movable (the base class already deletes both).


**The header, exactly (`components/cmphysics/hostedjoltworld.hpp`; tests are written against this):**

```cpp
#include <Jolt/Jolt.h>   // own include block, first
#include <Jolt/Physics/PhysicsSystem.h>
#include <Jolt/Physics/Body/BodyFilter.h>  // not needed by users; filters below
#include <opas/physics/PhysicsWorld.hpp>
#include <memory>
#include <optional>
#include <string>

namespace CMPhysics
{
    // Runs the host's PhysicsSystem::Update for HostedJoltWorld::step(). Not owned.
    class SystemStepper
    {
    public:
        virtual ~SystemStepper() = default;
        virtual void update(float dtSeconds) = 0;
    };

    struct HostedWorldConfig
    {
        float unitsPerMeter = 1.0f;
        float stepSeconds = 1.0f / 60.0f;
        JPH::ObjectLayer movingLayer = 0;
        std::optional<JPH::ObjectLayer> staticLayer;
        std::uint32_t maxBodies = 1024;
        std::uint32_t maxJoints = 1024;
        const JPH::BroadPhaseLayerFilter* rayBroadPhaseFilter = nullptr; // null: all
        const JPH::ObjectLayerFilter* rayObjectLayerFilter = nullptr;    // null: all
        SystemStepper* stepper = nullptr;                                // null: step() does nothing
    };

    class HostedJoltWorld final : public opas::physics::PhysicsWorld
    {
    public:
        // nullptr and a message in *error (if given) for an invalid config. Main thread.
        static std::unique_ptr<HostedJoltWorld> create(
            JPH::PhysicsSystem& system, const HostedWorldConfig& config, std::string* error = nullptr);
        ~HostedJoltWorld() override;

        void beginStep();
        void endStep();
        // ... every opas::physics::PhysicsWorld virtual, overridden.
    };
}
```
Include path for users: `<components/cmphysics/hostedjoltworld.hpp>`; the interface headers are `<opas/physics/PhysicsWorld.hpp>`. `PhysicsWorld::createBody` etc. are the interface's, unchanged.

**Config (`HostedWorldConfig`, plain data, validated by `HostedJoltWorld::create`, which returns `nullptr` and a message on bad input; no exception):**
- `unitsPerMeter` (> 0, finite): the length unit of the host's world; **the one place meters become world units** (see "Units").
- `stepSeconds` (> 0): what `fixedStepSeconds()` returns, and the `dt` listeners get; the host's physics step (`mPhysicsDt`).
- `movingLayer`: the `JPH::ObjectLayer` of Dynamic and Kinematic bodies (the game: the new `RAGDOLL`; the editor: `StudioWorld::sLayerDynamicWorld`).
- `staticLayer`: `std::optional<JPH::ObjectLayer>`. Empty means this host does not let CreativeMotion create Static bodies: `createBody` with `MotionType::Static` and `setMotionType(..., Static)` fail with `InvalidDescription` and `false`. The game leaves it empty (static world belongs to the game); tests and the editor set it.
- `maxBodies`, `maxJoints` (> 0): capacity limits, reserved up front; the effective body limit is the smaller of `maxBodies` and the system's `GetMaxBodies()`.
- `rayBroadPhaseFilter`, `rayObjectLayerFilter`: non-owning pointers (may be null: everything) used by `castRay`; the host guarantees they outlive the adapter.

**Mapping (each line is a requirement):**
- Bodies: `BodyDesc` to `JPH::BodyCreationSettings`, as `JoltWorld::createBody` does, with `mUserData = 0`, `mObjectLayer` as above, `mOverrideMassProperties = CalculateInertia` with the converted mass for Dynamic (and Kinematic with mass > 0), friction, restitution and damping copied. Shapes: box (convex radius `min(JPH::cDefaultConvexRadius, 0.5 * smallest half extent)`, **after** unit conversion), sphere, capsule along local Z. Positions use `JPH::RVec3` (double precision, `extern/CMakeLists.txt` sets `DOUBLE_PRECISION ON`).
- Handles: slot tables with generations as `JoltWorld`; a second table from `BodyID::GetIndex()` to slot index for `castRay`. A ray hit on a body that is not the adapter's (the host's world, an actor) returns `RayHit` with an **invalid** `BodyId` and a correct point, normal and fraction.
- Joints: `createJoint` as `JoltWorld::createJoint`, anchor converted to world units; angles unchanged. `setJointMotor` as `JoltWorld::setJointMotor`; **motor gains are converted by the torque factor** (see "Units"), and a converted `maxTorque` that would overflow `float` is clamped to `std::numeric_limits<float>::max()` (the default "unlimited" maximum is already that value, so an unconverted product would become infinity, which Jolt must not receive).
- `setJointTarget` (both overloads) as `JoltWorld`; angular velocities are unchanged by units.
- Drive: `applyImpulse` (impulse converted by `unitsPerMeter`, point converted), `setVelocity` (linear converted), `setBodyDamping`, `setKinematicTarget` (`MoveKinematic` with `stepSeconds`, remembered and stopped at the end of the step as in `JoltWorld::stopKinematicBodiesAtTargets`), `setMotionType`/`getMotionType` as `JoltWorld`, but a body that leaves Static moves to `movingLayer` and one that becomes Static moves to `staticLayer`.
- Collision groups: as `JoltWorld` (one `GroupFilterTable` per group, shared by reference count with its bodies, the Jolt group ID a serial number that is never reused).
- Read: `readBody`, `readBodies` (positions and velocities converted back to meters, `awake` from `BodyInterface::IsActive`). `readBodies` allocates nothing.
- `castRay`: `NarrowPhaseQuery::CastRay` with the configured filters and an `IgnoreSingleBodyFilter`, origin and direction converted to world units, `fraction` unchanged.

**Stepping, in two modes** (the host decides who calls `Update`):
- `beginStep()` and `endStep()`: for hosts that run `PhysicsSystem::Update` themselves (the game; `StudioWorld`). `beginStep()` marks the world "in step" and calls `onPreStep(world, stepSeconds)` of each listener registered before the call, in registration order; `endStep()` zeroes the velocity of kinematic bodies moved this step, calls `onPostStep` of the same listeners, removes listeners that were removed during the step, and clears "in step". Neither calls `Update`. Calling `beginStep` while in step, or `endStep` outside a step, does nothing.
- `step()` (the interface call): `beginStep(); stepper->update(stepSeconds); endStep();` where `stepper` is an optional non-owning `SystemStepper` the host passes at creation (one virtual `update(float dt)`; a test or a standalone host gives one that calls `Update`). Without a stepper, `step()` does nothing and says so in its comment. During a step, `createBody`, `destroyBody`, `createJoint`, `destroyJoint`, group changes, `setBodyDamping`, `setJointPositionSteps` and `setMotionType` fail with `CalledDuringStep` / `false`, as in `JoltWorld`.
- Listener semantics as `JoltWorld`: one added during a step starts next step; one removed during a step is not called again.

**Threads (which thread each callback runs on).** Everything in `HostedJoltWorld` is called on the **main thread** only: construction, destruction, all create, destroy, drive, read and cast calls, `beginStep`, `endStep`, `step` and both listener callbacks. In the game, `beginStep` and `endStep` are called around `PhysicsSystem::Update` in `stepSimulation` on the main thread, so listeners run on the main thread, **not** on a Jolt worker. The adapter registers no Jolt callback of its own (no `PhysicsStepListener`, no contact listener, no body activation listener), so none of its code runs on Jolt's workers. It may run at the same time as the game's asynchronous actor job (`MWSimulation`, see "What I read"): that job reaches Jolt only through its thread-safe queries, and ragdoll bodies are outside its layer masks. Listeners must not touch game objects (`MWWorld::Ptr`, scene nodes) except as the main thread's own code already does, and must not call into the adapter's structural calls (they would fail anyway). Nothing is locked by the adapter; the thread rule is the lock.

**Units (the one named boundary).** The interface speaks meters, kilograms, seconds, radians. Let `s = unitsPerMeter`. In `HostedJoltWorld`'s own file, the anonymous-namespace functions `lengthToWorld`, `lengthFromWorld`, `impulseToWorld`, `torqueGainToWorld` (and the `Vec3` versions) are the only code that multiplies by `s`; nothing else in the repository converts for this adapter. Factors: length, position and linear velocity: `s`; mass: 1 (kg); impulse (kg m/s to kg u/s): `s`; angular velocity, angles, friction, restitution, damping coefficients per second: 1; **rotational motor gains** (stiffness N m/rad, damping N m s/rad, maximum torque N m become kg u^2/s^2 per rad, etc.): `s^2` (about 4900), because a torque is mass times length squared per second squared and the inertia Jolt derives from the shape grows with `s^2`. Gravity is the host's (the adapter never sets it). Jolt's built-in tolerances (penetration slop, speculative distance, sleep velocity) are constants in Jolt units; in Morrowind units they are about 70 times smaller relative to a limb than in meters. This is a **risk**, checked in stage b by looking at a settled ragdoll (open question 4), not assumed away.

**Determinism.** No clock, no randomness, no iteration of unordered containers: handle tables are vectors, free lists are LIFO as in `JoltWorld`, listeners run in registration order. The same sequence of calls on the same build gives the same results: the tests compare two worlds bit for bit. Cross-platform bit-identity is **not** claimed (the game's Jolt build does not turn `CROSS_PLATFORM_DETERMINISTIC` on for the world as a whole, and the game's step is not under the adapter's control).

**Allocation.** All containers are `reserve`d at creation (`maxBodies`, `maxJoints`, groups, kinematic list, a fixed number of listeners: 16, creation fails beyond it). `beginStep`, `endStep`, `readBody`, `readBodies`, every drive call, `setJointTarget`, `setJointMotor`, `castRay` and `fixedStepSeconds` make no heap allocation in the adapter's own code (Jolt's own internal use is Jolt's, and `createBody` and `createJoint` allocate: they are not per-step calls). Tested by a counting global `operator new` around those calls.

**Save games.** None. The adapter has no state that is saved (decision 0005 and the architecture rule; a ragdoll is rebuilt when needed).

**Actor capsule against simulated pelvis.** Out of scope (CreativeMotion M10's second item and M11's reconciliation). In this task a ragdoll is a separate set of bodies; the actor's capsule stays where the game puts it. In stage b a ragdoll does not collide with the capsule (layers), so the two do not fight.

### Stage b: attach to the game behind a setting, and a debug scenario

- **Layer `RAGDOLL` = `1 << 11`**, broad-phase layer `MOVING` (mapped in `GetBroadPhaseLayer`). `JoltObjectVsBroadPhaseLayerFilter`: `RAGDOLL` collides with broad phases `WORLD` and `MOVING`; `JoltObjectLayerPairFilter`: `RAGDOLL` collides with `WORLD`, `HEIGHTMAP`, `DOOR` and `RAGDOLL`, and `WORLD`, `HEIGHTMAP`, `DOOR` gain `RAGDOLL` in their lists (the filter must be symmetric). Not with `ACTOR`, `PROJECTILE`, `WATER`, `DEBRIS` (the dead actor's own capsule), `SENSOR`, `DYNAMIC_WORLD`: a ragdoll does not push the living, is not hit by projectiles and does not shove its own corpse capsule, and nothing the game does today meets it. `sRaycastObjectLayers` (11 entries) gets `RAGDOLL`, so that script rays can be masked to it; `CollisionMask_Default` and `CollisionMask_AnyPhysical` do **not**, so existing queries never see a ragdoll. Self-collision inside one ragdoll is by CreativeMotion's collision groups on one object layer.
- **Gravity:** the sign of the `SetGravity` call is the only option that keeps ragdoll code free of hacks; it is an inherited change and is **open question 2**. Until toddhow answers, stage b is not started.
- **Hosting:** `PhysicsSystem` owns `std::unique_ptr<CMPhysics::HostedJoltWorld> mRagdollWorld`, created lazily the first time a ragdoll is wanted (never when the setting is off), declared **after** `mPhysicsSystem` and the job system so that it is destroyed first (members are destroyed in reverse order). `stepSimulation` calls `beginStep()` before and `endStep()` after each `Update` in the loop, only if `mRagdollWorld` exists. `staticLayer` empty; ray filters mask `WORLD | HEIGHTMAP | DOOR | RAGDOLL`.
- **Setting:** `[Physics] creativemotion ragdolls = false` (new, off by default; `components/settings/categories/physics.hpp`, `files/settings-default.cfg`). When off: no adapter object, no Jolt body or constraint of ours, the `Update` loop has one extra null-pointer test, and no existing query mask includes the new layer. **Off means unchanged** is checked by: (1) a unit test of the hosting code path with the pointer null; (2) the game's body count and the 32 Lua integration tests with the setting off, equal to the fork point's; (3) a stated in-game check.
- **Debug scenario (no gameplay change):** a console instruction `cmRagdoll` (open question 5) that, with the setting on and the console target an NPC, builds one ragdoll from CreativeMotion's humanoid rig (`components/creativemotion/data` or the file the task names when stage b starts; not a Bethesda file) at the NPC's position and yaw, converted to meters at one named function in the new game-side file (`MWPhysics::...::toMetres`, using `Misc::Constants::UnitsPerMeter`), lets it fall and settle on the world through the game's Jolt debug draw (`MWRender::JoltDebugDrawer`, already drawing all bodies), and destroys it with the command `cmRagdoll off` or when the cell unloads. The NPC's mesh and capsule are untouched. The in-game check: capture a frame (`--auto-screenshot`) and look at it before committing, as the project's rule for anything that can affect rendering (it only adds debug lines, but the rule is cheap).

### Stage c: the editor's `StudioWorld`

### Stage b as decided (2026-11-01, toddhow's answers 17 to 20 in `docs/decisions/0010-rendering-and-studio-answers-2026-11-01.md`)

This section replaces the stage b text above where they differ. The exact interfaces are here because tests are written from them.

- **Layer `RAGDOLL` (answer 17):** as in "Stage b" above (`1 << 11`, broad phase `MOVING`, meets exactly `WORLD`, `HEIGHTMAP`, `DOOR`, `RAGDOLL`; `WORLD`, `HEIGHTMAP`, `DOOR` gain `RAGDOLL`; `JoltObjectVsBroadPhaseLayerFilter`: `RAGDOLL` collides with broad phases `WORLD` and `MOVING`). `sRaycastObjectLayers` has 12 entries and includes `RAGDOLL`; `CollisionMask_Default` and `CollisionMask_AnyPhysical` do not.
- **Gravity (open question 2, settled without touching the game's gravity):** the game's actors do not use Jolt's gravity. They fall by their own `mInertia.z -= time * GravityConst * UnitsPerMeter` (`apps/openmw/mwphysics/movementsolver.cpp`, around line 514, a downward pull), while `PhysicsSystem::PhysicsSystem` sets Jolt's gravity to `+Z` (`physicssystem.cpp`, `SetGravity`). The call is **not changed**. Instead `HostedWorldConfig` gets `float gravityFactor = 1.0f` (finite, otherwise `create` fails with a message); every Dynamic body the adapter creates gets `JPH::BodyCreationSettings::mGravityFactor = gravityFactor`. The game passes `-1.0f`, so a ragdoll falls down in a world whose gravity points up; the editor's `StudioWorld` (stage c) keeps 1. This is the same mechanism Jolt offers per body; the adapter applies it to all its bodies, so ragdoll code stays free of sign hacks. (Projectiles keep their own factor 0.)
- **Motors (answer 19):** the damping-only-motor workaround of stage a stays (`kDampingOnlyStiffness`); nothing to build.
- **Scale (answer 19):** this stage measures it. Report: whether a settled limp ragdoll at 70 units per meter jitters, sleeps, or rests inside the floor (numbers in the stage log). The adapter converts meters at one place only (stage a, unchanged).
- **CreativeMotion edits:** none were needed by this stage (list here any that are made).
- **`MWPhysics::RagdollHost`** (`apps/openmw/mwphysics/ragdollhost.hpp` and `.cpp`; game-side, testable without `PhysicsSystem`). Owns one `CMPhysics::HostedJoltWorld` over a `JPH::PhysicsSystem&` it does not own, and at most one debug ragdoll built from an embedded humanoid rig and profile (the two JSON files of CreativeMotion's repository `data/rigs/humanoid.rig.json` and `data/profiles/humanoid-default.profile.json`, source commit named in the `.cpp`; embedded so no data file has to be installed). #include <Jolt/Jolt.h>
#include <Jolt/Physics/PhysicsSystem.h>
#include <cstddef>
#include <memory>
#include <string>

namespace MWPhysics
{
    // Where the debug ragdoll is removed on its own: its lowest body this far below its spawn point (metres).
    constexpr float cRagdollKillDepthMetres = 20.0f;

    struct RagdollStatus
    {
        bool present = false;          // a ragdoll exists
        std::size_t bodies = 0;        // its body count
        double lowestZ = 0.0;          // lowest and highest body centre, in game units
        double highestZ = 0.0;
        float maxSpeedMetresPerSecond = 0.0f; // fastest linear speed of any body
        bool allAsleep = false;        // every body is asleep in Jolt
    };

    class RagdollHost
    {
    public:
        // Main thread. nullptr and a message if the adapter refuses. The system must outlive the host.
        static std::unique_ptr<RagdollHost> create(
            JPH::PhysicsSystem& system, float unitsPerMeter, float stepSeconds, std::string* error = nullptr);
        ~RagdollHost(); // removes the ragdoll, then the adapter: the system is left as it was found

        // Builds (replacing any earlier one) a limp humanoid ragdoll standing at feet (game units, double precision)
        // facing game yaw (radians, the NPC's rot[2]). Returns false and a message on failure; then no ragdoll exists.
        bool spawn(const JPH::RVec3& feetUnits, float yawRadians, std::string* error = nullptr);
        void remove();                 // no ragdoll afterwards; no-op if none
        bool hasRagdoll() const;

        // Around the host's PhysicsSystem::Update, main thread, once per Update. endStep also removes the ragdoll
        // if cRagdollKillDepthMetres was passed. No allocation.
        void beginStep();
        void endStep();

        RagdollStatus status() const;  // no allocation
    };
}

  Layers: the adapter's `movingLayer` is `Layers::RAGDOLL`, `staticLayer` empty, ray filters allow `WORLD | HEIGHTMAP | DOOR | RAGDOLL` (object layers) and the broad phases `WORLD` and `MOVING`, `gravityFactor` -1, `maxBodies` 64 and `maxJoints` 64 (a debug scenario, one ragdoll). The ragdoll is built, then made limp with `opas::motor::makeLimp` using the profile (`death` section), so it falls and settles. The conversion of the spawn pose to meters is one function, `RagdollHost::toMetres`, private to the `.cpp` and the only code there that divides by `unitsPerMeter`.
- **Hosting in `PhysicsSystem`:** `std::unique_ptr<RagdollHost> mRagdollHost`, created lazily by the first successful `spawnDebugRagdoll`, never when the setting is off; reset first in `~PhysicsSystem`. `stepSimulation` calls `mRagdollHost->beginStep()` before and `endStep()` after each `Update` in the loop, only if the pointer is non-null. New public methods `bool PhysicsSystem::spawnDebugRagdoll(const MWWorld::ConstPtr&, std::string& message)` and `void removeDebugRagdoll()`; `MWBase::World` gets `bool spawnDebugRagdoll(const MWWorld::ConstPtr&, std::string&)` and `void removeDebugRagdoll()`, forwarded by `World`.
- **Setting:** `[Physics] creativemotion ragdolls = false` (`Settings::physics().mCreativeMotionRagdolls`). With it false, `spawnDebugRagdoll` returns false with the message `creativemotion ragdolls is off` and creates nothing.
- **Console commands (answer 18):** `cmRagdoll` (implicit or explicit reference, so `cmRagdoll` with an NPC selected in the console, or `"name"->cmRagdoll`) and `cmRagdollOff`, opcodes `0x2000327` (`cmRagdoll`), `0x2000328` (explicit) and `0x2000329` (`cmRagdollOff`) in `components/compiler/opcodes.hpp` (`Compiler::Misc`), registered in `components/compiler/extensions0.cpp`, implemented in `apps/openmw/mwscript/miscextensions.cpp`, listed in `apps/openmw/mwscript/docs/vmformat.txt`. They report the result in the console. A separate command `cmRagdollOff` was chosen over an argument because segment 5 instructions take no optional arguments.
- **Cell unload:** not hooked. The ragdoll is removed by `cmRagdollOff`, by the next `cmRagdoll`, by the kill depth, and when the physics system is destroyed. (Deviation from the first text, which said "or when the cell unloads"; reason: the world has no single place that tells the physics system a cell unloaded, and the kill depth covers the case that matters, a ragdoll falling through a vanished floor.)
- **Threads:** `spawn`, `remove`, `beginStep`, `endStep`, `status` and both listeners run on the main thread: the script interpreter and `stepSimulation` are both called from `World::update` on the main thread, one after the other. The asynchronous actor job (`MWSimulation`) may run at the same time; it reaches Jolt through the thread-safe `BodyInterface` and queries with masks that exclude `RAGDOLL`, and `HostedJoltWorld` calls `PhysicsSystem::GetBodyInterface()` (the locking one), so adding and removing bodies is allowed alongside it. Nothing of the host runs on a Jolt worker thread. Nothing in `RagdollHost` locks.

## Constraints
Determinism, allocation and threading as above. Never a second Jolt world: the adapter takes a `JPH::PhysicsSystem&` and has no constructor that creates one. Jolt usage per the root guide: `<Jolt/Jolt.h>` first in its own include block, `JPH::RVec3` for world positions, no shape smaller than its convex radius (the box radius rule above; sphere and capsule have none to violate beyond Jolt's own checks, and the adapter's validation requires positive dimensions). `components/` includes nothing from `apps/`. `components/creativemotion/` is not edited. Public header: Jolt types appear only in `HostedWorldConfig` (filters, layers) and in the constructor argument; no Jolt type appears in the `PhysicsWorld` signatures. clang-format 14 and `-Werror` clean. Off by default: stage a has no setting because nothing in the game uses it.

## Open questions for toddhow
1. **Where the adapter lives.** I chose `components/cmphysics/` (new, in the `components` library, which already links Jolt). The alternative is inside `apps/openmw/mwphysics/`, which the editor cannot use. OK?
2. **Gravity sign in the game.** `PhysicsSystem::PhysicsSystem` sets gravity to +Z. No dynamic body is affected today, but a ragdoll would fall upward. I propose flipping the sign (stage b, one line, nothing else is affected: projectiles use gravity factor 0 and actors are kinematic). The alternative is a per-body gravity factor of -1 in the adapter, which is a hack that would be wrong for the editor. Stage b waits for your answer.
3. **A new object layer `RAGDOLL` (1 << 11).** It touches three functions in `joltlayers.hpp`. The alternative is reusing `DEBRIS`, which needs no change to the filters but collides only with `WORLD` and `HEIGHTMAP`: no collisions between a ragdoll's non-neighbouring parts and none with doors. I recommend the new layer.
4. **Scale risk.** Jolt's tolerances are tuned for meters; the game's world is about 70 times larger per meter. Passive ragdolls should still work (the game already runs actors there), but sleeping and resting contact could look jittery. Stage b's check will look at it; if it is bad the fix is a separate task (a scaled `PhysicsSettings`, a change to the game's world setup).
5. **How the debug scenario is started.** A console instruction needs new mwscript opcodes (`apps/openmw/mwscript/`), the most invasive option. The alternative is an environment-variable-driven check like the project's other `tools/*_check` scripts. I would use the environment variable unless you want the console command.
6. **Share code with CreativeMotion's `JoltWorld`.** The adapter repeats about 600 lines of its body, joint and group logic, because the vendored copy cannot be patched. A CreativeMotion task spec could split `JoltWorld` into "operations over any `PhysicsSystem`" plus its own owner, so that this adapter becomes a thin layer. Until it exists, a fix in one must be mirrored by hand: I will name the vendored copy's CreativeMotion source commit in the file header.
7. **Sub-steps and balance.** The game runs one collision step per 1/60 s; CreativeMotion's balance needs at least 120 Hz internally (`WorldConfig::subStepsPerStep`, `physics/interface`). Passive ragdolls do not. For M11 either the host's `cCollisionSteps` rises when a balancing character exists, or the adapter steps `Update` itself with more sub-steps. Not decided here.

8. **Two Jolt versions.** The game pins Jolt v5.5.0 (`extern/CMakeLists.txt`); CreativeMotion's own build pins a newer commit (v5.6.0 development, `components/creativemotion/cmake/OpasDependencies.cmake`), and its 2,887 tests ran on that. v5.5.0 has no `EMotorState::PositionAndVelocity`, so the adapter uses `Position` and gives a damping-only motor a tiny stiffness (`kDampingOnlyStiffness`); this is a difference from the reference that the CreativeMotion tests do not cover. Options: raise the game's Jolt (a large inherited change) or have CreativeMotion test against v5.5.0 too.
