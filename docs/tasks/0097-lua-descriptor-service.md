# Task: The script-binding descriptor service (Lua namespaces for game packs)
Status: **APPROVED (2026-11-09); stages A, B and C built (see the stage logs).** Full loop required when approved (it touches the SDK, the extension loader's service hand-out and `apps/openmw/mwlua`, and takes input from mod scripts).
Design doc section: `docs/design/game-packs.md` sections 4 (Lua row of the table) and 5.8; decision 0014 point 4 and 5 (`docs/decisions/0014-script-runtimes-and-lua-namespaces-for-game-packs.md`); task 0084 stage log, "leftovers lane I", item I3 (the descriptor service was not built).
Goal: let a game pack (`kind: "game"` only) publish named, versioned function descriptors that the core turns into Lua packages in its single sandboxed Lua host, with no Lua or `sol` type ever crossing into the SDK.
Inherited code touched (at the current `main`): `apps/openmw/mwlua/luamanagerimp.cpp` (`LuaManager::initPreLoad`, `initPostLoad`), `apps/openmw/mwlua/luabindings.cpp` (`initCommonPackages`, `initGlobalPackages`, `initLocalPackages`, `initPlayerPackages`, `initMenuPackages`, `initLoadPackages`), `components/lua/configuration.cpp` (stage C only: one manifest keyword), `components/lua/luastate.cpp` (read only: `addCommonPackage`, `runInNewSandbox`, `requireGen`). New: `apps/openmw/mwlua/packbindings.*`, `sdk/include/openeden/game/bindings.hpp`.
Inputs / outputs: a `BindingsService` handed to game packs only (via `PackScopedHost`, task 0084); descriptors in; one read-only Lua table per (namespace, script context) out.
Constraints: see "Constraints" below.
Acceptance criteria: see the stages.
Out of scope: any Lua API from ordinary extensions or the common pack (decision 0003 stands); record descriptors (decision 0013, separate); callbacks into Lua from a pack; the Papyrus and ObScript natives (they use their own contracts, task 0092/0093); GUI windows; changing what `openmw.*` packages offer.

## Engine facts this spec relies on (read at the current commit)
- **Packages are registered per script container, by name.** `initCommonPackages` (`luabindings.cpp`) gives `openmw.async/markup/util/vfs` to every sandbox through `LuaState::addCommonPackage` (`components/lua/luastate.cpp`, made read-only unless it is a function); `initGlobalPackages` gives `openmw.core/types/world`; `initLocalPackages` gives `openmw.animation/core/types/nearby`; `initPlayerPackages` adds `openmw.ambient/camera/debug/input/postprocessing/ui`; `initMenuPackages` and `initLoadPackages` are the menu and load contexts. `LuaManager::initPreLoad` and `initPostLoad` (`luamanagerimp.cpp`) hand each map to `mLoadScripts/mGlobalScripts/mMenuScripts.addPackage(...)`; local and player packages are kept in `mLocalPackages/mPlayerPackages`.
- **The only permission model is "which packages exist in this script type's sandbox".** There is no per-function permission. A script gets a fresh `sol::environment` over a whitelisted base (`LuaState::runInNewSandbox`, `safePackages = coroutine, math, string, table, utf8`); `require` is `requireGen` (`luastate.cpp`): a package not in `loaded` falls through to a VFS file loader, so requiring an absent package fails at the call, inside the script, not at load.
- **Object access is split by type, not by flag.** `MWLua::GObject` (global scripts, mutable), `LObject` (local, read-only), `SelfObject` (`apps/openmw/mwlua/README.md`, "Bindings").
- **Threads.** Lua `update()` runs on a worker (`Worker::update` calls `LuaManager::update`, `worker.cpp`) by default (`[Lua] lua num threads = 1`, `files/settings-default.cfg`). The README says the Lua thread is paused while other game state updates run, so state that does not affect the scene graph may be changed immediately, and anything that affects it is queued with `LuaManager::addAction` and applied by `LuaManager::synchronizedUpdate` on the main thread (`luamanagerimp.cpp`). `LuaManager::sendExtensionEvent` is the existing precedent for a non-Lua caller feeding Lua: it builds a table inside `mLua.protectedCall`.
- **Caps already there.** A count hook (`LuaState::countHook`) raises a Lua error after `[Lua] instruction limit per call` instructions (default 100000000); an allocator hook enforces `[Lua] memory limit` (`LuaState::trackingAllocator`). Neither counts time spent inside native code.
- **Versioning precedent.** `core.API_REVISION` (`corebindings.cpp`, `Version::getLuaApiRevision()`, `OPENMW_LUA_API_REVISION` in the root `CMakeLists.txt`) is one integer for the whole API; scripts compare it themselves. The `.omwscripts` parser (`components/lua/configuration.cpp`) knows only the flags `GLOBAL, CUSTOM, PLAYER, MENU` (and record-type words for `CUSTOM`/attach); RECALLED-VERIFY that it has no way to name a dependency.
- **Saves.** Script saved data goes through `LuaUtil::serialize` with `MWLua::UserdataSerializer` (`userdataserializer.*`), which knows object references only. RECALLED-VERIFY: what the serializer does with an unknown userdata (expected: an error naming the type).
- **SDK rule.** `CI/check_extension_sdk.sh` (a) bans the words `LuaTable`, `lua_State`, `sol::...`, `ScriptingService`, `registerModule` and others in `sdk/include/openeden/`; (b) fails on any `[Ll]ua` in the SDK headers after stripping `markForwardedToLua`, `isForwardedToLua`, "forward(s/ed) to Lua", "a Lua event", "Lua scripts", "in Lua", "Lua API". So the new header must not say "Lua" at all (call the concept "script bindings"), and the core, not the SDK, knows the target language.

## The four gaps: options and recommendations

### Gap 1: the descriptor type system
Needs: enough to express Papyrus/ObScript-flavoured game queries (actor value, form lookup) without a general object model; nothing a pack can use to hold a Lua state or leak a `sol` type.
- **Option A, scalars only:** bool, int32, double, string (UTF-8). Smallest, fully testable, no handles.
- **Option B (recommended): A, plus an opaque handle, an optional and flat arrays.** `Handle` is a 64-bit value the pack mints (a generation-checked entity or form id, as the extension entity service does); in Lua it is an opaque userdata that compares equal by value and has no methods. `Optional<T>` maps to `nil`. `Array<T>` of scalars or handles, flat, length-capped. Results of a call return one value (or none).
- **Option C, tables and callbacks:** structured records in and out, and Lua callbacks. Rejected: it rebuilds a binding generator and puts script-owned references inside the pack (lifetime, determinism, saves).
Rules (all tested): argument count at most 8; a string at most 64 KiB; an array at most 256 elements; an integer outside int32 and a non-finite number passed for an int are a Lua error naming the function and argument, not a clamp; a number result that is NaN is returned as is (the pack's business) and documented. **Errors:** a handler returns `Status { Ok, BadArgument, NotFound, Refused, Internal }` plus an optional short text; the core turns anything not `Ok` into a Lua `error()` located at the calling script (`"core.skyrimse.actor.getValue: NotFound: no such actor value"`), because the script runtime's own error reporting already shows script and line. Exceptions: handlers are `noexcept` in the contract; the core wraps each call in a catch-all as a second line (an escaped exception becomes `Internal`, logged once per function), so none crosses either way.

### Gap 2: registration and sandbox permissions
- **Registration point.** A new SDK service, `BindingsService` in `sdk/include/openeden/game/bindings.hpp`, handed only to `kind: "game"` (the same `PackScopedHost` rule as the other game services, task 0084; other kinds get `nullptr` and a `CapabilityDenial`). Called from the pack's `start()`; one call per namespace: `declareNamespace(NamespaceDescriptor)`, where a namespace carries `name`, `version`, and a list of `FunctionDescriptor { name, params, result, access, threadRule, handler }`. The handler is a plain function pointer plus a context pointer, or an interface with a `noexcept` virtual `call(args, result)` (decided at implementation, tests are the same either way). The core refuses: a name that does not start with the session's game id; a duplicate namespace or function; a name that is not `[a-z][a-z0-9_]*`; more than 64 namespaces or 256 functions each. A refused declaration is a pack failure, not a silent skip.
- **Timing.** Packages must exist before `LuaManager::initPostLoad` builds the maps. RECALLED-VERIFY the start order of the extension host against `Engine::prepareEngine` / `LuaManager::init`; if the pack starts later, the core builds the pack's package lazily inside the sandbox loader (the `maybeRunLoader` function path in `runInNewSandbox`), which already evaluates a function package "once per sandbox, on first require". Stage A starts with that survey and picks one.
- **Permissions.** The model that exists is per-script-type package presence, so use it, and add one coarse axis per function, `access`:
  - **Option A (recommended): `Read` and `Mutate`.** `Read` functions are bound in global, local and player sandboxes (and menu only if the namespace says `menuSafe`, default false: menu scripts run with no game loaded). `Mutate` functions are bound in **global sandboxes only** (the `GObject` rule); in a local script the key is absent, and the strict index function gives "Key not found". Mod scripts cannot make a function visible anywhere the descriptor did not allow.
  - Option B: a free per-function context bitmask. More flexible, but pushes the `GObject`/`LObject` reasoning onto each pack author; revisit if a real case needs it.
  - Option C: reuse `.omwscripts` flags as permissions. No, they say where a script attaches, not what it may call.
- **Naming.** Decision 0014 point 4 says `core.<game>.*`. The inherited packages are `openmw.*`. Package names are free strings (`addPackage`), so `require("core.skyrimse.actor")` works with no engine change (open question 1 asks whether a prefix that cannot be mistaken for the inherited `openmw.core` is better).

### Gap 3: the thread rule for a call
Facts above: Lua runs on its own worker while the main thread renders; the scene graph must not change from it.
- **Option A (recommended): two rules, fixed by `access`.** `Read` handlers are called on the **Lua thread**, synchronously, and must not touch rendering or scene-graph state, take the main thread's locks, or allocate unboundedly; they read the pack's own state, which is only written during the pack's `GameSimulation` phase (the core must guarantee Lua `update` and that phase do not overlap: RECALLED-VERIFY against `Worker::allowUpdate/finishUpdate` and `Game::run`; if they can overlap, `Read` handlers get a lock-free snapshot or the rule becomes main-thread only). `Mutate` handlers are never run in the Lua call: the core copies the validated arguments into a **fixed-capacity queue** (4096 entries, overflow dropped, counted, logged once per function and frame) and runs them on the **main thread** in call order from the point where `synchronizedUpdate` drains `addAction`. A `Mutate` call returns nothing to Lua (results come back as events, the way inherited mutators work). This keeps simulation order deterministic whatever `lua num threads` is, and matches how the inherited bindings treat scene-graph changes.
- Option B: everything on the main thread via the action queue. Simplest to reason about but makes every query asynchronous, which game queries cannot use.
- Option C: a per-function flag chosen by the pack. Puts the thread hazard back on pack authors; rejected for now.
The pack states, per function, `maxCost` (a number the core logs when a call exceeds it, no enforcement): native time is outside the Lua instruction limit, so a slow `Read` is only visible in the profiler scope the core opens around each call (`lua.pack.<namespace>.<function>`, off when profiling is off).

### Gap 4: versioning
- **Declaration.** Every namespace has `version { major, minor }` (the same shape as `openeden::sdk::Version`). Minor is additive (new functions, new optional trailing arguments are not allowed: add a new function). Removing, renaming or retyping is a major change. The core checks at declaration: major at least 1; a pack may not lower a version it declared earlier in the same session (not an issue until hot reload exists).
- **A script asks.** Two ways, both supported:
  1. **Manifest (decision 0014 point 5; recommended as the primary way).** A new `.omwscripts` keyword on a script line, `REQUIRES: core.skyrimse.actor>=1.2`, parsed in `components/lua/configuration.cpp`. When the session's game pack does not provide that namespace, or its major differs, or its minor is lower, the script is **not started** and one log line names the script, the requirement and what the session has; other scripts are unaffected. With no game pack, the same line. A script with no `REQUIRES` is never checked. This is the one inherited-file change of the task (a small parser addition, tested against the existing config tests; scripts without the keyword parse as before).
  2. **In code.** Every namespace table has `API_VERSION = { major = M, minor = m }`, read-only, and a script may `pcall(require, name)` and compare. Always available, needs nothing from stage C.
- **On mismatch at run time** (a function removed by a pack update after a script was written): the call is an ordinary Lua "Key not found" error from the strict table, in that script only; the Lua count and memory limits are untouched.
- **Saves.** Nothing about bindings is written to a save. A saved Lua script whose `REQUIRES` fails at the next load is not started, with a warning; whether its saved data is kept or dropped follows the inherited behaviour for a script that cannot start (RECALLED-VERIFY; the spec's stage C test pins whatever it is). Handles are **not** serialisable: a script that puts one in its saved data gets the serializer's error for an unknown userdata (open question 3).

## Constraints
- **Off by default / unchanged:** with no game pack declaring a namespace, no package is added, the Lua host builds the same package maps as today, and Morrowind behaves exactly as before (the Morrowind game pack declares none until a later task decides to). Verified by a test that builds the maps with no pack and compares the key sets with today's, and by the 32 Lua integration tests.
- **Extensions and the common pack:** `BindingsService` is `nullptr` for them; no `register`-style method exists on any other service (`CI/check_extension_sdk.sh` unchanged; stage A adds a line that `bindings.hpp` contains none of `sol`, `lua`, `Lua`, `lua_State`).
- **Determinism:** namespaces and functions are stored and bound in declaration order (a vector, never an unordered map); the deferred queue is drained in call order on the main thread; no clock, no randomness.
- **Hostile scripts:** every argument is checked before the handler sees it (type, count, caps above); handles are validated by the pack (a stale handle is `NotFound`, never undefined behaviour); the deferred queue and its argument storage are preallocated and bounded; a script cannot make the core allocate without bound (strings and arrays are copied under the caps).
- **Allocation:** a `Read` call allocates nothing for scalar arguments and results after warm-up (counted in a test); string and array results copy into Lua.
- **Threading:** stated per function in the descriptor (Gap 3) and in the pull request; no handler runs on a render or audio thread.
- **Errors:** no exception crosses in either direction; every pack failure is a `Status` or a located Lua error.
- **Saves:** unaffected; bindings and handles are not persisted.
- **Cite engine facts:** everything above is cited to a file and function or marked RECALLED-VERIFY; stage A closes every RECALLED-VERIFY before code.

## Stage A stage log (2026-11-09; Windows only, local commits, not pushed)

**A0 survey: the three RECALLED-VERIFY facts, settled at the current `main`.**
1. **Start order.** The game pack starts BEFORE the Lua packages exist. `Game::Game` (`apps/openmw/game.hpp`) calls `mEngine.mExtensionHost->startGamePack(...)` first (it runs `LifecycleManager::initializeGamePack`, `components/extension/lifecycle_manager.cpp`), and only later `mLuaManager->init(...)`, which runs `initPreLoad`, `contentFilesLoaded` and `initPostLoad` (`apps/openmw/mwlua/luamanagerimp.cpp`). So the pack's `start()` has declared its namespaces by the time `initPostLoad` builds the package maps, and stage A builds the packages eagerly there. No lazy build inside `runInNewSandbox` is needed.
2. **Lua update versus game phases.** In this tree `MWLua::Worker` (`apps/openmw/mwlua/worker.*`) is not instantiated anywhere (no user in `apps/` or `components/`; `[Lua] lua num threads` is read only by the dead `Worker` constructor). `Engine::frame` (`apps/openmw/vsgengine.cpp`) calls `mLuaManager->synchronizedUpdate` and `mLuaManager->update` on the main thread, in sequence with `gameState->run(dt)`, which is where `runPhase(GameSimulation ...)` runs (`apps/openmw/game.hpp`). So Lua `update` and the pack's phase callbacks never overlap today, and a `Read` handler runs on the main thread. The header says "the thread that runs the script" so the rule survives a later worker; the spec's lock-free-snapshot fallback is not needed now. `apps/openmw/mwlua/README.md` still describes OpenMW's worker thread; it is stale for this tree (not edited).
3. **Unknown userdata in the serializer.** `LuaUtil::serialize` throws `std::runtime_error("Value is not serializable.")` for a userdata no serializer handles (`components/lua/serialization.cpp`, `serializeUserdata`), and "Light userdata is not allowed to be serialized." for light userdata. `MWLua::UserdataSerializer` (`userdataserializer.cpp`) handles object references and object lists only. So a handle (stage B) will fail a save of the script that stores it with that error; stage A has no userdata in results (scalars only), so nothing to pin yet.

No fact contradicts the spec's design; Gap 3's thread rule is simpler than the spec thought (main thread today).

## Stages B and C stage log (2026-11-10; Windows only, local commits, not pushed)

**Decisions taken from the spec's recommendations (recorded here):**
- **SDK 2.0 for `bindings.hpp`** (`kBindingsVersion`): members appended to `BindingValue` (`handle`, `present`, `elements`, `count`), `FunctionDescriptor` (`paramShapes`, `resultShape`) and `NamespaceDescriptor` (`menuSafe`), and enumerators at the END of `BindingType` (`Handle`) and `BindingAccess` (`Mutate`); a new `BindingShape` (Single, Optional, Array). Appended struct members change the struct size, so this is a major bump of the header's own version (nothing had used 1.0; `kSdkVersion` stays 4.0).
- **Shapes:** a parameter or result is Single, Optional (nil in a script; a trailing optional parameter may be left out) or a flat Array (at most 256 elements, scalars or handles, no nesting). Argument count: at most the declared count; fewer only if every missing one is Optional.
- **Array arguments** are read raw (`lua_next`, `lua_rawgeti`: no metamethod runs) and must be a sequence 1..n with no other keys; a hole, an extra key, more than 256 elements or a bad element is an error naming the argument and the element position. Element storage is a per-thread fixed array (8 x 256 values), no allocation.
- **Handle** = full userdata (not light userdata) holding 64 bits, locked metatable: `__eq` by value, `__index`/`__newindex` raise "pack handles are opaque", `__tostring`, `__metatable` set. The sandbox's `getmetatable` is tables-only, so a script cannot reach it. Two equal handles are two different TABLE KEYS (identity); scripts compare with `==`. A handle in a script's saved data makes `LuaUtil::serialize` throw "Value is not serializable."; `ScriptsContainer::save` catches that per script, logs it and writes the script with no data, so the save itself still works (read at `components/lua/scriptscontainer.cpp`; pinned for `serialize` only, the container path is by reading).
- **Contexts** (`MWLua::PackContext`): Global gets Read and Mutate functions; Local (also used for player scripts) Read only (a Mutate key is absent: "Key not found"); Menu gets a namespace only if it is `menuSafe` (Read only); load scripts get none. Open question 5 taken as "menuSafe namespaces may exist".
- **Mutate:** no result (a Mutate function that declares one is refused at declaration). The call is validated in the script's call, copied into `openeden::extension::MutateQueue` (new, `components/extension/mutate_queue.*`: two batches under a mutex, 4096 call slots, 1 MiB byte arena and 8192 value slots per batch, all allocated when the first Mutate function is declared, none after) and returns nothing. `LuaManager::synchronizedUpdateUnsafe` drains it right AFTER `applyDelayedActions()` (inherited delayed actions first, then the pack's calls, both on the main thread, in call order); `addAction` is not used (it allocates a `std::function` and throws inside `applyDelayedActions`). A full queue or arena drops the call, counts it (`BoundFunction::droppedTotal`) and logs once per function per drain; a retired pack's queued call is dropped (`DrainResult::retired`); a non-Ok status or an escaped exception is counted and logged once per function.
- **Stage C `REQUIRES=` syntax:** the spec's `REQUIRES: ...` cannot sit on a script line (the parser splits at the first `:` and wants the line to end in `.lua`), so it is a TAG in the tag list: `GLOBAL REQUIRES=core.skyrimse.actor>=1.2: scripts/x.lua`, several allowed (`REQUIRES=a>=1.0, REQUIRES=b>=2.1`). A malformed tag throws with the line. The requirement is stored in `ESM::LuaScriptCfg::mRequires` (end of the struct; not written to or read from content files; only `.omwscripts` carry it). `ScriptsConfiguration::init(cfg, remap, check)` drops a refused script after duplicates and merges are settled (a `+` merge unions requirements), as if its mod were absent: it starts nowhere, `findId` does not know it, a saved script of it finds no mapping (the inherited data-drop path), `reloadlua` goes through the same function. One Warning line per refused script names the script, the requirement and what the session has.
