# Task: creativemotion_editor, the Rig & Motor Limits Inspector (plan section 5.1, item 2)
Design doc section: `docs/design/eden-studio-plan.md`, section 5.1 item 2 and section 8, Phase 4 ("first real module"); `docs/decisions/0007-eden-studio-editor-design.md` (core systems' tools are separate editor libraries on a fixed core list); `docs/tasks/0031-eden-studio-editor-module-api.md` (the API this module is built against).
Goal: a library `creativemotion_editor`, on Eden Studio's core list, that opens CreativeMotion's `.rig.json` and `.profile.json` files, draws the rig's collision shapes and joint limit cones and pyramids in the 3D view, and shows and edits joint limits and motor stiffness, damping and maximum torque in the inspector, through the editor's undo stack.
Inherited code touched: none. Reads `components/creativemotion/` (vendored, never patched): `core/rig/include/opas/rig/{Rig,RigFile,Profile,ProfileFile,Skeleton}.hpp` (`opas::rig::loadRigFile`, `writeRig`, `validateRig`, `loadProfileFile`, `writeProfile`, `computeWorldRest`, `motorFor`), `core/math/include/opas/math/{Vec3,Quat,Transform}.hpp`. The loaders and canonical writers are callable, so no CreativeMotion task note is needed.
Inputs / outputs: new library `editor_modules/creativemotion_editor/` (built as `creativemotion_editor`, output `editor-modules/`), linking `opas::rig` and the Editor Module API headers only (no Studio code, no Qt, no engine type). Inside the library `creativemotion_editor::openRig` and `openProfile` (below) are what the module registers, and what the tests call.

Status: started 2026-11-01 at toddhow's word (step 3 of the CreativeMotion work). Full loop. Stays inside the Editor Module API; every gap is listed under "Gaps" and is fixed by growing the API, not by putting CreativeMotion code into Eden Studio.

## Design

**Units.** CreativeMotion is meters, kilograms, seconds, radians, right-handed, Z up; the Editor Module API's `Vec3` is also meters, Z up, so the module converts only the type, in one place: `creativemotion_editor/convert.hpp` (`toEditor(opas::math::Vec3)`). The conversion from meters to the world's Morrowind units happens once, in Studio (`CSVModule::ModuleUi`'s overlay sink, task 0031), never in the module. Angles stay in radians in the file, the property descriptions and the inspector (units text `rad`); motor gains in `N*m/rad` (stiffness), `N*m*s/rad` (damping) and `N*m` (maximum torque), as `docs/formats/profile.md` says.

**Asset types** (registered with `registerAssetType`): `opas.rig` with extension `.rig.json`, `opas.profile` with extension `.profile.json`. Inspector sections: one for each, `selectionKind` equal to the format ID, showing the document's properties. A workspace `creativemotion` ("CreativeMotion") with one panel `creativemotion.panel` (docked right) that shows the active asset's properties, and a gizmo provider `creativemotion.gizmos` for the active asset's gizmos. Every registered ID starts with `creativemotion.`.

**Functions** (header `editor_modules/creativemotion_editor/documents.hpp`, namespace `creativemotion_editor`): `std::unique_ptr<openeden::editor::AssetDocument> openRig(const std::filesystem::path&, std::string& error)` and `openProfile(...)` with the same signature; `constexpr const char* kRigFormat = "opas.rig"`, `kProfileFormat = "opas.profile"`. Both return null and fill `error` (with the loader's located message, `file:line` or JSON pointer) if the file is missing or invalid; a rig must pass `validateRig` and a profile `validateProfile` against ... no rig is known when a profile alone is opened, so a profile is checked on its own as `loadProfileFile` does, and the document's `isDirty()` starts false. The module library exports `openeden_editor_module_descriptor` through `OPENEDEN_EDITOR_MODULE("creativemotion_editor", ...)`; its sources are also linked into the tests (`creativemotion_editor_module.cpp` holds the module class).

**Rig document** (`.rig.json`).
- Read-only properties: `rig.name` (String), `rig.bones`, `rig.bodies`, `rig.joints` (Int). Group "Rig".
- One group per joint (the group is the bone's name), with six Float properties in radians, `unit = "rad"`, range `[-pi, pi]`: `joint.<bone>.planeSwingMinRad`, `joint.<bone>.planeSwingMaxRad`, `joint.<bone>.normalSwingMinRad`, `joint.<bone>.normalSwingMaxRad`, `joint.<bone>.twistMinRad`, `joint.<bone>.twistMaxRad` (the fields of `opas::rig::Joint`; a cone stores its half angles as min = -half, max = +half). Also a read-only String `joint.<bone>.swing` ("cone" or "pyramid").
- `makeSetCommand(id, double)`: builds the rig that results from the change, runs `opas::rig::validateRig` on it, and returns null if the value is not finite, the id is unknown, the type is wrong, or the result is invalid (for a cone, a change that breaks the rule that min = -max is therefore refused; for a pyramid a range that no longer contains 0 or min > max is refused). Otherwise the command's `redo()` sets the new value, `undo()` restores the old one, `mergeId()` is a number that is the same for edits of the same property (and different for different properties) so that dragging a field is one undo step, `mergeWith` absorbs a later edit of the same property, and the document becomes dirty on `redo()`.
- `save(error)` writes `opas::rig::writeRig(rig)` to the file it was opened from (canonical text: opening a canonical file and saving it unchanged gives the same bytes), clears the dirty flag, and returns false with a message if the file cannot be written.
- Gizmos: `gizmos()` returns two, `creativemotion.rig.shapes` and `creativemotion.rig.limits`, owned by the document and reading the current rig (so an edit changes what they draw). `draw` submits lines in meters, in model space (the model root at the overlay origin), at the rest pose (`opas::rig::computeWorldRest`).
  - Shapes (gizmo `creativemotion.rig.shapes`), in body order, each at the body's world transform (the bone's world rest transform times `Body::local`), colour light grey (0.8, 0.8, 0.8, 1): a box is its 12 edges; a sphere is 3 great circles (in the local XY, YZ and XZ planes) of 24 segments each, 72 lines; a capsule (along local Z, cylinder half height `h`, radius `r`) is 100 lines: the two circles of 24 segments in the XY plane at z = +h and z = -h (48), four lines along Z at (+-r, 0) and (0, +-r) from z = -h to z = +h (4), and at each end two half circles of 12 segments each, in the XZ and YZ planes, bulging outward from z = +h up to z = h + r and from z = -h down to z = -h - r (2 ends x 2 planes x 12 = 48).
  - Limits (gizmo `creativemotion.rig.limits`), for each joint in rig order, at the joint bone's world rest origin O with the bone's world rest rotation R. The joint frame in the bone's frame has X = `twistAxis`, Z = `planeAxis`, Y = Z cross X (that is `planeAxis` x `twistAxis`); a direction (dx, dy, dz) in joint coordinates is `R * (dx*X + dy*Y + dz*Z)` in the model. L = `kLimitLengthM` = 0.1. The lines, in this order:
    1. the twist axis: one white line from O to O + L * (direction (1, 0, 0));
    2. for a cone (the joint's swing is cone) whose plane and normal half angles are not both zero (half angles are `planeSwingMaxRad` and `normalSwingMaxRad`): the rim loop, 24 lines, orange (1, 0.6, 0.1, 1), joining the points P(k) = O + L * dir(k) for k = 0..23 in order and back to P(0), where for t = 2 pi k / 24, p = planeHalf * cos t, n = normalHalf * sin t and dir = (cos p cos n, cos p sin n, -sin p) in joint coordinates (that is Rz(n) Ry(p) applied to (1, 0, 0), right-handed); then 4 orange spokes from O to P(0), P(6), P(12), P(18);
    3. for a pyramid: the loop of 4 orange lines joining the corners C0 -> C1 -> C2 -> C3 -> C0, then 4 orange spokes O -> C0 .. C3, where the corners are the directions dir(p, n) = (cos p cos n, cos p sin n, -sin p) for (p, n) = (planeMin, normalMin), (planeMax, normalMin), (planeMax, normalMax), (planeMin, normalMax); points are O + L * dir;
    4. the twist arc: 16 cyan (0.1, 0.9, 0.9, 1) lines through the points O + 0.25 * L * R * (0, cos a_i, sin a_i) in joint coordinates for a_i = twistMin + (twistMax - twistMin) * i / 16, i = 0..16 (17 points, 16 lines). Drawn even when the range is zero (then 16 zero-length lines).
    A hinge (a cone with both half angles zero) therefore draws 1 + 16 lines; a cone 1 + 24 + 4 + 16 = 45 lines; a pyramid 1 + 4 + 4 + 16 = 25 lines.
  - Each gizmo has no handles (see Gaps); `drag` returns null.
- The document's `tracks()` is empty.

**Profile document** (`.profile.json`).
- Read-only: `profile.rig` (String, the rig name it was tuned for), group "Profile".
- Properties `default.stiffnessNmPerRad` (Float, `>= 0`, unit `N*m/rad`), `default.dampingNmsPerRad` (`>= 0`, `N*m*s/rad`), `default.maxTorqueNm` (`> 0`, `N*m`), group "Default motor"; and the same three for each joint override of the profile as `joint.<bone>.stiffnessNmPerRad`, `.dampingNmsPerRad`, `.maxTorqueNm`, group `<bone>`. Tooltips say what the number means (`docs/formats/profile.md`: torque = stiffness x angle error - damping x relative angular velocity, clamped to the maximum torque).
- `makeSetCommand(id, double)`: refuses (null) non-finite values, unknown ids, wrong types, and values outside the ranges above; otherwise as for the rig (merge by property, dirty on redo). `save` writes `opas::rig::writeProfile`. The module does not add or remove overrides in this task.
- No gizmos, no tracks.

**Sample data and checks.** Tests build rigs and profiles in code (with `opas::rig` types, written by `writeRig`/`writeProfile` into temp folders). The real-editor check uses CreativeMotion's own `data/rigs/humanoid.rig.json` and `data/profiles/humanoid-default.profile.json` copied to a scratch folder: they are not committed here and are not Bethesda assets.

## Constraints
- Editor module only: no CreativeMotion code in Eden Studio (plan 2.2 and 9); the module includes only the Editor Module API headers, the standard library and CreativeMotion's rig headers. Nothing in `apps/openmw` loads it (the game never loads editor code). `components/creativemotion/` is not edited.
- Extensions do not affect saved games (decision 0005); a module edits project files only. The module reads no physics and changes none (the push sandbox is out of scope: it needs the in-engine ragdoll adapter, M10).
- No exception leaves the module's callbacks (the host catches them, but the loaders and writer do not throw).
- Deterministic: drawing the same rig twice gives the same lines in the same order; no random, no clock.
- No change to `components/render`, `components/pipeline`, `apps/openmw/mwrender`, `files/shaders`, `settings-default.cfg`.

## Acceptance criteria
- [x] `openRig`/`openProfile` open a valid file (dirty false) and give null plus a message for a missing file, a file that is not JSON, a wrong `format`, and an invalid rig (for example a joint on a bone that does not exist). (unit tests)
- [x] Rig properties: the described ids and types exist for every joint; values read back equal the rig's; ranges `[-pi, pi]`; `joint.<bone>.swing` reads `cone` or `pyramid`. (unit test)
- [x] Rig edits: a valid change returns a command, changes nothing until `redo()`, `undo()` restores the exact old value, same-property commands merge into one that undoes to the oldest value, different properties do not merge; refused: NaN and infinity, a wrong type, an unknown id, a pyramid range that excludes 0, min > max, a cone edit that breaks min = -max, a value outside `[-pi, pi]`. (unit tests)
- [x] Save: an unchanged canonical rig saves byte for byte; after an edit and save the file loads back with the new value, and the file differs from the original only in that value's line; saving to a vanished folder reports an error. Same for profiles. (unit tests)
- [x] Profile properties and edits: default and per-joint gains, ranges (`maxTorqueNm > 0`, others `>= 0`), refusals, merge, undo, save. (unit tests)
- [x] Shape gizmo: for a rig with one box, one sphere and one capsule body at known transforms, the gizmo draws 12 + 72 + 100 lines in that order, every box line's endpoints are corners of the box in the world, every sphere point is at the radius from the body's world centre within 1e-9, every capsule line lies within the capsule's bounds (distance from the capsule's axis segment at most r + 1e-9); the transform used is the bone's world rest transform times the body's local transform. Drawing twice gives the same lines. (unit test)
- [x] Limits gizmo: the line counts above (hinge 17, cone 45, pyramid 25 per joint), the twist axis line, the rim points P(k) of a cone and the corners of a pyramid equal the formulas in "Design" within 1e-9 (the test computes them independently in joint coordinates for a joint whose bone has a non-identity world rest rotation), and the twist arc's first and last points are at `twistMin` and `twistMax`; after an edit (`redo()`) the gizmo draws the new limits. (unit tests)
- [x] The module: `registerUi` registers the two asset types with the right extensions and format IDs, the workspace, the panel, two inspector sections, the gizmo provider (and nothing under a name that does not start with `creativemotion.`); loaded through `ModuleHost` as a real shared library it goes `Loaded`, and a clean `shutdown` leaves the registry empty. (unit tests)
- [x] In the real editor (the library loaded through `OPENEDEN_CS_MODULES`, CreativeMotion's humanoid rig and profile as module assets): the Module assets group lists both files; opening the rig shows its joint limit properties in the panel and the inspector, the 3D view shows the shapes and limits overlay (image looked at), editing a limit is one undo step and Undo restores it, saving writes the canonical file; opening the profile shows the motor stiffness, damping and maximum torque with units, an edit is one undo step. (logged unattended checks and images) (`OPENEDEN_CS_RIGCHECK` on CreativeMotion's humanoid rig: 90 joint fields shown; a twist limit edit (two edits) was one undo step, Undo restored 0.785, Save changed only that line of the file (`diff` of the file against the original shows one line); the profile showed 450 N*m/rad, 30 N*m*s/rad, 500 N*m; a stiffness edit was one undo step. The overlay was looked at in a frame taken from 4 m away: the grey shapes, orange limits and cyan twist arcs of a person-sized rig. Edit > Undo through the editor's menu was not clicked. The checks were repeated after the review fixes except for the final rerun, see the stage log.)
- [ ] `eden-studio-tests`, `components-tests`, `openmw-tests` pass on Windows; the Linux gate passes; the tree passes `CI/check_clang_format.sh`; a fresh reviewer read each stage.
Out of scope: the push sandbox, the animation graph editor, the reconciliation inspector, the face timeline (plan 5.1 items 1, 3, 4, 5), adding or removing joints, bodies or overrides, helper bone editing, editing shapes or masses, rotating or placing the rig in the world, handles and viewport dragging, drawing labels.

## Gaps found (the plan says: fix by growing the API, not Eden Studio)
- **No picking or dragging of overlay data** (API 3.5): joint limits can be edited only as numbers; a handle on the cone rim would need viewport picking of overlay items and `Gizmo::drag` calls from mouse input.
- **No labels** (the debug geometry has no text): bone names cannot be drawn next to joints; they appear as property groups instead.
- **No selection of a bone** (3.7 "entity, bone or asset" selection): the panel shows every joint of the rig; selecting a bone to show only its joint and highlight its gizmo needs a selection kind for bones in the API.
- **Overlay placement:** an asset has no place in the world, so Studio puts the model root where the user looks (task 0031); a rig attached to an actor in the cell would need entity selection.
- **Pose:** the gizmos draw the rest pose; showing the limits on a posed or simulated rig needs the push sandbox's preview scene (3.5) and the in-engine ragdoll (M10).
