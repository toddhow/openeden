# Task: GPU-driven culling and indirect draws for static objects
Design doc section: `docs/design/world-lod-and-streaming.md`, section 8 (tier High: "GPU-driven tile and instance culling with indirect draws") and the staging row S9; the technique, the VSG constraints and the sources are in `docs/research/0040-gpu-driven-culling.md` (read it first; every source is named there, and what could not be read is marked). Builds on `docs/research/0025-lod-baseline.md` (the S0 baseline), `docs/tasks/0059-lod-s4-object-clusters.md` (the clusters that already removed the far draws) and `docs/tasks/0062-lod-s5-model-lod-chains.md` (whose stage a is the model for this spec's gate).

## What the evidence says (read from the repository)

- **The draws the baseline blamed were mostly removed by the clusters.** The 33.8k census draws of note 0025 (view 30000, distant terrain and object paging on, 3.87 ms) are an object-paging figure. With object clusters on, the same pose is 28.2k census draws and 3.53 ms median, the far ring is about 11 clusters and 272 draws, and the whole far field with object paging off costs 188 draws against 23.8k for object paging (root `CLAUDE.md`, changelog rows "World LOD S4d" and "S4c", 2026-11-02). What remains is mostly the **live objects of the active grid and the chunks next to it**.
- **The baseline's author did not recommend this for this machine.** Note 0025 section 9: "GPU culling (S9) is not needed to fix this machine, but it matters for weaker CPUs."
- **The only per-draw CPU number the repository has is a slope:** 3.87 ms against 2.24 ms for 33.8k against 7.0k census draws, about 60 ns per census draw, of wall time, with nothing attributed to the record traversal (note 0025 section 8: "CPU time split: update, cull, record, submit: Not measured").
- **The record traversal was timed once, and it was cheap:** `loop.record.submit` 1.0 ms mean in the cell-load hitch frames (note 0026 section 2). Those are loading frames.
- **S0 ran with shadows off.** Every shadow cascade and every point-light face (task 0077) is another command graph with its own record traversal over the casters; the multiplication of the per-draw cost is the strongest argument for this feature and is unmeasured.
- **Recording is one thread per command graph, and the main thread waits for all of them.** `Viewer::setupThreading` (VSG 1.1.16; `RenderManager` passes threading on unless `VSGOPENMW_NO_VIEWER_THREADING` is set) starts a thread per graph, and `Viewer::recordAndSubmit` (`Viewer.cpp`, line 820 onward) sets the frame block and then `_submissionCompleted->arrive_and_wait()`: **read: the main thread does not return until every graph has recorded and submitted**. So record and `loop.callback` run one after the other, never overlapped, and `loop.record.submit` on the main thread is the wall time of the slowest graph (graphs record in parallel with each other when cores are free). The main scene's cull-and-record is one thread.
- **The game enables four device features** (`samplerAnisotropy`, `occlusionQueryPrecise`, `depthClamp`, `fillModeNonSolid`). The RTX 4070's report has `multiDrawIndirect`, `drawIndirectFirstInstance`, `drawIndirectCount`, `descriptorIndexing`, `bufferDeviceAddress` and mesh shaders present (the S0 run's `device-report.json`, copied into research note 0040 section 3); `shaderDrawParameters` is a Vulkan 1.1 feature, **verify** its value in the report (the report keys listed in task 0054 do not include it). None of them is enabled on the game's device.
- **There is no bindless in the object shader.** Each model part has its own descriptor set of 18 bindings (`Pipeline::Graphics::Graphics`), and the textures' roles are chosen by pipeline defines. One indirect draw can only cover instances that share pipeline, descriptor set and vertex and index buffers.
- **Per-draw data is a 128-byte push constant** (`pc.projection`, `pc.modelview`; `lib/pushconstants.glsl`), the modelview formed in double precision by VSG (`MatrixStack::record`). An indirect path needs the transform in a buffer and a rule for float precision at large coordinates.

So: the evidence **does not yet support** the work. It supports measuring it.

## Design (applies only if stage a says go)

**Scope.** Static objects that are *pure*: no controller, no per-instance material or switch, no particles, no morph, no skin, no `DistanceLOD` children, opaque, not alpha-to-coverage. Defined by a predicate on the loaded model graph (stage b writes and tests it; stage a counts what it admits). The object clusters are in scope only as the trivial case: they are about 270 draws and gain nothing, so they are not converted unless stage a shows otherwise. **Out of scope: actors, anything with a controller, depth-sorted or blended draws, alpha-to-coverage draws, terrain, the sky, water, particles.**

**Batches.** One batch per (pipeline, descriptor set, vertex arrays, index array), i.e. per distinct model part, as in the research note section 5.5 (a). A batch node is a `vsg::Node` holding its instance storage buffer, an indirect-argument buffer, and the commands to draw it. The number of indirect draws equals the number of distinct batches in range, not the number of objects.

**Instance data and precision.** An instance is its transform relative to its chunk's origin (a cell centre; float is exact enough), plus the bounding sphere. Each frame the CPU pushes one `view * translate(origin)` per chunk, formed in double precision and converted once (the rule `MatrixStack::record` follows today). The vertex shader multiplies instance matrix by chunk matrix. A unit test proves the result equals the double-precision modelview within a stated tolerance at coordinates up to 200,000 units.

**The cull pass.** A `ComputeBin` with submit order -5 (before the shadow graphs at -3; equal orders submit in arbitrary order, so it takes its own number). One dispatch per view that draws batches (main view, then each cascade and point-light face when those draw static objects), 64 threads per group, one thread per instance: sphere against the six frustum planes, then `atomicAdd` into the batch's instance count and a write into the batch's visible-index list. The planes come from the same view and projection the CPU uses; the GPU test is float against VSG's double and is given a conservative bias so the GPU's visible set is a **superset** of the CPU test's (`gpucullmath.hpp` states the bias and the tests prove it). A barrier closes the pass (compute write to `DRAW_INDIRECT` and vertex-shader read).

**The draw.** Fixed `drawCount` of indirect commands with `instanceCount` written by the GPU (a culled batch has 0): needs `multiDrawIndirect` and `drawIndirectFirstInstance` only, and VSG's existing `DrawIndexedIndirect`. The `drawIndirectCount` variant (a GPU-written count, a custom `vsg::Command` calling `vkCmdDrawIndexedIndirectCount`) is not needed and not proposed. The device features are enabled only when `gpu culling` is on (`Engine::createRenderEngine`); a device that lacks them logs one line and the setting does nothing.

**Hi-Z (stage d).** A depth pyramid of the previous frame's linear depth (R32F, `HdrTarget::linearDepthView()`; needs `hdr` and `gbuffer`; the depth is reversed, so the pyramid keeps the nearest value per texel and the test is against the box's nearest depth), the two-pass method of research note 0040 section 5.2. Requires the G-buffer path: without it the stage is not built. The jitter of TAA is removed from the box's projection (use the unjittered camera, `mSceneCamera`, `apps/openmw/mwrender/CLAUDE.md`).

**Settings** (`[Rendering]`, read at start, all off or neutral by default): `gpu culling` (bool, false; needs the device features, hence a physical device that has them), `gpu culling hiz` (false), `gpu culling debug` (`none`, `verify`: every 30 frames read back the visible lists and compare them with the CPU reference, log mismatches; `count`: read back the indirect counts for the frame counters).

## Stage a: measure (no behaviour change; ends in a go/no-go table)

The gate exists because the evidence above is thin. Stage a adds only measuring code, behind existing flags, and the numbers it produces decide whether b to d are written.

1. **Split the CPU frame** on the `heavy_lod_*` scenes of `tools/render_scenes.txt` (`tools/benchmark.sh`) with `[Cells] load trace` on: `loop.callback` (game update), `loop.viewer.update`, `loop.record.submit`, `loop.present`, per frame, medians and p95 (the scopes exist in `Engine::loop`; note 0025 predates them). Report the record's share of the wall time.
2. **Find the record thread's cost directly.** Attach `vsg::Instrumentation` (`Viewer::assignInstrumentation`; `vsg::Profiler` or a small `Instrumentation` subclass that sums time per node type) behind a new debug flag, in a test build only if it costs too much; report the time in `CullNode`/`CullGroup`, `Transform`, `StateGroup`, draw nodes and `State::record`. If it does not work with the engine's threads, say so and use a per-graph timer around `recordAndSubmit` instead.
3. **Count real draws.** With the same instrumentation (or a counting subclass of `VertexIndexDraw` in a scratch build), count the draw nodes recorded per frame per graph, against the census. Quote both.
4. **Run the scenes in four settings:** shadows off (as S0); `object shadows` on with four cascades; object shadows plus point-light shadows with four lit lights (task 0077); and each with object clusters on and off. The long-view pose (`heavy_lod_air30000_on`) and the ground pose (7168) and an interior with many lights (Arrille's Tradehouse) are the minimum.
5. **Classify the draws.** Over a long-view frame, count the draws and the distinct (pipeline, descriptor set, vertex array) batches among them, and how many of the draws are pure-static by the predicate (a count, no conversion). The ratio of draws to batches is the instancing gain; if it is under about 3, instancing does not pay either.
6. **Report the wait.** Because the main thread waits for all graphs (above), the saving a faster record can give on this machine is bounded by the main thread's `loop.record.submit` (the slowest graph), not by the sum over graphs. Report both, per setting of item 4, and which graph is the slowest (the main scene, a cascade, a point-light face).
7. **Estimate the weak-CPU case** by running the scenes with the process pinned to fewer or slower cores (the machine's tools allow an affinity mask) and report the same split; this is the case note 0025 section 9 gives as the reason. With few cores the graphs no longer record in parallel, so the **sum** over graphs is the relevant figure there.
8. **Attribute the draws by subtree.** Make the census (`components/render/scenecensus.*`) report per subtree: the live active grid (`Scene` objects), the distant chunks (`DistantObjects::node()`), the LOD clusters (`LodClusters`), terrain (live and tiles), actors, sky and effects. If most of the roughly 28k census draws sit in the distant chunks between the active grid and the start of the level-1 clusters (about 10,000 units), the cheapest fix is not GPU culling: it is the merge that OpenMW's object paging did and `DistantObjects` does not port, or clusters that start closer (see the decisions).

**The gate (proposed numbers, toddhow decides them).** Stage b starts only if, on the long-view pose with clusters on, the main thread's `loop.record.submit` (item 6: the wait for the slowest graph; it is in series with the callback, so on this machine it is the saving) is at least **1.0 ms or 25 percent of the median CPU frame, whichever is smaller**, in at least one of the shadows-on settings of item 4 (or, in the pinned-cores run of item 7, the sum over graphs is), AND the draw-to-batch ratio of item 5 is at least 3, AND item 8 does not show that the draws are mostly in a subtree that merging or closer clusters would remove more cheaply. 1.0 ms is chosen from the 60 ns-per-draw slope (about 17k draws' worth) so that a path that removes most of it is worth a new shader mode and a device-features change. If the gate fails, the spec is closed with the table; the numbers go into a research note and the changelog.

## Constraints

Determinism: the cull result is a pure function of the camera and the instance data; no clock, no unordered iteration. A batch's instance order is the order the chunk lists them (stable); the GPU's visible-list order is not (atomics), so nothing may depend on it (the vertex shader reads instances by index and the draw order inside a batch has no visible effect on opaque draws with a depth test, except the coplanar case below). Allocation: buffers and descriptors at chunk build and on a resize; no per-frame heap allocation in the added CPU code (push constants and the per-chunk matrices are values updated in place). Threading: instance data is written on the chunk's build thread and uploaded on the main thread (`CompileContext::compile`); the cull pass is recorded with the other compute graphs; nothing here touches physics. Ownership: `RenderManager` owns the pass by `std::unique_ptr`; a batch node owns its buffers by `vsg::ref_ptr` (the scene graph's usual ownership, with the reason in a comment); retired batches go to `CompileContext::detach`. Off by default and unchanged when off: with `gpu culling = false` no buffer, pass, bin, batch node or device feature exists, every object is a normal draw, and the SPIR-V of every existing pipeline is byte-identical (the `GPU_INSTANCE` define is absent). Units: instance data in game units, relative to the chunk origin.

## Acceptance criteria

- [ ] **Stage a's table exists** and is in the stage log: the CPU split (item 1), the record time by node type (item 2), the real draw count against the census (item 3), the four settings (item 4), the batch ratio (item 5), the wait of the main thread (item 6), the weak-CPU run (item 7) and the draws by subtree (item 8), each with the commit and the machine. The gate decision is written under it.
- [ ] **Off means unchanged.** `gpu culling = false`: the shaders' SPIR-V of every pipeline equals the commit before (a test over the permutation lists and the GLSL compile, as task 0077's), the frame of the benchmark scenes equals the commit before within the spread of two runs of the old executable (`OPENEDEN_FIXED_FRAME_TIME`, three off runs, the method of `components/render/CLAUDE.md`), the frame counters equal.
- [ ] **Culling is a superset of the CPU test** (stage b): over random instance sets and random cameras (including the extremes: a sphere touching a plane, an instance behind the camera, a huge sphere), every instance the CPU frustum test keeps is kept by the GPU test (a unit test of `gpucullmath.hpp`, and `gpu culling debug = verify` in game over a flight with zero misses). A false keep is allowed and counted (the conservative bias), a false cull is a failed test.
- [ ] **Identical result within the noise** (stage c): with the path on, the frames of the benchmark scenes differ from the off frames by no more than two off runs differ from each other (the pixel-difference measure and threshold of tasks 0072 and 0076). Not byte-identical: batching changes the draw order of opaque surfaces and coplanar surfaces of equal depth can swap. Blended and alpha-to-coverage draws are not on the path, so their order is unchanged.
- [ ] **No popping.** A flight along a path at 3 ms per frame, a frame every 10, with `verify` on: no object appears or disappears that the CPU path draws at the same frame (checked by the verify mode and by viewing the frames), no flicker at the frustum edge.
- [ ] **Precision.** The instance transform rebased to the chunk origin gives, at coordinates up to 200,000 units, a vertex position within 0.01 units of the double-precision path (unit test of `gpucullmath.hpp`), and a frame at the world's far corner shows no jitter.
- [ ] **Draw-call count and CPU time** (stage c): on the long-view pose with clusters on and each of the shadow settings of stage a, the number of recorded draws falls by at least the batch ratio of stage a divided by 2 and the median CPU frame time falls by at least **0.5 ms or 13 percent** (the figures are proposals), with the GPU main pass not more than 0.1 ms slower, measured as the other renderer tasks do (`gpu timing`, medians over 500 rendered frames above 0.1 ms: the stats-file pitfall in `components/render/CLAUDE.md`). If it does not, the path is not shipped on, whatever else works.
- [ ] **Device handling.** A device without the features: one log line, the setting has no effect, the game runs on the CPU path. The features are requested only with the setting on (`Engine::createRenderEngine`). Checked by forcing the report's answer false in a test.
- [ ] **Hi-Z** (stage d, if built): no object is culled that the CPU path shows in a frame (verify mode against a reference that has no occlusion), including during a fast camera turn and when an occluder moves; the pyramid build costs under 0.1 ms at 1080p.
- [ ] **Documentation and tests:** `components/render/CLAUDE.md`, `apps/openmw/mwrender/CLAUDE.md` and `files/shaders/CLAUDE.md` updated; the changelog; a fresh reviewer's findings; the Linux gate (the path must also run on llvmpipe: it claims the features).

Out of scope: actors and anything animated; terrain and sky; mesh shaders and meshlets (the design doc's tier Ultra); device generated commands; bindless materials and descriptor indexing (the object shader would need a rewrite: open question 3); asynchronous compute on the dedicated queue family; GPU-driven LOD selection for model chains (task 0062, whose chain levels could later share the instance buffer); making the setting the default.

## Risks

1. **It does not pay.** The most likely outcome on this machine. Stage a exists to find it out cheaply.
2. **Float precision far from the origin** (jitter): the chunk-origin rule and its test are the mitigation; a bug here is visible only in the far corners of the world.
3. **A new vertex path in the most complicated shader.** The define keeps the old SPIR-V identical, but the Slang twin (`default.vert.slang`), its permutation lists and the 71k-set open-endedness (`files/shaders/CLAUDE.md`) mean every set the path uses must have a twin or fall back to the GLSL together (the mixed-pipeline rule).
4. **Device creation change.** Enabling features at creation can fail on a device that reports them but rejects the combination; the fallback is the CPU path, not a failure.
5. **Synchronisation.** A compute-to-draw barrier written by hand with no validation layer installed (none is: `CLAUDE.md`, "Debugging the VSG build"); the pass follows `View::VolumeFog`'s barriers, and the verify mode catches wrong data but not a missing barrier on this one driver. A synchronisation bug may only show on another vendor.
6. **Buffer lifetime** when a chunk is detached while a frame still reads its buffers (the deletion queue's rule; the LOD cluster pitfall about shared `BufferInfo`, mwrender `CLAUDE.md`).
7. **The shadow passes** need their own cull dispatch per view; their frusta and the casters' masks (`Shadow::viewMask`) must be applied, or the GPU draws objects into a cascade that the CPU would skip.
8. **Interaction with other features:** cell hand-over (`DistantObjects::setClusteredCells`, `staticsReady`) assumes live chunks are scene-graph nodes; the batch node must keep that contract (detaching a chunk detaches its batches); incremental cell build (task 0060 stage g) adds objects over frames, so the instance buffers grow incrementally; object picking uses the render scene graph (`World::castRenderingRay`) and would not see an instanced object unless the batch node implements the intersector's interface (`vsg::Intersector` visits `VertexIndexDraw`; an indirect draw has no index count to test). The focus and activation rays go through `World::castRenderingRay` to `RenderManager::castRay` and `MWRender::castRay` over the whole scene graph (`*mScene`, `mIntersectorScene`; `apps/openmw/mwworld/CLAUDE.md`: "Picking, activation rays, tooltips ... use the render scene graph"), and Lua's `nearby.castRenderingRay` reaches the same code. **Excluding activators, doors, containers and items from the conversion is not enough:** a converted static wall that the intersector cannot see would let the player activate a door or pick up an item through it. Either the batch node keeps a CPU-side intersection path (the instance list and the model's geometry, so `castRay` still hits it) or conversion is limited to subtrees the ray's masks skip (**verify** the masks `MWRender::castRay` applies in `apps/openmw/mwrender/intersect.hpp`). The pure-static predicate must include this condition, and stage c has an acceptance test: a ray through a converted wall hits the wall.

## Decisions for toddhow (recommendation first)

1. **Run stage a and stop there if the gate fails?** Recommended: yes. The gate numbers are proposals (1.0 ms or 25 percent of the main thread's record wait, ratio 3, draws by subtree); change them if you want a lower bar.
2. **If the gate passes: merging, instancing, or a compute cull?** There are three, cheapest first. (i) **Merge distant objects into shared geometry**, which OpenMW's object paging does and `DistantObjects` deliberately does not port (`distantobjects.hpp`: "Not ported: merging objects into shared geometry ... So each object is its own draw"); it is ported, known code and needs no shader or device change. Task 0059's clusters are the same idea baked ahead of time, so "clusters that start closer" (a lower level-1 distance, more memory) is the same lever. (ii) **Instancing with CPU culling per chunk** (research note 0040 section 7). (iii) **The compute cull** of this spec's stages b and c. Recommended: let stage a's item 8 decide: merge or closer clusters if the draws are in the distant chunks; instancing if they are in the live grid and the ratio is high; the compute cull only if the packed CPU loop is itself a measured cost. The spec's stages b and c are written for (iii); (i) and (ii) are smaller tasks with their own specs.
3. **Descriptor indexing and bindless materials?** Recommended: no. It rewrites the object shader's texture access; batching by model part gets most of the draw reduction.
4. **Device features at creation:** recommended: enable `multiDrawIndirect` and `drawIndirectFirstInstance` (and `shaderDrawParameters` if the vertex path uses it) only when `gpu culling` is on, and never require them. Not `drawIndirectCount`.
5. **Scope:** recommended: pure static, non-interactive objects (statics, not activators, doors, containers, items), opaque, with a working ray path (risk 8); clusters not converted; actors stay on the CPU path.
6. **Hi-Z:** recommended: do not build it unless stage a shows a GPU-side cost; this machine's GPU main pass is 0.35 ms.
