## What S0 and the clusters told us

- **The measured frame is CPU-bound, and model LODs do not remove draws.** At the ground pose (`--start Balmora`, 7168 view) the scene holds 6,548 census draws and 459,719 census triangles; the frame is 3.10 ms median wall time and the main scene pass takes 0.064 ms on the GPU (note 0025, sections 2 and 3). A model chain replaces the triangles of a model with fewer, in the same draw; the number of draws per object is unchanged. So on the RTX 4070 the expected gain in frame time is **about zero**, and this spec must not promise one.
- **Where the gain is:** (1) a weaker GPU or the software device, where vertex and fill cost are real (the point of the weak-GPU goals, design doc section 8); (2) the shadow cascades, which draw the objects again for each cascade (the triangle cost multiplies; the share of the frame is **not measured**, S0 ran with shadows off); (3) quality at the join with the clusters, where the chain's last level can be made to resemble the cluster so that the hand-over is not a change of look (note 0025 section 7 and task 0059 found the visible losses are at the far edge); (4) memory and bandwidth for vertex fetch of dense cities (Vivec). None of these is measured today.
- **What the objects cost at the boundary:** a cluster tile (level 1) replaces the live objects of cells outside the active grid; the live objects of the 3 x 3 grid (`Constants::CellGridRadius` = 1, `constants.hpp`) are drawn from the full-detail models at any distance up to the view distance's cull. A person standing in a cell sees its own and the neighbours' statics up to 1.5 to 2.5 cells away (about 12,000 to 20,000 units, depending on the diagonal) at full detail; a tower 15,000 units away is drawn with all its triangles while its cluster version (error 128) would be indistinguishable at the 8 pixel threshold. That is the range chains cover.
- **The clusters' triangle budget showed what error is acceptable:** level 1 clusters at error 128 with an 8 pixel threshold are chosen beyond 9,976 units (task 0059, D4). The same formula for a chain level (below) gives the distances in this spec.
- **Cell loads hitch** (note 0025 section 4) and are about CPU work at load; chains add objects to compile at load, so they are a risk for S6 (see "Risks", item 2).

## What a model is, today (read from the code)

- A placed static is a `MatrixTransform` over a **shared** model graph: `Scene::insertModel` calls `MWAnim::createObject(mesh, useAnim, light, ctx)` and `loadTransform(ptr, *anim->transform())`; a comment there says "Instances of one static model share their switch", and `makeSwitchesUnique` makes a copy only for a harvestable container whose plant switch changes per instance. So instances share the geometry, descriptors and pipeline of their model.
- The model's geometry is `vsg::VertexIndexDraw` nodes inside `vsg::StateGroup`s built by `handleGeometry` and `createStateGroup` in `components/vsgadapters/nif/nif.cpp`, with arrays in a fixed order (vertex, normal, colour, then texture coordinate sets) and a texture descriptor set (task 0059, stage d plan).
- `vsgUtil::DistanceLOD` (`distancelod.hpp`) draws every child whose range contains the eye-space distance from the eye to `center` (in the node's own units: eye distance divided by the scale above the node), and "every matching child is drawn". Only recording selects: compile, bounds and intersection see every child. It exists for NIF's `NiLODNode` ranges; `distantobjects.cpp` (line 192 to 196) uses one per placed distant object with the range `[0, distantObjectMaxDistance(radius, 1, minSize)]` where that function is `radius * scale / minSize` (`distantobjectcells.cpp`), the inherited "object paging min size" rule (default 0.01: an object is dropped where its radius is below 1/100 of the distance).
- **The census would count every child of a `DistanceLOD`.** The S0 census (`components/render/scenecensus.*`, 49 lines) sees draw nodes by traversal; it has no mention of `DistanceLOD` (grep shows none), so with chains the census would **go up**, not down, as the graph holds every level. The acceptance criteria below therefore need a census that applies the ranges for the eye (stage a does it).
- Skinned actors are not static: `createObject(mesh, useAnim, ...)` with `useAnim` true builds animation and bone state; they are excluded in this version.
- Textures are the original block-compressed pictures with their own mip chains; the downscaler of task 0049 can already cap their size.

## Design, in plain language

**A chain.** For each eligible model, the baker keeps level 0 (the original, never touched) and makes up to three simpler versions, each with a larger tolerated **error**: the largest distance, in the model's own units, that the simplified surface may differ from the original. Simplification is `meshopt_simplify` with an absolute error target (the same call task 0059 uses, with the same lessons: border locking and a floor on triangles per piece, because thin double-sided sheets otherwise collapse to nothing; `clusterbuild.cpp` has the working option set). Level k is made **from level 0**, never from level k-1 (record 0010: from full detail; no error piles up).

**The cheap trick: only the index buffer changes.** `meshopt_simplify` can reduce an index buffer while keeping the original vertex buffer (its output is a smaller list of indices into the same vertices). So level k of a model is the *same* `StateGroup` tree (same pipeline, same material, same textures, same vertex arrays) with a *smaller index array* in each `VertexIndexDraw`. Memory cost is only the extra index buffers (at most about +75% of the original index memory for three levels of 1/2, 1/4, 1/8, and in practice less); no new vertices, no atlas, no material rebuild, the textures and their mips are shared, and the look cannot differ in colour or normals because vertices are the same ones (normals at vertices are the original smooth normals; a simplified surface lit with them is the ordinary cheap approach). Unreferenced vertices stay in the buffer (a little memory is not saved; the vertex fetch is by index, so they cost nothing per frame). The alternative of building a compacted vertex set per level is a later option.

**Which draw is which.** A chain stores, for each `VertexIndexDraw` of the model in a fixed depth-first order of its graph, the vertex count and index count it was made from and, per level, the simplified indices. At load, the runtime walks the freshly read model in the same order, **checks that each draw has the stored vertex count and index count** (a mismatch means the file is not the one the chain was made from: no LOD for that model, one log line) and clones the tree with the replacement index arrays. The baker produces the numbers by reading the model into the same VSG graph (`vsg::read(mesh, nodeOptions)` needs no GPU; `PreloadCell::operate` does the same on a worker, `preloadcell.cpp`), not by `flattenNifModel`, which is a different reader of NIF geometry (task 0059 stage c): using the runtime's own reader removes any chance that the order of draws differs. Whether `vsg::read` of a NIF in a GPU-free process works in the baker (the content-only start of task 0061 stage f) is **verify**.

**Choosing the level.** The error on screen is the formula of the design doc (3.3) and of the selection code (`components/lod/tileselection.*`):

    pixels = error * viewportHeight / (2 * distance * tan(fovY / 2))

With 720 pixels and a 60 degree vertical field of view, `viewportHeight / (2 * tan(fovY / 2))` = 623.5 (arithmetic, from the formula; the engine's actual field of view is a setting and the camera code was not read here: **verify**). A level of error `e` units may be used while `pixels <= T`, i.e. up to distance `e * 623.5 / T`. At `T` = 1 pixel (a threshold that is about "no pixel is moved by more than one"):

| Level | Error as a fraction of the model's bounding radius `R` | Example `R` = 400 units (a house) | Switch distance at T = 1 px (the level may be used from here) | At T = 2 px |
| --- | --- | --- | --- | --- |
| 1 | 0.5% R | 2 units | 1,247 | 624 |
| 2 | 1.5% R | 6 units | 3,741 | 1,871 |
| 3 | 4% R | 16 units | 9,976 | 4,988 |

(Arithmetic only: `e = fraction * R`, distance `= e * 623.5 / T`. The fractions are **starting values to be tuned from frames**, like every number in this task.) So a house gets its level 3 beyond about 10,000 units at 1 px: just inside the active grid's edge; the cluster at error 128 takes over beyond the grid at 8 px. The chain's last level (error 16) is finer than the cluster's (error 128) by construction, so the live-to-cluster hand-over of task 0059 is a change from a *better* to a *coarser* picture at the point where the coarser one is already within the pixel threshold, as designed. The model's own bounding radius is `R` (`vsgUtil::getBounds`, `cullnode.hpp`, as `buildChunk` uses).

**Hysteresis** (design doc 3.3): level k+1 is chosen when `pixels(e_{k+1}) <= T` and level k comes back only when `pixels(e_{k+1}) >= 1.4 T` (the 0.7 factor of the terrain, inverted). With a stateless distance-driven fade (below) hysteresis is implemented in the **selection ranges** that the fade overlaps, not as stored per-object state: the switch distances have two values (out and in), and the cross-fade zone spans the gap, so a camera hovering at a boundary moves inside the fade zone and nothing flips.

**The cross-fade, and why it is hard here.** Task 0059 dithers a cluster by a factor held in the material (`material.specular.a`, read by the `LOD_FADE` block of `main.frag`: `dither8(...) == 0 -> discard`). That works for clusters because each cluster's draws are its own. A **placed model's** draws are *shared by every instance of the model*, so a per-material fade value cannot be different for two instances at different distances. Options:

| # | Mechanism | How the fade value reaches the shader | Cost and risk |
| --- | --- | --- | --- |
| A | **Distance-driven, stateless** | the fragment shader computes its own fade from the fragment's view-space distance (`frag_in.viewPos`, already used in `main.frag`) and two numbers that describe the level's fade band, `[nearEdge, farEdge]` in world units, stored per level material. Level k fades **out** across its band and level k+1 fades **in** across the same band; the two dither patterns are complementary so their sum is one solid surface | no per-object state, no push constant, no timer; hysteresis is the band width; but the fade follows the *fragment's* distance, not the object's, so a long object dissolves along its length (a visible sweep, not a pop; for large objects the band is a fraction of their size); the band depends on the instance scale, which differs per instance while the material is shared (a scale-0.5 house switches at half the distance): handle by scale **buckets** (instances whose scale rounds to the same eighth share one material set) |
| B | Time-driven per instance | a per-draw value: a vertex-stage push constant is the only existing per-draw channel (the layout has one range, `VK_SHADER_STAGE_VERTEX_BIT`, `getCompatiblePushConstantSize()`, `graphics.cpp` line 181; the fragment stage needs a varying) | state per instance, a changed push constant range and a varying; the most faithful to design doc 7.2 (time-based fade 0.4 s) but touches every pipeline's layout |
| C | Per-instance material copy for the duration of a fade | a copy of the material descriptors for the fading instance | memory and compile churn exactly when the frame is busy |
| D | No fade for models, haze only (Low tier behaviour) | none | pops of tiny size at the distances above (a 2 unit error is under one pixel at the switch distance by construction); acceptable on Low, the design doc's Low tier |

**Recommendation: A**, with scale buckets, because it needs no new per-draw channel and gives stability for free. The unknown that decides it is the visual result of a distance-driven dither on large objects: stage b is a prototype on two or three models whose purpose is to look at that, with B as the fallback. D is the Low tier in all cases (design doc 8.2).

**The dither itself** reuses `dither8` of `main.frag` and the `LOD_FADE` mode of task 0059; what changes is where the fade value comes from: for a cluster it is the material's number, for a model level it is computed in the shader from the fragment distance and the band stored in the material (`Pipeline::Mode::LOD_FADE_DISTANCE`, a second mode, or a flag of the first; **verify** which is smaller to do given how `Mode` selects shader variants).

**Interplay with the clusters and the hand-over.** The chain applies only to objects drawn from the real scene graph, i.e. the active grid's objects (`Scene::loadCell` -> `insertModel`). The hand-over of task 0059 (live objects fade in as a cell becomes active, the cluster fades out; `Lod::stepTileFade`, `stepCoverage`) is **not changed**: the live objects appear at whatever level their distance says (the coarsest, for cells entering the grid at the far side), already dithered by the cluster's own fade for the cluster half. The new rule is only: a placed model that is drawn at all is drawn at the level its distance chooses. The active grid keeps being a cell-count rule (3 x 3), not a distance, so objects exist up to about 20,000 units diagonal.

**Which models are eligible, and the exclude list** ("blacklist"). Eligible: models read as static geometry (`useAnim` false) that the classifier of task 0059 would let into a cluster, i.e. the statics: not skinned, not animated (no controllers), no particle systems, no billboards, no existing `NiLODNode`/own ranges (their `DistanceLOD` has its own meaning and is left alone), at least 200 triangles at level 0 (below that a level gains nothing and costs a node; value to be tuned), and a level is kept only if it removes at least 20% of the triangles of the previous one (otherwise it is dropped: a level that does nothing is cost without gain). Alpha-tested foliage is eligible (trees are the biggest triangle sink in the swamp), but a level that changes the alpha-tested silhouette by more than its error is the reason the cutout leaves are the first thing to look at in frames (task 0059 found palms and swamp trees to be the visible loss). Excluded automatically and recorded in the pack's manifest with the reason: skinned, animated, particle, billboard, own-ranges, blended-only (sorting), too few triangles, "simplifier collapsed a piece" (the Prune and double-sided sheet problem of task 0059), and a model whose level 3 would exceed 8 times its radius-based error budget. Excluded by the user or a mod: a plain text list, `model_lod_exclude.txt` in the user config area (one model path per line, `#` comments, normalised with `VFS::Path::Normalized`), plus `[WorldLod] model lod exclude` for one-off paths; a mod may ask for exclusion of its own models by shipping the same file name in its data folder (read through the VFS, so mods stack). The name is "exclude list" on purpose: `DistantObjects::blacklist(refnum, ...)` is a different thing (it hides *references* a script disabled) and must not be confused with it.

**The data side: baked, not generated at load.** Recommendation: **bake**, in task 0061's unit model, one unit per model (kind `model`, key = a 56-bit hash of the normalised model path; parameter digest = tool version, layout version, level fractions, minimum triangles; input digest = BLAKE3 of the model file, read through the VFS, so a mod that replaces the file invalidates exactly that model). The units are assembled into `models.edenpak` of a generation; the runtime looks a model up by key with `Archive::findKey` and reads its chain with `readRange` on a worker (task 0060 request kind `model`). Reasons: simplification is deterministic work done once, not at the cell load that already hitches (note 0025 section 4); results are the same on every run; the cost at load is a read of a few KB (the chain of a model is its extra index buffers); it fits the generations, the staleness rule and the resume of the baker. **Load-time generation as a fallback is not built**: a model without a baked chain is simply drawn at level 0, as today, so a missing or stale pack never changes correctness. The alternative, generating on a worker the first time a model is used, would need `meshopt_simplify` of every new model within the loading of a cell (the number is small per model, but **not measured**) and a cache anyway; it is the right choice only if the bake proves impractical. The size estimate: 1,175 models, with the index buffers of three extra levels at about 0.5, 0.25 and 0.125 of level 0, plus the table; a few MB (arithmetic, assuming level 0 is of the order of the 5 to 25 M triangles of the clusters' inputs: the real number comes from the bake).

**Texture level of detail interplay.** A coarser model level is used where the object is small on screen, so its texture is minified, and the GPU already picks a lower mip. A model chain therefore needs no change in textures. For streaming (task 0060 stage h) the level chosen is a hint of the mip wanted (a level-3 model needs only the tail mips): the chain's selected level is exposed as data the streamer can read; nothing is built here. The downscaler's cap (task 0049) keeps working because the textures are untouched.

**Skinned actors** are out in version 1: their level would need to keep bone weights, which `meshopt_simplify` can do with attributes but the animation code (`BonePose`, the CreativeMotion pose driver, foot IK) assumes the full skeleton mesh. Actors are few and near; the gain is small. A later task.

**Shadows.** The shadow cascades draw the same graph; with chains they draw the level the *main* camera selected (the selection is per instance by the eye distance of the main view; the recording selection in `DistanceLOD::accept(RecordTraversal)` uses the eye of the view being recorded, so a cascade view sees its own eye position: **verify** which eye a light view passes; if the cascade uses the light's position the ranges are wrong for it and the shadow views need the main eye). This is both an opportunity (cheaper shadows) and a risk (shadows that pop with the level); the first frames with shadows on decide.

## Constraints

- **Determinism.** The baked chain is a function of the model file and the parameters; thread count and order do not change bytes (as task 0059); level selection depends only on camera position, field of view, viewport height and the stored errors, never on a clock; the fade of option A has no time at all.
- **Allocation.** No allocation in the per-frame path: `DistanceLOD` ranges are fixed at insert time; a field-of-view or viewport change recomputes the ranges of the (few hundred) distinct models' bucket nodes, not of every instance, by updating shared band numbers once.
- **Threading.** Chains are read and decoded on workers; compile on the compile worker; attach to the scene on the main thread only (the `insertModel` call is already main-thread); `DeletionQueue` for anything dropped.
- **Untrusted input.** The chain payload is derived data: every count and index is checked against the model as read; a mismatch means "no chain for that model" and one log line; a chain can never reference a vertex that does not exist; sizes capped.
- **Off means unchanged.** With `[WorldLod] enabled = false` or `model lods = false`: `insertModel` builds exactly the nodes it builds now, no pack is opened, the shader variant is not compiled; compared by a frame of the Balmora pose (0.000 percent of pixels over 4 grey levels) and the 32 Lua tests.
- **Gameplay unchanged:** collision uses Jolt shapes made from the full-detail model (`PhysicsShapeManager`), never the chain; picking and shadows' occluders by the rendered level are visual only.
- **Units.** Model units (Morrowind), the camera in world units; the error is in model units multiplied by the instance scale by the bucket.
- **No game assets in the repository;** new files under `components/` use lowercase letters and digits only; the shader change is an edit of the existing GLSL (decision 0009, as task 0059 logged).

## Risks and open questions

1. **Distance-driven dither on large objects** (option A) may look like a sweeping dissolve; the prototype exists to find out. Fallback B changes the pipeline layout.
2. **Load-time cost.** Each extra level is another `VertexIndexDraw` (and index buffer upload) per draw of the model; a cell with many new models multiplies compile work on first sight. Chains are attached only when ready, off the main thread, and the hitch flight of task 0060 stage a must be re-run with chains on.
3. **Scale buckets** multiply material sets by the number of distinct scales used (Morrowind statics use a handful: **not measured**); the baker/runtime counts them.
4. **Shadows' eye** (above) is unverified.
5. **Foliage and thin sheets** are where simplification misleads (task 0059): the first frames to look at are the Bitter Coast trees and Ald-ruhn rocks and shells.
6. **`DistanceLOD` as the selector** draws every child in range, which during the fade band is two levels, a doubling of those objects' draw commands inside the band (the census must count it). If the band covers many objects this adds draws exactly where the S0 numbers say draws are the cost; band width must be a small fraction of the switch distance (a starting value of 15 percent of it; to be measured).
7. **Normals of simplified surfaces** keep the original vertex normals; on a heavily simplified wall they are slightly off. At the pixel errors above this is not expected to show; frames decide.
8. **Where the rest of the world is:** impostors for trees (S10) are the next step after the chain's last level; not here.
