Full loop (CreativeMotion adapter and physics area).
Goal: in Eden Studio the user picks a ragdoll body (a "bone"), sets an impulse (direction, size, point), presses Push, and watches the ragdoll react in the editor's one simulation, with Play, Pause and Step working as for every other tool.
Inherited code touched: none planned. Editor code only (`apps/opencs/`), plus CreativeMotion's editor module (`creativemotion_editor`, its own task specs for its code). `components/creativemotion/` is never edited in place.

## Why this was not done as a small step inside task 0035
Applying an impulse is one call (`opas::physics::PhysicsWorld::applyImpulse(body, impulseNs, worldPointM)`, implemented by `CMPhysics::HostedJoltWorld::applyImpulse`), and `StudioWorld::cmWorld()` now hands that interface out. But a push needs things that do not exist yet, and each is a design choice, not a one-line change:
1. A ragdoll in the editor: `opas::motor::buildRagdoll` needs a rig and a profile (the game embeds copies in `apps/openmw/mwphysics/ragdollrigdata.cpp`); the editor's module already loads rigs for the inspector (task 0032), but nothing builds a ragdoll from the loaded rig in the world.
2. Which body is "the bone": a map from rig bone to `BodyId` (the builder's `Ragdoll` result has it), and a way to select it (picking or a list; the module API has no picking yet, see `apps/opencs/CLAUDE.md`, "Not yet").
3. The impulse gizmo (overlay lines exist; dragging handles does not).
4. Undo: a push changes the simulation, not project data. It must not go on the document's undo stack; "reset" (rebuild the scene) is the undo.
5. Determinism: a push happens between steps (while Paused, or queued for the next step's start), never from a step listener (`HostedJoltWorld` refuses structural calls in a step, and `applyImpulse` is not allowed there either).

## Design (proposed)
- Stage A (model, `apps/opencs/model/physics/`, no Qt widgets, tested in `eden-studio-tests`): `CSMPhysics::PushScene` owns a ragdoll built through `StudioWorld::cmWorld()` from a rig and profile, remembers bone name to `BodyId`, offers `push(boneName, impulseNs, worldPointM)` (queued, applied just before the next step, once) and `reset()`; destroyed or reset before `StudioWorld::clear()` matters not (clear makes its handles stale).
- Stage B (the module's panel): a rig and bone list, an impulse form (`makePropertyForm`), Push and Reset buttons, an overlay arrow for the last impulse. All through the editor module API; gaps found are fixed by extending the API (decision 0007).
- Stage C (checks): a ragdoll dropped, pushed while Paused, stepped; positions logged and identical across two runs; a frame captured and looked at.

## Constraints
Main thread only. No allocation in the per-step path of `PushScene` (a fixed queue of pending pushes). Lengths in meters at the interface, as everywhere in the adapter. Off unless the user opens the panel: with the panel closed the editor world is exactly as before (checked by the existing `StudioWorld` tests).

## Acceptance criteria (to be refined when approved)
- [ ] A rig loaded in the editor becomes a ragdoll in `StudioWorld` through `cmWorld()` and falls onto the editor's static box (unit test, `eden-studio-tests`).
- [ ] `push` on a named bone changes that body's velocity by `impulse / mass` (within a stated tolerance) after the next step, and not before (unit test).
- [ ] Two runs of the same scenario, 240 steps, give bit-identical body positions (unit test).
- [ ] `reset()` and `StudioWorld::clear()` leave the Jolt body count as before the scene was built (unit test).
- [ ] In the editor, Play, Pause, Step and a Push on a ragdoll's pelvis show the ragdoll moving; a frame is captured and looked at.
Out of scope: balance, stumbling and get-up (they need CreativeMotion's M11 and the sub-step decision of task 0035's open question 7), pushing living actors in a cell, the game, saving a scenario.

## Open questions for toddhow

2. Is picking a bone with the mouse required for the first version, or is a bone list enough?
3. Should a push also be possible while Playing (applied at the start of the next step), or only while Paused?

## Decisions on the open questions (2026-11-08, toddhow: "take your recommendations")
1. **Rig and profile.** The scene is rig-agnostic: `PushScene::create` takes any `opas::rig::Rig` and `Profile`. The embedded game rig (`apps/openmw/mwphysics/ragdollrigdata.cpp`) cannot be used by the editor (`apps/opencs` may not include `apps/openmw`, and this task touches no inherited code), so the first option is read as "the rig the user has open": the sandbox is fed by the rig and profile the Rig & Motor Limits Inspector holds. The tests use the module tests' own four-body rig (`CMTest::makeLimitsRig()`), not the CreativeMotion repository's data files (outside this repository).
2. **Bone choice.** A bone is chosen by NAME. The list is `PushScene::boneNames()`; the API 1.2 selection already turns a click on a joint's handle into `{"joint", bone}` (and the module has Next/Previous Joint), so the panel can push "the selected joint's body" and mouse picking comes from the existing handles without new picking work. (The spec marks no recommendation here; this is the cheapest reading that still allows picking later.)
3. **Push while Playing.** Yes. A push is queued and applied once, just before the next step, so while Paused it waits for the next Step and while Playing for the next tick (tested both ways).

## Stage log

### Stage A: the model (2026-11-08)
**What exists.** `CSMPhysics::PushScene` (`apps/opencs/model/physics/pushscene.hpp/.cpp`, in `csmodel`, no Qt, no render types): builds a ragdoll through `StudioWorld::cmWorld()` with `opas::motor::buildRagdoll` (placement: rig root position in meters and a yaw), makes it limp (`makeLimp`, as the game's debug ragdoll), keeps bone name to body (rig body order), and has `push(bone, impulseNs, worldPointM)` (queued in a fixed `std::array` of 16, finite values only, at most 100,000 N s, false when full or the ragdoll is gone), `applyPending()`, `reset()` (drops queued pushes and the last applied one, rebuilds at the placement), `boneState`, `boneMassKg`, `lastApplied()` (for an arrow; stores a body index, no string copy), `present()`. Ownership: the scene owns the handles, must be destroyed BEFORE the world, removes its ragdoll and its hook in the destructor; after `StudioWorld::clear()` the handles are stale and `present()` is false until `reset()`.

**One addition to `StudioWorld`** (editor code, not inherited): `StudioWorld::PreStepHook` with `addPreStepHook` / `removePreStepHook`. `stepOnce()` runs the hooks first (registration order), before the observer's `beforeStep` and before the adapter's `beginStep`, so the push is applied outside a step. Reason: `CS::Editor` already holds the single observer slot (`editor.cpp`), and a push must not be applied from a step listener. A hook that throws is logged and the step still runs. No existing test was edited.

**Spec correction.** The spec says `HostedJoltWorld` refuses `applyImpulse` inside a step. It does not check `mInStep` there (`components/cmphysics/hostedjoltworld.cpp`, `applyImpulse`); what keeps a push out of a step is that the queue is drained only from the pre-step hook. Not changed (`components/cmphysics` is full-loop and outside this task).

**Tests (24: `testpushscene.cpp` 20 and `teststudioworldhooks.cpp` 4), written first and run red against stubs:** 22 of 24 failed (the 2 that passed are the "invalid rig / profile is refused" tests, which a stub that always answers `nullptr` satisfies); then green after the code: 50 of 50 in the `CSMPhysics*` suites, `eden-studio-tests` 901 of 901. Covered: bodies built in rig order with their names and masses (and `bodyCount()` unchanged); an invalid rig and a profile for another rig refused with a message and nothing left in the world; the ragdoll falls and rests on the static slab (600 steps, every body above it); delta v = impulse / mass on a one-body rig against an identical control world (3.0 m/s within 0.01, not before the step, once only, off-centre also spins); a pelvis push on the ragdoll moves it; a pushed sleeping ragdoll wakes (1500 steps to sleep first); Playing (next tick) and Paused (next Step); queue order and the fixed capacity; bad pushes (unknown bone, NaN, infinity, over the cap) queue nothing; reset restores the pose and the Jolt body count and drops queued pushes; destroying the scene leaves the world as found (and stepping afterwards does not call the removed hook); `clear()` then a pending push does not crash and `reset()` rebuilds; two runs of 240 steps with a push at step 100 give BIT-IDENTICAL positions of every body; the push changes the outcome; two scenes in one world push only their own bodies. A mutation (the queue count not cleared after applying) fails 6 named tests. The `StudioWorld` hook has its own 4 tests (order against the observer and the adapter's listeners, `tick` only when stepping, add twice / remove unknown, a throwing hook contained).

**Checks.** `tools/edenstudio_check/check.sh` and `tools/modulecheck/check.sh` pass (`OPENEDEN_QUIET_WINDOW=1`, real user folder unchanged), `eden-studio` rebuilt. GCC 13 `-Werror -Wall -Wextra -Wshadow -pedantic -fsyntax-only` is clean on `pushscene.cpp`, `studioworld.cpp` and the two test files (`openeden-linux` image); clang-format 14 (`openeden-cf14`, binary `clang-format-14`) was applied to the six changed C++ files.

### Stages B and C: BLOCKED (nothing built)
The Editor Module API (`sdk/include/openeden/editor_module/`, version 1.2) gives a module no access to the simulation: no way to build a ragdoll in `StudioWorld`, to push, to read a body, or to ask for a reset (the only simulation word in the API is the `SimulationStepped` event). The module (`creativemotion_editor`) is built against the API and CreativeMotion's rig headers only, with no Jolt, Qt or Studio types, so its panel cannot reach `PushScene`. The spec (stage B) says gaps are fixed by extending the API; the task assignment said to stop and report instead. Stopped here. Two ways forward, for toddhow:
- **Option 1 (recommended): API 1.3, additive.** One new virtual at the END of `EditorContext`, `virtual SimulationSandbox* simulationSandbox() { return nullptr; }`, with a new small interface in `types.hpp` that carries no `opas`, Jolt or Qt type: `build(rigPath, profilePath, rootPositionM, yawRad, error)`, `bodyNames()`, `push(bone, impulseNs, worldPointM)`, `pending()`, `reset()`, `bodyPositionM(bone)` and `lastPush()` for the arrow. The host implements it over `PushScene` (and keeps the `StudioWorld` hook); old modules keep loading (the same frozen-header test libraries; a 1.3 module is refused by older hosts with both versions named). Cost: the version pins in four existing tests change again (as 0091 listed), and the API is the full-loop area.
- **Option 2: a Studio built-in panel, no API change.** `apps/opencs` shows a "Push Sandbox" panel over `PushScene`, fed by the rig and profile files the CreativeMotion module has open (the host reads them with the same `opas::rig` loaders). This departs from "in the `creativemotion_editor` module" and from decision 0007's idea that tools come from modules, but needs no SDK change and could move into the module later.

Either way the remaining work is: the panel (rig and bone list or the joint selection, an impulse form, Push and Reset), the overlay arrow, wiring the world's lifetime in `CS::Editor`, and a new check `tools/pushsandbox_check` (drop, Pause, Push, Step, frames viewed; positions identical across two runs).
