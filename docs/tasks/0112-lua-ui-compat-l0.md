## Stage log

### L0 (2026-11-11)

**MyGUI's DummyPlatform.** `MyGUI.DummyPlatform.lib` exists in the vcpkg tree (`MyGUI_DummyPlatform.h`, `MyGUI_DummyRenderManager.h`, `MyGUI_DummyDataManager.h`). The dummy render manager answers `createTexture` and `getTexture` with a null pointer, which `ResourceTrueTypeFont` and `LuaImage` cannot use, and the library is a separate one that other MyGUI packages may not ship, so the harness does NOT use it: `StubRenderManager` (implements `MyGUI::RenderManager` and `IRenderTarget`: vertex buffers that draw nothing, textures that keep their pixels in a vector, a size for any texture file asked for: 16 x 16 unless set), `FolderDataManager` (files from `files/data/mygui`, `files/data/fonts` and the test data folder) and `MyGUIPlatform::ScalingLayer` registered as the game does (`openmw_layers.xml` names it for one layer). Fonts and text metrics therefore work under this harness, with the real MyGUI font code; the font is the game's own DejaVu file at size 16 (`testfont.xml`: the game's `omwfont` settings with resolution 58; GUI scale 1), not the user's Morrowind font.

**Lua side.** A real `LuaUtil::LuaState` with the real util package (`LuaUtil::initUtilPackage`) and the real content constructor (`LuaUi::loadContentConstructor`). `openmw.ui` is a table of the harness: `TYPE`, `ALIGNMENT`, `content`, `texture` (same code as `uibindings.cpp`, over `LuaUi::ResourceManager`), `_getDefaultFontSize` (16) and `_getMenuTransparency` (1); `openmw.core.getGMST` returns the header and normal text colours. The MWUI scripts of `files/data/scripts/omw/mwui` and `openmw_aux/ui.lua` are loaded unchanged from the repository by a small `require`. A case file is a Lua chunk that gets `ui` and `util` and returns a list of `{ name, layout, steps = {...}, unorderedChildren }`. Layouts are created with `Element::make` and `create`; each step mutates the layout tables and `Element::update` is applied.

**What is recorded.** One line per widget, indented by depth: type name (`LuaFlex`...), rectangle (`getCoord`, relative to the parent), own visibility, alpha, and for text widgets `getTextSize`. Template children are marked `template`. The MWUI templates build their parts by iterating a Lua hash table (`pairs` in `borders.lua`), so the order of siblings is not stable; the `mwui` family records with sorted siblings (`unorderedChildren = true`), all other families keep creation order. The goldens were identical across three separate process runs.

**Tests, written first.** The hand-derived tests were written before the harness existed (the first build failed to compile: no harness). They passed at once on the old code once the harness worked (10 of 10); the corpus goldens cannot be red-first (they record). Instead the old code was mutated (a private link with a changed copy of the file ahead of the library's object): `LuaFlex` centre alignment `/ 2` to `/ 3` and the grow remainder `+ 1` made 7 tests fail (3 hand-derived, 4 families); `widget.cpp` anchor `-` to `+` made 4 fail (the anchor test, widget, container_window, template_update).

**Findings pinned as they are (inherited behaviour, not fixed here):**
- A Flex whose children are larger than it and have `grow` shrinks them: children of 15 and 15 with grow 1 in a Flex 20 wide come out 10 and 10 (`grow_without_free_space`): the negative free space is shared out.
- `grow` below zero counts as zero; `stretch` is clamped to 0..1 and uses the integer part of its product.
- In a Container, a child with `relativeSize` adds nothing to the fitted size (`childScalingSize` is empty).
- Not recorded because it would crash: changing the TYPE of a ROOT layout and calling `update` (`Element::update` dereferences `mRoot->getParent()`, which is null for a root). Found by reading, not run; a crash in L1 would be inherited.

**Not covered / limits.** (1) The layouts of the other built-in scripts (`console/menu.lua`, `console/player.lua`, `input/playercontrols.lua`, `input/settings.lua`, `mechanics/playercontroller.lua`, `settings/menu.lua`, `settings/renderers.lua`, `ui.lua`) need the game's Lua state (storage, input, core, settings) and were NOT built: only the eight MWUI files they all use are. A dump from a running game was not made. (2) Tier 3 events (hover, press, drag, focus, key and text input) and an `Element` used as another's content (needs the `Element` usertype of `uibindings.cpp`, which lives in `apps/`) are not covered. (3) The text rectangles hold for DejaVu at size 16 and the in-memory glyph textures; they pin the arithmetic around MyGUI's text measure, not the Morrowind bitmap font. (4) The harness's texture sizes are 16 x 16 unless a case sets them, so `Image` sizes that come from the texture file are only partly pinned (the corpus gives sizes). (5) FreeType's version could change the text numbers: a text golden that moves with a library update is to be reviewed, not regenerated blindly.

**Linux and FreeType (a deviation from 16.4, to check first at the Linux gate).** The research note asks for text on the real font to be compared within +-1 px with equal line counts, and exactly only for an injected fixed-advance font. These goldens compare exactly on the real DejaVu font, rendered by the vcpkg FreeType of the Windows build; Linux CI uses Ubuntu's FreeType, so the `text` family and the text lines of `mwui` and `template_update` may differ there by a pixel or so. If they do, the right fix is a tolerance for text extents (and an exact check of everything else), not a re-recorded golden. The other families contain no text.

**Order dependence.** The harness creates and destroys MyGUI's singletons (log, render and data managers, `Gui`) in every test, so nothing is left behind. It collided with one existing test that leaked them (see the 0111 log: `testbitmapfontmygui.cpp` was changed, awaiting approval). All `ui_rml` test files and the `lua_ui` files in one binary: 175 tests pass in default order and with five shuffle seeds.

**Evidence.** Private link (the changed test files and the harness compiled with the build's flags, linked against the previous build's libraries; the whole `components-tests` was not built because the disk had 1 to 3 GB free): `LuaUiGeometry*` 22 of 22 pass, three process runs identical. Not run: the Linux gate (Docker hung; GCC traps avoided by hand), clang-format 14, clang-tidy, the whole `components-tests`, a fresh review. A game run with Lua UI windows open to show frames unchanged was NOT made: no `lua_ui`, `mwlua` or `mwgui` file changed, so the claim "no change to `lua_ui` behaviour" rests on the diff, not on frames.
