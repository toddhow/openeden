- **Tabs.** The tab count of the entry point is the third byte of `DATA`; the tab index in `PRKC` is 0-based. ## Design
1. **A perk model of its own, pure** (`perks.hpp`/`perks.cpp`): `PerkRecord` (editor id, effects with kind, priority, entry point, function, EPFT, the first and second float of `EPFD`, the form of `EPFD`/the ability spell, and the CTDA list of each tab), `AbilitySpell`/`AbilityEffect` and `MagicEffectRecord` (just what an ability needs), strict decoders (sizes against the layout, finite floats, a located reason, counted odd subrecords, caps on effects and conditions), a `PerkLibrary` interface (`perk`, `spell`, `effect`; `CombatIndex` implements it) and the evaluator below. Conditions are kept as `survey::Ctda` and run by the existing `conditions::Evaluator`.
2. **Participants and a world for them.** A `PerkParticipant` is one thing a tab can name: an actor (base, race, sex, level, perks, keywords, base actor values, sneaking/blocking/power-attacking/undead flags), a weapon (form, keywords, animation type), an armour piece (form, keywords, slot) or a spell (form, keywords, skill). `PerkConditionWorld` is a `conditions::ConditionWorld` over up to four participants; `resolveRunOn(0, ...)` returns the participant of the tab being evaluated, other run-ons resolve to nobody (fail closed, counted). It answers `HasPerk`, `HasKeyword` (an actor's own list and its race's, a weapon's `KWDA`, an armour's), `GetBaseActorValue`/`GetActorValue` (the 18 skills, Health, Magicka, Stamina), `GetLevel`, `GetIsRace`, `GetIsSex`, `GetInFaction` (the actor's factions), `GetIsID`, `GetEquippedItemType`, `IsSneaking`, `WornHasKeyword` and five functions only the perk evaluator knows (568 IsSprinting, 569 IsBlocking, 673 IsPowerAttacking, 697 IsAttackType, 715 IsUndead: `conditions::Evaluator::setExtraFunctions`, an additive per-evaluator table; the global table is NOT changed, so every other list that holds one still fails closed and dialogue and package choices cannot move) below. Anything else keeps the default answer (nothing), so a condition on it is false: a perk whose condition the engine cannot answer does not apply (a counter says how often).
3. **Entry point application**: `applyEntryPoint(library, entryPoint, ownerPerks, participants, value)`: collect the effects of the owner's perks for that entry point, order by priority (higher first, ties by perk form id then effect index; RECALLED-VERIFY: the Creation Kit says higher priority is applied first), evaluate each tab's conditions (a tab with no conditions passes), then apply the function: Set (replace), Add, Multiply, Multiply-by-1-plus-actor-value (reads the actor's value of the index, default 0 so it is a no-op), and for Select Spell (51, 52, 53, 67, 69) `selectSpells` returns the spell forms in the same order. Functions 4, 5, 6.. and the text functions are counted as unsupported and ignored. Tab roles by entry point are a table (`entryPointRoles`): `[Owner, Weapon, Target]` for 0, 1, 2, 28, 35, 37, 51, 53; `[Owner, Weapon]` for 26, 27, 52, 67; `[Owner, Attacker, Weapon]` for 36; `[Owner, Armour]` for 85, 32; `[Owner, Spell, Target]` for 29, 30, 41, 42, 88, 77; `[Owner, Spell]` for 38; `[Owner]` for 39, 40 and any other entry point (tab 1 and 2 conditions of an unlisted entry point fail closed). Ability effects (kind 1) are not evaluated here; `abilityModifiers` sums, for a list of ability spells, the magnitude of the value-modifier effects per actor value.
4. **Where the entry points are used in combat** (the first implementation; each is behind the owner having a perk with that entry point, so with no perks nothing is computed):
   - 0 CalculateWeaponDamage: the weapon's base damage before the skill multiplier (attacker, weapon, target).
   - 35 ModAttackDamage: multiplies the attack damage (melee and bow) after the skill and power attack; 28 ModPowerAttackDamage: power attacks only.
   - 36 ModIncomingDamage: the victim's perks, after the attacker's, before armour.
   - 85 ModArmorRating: per worn piece (owner, armour); abilities adding `DamageResist` add to the rating (one point of the actor value is one point of rating).
   - 27 ModPowerAttackStamina: the stamina cost of a power attack.
   - 33 ModIncomingStagger (victim) and 34 ModTargetStagger (attacker): the stagger value the blow carries.
   - 39 ModPercentBlocked: the fraction a block takes off (capped at 1.0).
   - 21 ModRecoverArrowChance: the arrow-in-inventory chance (a Set of 66 for Hunter's Discipline).
   - WeaponSpeedMult ability (Quick Shot): bow draw speed, `bowDrawSpeed(weaponSpeed, bonus)` with the ability's magnitude; 20 ModBowZoom has no call site (there is no zoom).
   - 1 and 2 critical chance and damage, 26 bashing damage (a bash deals 0 damage by decision 0018), 37 target damage resistance, 40 shield deflect arrow chance, 50 sweep attack: the evaluator handles them (tests), there is no call site yet (no critical rolls, no bash damage, no sweep; 37 has a data ambiguity: Skullcrusher stores 0.25 as a multiply, which cannot be "ignores 25 percent").
   - Spells, hit spells, prices, lockpicking, alchemy, enchanting, tempering, detection, activation: the other top-21 entry points (29, 30, 38, 51, 8, 60, 56, 59, 66, 74, 76, 77, 88, 57, 32, 14): the evaluator is generic and each has a test; there is no call site because the systems (magic S5-8, trade, lockpicking, crafting) do not exist.
5. **Actors get perks** from `ActorNpc::mPerks` (`PRKR`, followed through the template "spell list" use flag; RECALLED-VERIFY: the flag that covers `PRKR`), plus the pack settings `[extension.skyrimse] combat test player perks` and `combat test npc perks` (comma separated PERK editor ids, empty by default; the second adds the perks to every NPC fighter), and abilities from the NPC's and race's `SPLO` lists. All of it only when `combat perks` (pack setting, default true) is on. `FighterProfile` gains `mPerks`, `mKeywords`, `mPieces`, `mValues`, `mAbilityDamageResist`, `mWeaponSpeedMult`, `mFemale`, `mLevel`, `mRace`, `mBase` (defaults mean "nothing", and an empty perk list skips all of it).
6. **Determinism and allocation.** No random numbers and no clock; perk lists are sorted by form id; the evaluation uses fixed arrays (at most 64 effects per query); a hit allocates nothing in the perk code except what the existing trace already builds. Perk code runs on the main thread inside `combatUpdate`.
7. **Existing code touched, kept additive**: new members with defaults in `WeaponRecord`, `ArmourPiece`, `ArmorExtra`, `ActorNpc`, `FighterProfile`, `CombatRecords`, `CombatIndex`, `CombatData` (a defaulted virtual); `conditions.hpp` gains `ExtraFunction` and `Evaluator::setExtraFunctions` (empty by default); the global function table is untouched. Tab roles are from the data (which condition functions each tab holds) and memory; xEdit and CommonLibSSE were NOT read this session for them (decision for toddhow: confirm 33, 34 and the rows with no conditions in the installed data).

## Out of scope
Spell perks' effects (magnitude, cost, duration, hit spells: S5-8), the player's perk points and tree, quest perks (type 0), perk scripts (VMAD), the perk-level prerequisite conditions (they gate learning, not applying), critical hits, bash damage, shield deflection, prices, crafting entry points, race-specific `RACE` abilities beyond `DamageResist` and `WeaponSpeedMult`, saving perks (the pack has no per-session perk state: perks come from records and settings), Papyrus `Actor.HasPerk` (the Papyrus host keeps its own world; making it answer from `CombatIndex` is a follow-up).

## Stage log (2026-11-15; same hand wrote tests and code, tests first for the pure parts and red against stubs, no fresh reviewer; Windows only, local commit on the worktree branch from `b1023828c4`, not pushed)

Plain words: with `[Game] neutral combat` on, an actor's perks now change its fights. The perks come from the NPC_ record's `PRKR` list, from two new pack test settings (`combat test player perks`, `combat test npc perks`: comma separated PERK editor ids), and abilities from the actor's race and NPC spell lists.
