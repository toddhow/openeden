# Task: Skyrim SE, the first pack skeleton
Design doc section: `docs/design/game-packs.md` sections 1, 3, 5 and stage f of section 10; `docs/research/0043-separating-formats-from-game-rules.md`; `docs/research/0036-extended-skeletons-measured.md`; `docs/design/advancedbodies-in-openeden.md`.
Goal: a `compat_skyrimse` compatibility pack and a `game_skyrimse` game pack skeleton that identify Skyrim SE installs, register its archives and plugin header reading, and give Skyrim meshes and skeletons to Eden Studio and the AdvancedBodies tools, running none of Skyrim's rules.
Inherited code touched, at commit `671c7676e9`: none expected in the core; the skeleton is built against the SDK of task 0084 and the common pack of tasks 0082 and 0083. Read for reference: `extensions/compat_morrowind/` (the pattern: `extension.json`, `morrowind_compat_extension.cpp`, the `GameContract` implementation), `components/esm4/reader.*`, `components/bsa/compressedbsafile.cpp` (TES4 BSA with LZ4), `apps/edenskelstat`, `components/bodynif/skeletonread.*`.
Inputs / outputs: `extensions/compat_skyrimse/` (an extension: `openeden.game` implementation with id `skyrimse`, units per meter, default humanoid skeleton path convention, the pack's NIF `SceneOptions`) and `game_packs/skyrimse/` (a `kind: "game"` pack that registers the Skyrim SE content probe, archive kinds, record type ids it recognises and a *null* `GameRules`); an Eden Studio mesh/skeleton viewer entry for Skyrim data using `Nif::Scene`.
Status: APPROVED by toddhow 2026-11-08; stages a to d built (see the stage log), stage e (Eden Studio) built 2026-11-08; depended on tasks 0082 to 0084. **Full loop** for the game pack (loader, contracts, untrusted input); the compatibility pack may use the lighter loop only if toddhow marks it.

## Why Skyrim SE is the second game (toddhow, 2026-11-04: decided)
- It differs most from Morrowind (Gamebryo 20.2.0.7 user version 12 stream 100; `BSTriShape`; form ids and master lists; localised strings; LZ4 BSAs; Havok and Papyrus), so it shows where the boundaries are wrong.
- toddhow owns the content and the measurements: CBBE 3BBB, XPMSSE, HIMBO and The New Gentleman, read with the engine's reader in research note 0036; a seamless body, which AdvancedBodies uses without a merge step (design doc H13 to H20 of `advancedbodies-in-openeden.md`).
- Oblivion and Fallout 3/New Vegas are a later, cheaper step: `components/esm4` already covers parts of them. They are not an alternative to this task.

## Scope of the skeleton
- **Identify:** probe a Skyrim SE install (the Data folder, `Skyrim.esm`, `Update.esm`, the DLC masters) from plugin headers (task 0083); a profile `game=skyrimse` selects the pack; the launcher/probe never starts a game.
- **Archives:** open the install's BSA files through the registered archive factory (TES4 BSA version with LZ4; whether Skyrim SE is version 105: **verify** from the install, the reader's own version check is cited in the stage log) and list the meshes and skeleton paths used by toddhow's set.
- **Meshes and skeletons:** read XPMSSE skeletons and the body meshes as `Nif::Scene` (task 0082), apply the Skyrim `SceneOptions`, and provide them to Eden Studio's mesh viewer (task 0043's viewer) and to `edenskelstat`/the skeleton-map tools with unchanged results (the aggregates of note 0036).
- **Not drawn in the game:** `BSTriShape` rendering in the game is a separate task (research note 0036 section 9 item 8).
- **`GameRules`:** a null implementation that refuses to start a game with the message "Skyrim SE rules are not implemented" and lets the editor and tools run.
- **Records:** type ids recognised and skipped with counts; no Skyrim record decoder beyond what `components/esm4` has. Rules, Havok `.hkx` animation, Papyrus (`.pex`), the Creation Engine's scripts, perks and quests are out of scope and are named as the next design questions (design doc section 9, question 6).

## Constraints
- No Bethesda assets in the repository: tests use generated plugins, generated NIFs (task 0082's builder) and an install-in-place mode that writes aggregates only (the pattern of note 0036). Paths of toddhow's mod folders are never written into files in the repository.
- The pack reads the user's own installed data; it ships none.
- Off by default and absent unless installed: with `game=morrowind` nothing about Skyrim loads (no extra files read, no startup cost beyond a manifest scan; measured).
- The Morrowind path is unchanged: the same gates as task 0085.
- Determinism, hostile input and allocation rules as in tasks 0082 to 0084.

**Decisions made while building (for toddhow; all small, all reversible).**
1. *The null `GameRules`.* `game_rules.hpp` does not exist in the SDK (task 0084 left it for 0085, whose calls come from `MechanicsManager`), so there is no interface to implement and none was added. The refusal is the pack's `start()` failing with `Skyrim SE rules are not implemented` after it has registered its probe: a game pack's failure is a session error that names the pack, shows at the main menu and refuses saving (task 0084), which is the behaviour the spec asks of the null rules. 2. *The content probe convention.* The core has no caller that fills an `sdk::ContentHeader` yet, so the pack's own convention is: `gameTag` `"TES4"` and `formatVersion` the record header's form version, accepted for 43 and 44 (what `Content::guessGame` calls Skyrim SE). `toContentHeader()` builds it from a `Content::Header`. The core should adopt or replace this when it first probes.
3. *Record types are recognised and counted, not registered.* `RecordService::registerRecordType` asks the core to store a record of `sizeBytes`; the pack decodes none, so it registers none (a test pins that `NPC_` is not in the host's table). Recognition is the table in `pack_core.cpp`, written from recall; the real-data run found no type outside it in the five masters (0 unknown of 1,178,642 records), so the recall was complete for them.
4. *Archive kinds.* The pack does not register archive factories: `VFS::registerBethesdaArchiveKinds()` (task 0083 stage 3) is the host's start-up call and already covers the TES4 BSA. The pack adds a version check (`BSA version N is not Skyrim Special Edition's (105)`) and a pre-check of the header counts against the file size, because `CompressedBSAFile::readHeader` reserves from the counts before it reads anything.
5. *Units per meter* is Morrowind's value, not measured for Skyrim (both games use the same unit as far as recalled). *The female skeleton path* was wrong in the first draft (`skeletonfemale.nif`) and is `character assets female/skeleton_female.nif`, found by listing the installed archive; the four bone names of the contract were confirmed as nodes of the installed `skeleton.nif`.

### Review fixes, round 5 (2026-11-08; fresh review `I:\Projects\OpenEden-work\review5\REVIEW_skyrim_0085.md`)

**Correction of an earlier claim.** The stage e text above (and the commit message of `4ce4190a31`) says the scene path is for "Skyrim SE". That is not what the code does: `chooseNifReader` looks at the header text alone, and "20.2.0.7" is shared by Fallout 3 and New Vegas (user version 11), Skyrim LE, Skyrim SE, Fallout 4 and Fallout 76 (`components/nif/niffile.cpp`). **Every 20.2.0.7 file takes the scene path**; the ones that are not Skyrim SE get the scene reader's refusal (the reader defaults to the Skyrim SE version set). Before stage e they went to `MWAnim::createObject`, which also refuses them under the editor's Morrowind default (the editor never calls `setDefaultReadOptions`), so nothing that opened before stops opening; only the error text changed. The dispatch was deliberately **not** changed in this round (toddhow's call): if the editor ever sets `VersionSet::Any`, those files would still be sent to the scene reader. Morrowind 4.0.0.2 and Oblivion 20.0.0.5 take the engine path (tests cover 4.0.0.2, 20.0.0.5, 20.2.0.70 and 20.2.0).

**Fixed.** `buildSceneModel` treats the file as untrusted. Limit: every coordinate, translation, scale and matrix entry is finite and at most 1e7 (a Skyrim world is about 1e5 units across). A node whose own transform is not usable is placed as if it had none; a node whose world transform leaves the limit is placed with its parent (so a long chain of large scales cannot overflow); a shape with a vertex outside the limit, a triangle list that is not a multiple of three or an index past its vertices is left out; non-finite normals are dropped; a bind transform that is not usable gives no bone point; `bindBonePosition` returns the origin for a NaN scale or translation. All with one warning each (at most 32, then "and N more"). 13 hostile-input tests (`MeshSceneModelHostile` in `testscenemodel.cpp`): **8 of 13 red first**; the five that passed pin what the code already did (self-parent, a three-node cycle with a leaf, indices outside their arrays, a texture set outside its array, a 200,000-deep chain walked without recursion). `MeshScene::loadScene` now catches an exception from `buildSceneModel` and reports it as a load error (a `bad_alloc` can no longer leave `load()`), resets `mObject` (a stale engine object would have been drawn as the model) and `load()` starts by clearing `mFromScene`, `mSceneBones` and `mSceneHierarchy`. Loading a second file into one `MeshScene` is still not supported (`finishLoad` adds a new root without removing the old one); this only stops stale state. Not testable here: `MeshScene` needs a GPU host, so the try/catch and the resets are by reading, built but not run.


### Record loading, first slice (2026-11-10; same hand wrote tests and code, no fresh reviewer; Windows only, local commit, not pushed)

**What was built.** A game-neutral, engine-type-free model of Skyrim SE records inside the pack: `game_packs/skyrimse/include/game_skyrimse/records.hpp` and `src/records.cpp` (plain structs, no ESMStore, MWWorld, renderer, Jolt, Qt or OSG type; nothing is wired into the engine). **Hostile input.** Every subrecord size is checked against the bytes left in the record (XXXX handled), strings, lists and the record's inflated size are capped (`ParseLimits`: 16 MiB a record, 4096 entries a list, 64 KiB a string, 256 errors kept and the rest counted), a bad record is a located `Content::Error` (file, record offset, type, message) and the walk goes on, a damaged file keeps the records before the damage (`mWalkError`), string tables check counts, offsets and lengths against the bytes before anything is allocated. **2. Rotation convention, settled by terrain (X and Y are no longer RECALLED-VERIFY).** The first idea, scoring candidate conventions by how deeply the oriented bounding boxes (OBND) of tilted statics penetrate their neighbours in interior cells, **does not discriminate**: 60,151 tilted statics in 599 interiors, 99 percent of them penetrate a neighbour by more than 10 units under every one of the 48 candidates (6 axis orders x 8 sign choices), mean depth 184.8 to 186.3: interlocking kit pieces and loose bounds hide it. The method that works: placements on sloped ground are aligned with the terrain by the level designers, so the right convention turns an object's up axis (R * +Z) toward the terrain normal. The throwaway tool (`tools/skyrimcell_check/rotation_ground.cpp`, built by hand, not in CMake) reads the LAND heights (VHGT: 33 x 33 signed bytes of gradient, row offsets, times 8, 128 units a step) of Skyrim.esm's Tamriel (11,186 land cells), takes the normal from central differences at each placement, and keeps statics, movable statics, trees and flora that stand within 150 units of the ground on slopes (normal z below 0.995). **79,340 placements (tilt 0.05 to 0.90 rad), mean angle between the up axis and the terrain normal:** untilted 0.357 rad; **X applied first, then Y, then Z, every angle negated (Rz * Ry * Rx) 0.2029 rad, closer than untilted for 81.3 percent**; the same signs with Y before X 0.2042; X negated and Y not 0.438; Y negated and X not 0.455; **no sign flipped, both positive 0.627 rad (7.2 percent closer)**; every other order is worse than untilted or about equal (YZX 0.313, XZY 0.336, XYZ 0.413). Tilts of 0.3 to 1.2 rad (31,921 placements): 0.237 against 0.480 untilted, 82.8 percent; 0.6 to 1.5 rad (7,556): 0.482 against 0.610, 66.4 percent, and X-then-Y beats Y-then-X (0.482 against 0.497), so the order is also supported where it matters. The Z sign cannot be seen this way (a turn about Z does not move the up axis); it stays settled by the frame of the inn (earlier slice). **The convention in `placementMatrix` is confirmed unchanged: Rz * Ry * Rx with every angle negated**, and it is the one `components/misc/convert.hpp` `makeOsgQuat` and `MWWorld::makeDirectNodeRotation` apply to the TES4-family references the game loads (read in this tree, not tested).
