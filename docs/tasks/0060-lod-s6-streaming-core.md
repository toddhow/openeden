## What S0 and the clients so far told us

- **The hitches are the target, and they are not attributed.** Note 0025 section 4: in the fast flight with nothing distant, 11 of 18 border crossings gave a frame over 25 ms (27.3, 110.0, 32.0, 51.8, 43.7, 74.3, 27.5, 25.8, 27.6, 60.1, 27.7 ms) and every frame over 25 ms sits on a rise of the loaded-cell count, in bursts of three cells; the median frame during the flight is 2.0 to 2.1 ms, so the stalls are rare and large. "The hitch cannot be pinned to a part of the load (no timestamps inside it); S6 adds them." The second row of that table (distant terrain and object paging on) ended at a crash in the deletion queue, fixed in task 0054; the same flight with the fix has not been recorded with tiles and clusters on.
- **The frame is CPU-bound** (3.87 ms wall against 0.35 ms GPU main pass at 30000 view). Streaming must therefore save CPU on the main thread, not GPU time.
- **Memory is not the pressure on this machine** (716 to 793 MiB resident, 219 to 252 MiB device). Budgets matter for weaker cards and the software device; with tiles and clusters on, Balmora grew to 953 MiB resident and 269 MiB device (task 0055 S1f) and a 12-cluster far ring added 49 MiB and 16 MiB (task 0059 stage d). So the budget logic has to be correct and cheap now, and tested with small numbers, even though it will not bind on the RTX 4070.
- **The software device** (note 0025 section 6) is a single queue family (graphics, compute, transfer, sparse), memory budget extension present: it proves "runs at all" and memory behaviour, nothing about GPU speed.
- **What the first clients do today** (so S6 replaces it): `LodTerrain` reads every tile once at start on one `std::async` worker and builds at most 4 tiles a frame on the main thread (task 0055 S1d); `LodClusters` opens the pack and reads each tile's header on a worker, then `readCluster` and texture reads per wanted tile on `std::async` (`lodclusters.cpp`, lines near 228 and 575), with a `DecodeBudget` of 512 MiB per read (line 183), and builds and compiles one tile a frame on the main thread; tile load mean 4 ms, worst 12 ms (task 0059 stage d). None has priorities, a queue, cancellation, a memory budget or eviction.

## What the cell loader does today (read from the code; the hypothesis list for stage a)

Facts, with file and function:

- `Scene::changeCellGrid` (`scene.cpp` line 593) unloads cells outside the grid, then loops over the cells to load, nearest first (`sortCellsToLoad`), and calls `Scene::loadCell` for each **on the main thread**. A border crossing therefore loads a row of three cells inside one frame.
- `Scene::loadCell` (line 404) does, in order: `getLandManager()->getLand` and the Jolt height field (`mPhysics->addHeightField`), `mNavigator.addHeightfield`, the pathgrid, local scripts (`getLocalScripts().addCell`), `cell.respawn()` when asked, `insertCell`, the window manager's `addCell`, water setup, `exteriorCellLoaded` (the sky-visibility field of task 0036).
- `Scene::insertCell` (line 935) walks every object of the cell with `InsertVisitor` and calls `addObject` for the renderer and for physics. For a static the renderer path is `Static::insertObjectRendering` -> `MWRender::Scene::insertModel` (`mwrender/scene.cpp` line 116), which calls `MWAnim::createObject` (a model read through the resource caches, a blocking read if the model was not preloaded) and then **`context.compileContext->compile(anim->node())` on the calling thread**, the main thread, once per object, before the object is added to the cell group.
- `RenderManager::changeCellGrid` (line 1902) calls `updateTerrain`, which calls `mTerrain->updateView(...)` and then `compile->compile()` on the main thread (line 1739); `Terrain::Paging::updateView` compiles on the main thread too (design doc 5.5).
- **Preloading exists and does the worker half** (`preloadcell.cpp`): `CellPreloader::preload` queues a `PreloadCell` on `mOperationThreads` (`[Cells] preload num threads = 1`, `rendermanager.cpp` line 266 `numLoadingThreads = 1`); its `operate` reads the land, each model with `vsg::read(mesh, nodeOptions)`, the animations and the collision shapes, and compiles the nodes through a **separate one-thread** `mCompileThreads` (`vsgUtil::CompileOp`, so a worker compile has a precedent here). It keeps what it read referenced for `preload cell expiry delay` after the last request (`CellPreloader::updateCache`, steady-clock time stamps, the cell cache holds 12 to 20 cells). `Scene::preloadExteriorGrid` requests cells that will be needed when the player nears a border, using the predicted position (`[Cells] prediction time`, `Scene::preloadCells` line 998).
- `vsgUtil::DeletionQueue::advanceFrame` (`deletionqueue.hpp`) releases the vector that expired **on the thread that calls it**, the main thread once a frame (`Engine::loop`); the class comment says objects are released "after the mutex is let go". When a cell unloads, its node tree reaches the queue and is freed on the main thread three or four frames later.

**Hypotheses for the 25 to 110 ms (none measured; stage a measures each):** (H1) the compile of every object of three new cells on the main thread when a model was not yet preloaded or its instance still has to be compiled; (H2) a blocking model or texture read on the main thread when the preloader had not finished (the preloader has one thread, and `preload exterior grid` only reaches `[Cells] preload distance` = 1000 units ahead); (H3) the terrain `updateView` compile on the main thread; (H4) Jolt `addHeightField` plus object body creation and the navigator's `addHeightfield`/`updateBounds` for three cells; (H5) freeing the unloaded cells' node trees in `advanceFrame`; (H6) scripts and Lua cell events (`addCell`, `cellLoaded` extension callback at the top of `loadCell`); (H7) the sky-visibility field. The spec does not guess which dominates; it builds the instrument first.

## Design, in plain language

Think of a conveyor belt with a sorting desk. Things the game would like to have (a terrain tile, an object cluster, a model, a texture level) are **requests**. The sorting desk (the **scheduler**) keeps them in order of urgency, drops the ones nobody wants any more, and gives the most urgent to **reader threads**, which fetch the bytes from the pack or the loose file and decode them. A finished item waits in a **ready queue** until the main thread has room: each frame the main thread takes a small slice, hands it to the GPU, and attaches it. A **budget** keeps the total memory below a limit by throwing away the least recently wanted items. Everything is counted so that we can see what it does.

**Requests and priorities.** A request is: a 64-bit key (the tile or cluster key of `components/lod/tilekey.hpp`, or a hash of a model path), a kind, a priority class and a score. Classes, highest first (design doc 5.2): **blocker** (the frame cannot draw correctly without it: the coarse ancestor of a tile about to be refined, a tile under the camera), **near** (inside the active grid), **visible** (chosen by the tile selection for the camera now), **prefetch** (chosen for the predicted camera), **background** (the baker's own reads and speculative warm-up). Within a class: larger pixel error first (the item that shows more of the screen), then smaller distance, then the key, so the order is deterministic. A request is **cancelled** if it has not started and is no longer wanted; one in flight finishes and its result goes to the cache (design doc 5.2). Duplicate requests for one key merge and keep the highest class.

**Prefetch from velocity** (design doc 5.9): the clients run their selection twice, for the camera now and for `position + velocity x T`. `T` is 1 s walking (the cell preloader's `prediction time`), growing with speed to a cap of 5 s when flying or fast travelling, clamped to the world; tiles chosen only for the predicted pose are **prefetch**. Cell adjacency: the cells next to the player's cell, in the direction of motion, are requested as **near** a cell border ahead of the crossing, the extension of what `preloadExteriorGrid` does with its fixed 1000-unit distance.

**IO and decoding.** The reads are positional and need no shared file position: `VFS::File::readRange` and `VFS::Manager::readRange` for loose files and uncompressed BSA (`Platform::File::readAt` on a handle opened for the call, `components/vfs/CLAUDE.md`, "Range reads"), and `EdenArchive::Archive::readRange(entryIndex, offset, size, destination, budget)` for pack entries (thread-safe; it checks the chunk hash and decodes the zstd chunk inside the call; `DecodeBudget` is not thread-safe, so each worker has its own). A compressed BSA or BA2 entry has no cheap range (the default opens the entry and decompresses it), so those reads are whole-entry and cost what they cost. The first version uses **one pool of reader threads** (`io threads`, default 2) that does the read and the decode in one call, because `Archive::readRange` already does both; a separate decode pool (design doc 5.4) is only worth it if `Archive` gets a raw-chunk read (the interface has `chunk()` metadata; whether a raw read exists is **verify**). Optional faster paths (overlapped IO, `io_uring`, DirectStorage) stay behind the same interface and wait for measurements (design doc D8); none is required. Buffers come from a **pool** of fixed-size blocks so that reading allocates nothing per request; the number of blocks bounds the memory in flight.

**The GPU upload.** Today VSG's `CompileManager::compile` runs on the calling thread and its transfers are recorded by VSG's `TransferTask` during the frame (`vsgUtil::CompileContext::onCompiled` -> `vsg::updateViewer`, `Engine::createCompileContext`). What I read in VSG v1.1.16's source (`build-jolt/extern/fetched/vsg/src/vsg/app/TransferTask.cpp` and `Viewer.cpp`): the transfer task keeps **one staging buffer per frame in flight** grown to the total of that frame's copies (`TransferTask.cpp` lines 419 to 485), submits one command buffer per frame (`transferQueue->submit`, line 546), and `Viewer.cpp` lines 513 to 522 picks the transfer queue as the first queue whose family has both TRANSFER and GRAPHICS flags (so a dedicated transfer-only family is not chosen; on a device with two queues in the graphics family the second is used, otherwise the main queue). All of this is **verify** against the pinned source before stage e, and I did not trace how a compile on a worker thread feeds it. The consequence for the design: VSG already has a staging buffer and a transfer submit, and **the controllable thing is how much we hand it per frame**. So the plan is (e1) a per-frame byte budget on the main thread, counted from the payload size of what is attached this frame (`hintMemorySize`, 8 MiB starting value, design doc 5.5), plus moving the `compile` call of tiles and clusters to a compile worker the way `PreloadCell` does (a compile of a detached subgraph; the attach to the scene graph stays on the main thread, the threading rule of task 0059); (e2) only if frame traces show upload spikes that e1 cannot spread, our own staging ring and, where the device report lists a transfer-only family, a separate queue. e2 means working below VSG's `TransferTask`; it is a deliberate non-commitment of this spec.

**Budgets and eviction** (design doc 5.7). Two budgets that do not trade with each other by accident: **geometry** (tile and cluster meshes and the compressed RAM cache) and **textures** (the object and terrain textures and tile albedo pictures). Total device-local memory comes from the device report (`memory.deviceLocalMiB`, the same figure task 0049 uses) and, where `VK_EXT_memory_budget` exists, its live budget (the frame counters already read it: `gpu_used_mib`, note 0025 section 1). Starting values: textures keep task 0049's static share (35% of device-local memory for the `auto` cap); streamed geometry gets 15% (a guess; Morrowind needs about 250 MiB with the far ring of clusters, note 0059, so on a 4 GiB card it is 600 MiB: never reached). Eviction is least-recently-**wanted** (a frame stamp set each time the selection wants the item, not a clock): when over budget the scheduler evicts unwanted items, oldest first, never an item wanted this frame and never a **pinned** one (the coarsest tile levels that together cover the map, and the tail mips of loaded textures). If everything unpinned is wanted and still over: first raise the texture floor (the downscaler's cap is "the global minimum mip", task 0049), then the tile error threshold, and only then fail requests (design doc 5.7); both with hysteresis. A freed GPU object goes to the `DeletionQueue`, so it lives as long as a queued frame may use it. Eviction is a main-thread decision so that it can never race with the selection.

**Texture mip streaming** (design doc 5.8) is stage h and later, and the highest risk. The container already lays out KTX2 texture entries tail first: chunk 0 holds the headers and the small levels, each larger level one or more chunks (archive spec section 10.2, the texture annex stub, draft, `layoutParamB` = levels in chunk 0). Vulkan without sparse images cannot add mips to an allocated image, so higher mips mean a new image and a copy; the design doc's recommendation stands (tile textures first, which are ours; pooled size classes for the active grid's textures; sparse residency only as an optional tier). Mod textures that arrive as plain DDS cannot be streamed by level at all today (no range index by level); they stay whole.

**Interaction with the existing preload code.** `CellPreloader` and `Terrain::Preload` are not removed. Stage g routes their reads through the same scheduler as class **near** (the cell under the player or the one a teleport door leads to: **blocker**), so one queue orders all the loading, but only after stage a has shown that is where the time goes.

**Instrumentation.** `ctr_*` columns through `Render::FrameCounters` (requests queued, started, finished, cancelled, per class; bytes read, decoded; upload bytes this frame; items resident and bytes per budget; evictions; cache hit rate), a **trace** of named scopes with begin and end in microseconds from a monotonic clock, written only to a diagnostic file and never used by any decision (the determinism rule applies to the scheduler's ordering, not to a log), and one summary log line every 10 seconds when `[Streaming] log` is on. A frame over `hitch threshold` (default 25 ms, the note 0025 threshold) writes the scopes that ran in it. An on-screen overlay is a separate decision: whether MyGUI has a debug window to extend is **verify** (the root guide notes the profiler overlay as not done in task 0017).

## Graphics tiers and weak GPUs (what degrades)

| Setting | Low | Medium (default when enabled) | High | Why |
| --- | --- | --- | --- | --- |
| `io threads` | 1 | 2 | 3 | fewer than 4 cores or a slow disk |
| `decode`/read pool concurrency of the CPU side | 1 | min(cores - 2, 2) | min(cores - 2, 4) | the main thread and the render threads come first |
| `upload bytes per frame` | 2 MiB | 8 MiB (design 5.5) | 16 MiB | no dedicated transfer queue (the software device has one family) means copies share the graphics queue |
| `prefetch seconds` (walking, flying cap) | 0.5, 2 | 1, 5 | 1.5, 8 | fewer prefetches on a slow disk cost fewer reads |
| `compressed RAM cache` | 64 MiB | 128 MiB | 256 MiB | the whole Morrowind LOD set is about 200 MiB on disk (notes 0055, 0059) |
| `geometry budget` | 8% of device memory | 15% | 20% | low VRAM: raise the tile error threshold first |
| Behaviour when over budget | raise texture floor, then tile threshold | the same, slower to recover | the same | design doc 5.7 |

These are starting values, **to be measured**; the tier is picked by the same `quality tier` setting as the rest of the LOD system (design doc 8.1). A missing optional feature turns off only that feature (design doc 8.3): no memory-budget extension means the budget is a fraction of the reported heap; no second queue means the byte budget is the only protection.

## Constraints

- **Determinism.** The scheduler's choice depends on (class, score, key) and on the frame stamp, never on a clock or on thread timing; two runs of the same camera path request the same keys in the same order (the order they finish in is not promised). No iteration over an unordered container where order matters. The trace uses a monotonic clock for display only.
- **Allocation.** No heap allocation in the per-frame path (selection, queue operations, budget accounting, the upload slice); the queue, the buffer pool and the counters are sized at start (a limit counted when hit, never grown silently).
- **Threading** (say it in each stage): the scheduler's `request`/`cancel`/`poll` are main-thread calls; reader threads run `Source::read` and push to a lock-protected ready queue; the compile worker runs `CompileOp` on detached subgraphs; scene-graph attach and detach, eviction and the byte budget run on the main thread; `DeletionQueue` stays mutex guarded; no raw pointers to GPU objects cross threads, only keys.
- **Untrusted input.** Pack bytes are checked by the container reader; the scheduler caps sizes per request kind and fails a request whose decoded size exceeds its cap; a failed request is counted, logged once per key, retried after a cool-down of 600 frames like the clusters' (`lodclusters.cpp` line 49) and the live path stays.
- **Off means unchanged.** With `[Streaming] enabled = false` no thread of this module starts, no counter column is added, `CellPreloader`, `Terrain::Preload`, `LodTerrain` and `LodClusters` run their present code; compared by a frame of the Balmora pose (0.000 percent of pixels over 4 grey levels, as task 0059 did) and the 32 Lua tests. The trace and counters are separate settings (`trace`, the existing `frame counters`) and off by default.
- **Units.** World units for distances, bytes for budgets, frames for ages; no wall-clock in decisions.
- **No game assets in the repository.** Tests use generated packs and loose files.
- New files under `components/` use lowercase letters and digits only. New strings in settings comments only; no new UI strings in this task (a launcher/in-game status line is task 0058's and S8's).

## Risks and open questions

1. **Worker-side compile in VSG 1.1.16.** `CompileManager` and the `TransferTask` it feeds were designed around the viewer's own threads; `compile` from a second thread works for the preloader (one compile thread, `numCompileTraversals` = 1 as the `CompileContext` comment requires). Whether a tile compiled on that thread and attached next frame can ever draw a frame with its data not yet uploaded is **verify** (the "geometry never uploads" class of failure of research note 0003, section 5.4, is the thing to avoid).
2. **The hitch may not be on the main thread's own code.** If stage a shows the stalls are `vkQueueSubmit`/present waits, nothing here helps and the spec's stage g becomes a report.
3. **A single reader pool and slow legacy archives.** Compressed BSA entries decompress whole; a scheduler that reads one huge entry blocks a thread. Mitigation: entries above a size are read by a thread reserved for them (decision when measured).
4. **DirectStorage, `io_uring`, memory mapping** are deliberately not here (design doc D8; mapped files also break the "delete at will" rule of design 4.7).
5. **Interplay with S8.** The baker's reads are class background; the launcher page's status contract is task 0061's.
6. **Dedicated transfer queue is not what VSG picks** (`Viewer.cpp` line 513 requires TRANSFER and GRAPHICS flags together): on devices with a transfer-only family e2 needs VSG changes or a replacement of `TransferTask`. **verify** and decide at e2.
7. **Prior art, from memory and not checked:** Unreal's texture streamer works to a pool size and drops mips under pressure; Unreal's World Partition streams cells around "streaming sources" by distance; Cesium's 3D Tiles refinement uses screen-space error with a request queue sorted by importance and cancels requests that are no longer visible. The design above is the same shape; none of it is a source for a number.
