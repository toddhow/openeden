## Design
- **Capabilities by kind.** The loader sets a capability mask from the manifest kind before `register`; `Host` returns the privileged services only if the mask allows. A feature extension that asks gets `nullptr` and may refuse to start. Tested both ways.
- **One game pack per session.** The loader refuses a second `kind: "game"` pack (clear error naming both); the game host takes `game=<id>` from `openmw.cfg` (profile line) and refuses a pack whose id differs.
- **SDK 4.0** (`kSdkVersion` {4,0}). The reasons are in the design doc, section 6; 3.x extensions are refused with "built for SDK 3.0; this host provides 4.0" (the pattern of decision 0006), the extensions in this repository are rebuilt, and `CI/check_extension_sdk.sh` is updated to know the new rule and to forbid a feature extension including a game-only header.
- **Static first.** `game_morrowind` (task 0085) is linked into the game through the same `Registrar` as a loaded pack; the test pack proves the dynamic route (an ordinary shared library on Windows and Linux, ABI phase A).
- **Save chunk service.** Named chunks keyed `{packId, chunkName, version}`; writes and reads on the main thread only (the existing `SaveGame`/`LoadGame` worker discipline in `apps/openmw/CLAUDE.md` applies: the pack's callbacks are invoked from the thread that serialises; the contract states it); unknown chunk of a missing pack is preserved on re-save (the property decision 0005 removed for extensions returns here for game packs). The Morrowind byte format is not touched by this task.
- **Contracts carry no third-party types and no implementation**; the record store and content loader sketches in the design doc are fixed here as signatures with tests against fakes.

## Constraints
- The core starts, runs N steps and shuts down with zero extensions **and** zero game packs (the empty-host test exists for extensions; it is extended).
- Determinism: pack load order by dependency, then manifest id; the determinism gate runs with packs discovered in a different order.
- Allocation: game-phase callbacks and contract calls per step allocate nothing (the allocation gate extended).
- No exception crosses the pack boundary; a faulting game pack is a session error (design doc 7).
- Off by default: a game host with no `game=` line behaves as today (Morrowind's code is still compiled in until task 0085 moves it, so "no game pack" is the existing path).

## Acceptance criteria
- [ ] Manifest v2 parsing, validation with located errors and canonical round trip (byte for byte); v1 manifests unchanged
- [ ] Capability tests: a `feature` extension asking for each privileged service gets `nullptr`; a `game` pack gets them; a `compatibility` pack gets what extensions get; the second game pack is refused
- [ ] Lifecycle tests: register, resolve, start, stop in the documented order with a game pack; the game phases run before the extension phases of the same name; a failing game pack ends the session with its id in the message and refuses saving
- [ ] Save chunk round trip with the test pack: write, read, unknown-pack chunk preserved on re-save; a save naming another game is refused cleanly
- [ ] Empty host with zero extensions and zero game packs: identical to before (the existing test, plus a frame-count comparison); `extension` gates (determinism, allocation, boundaries) pass
- [ ] `CI/check_extension_sdk.sh` and `CI/check_layer_rules.sh` pass; every in-tree extension rebuilt against SDK 4.0
- [ ] All unit tests and the 32 Lua tests pass; Morrowind plays the same (the three extension game checks under `tools/extension_*_check/` pass with `compat_morrowind` enabled)
- [ ] Linux `-Werror`, sanitizers, and the pitfall "a contract in an anonymous namespace" avoided (named namespaces; the Linux build proves it)
Out of scope: moving any Morrowind code; GUI windows and Lua descriptor services (stubs with the contract only, finalised in task 0085); a stable C ABI (P6); dynamic loading of `game_morrowind`.

## Open questions (recommendation first)
1. SDK 4.0 or 3.1? Recommend 4.0 (design doc section 6).
2. Is `compat_<game>` required to exist next to `game_<game>`? Recommend no: a game pack declares `requires` on the compatibility pack's contracts if it needs them.
3. Are game phases separate from the existing phases, or do game packs simply register in them with higher priority? Recommend separate, so the order is explicit and testable.

## Answers to the open questions (taken as recommended, toddhow away, 2026-11-06)
1. **SDK 4.0**, not 3.1. `kSdkVersion` is {4, 0}.
2. **No** `compat_<game>` is required next to `game_<game>`. Nothing in the loader looks for one.
3. **Separate game phases** (`Phase::GameSimulation`, `Phase::GameUpdateUi`), and in addition a game pack's callbacks in any other phase run before the other kinds' callbacks of that phase (see the stage log).

## Stage log (2026-11-06)
Names: the manifest `kind` values are the ones the tree already uses, `feature`, `compatibility` and `game` (the task text says them so; the hand-over used `extension` and `compat`, which are not accepted).

**Decisions taken where the spec was open** (each is a one-line change if toddhow wants otherwise):
- The game services are **not** handed out by `HostImpl::getXService()`. `LifecycleManager` gives each extension's `start()` its own `PackScopedHost` (`components/extension/pack_host.*`) that forwards everything except the five game services, which only `kind: "game"` gets; a request from another kind returns `nullptr` and is listed in `LifecycleManager::getCapabilityDenials()` with the extension, its kind and what it asked for. The game pack's save chunk service is scoped to its pack id. A Host that is not a `HostImpl` is forwarded to as-is.
- SDK headers are in `sdk/include/openeden/game/` (`save_chunks.hpp`, `records.hpp`, `content.hpp`, `script_host.hpp`, `ui.hpp`) and `sdk/include/openeden/pack_kind.hpp`, not under `contracts/`: they are services of `Host`, not contracts looked up through the registry, and one folder lets the CI check forbid a feature extension to include them. `game_rules.hpp` is **not** written: its calls come from `MWBase::MechanicsManager` by removal of what is Morrowind-only, which is task 0085's work.
- Records, content, script host and windows are real but small: the record type table (register, find), loaders asked in order (`probe` only), declared script languages, declared window ids. The Lua descriptor service is **not** built (the check script still forbids Lua words in the SDK).
- Manifest format **2** adds the kind check (`feature`, `compatibility` or `game`, located error otherwise); `game` needs format 2; format 1 reads exactly as before. The in-tree manifests stay format 1.
- One game pack per session: the first by ID is the session's, any further `kind: "game"` pack is refused in `LifecycleManager::initialize()` with a failure naming both (stage `game`); it is not a session error. The game host takes `game=<id>` (`openmw.cfg`, `--game`): only that pack loads, even if not in `extension=`; any other pack of kind game that is enabled is refused with a message at the main menu; with no `game=` line none loads. Packs are also searched in `game_packs/` (local and user data).
- A game pack failing at any stage (resolve, start, a phase, a dependency) sets `LifecycleManager::getSessionError()` ("Game pack 'x' failed at <stage>: <reason>. The game cannot go on and saving is refused."), makes `SaveChunkServiceImpl::collect()` fail with it, and `StateManager::saveGame` refuses with a message box. The game does not stop by itself yet: that needs a game pack to exist (task 0085).
- Phases: in `Game::run`, `GameSimulation` runs just before `PreSimulation` (unpaused), `GameUpdateUi` just before the window manager's update (also paused). A callback registered for them by another kind is refused and listed as a denial. In every phase the game pack's callbacks run first.
- Save chunks: `SaveChunkServiceImpl` writes chunks in registration order, then the preserved chunks of packs that are not loaded; `restore()` checks every chunk's version before any handler reads; an unknown chunk is kept and written again byte for byte; handler exceptions become a refusal naming the pack and chunk. `encodeChunks`/`decodeChunks` give canonical bytes with caps (a hostile count or size is refused). **Not hooked into `.omwsave` yet**: no pack writes a chunk and the Morrowind byte format is not touched.
- Save header: `ESM::SavedGame` gets `mGamePackId` and `mGamePackVersion` (subrecords `GPCK` and `GPVR`), written only when a game pack is active, so a save made with none is byte for byte what it was. `LoadGame::verifyProfile` refuses a save of another pack, of a pack when none is loaded, or of a newer pack version (`checkSavedGamePack`); a save with no recorded pack always loads.
