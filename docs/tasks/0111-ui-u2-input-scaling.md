# Task: UI system U2, input, GUI scaling, resize and the Slang twins of the overlay

Status: **APPROVED BY DIRECTION** (toddhow, 2026-11-10: U1 as a parallel track; decision 0015 ACCEPTED; U1's task 0104 leaves exactly these items open; decision 2 of its follow-up: Slang twins of `rml.vert/frag` come with U2).
Design doc section: `docs/decisions/0015-ui-system.md`; `docs/research/0045-ui-system.md` sections 13 to 16 (U0, U0b, U0c: IME hooks 14.5, controller bridge 15.7, scaling 15.3 and 15.10).
Goal: the RmlUi overlay (`[GUI] rmlui`, off by default) takes mouse, keyboard, text (with IME composition) and controller input only where it should, follows the game's GUI scaling factor and the window size, and draws with Slang twins of its two shaders when `[Rendering] slang shaders` is on; with `rmlui` off nothing changes.
Inherited code touched: `apps/openmw/mwinput/inputmanagerimp.{hpp,cpp}` (the three event callbacks of `SDLUtil::InputWrapper` are now a thin filter, `UiInputFilter`, which forwards unchanged when no overlay is set); `components/sdlutil/events.hpp` and `inputwrapper.cpp` (a `KeyListener::textEditing` virtual with a do-nothing default, called for `SDL_TEXTEDITING`; before it was read and dropped); `apps/openmw/vsgengine.{hpp,cpp}` (hands the input target to the input manager, the scaling factor to the overlay, text-input sync once a frame); `components/ui_rml/renderinterface.cpp` (twins together or neither); `files/shaders/CMakeLists.txt` and `apps/components_tests/vsg/testslangpermutations.cpp` (two stages added to the exact list). Nothing in `mwgui` or `myguiplatform` is changed: MyGUI is not touched.
Inputs / outputs: new in `components/ui_rml/`: `uiscale.*` (scale mapping), `inputmap.*` (SDL to RmlUi key, button and modifier tables, controller button mapping), `inputrouter.*` (who gets which event: pure), `ime.*` (composition over `Rml::TextInputContext` and the `TextInputHandler`), `inputtarget.hpp` (RmlUi-free interface the engine talks to), `Overlay` implements it; `files/shaders/gui/rml.slang`; `.interface` records of `gui/rml.vert` and `gui/rml.frag` (golden data).
Constraints:
- **Off is unchanged.** With `[GUI] rmlui` off no filter target is set, so every SDL event takes exactly the path it took (verified: same executable, fixed frame time, seed, frames byte-identical; and a synthetic input script gives the same game state).
- **Thread rule.** RmlUi runs on the GUI recording thread only. Input is queued from the main thread (mutex, bounded), and applied at the start of that thread's frame; the routing questions the main thread needs ("is the cursor over a document", "is a text field focused", "is a control focused") are answered from atomics the frame publishes (one frame old at most). Text-input start and stop (SDL, main thread) is a flag the frame sets and the engine's per-frame sync acts on.
- **Routing rules (decision for the record).** (1) Mouse move goes to both RmlUi and MyGUI/the game: the game tracks the cursor position and mouse look from it; a MyGUI widget under an overlay panel may highlight (limitation). (2) A press goes to RmlUi only if the cursor is over a document element that takes pointer events (`Context::IsMouseInteracting`, so a full-screen document sets `pointer-events: none` on its `body`); that button is then captured by RmlUi until released: its release, and nothing of it, reaches the game. (3) The wheel goes to RmlUi if the cursor is over such an element. (4) Keys, text and IME go to RmlUi only while a text input has focus there; a focused button does not take game keys. A key press consumed by RmlUi has its release consumed too, and a press the game saw has its release go to the game even when focus has moved since. (5) Controller: a document opts in with `nav-capture` on its `body`; while a focused element is inside such a document the d-pad, A, B and the right stick go to RmlUi (arrows, Return, Escape, wheel) and not to the game. (6) Escape in a text input removes the focus. (7) Nothing reaches RmlUi when it has no documents. (8) Only in GUI mode (the game shows its cursor, `WindowManager::isGuiMode`): in game mode the mouse is relative and its position means nothing, so nothing counts as over a document, and a focus the overlay still holds (a text field when a script closed the GUI mode) is let go once (`InputTarget::blur`) and no key, text or controller event is routed to it, so the game never loses its keyboard to a stale field. (9) The state the router reads is the one the frame thread published at the end of its last frame, so a press that comes in the same input update as the move before it is decided with the old hover; a user's moves come frames earlier, and the in-game script leaves two frames. (11) A press that is not the overlay's (not over a document) drops the focus the overlay holds, as a click away from a text field would in any UI; the press itself goes to the game. (10) The wheel the overlay takes is also removed from the move event that comes with it (`MouseMotionEvent::z` and `zrel`), since the mouse manager forwards the running total to MyGUI with every move.
- **Scaling.** The context stays in framebuffer pixels; `Context::SetDensityIndependentPixelRatio` takes `[GUI] scaling factor` (clamped to 0.25 to 8; not finite becomes 1); markup sizes are written in `dp`. Whole-number scales of the bitmap font draw nearest, others linear (`chooseSize`, unchanged). Mouse coordinates are framebuffer pixels (SDL's), not divided by the scale.
- **Resize.** The overlay follows the swapchain extent that `Engine::frame` already hands it each frame; the context size is reset when it changes.
- **Hot path.** The queue and the snapshots are preallocated; no allocation per event in the router.
Acceptance criteria:
- [ ] Pure tests written first (red against stubs): scale mapping; key, button and modifier tables (every SDL key RmlUi has an identifier for; unknown stays unknown); the router (every rule above, captured buttons, key release pairing, controller capture, nothing routed when disabled); the IME composition against a fake `Rml::TextInputContext` (start, update, commit, cancel, unicode).
- [ ] In a quiet-window game, synthetic SDL events (`SDL_PushEvent` from a test hook) click the panel's button (log line and counter), type into its text field (the field's value), scroll its list with the wheel, move controller focus between two buttons with the d-pad and activate one with A; the same click over a spot with no panel reaches the game (the MyGUI cursor position follows) and the game's keys are not consumed while no text field is focused. Frames viewed at scale 1, 1.5, 2 and after a window resize.
- [ ] `rml.vert` and `rml.frag` have Slang twins; `SlangPermutations` and `SlangInterfaceRecords` pass; the overlay frame with `slang shaders` on equals the GLSL's frame within the noise of two GLSL runs.
- [ ] `rmlui` off: byte-identical frames, same executable.
- [ ] `CI/check_layer_rules.sh` at 104 or fewer; the other `CI/check_*.sh` that need no Docker pass; test files registered.
Out of scope: the element protocol and the Lua component library (U3), render to texture, gamepad virtual cursor, clip masks, layers and filters, text selection with the mouse across documents, the Linux link and run, the real IME of an operating system (synthetic `SDL_TEXTEDITING` only), a real controller.

**Clipboard design.** RmlUi asks for the clipboard on the GUI thread; SDL wants it on the main thread. `ClipboardBridge::setFromUi` stores the text (the UI sees it at once) and queues it; `Overlay::syncTextInput`, once a frame on the main thread, writes it (`pump`). A paste: `Overlay::key` runs on the main thread when a key arrives, and when it is a paste chord (Ctrl+V, Command+V, Shift+Insert: `isPasteChord`) it first reads the system clipboard (`refresh`, which writes a waiting copy before reading, so a paste right after a copy gets the copy), then queues the key. Texts are cut at 1 MiB on a UTF-8 boundary. So no SDL call is made from the GUI thread.
