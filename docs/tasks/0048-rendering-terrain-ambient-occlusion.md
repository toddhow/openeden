# Task: Rendering, ambient occlusion on terrain
Design doc section: `docs/research/0008-modern-rendering-proposal.md`, section 5 (R2); builds on `docs/tasks/0029-rendering-ao.md` (the pass, "What was built": "Terrain writes zero ambient (D5 changed)"), `0036-rendering-gi-exterior-sky-visibility.md` (the exterior ambient the terrain uses), `0044-rendering-pbr-rmaos-textures.md` (the terrain's occlusion from `_rmaos`) and `0027-rendering-f4-material-model.md`. `docs/decisions/0010-rendering-and-studio-answers-2026-11-01.md`, answer 6 ("add terrain AO").
Goal: with `ao` on, the terrain is darkened by ambient occlusion like every other opaque surface, so that the ground gets contact darkness under rocks, walls, roots and cliffs and in hollows, objects no longer look as if they float on ground that does not react to them, and nothing that is already darkened (the `_rmaos` occlusion, the exterior sky-visibility field) is darkened twice by mistake.

## What is there now (read from the code)

- Task 0029 made ambient occlusion remove only the **ambient part** of each pixel's colour: the main pass writes that part to the G-buffer output `outAmbient` (location 5, `GBUFFER_AMBIENT`), and the tonemap computes `colour - ambient * (1 - ao)` (`Render::Ao::removeOcclusion`). A pixel whose `outAmbient` is zero therefore receives no occlusion, whatever the AO image says.
- The object shader writes it (`default/main.frag`: `ambientPart = outColor.xyz * (ambientLight * getAmbient(vertexColor) * pbrAmbientScale)`, scaled by the fog's share at line 472, written as `vec4(ambientPart, 1.0)` at 516).
- The terrain shader declares the output and writes `vec4(0.0)` (`terrain/main.frag`, the end of the `GBUFFER` block), and its comment says "the terrain has none (it takes no ambient occlusion)". Task 0029 recorded it as "Terrain writes zero ambient (D5 changed): it is occluded by nothing, but it still gives depth and normals, so it occludes others."
- The terrain's own lighting: in the `TERRAIN_PBR` path (`pbr material maps`, task 0044) `outColor *= materialTermsScaled(terrainAmbient, diffuse, vertexColor, terrainDiffuseScale * terrainS.occlusion, terrainDiffuseScale)` where `terrainAmbient` is `scene.ambient.xyz`, or `skyVisAmbient(...)` under `GI_SKY` (task 0036), and `terrainS.occlusion` is the blend of the layers' `_rmaos` blue channel (1 when a layer has no map). In the other path it is `materialTermsAmbient(skyVisAmbient(...))` under `GI_SKY` or `materialTerms(diffuse, vertexColor)` (ambient `scene.ambient.xyz`). `getAmbient(vertexColor)` is the material's ambient colour term, and `vertexColor` here is the land colour map. Weather effects (wetness darkening, snow and ash cover) change `outColor.xyz` **before** this lighting multiply, so the texture colour the lighting is applied to already includes them.
- Terrain depth and normals already enter the G-buffer, so terrain already occludes other pixels in the AO image (an object next to a cliff is darkened by it); what is missing is the other direction. The AO image is computed at half resolution from linear depth and normals; the terrain's stored normal is the **normal-mapped** normal when `TERRAIN_MAPS` is on (`outNormal = vec4(viewNormal, 1.0)`) and the geometry normal otherwise.

## Design, in plain language

The fix is small in code and has three places where it can go wrong, which is what this spec is for.

**What to write.** The terrain pixel's ambient part is "the colour the ambient light alone would give". That is, at the point where the terrain shader multiplies `outColor` by the lighting terms, the ambient part is the texture colour at that point (what `outColor.xyz` holds just before the multiply) times the ambient light the terrain really used times the ambient colour term times the scale the terrain really used (diffuse scale times the `_rmaos` occlusion, in the PBR path; 1 in the other paths). Writing exactly what `materialTermsScaled` and its siblings add as `ambient` keeps the subtraction in the tonemap exact: the pixel's colour then contains `ambientPart` as a summand, and AO removes `(1 - ao)` of it, never more than it has (a test pins that `removeOcclusion` never goes negative). It is the same rule the object shader follows, written once for the terrain.

**Double darkening, case by case.** Three things can already darken the terrain's ambient: the layer maps' `_rmaos` occlusion (a baked, per-texture crevice term, for example the dark joints between flagstones), the sky-visibility field (task 0036: how much sky the point sees, baked per exterior cell, so it already darkens under cliffs, trees and eaves at 256-unit resolution), and the new screen-space AO (small, close-range contact shadows at 100 units). They answer different scales (texture, building, contact) and the screen-space AO is a smaller-scale companion to the other two, so some overlap is expected and correct: it is the same thing objects have today (their ambient also includes `_rmaos` occlusion and the probe's own openness, task 0029 "What the next features must know"). The spec therefore does **not** try to remove one from the other, but it must make sure none is applied twice *by this change*:

1. The `_rmaos` occlusion is already inside `ambientPart` (as part of the scale), so the AO pass removes a share of an already-occluded ambient: fine, multiplicative, same as objects.
2. The sky-visibility ambient is the ambient light used, so it is inside `ambientPart` too. A cliff base that the bake darkened to 30% then gets screen-space AO on that 30%: darker still, but never more than `ao strength` says. If toddhow finds exteriors too dark with `gi exterior` and `ao` both on, the existing `ao strength` below 1 is the tool (documented in 0029 for `gi`); this spec adds no second knob.
3. **The fog.** The object shader scales the ambient part by the fog's share (`ambientPart *= applyFog(vec3(1.0), viewPos) - applyFog(vec3(0.0), viewPos)`) so distant, fogged surfaces keep the right fraction of ambient. The terrain must do the same or distant terrain would lose too much light when the AO image says "occluded" at long range; the terrain's fog function is the same `applyFog` (the shader already calls it), so the same two lines apply. A test of the CPU twin pins that a fully fogged pixel has zero ambient part.

**Which normal and which depth.** The AO pass reads the stored normals. For the terrain they are normal-mapped when `TERRAIN_MAPS` is on, so the fine detail of a rock texture's normal map would show in the AO as small-scale occlusion noise (the horizon search sees a bumpy plane). Two choices: write the geometry normal to the G-buffer for terrain when AO is on (changes what other effects that read the normal output see: the wetness and cover effects use their own normals; the G-buffer normal is used by the AO and the debug views, and by anything later such as screen-space reflections), or leave it. Recommendation: leave the output as it is and measure in stage c; the filter in the tonemap already weights neighbours by normal similarity, and the frames of task 0029 showed a plausible result on objects with normal maps. If the terrain looks noisy, the fix (the geometry normal, as `outNormal.w` already carries the roughness) is stage d.

**The sky and unlit terrain.** Nothing changes: terrain far away is the same shader; `ao` only reaches as far as `ao radius` in world units, which is small compared with the terrain's chunks, so distant terrain gets effectively no occlusion (the AO image sees almost no depth difference at a distance).

### Decisions toddhow can change (my recommendation first)

| # | Decision | Recommended | Alternative |
| --- | --- | --- | --- |
| D1 | What to write for terrain | The ambient part exactly as the terrain's lighting multiply adds it (texture colour times ambient light times ambient colour times the `_rmaos` scale), then the fog share | Write a flat estimate (`scene.ambient`), which would remove the wrong amount where the sky-visibility field changes the ambient |
| D2 | Setting | `ao terrain` (bool, true when `ao` is on): lets toddhow compare with and without in one build, and lets a user whose terrain looks too dark or noisy switch the terrain out | No setting: terrain always follows `ao` (simpler); or default false (conservative; contradicts decision 0010 answer 6) |
| D3 | Double darkening with `_rmaos` and the sky-visibility field | Accept the multiplication as for objects; no extra compensation; `ao strength` is the single control | Reduce AO where the sky-visibility value is already low (couples two systems; a later change only if frames show it is needed) |
| D4 | Normal used for terrain AO | The stored (normal-mapped) normal as now; revisit in stage d if noisy | Geometry normal for terrain when `ao` is on (changes the G-buffer output) |
| D5 | When the define is on | The terrain pipeline gets a new define `AO_TERRAIN` only when `ao`, `gbuffer` and `ao terrain` are all on (the same `Render::Ao::useAo` gate plus the setting); without it the shader writes `vec4(0.0)` as before | Always write the ambient part when `GBUFFER_AMBIENT` exists (slightly more ALU for users with `ao` off and `gbuffer` on) |
| D6 | Terrain without `pbr` | Works: the non-PBR branch has the same ambient expression with scale 1 | Require `pbr` for terrain AO |
| D7 | Coverage and wetness | Use the colour after wetness and cover (the shader's `outColor.xyz` at the multiply), which is how the lighting sees it | Use the base texture colour |

## The maths (stage a), `components/render/aomath.hpp`, namespace `Render::Ao`

- `vec3 terrainAmbientPart(vec3 textureColour, vec3 ambientLight, vec3 ambientColour, float scale, float fogShare)`: `textureColour * ambientLight * ambientColour * scale * fogShare`, with `scale` clamped to 0 or above and `fogShare` clamped to 0 to 1. Equal to the ambient summand of `materialTermsScaled` (a test builds the colour both ways for random inputs and compares).
- `bool useTerrainAo(bool ao, bool terrainSetting, bool gbuffer, bool materialOutput)`: `useAo(ao, gbuffer, materialOutput) && terrainSetting`.
- The existing `removeOcclusion` is reused unchanged; a new test shows that for a terrain pixel built from `terrainAmbientPart`, the result of `removeOcclusion(colour, ambientPart, 0)` equals the colour computed with no ambient light (so the part is exactly the ambient summand), and for `ao = 1` equals the colour.

Frames and cost.** Seyda Neen noon, a cliff base, a rock field and a forest floor, with `ao` on and `ao terrain` off and on; with `gi exterior` on and off; with `pbr material maps` on and off; the AO debug view `gbuffer debug view = ao` and `ambient` (the ambient view must now show the ground); GPU time with `gpu timing` and `tools/benchmark.sh` into a note (expected well under 0.1 ms: one more output value and a few multiplies per terrain pixel; the AO pass cost does not change because it already read terrain depth).

## Constraints

- Off means unchanged: with `ao = false`, the terrain pipeline gets no new define, the shader compiles to the same code as before (the `#else` branch writes `vec4(0.0)`), and frames equal the commit before by `diffmap` (Seyda Neen noon and night, Balmora exterior, `ToddTest` interior unchanged). With `ao` on and `ao terrain = false`, frames equal today's `ao` on frames exactly.
- No new image, descriptor, specialization constant or uniform; `Pipeline::Data::Scene` does not grow (640 byte hazard).
- No allocation per frame; threading unchanged (terrain chunks are built on workers, the define is set where the other terrain defines are).
- Shader conditions: one comparison per specialization constant, defines for everything new; check a frame after every shader change, as the last agents' blank-frame problems show.
- The editor's `SceneHost` never makes an `HdrTarget`, so it does not take this; it must keep building.
- Works with `hdr`, `gbuffer` and `pbr` (task 0029 D6), antialiasing 0 and 4.
