# Task: Eden Studio Editor Module API 1.2 (close the gaps two modules already hit)
Status: approved by toddhow on 2026-11-06 (his answers: 1 yes, the order selection and event bus, picking and dragging, labels, settings and tasks; 2 labels go through the SAME overlay path as lines and triangles, drawn by Studio's viewport and part of captured frames, not a Qt widget; 3 module settings live in `eden-studio.cfg` under `[module.<id>]`, matching `[extension.<id>]`; 4 dialogs and canvases wait until a module asks). Built 2026-11-06, stages a to f, local commits, the Linux gate not run (stage log at the end). Full loop (SDK headers and the module loader are in the full-loop list of the guide).
Design doc section: `docs/design/eden-studio-plan.md` sections 3.2, 3.3, 3.5, 3.7, 3.10, 3.11 and 8 (Phase 3); decision 0007.
Goal: grow the Editor Module API from 1.1 to 1.2 with the pieces the first two modules (`creativemotion_editor`, `advancedbodies_editor`) had to work around, so later modules (the push sandbox, ComplexClothing, the face timeline) are written against an API that has them.
Inherited code touched: none of OpenMW's world editing. New or changed: `sdk/include/openeden/editor_module/` (new virtual functions at the END of each interface, with do-nothing defaults, as 1.1 did), `apps/opencs/model/module`, `apps/opencs/view/module`, `apps/opencs/view/render` (picking of overlay items), the sample module.
Inputs / outputs: API version 1.2; a module built for 1.0 or 1.1 keeps loading (the version tests change only as 1.1 did: approval needed for the pinned lines); a 1.2 module is refused by an older host with a message naming both versions.
Constraints: determinism (no clock in the API); no allocation per frame in overlay submission beyond the existing `OverlayBuffer` caps; failure isolation unchanged (an exception in a module never reaches Studio); every addition off the hot path of the game (the game never loads editor modules).

## The gaps (from tasks 0032 and 0069 stage f)
1. **Picking and dragging of overlay data** (3.5): joint limits are editable only as numbers; a handle on a cone's rim needs the viewport to pick overlay items and call `Gizmo::drag` from mouse input, with an undoable edit on release.
2. **Labels** (3.5): the debug geometry has no text, so bone names appear as property groups instead of next to joints.
3. **Selection of a bone or entity** (3.7): the rig panel shows every joint; selecting a bone to show only its joint and highlight its gizmo needs a selection kind beyond "asset".
4. **Studio event bus** (3.10): selection changed, asset opened, simulation stepped, parameter changed, so modules stop polling.
5. **Settings pages** (3.11): a module's own preferences in Studio's preferences window.
6. **Background tasks** (3.11): a module can run a task off the UI thread with progress and cancel (the body cache read and the NIF dump block the UI today).
7. **Dialogs and canvases** (3.2, 3.3): not first priority; only if a stage needs them.

## Stages (each small, each with tests written first)
- **a. API shapes and the pinned version tests** (headers only; stubs in the host; the version message names both versions). The edited version tests need approval.
- **b. Selection and the event bus** (3, 4): a selection value the host owns and publishes; modules read it and subscribe; the rig panel uses it to show one joint.
- **c. Picking and dragging** (1): a pure picking function over overlay lines and triangles (ray to segment distance, ray to triangle), tests first; a drag session with an undo step at the end; the rig inspector's cone half-angle handle as the first user.
- **d. Labels** (2): text submitted as data like lines and triangles (position, string, colour), drawn by Studio's viewport as screen-space text; capped; no localisation in modules' strings yet.
- **e. Settings pages and background tasks** (5, 6): a module registers named settings with defaults (stored in `eden-studio.cfg` under its own namespace, like extension settings) and a task runner with progress and cancel on Studio's thread pool.
- **f. The sample module uses every addition**, as the reference and the test; the plan's Phase 3 text is updated.

## Acceptance criteria
- [ ] API version is 1.2; a 1.0 and a 1.1 sample module still load and run (tests build both against the old headers)
- [ ] A module built for 1.2 loaded by a 1.1 host is refused with a message naming both versions (test with `ModuleHost::setProvidedApiVersion`)
- [ ] Picking: a ray at a handle picks it within a pixel tolerance, the nearest wins, ties are decided by the item index (deterministic); a drag ends in one undo step; undo restores the value
- [ ] Selection and events: publishing and subscribing is single threaded on the UI thread, in registration order; an exception in a subscriber is contained and logged once
- [ ] Settings: defaults are written when absent, a value outside its declared range is clamped with one warning, the registered names are shown in the preferences window
- [ ] Background task: progress and cancel reach the task; the result is delivered on the UI thread; closing the document cancels its tasks
- [ ] `tools/edenstudio_check/check.sh`, `tools/bodypanel_check/check.sh` and `tools/modulecheck/check.sh` pass; `eden-studio-tests` and the Linux gate pass
- [ ] With no editor module loaded, Studio behaves exactly as before (the smoke check); the game and `openmw-tests` are untouched
Out of scope: NIF editing (task 0046), the push sandbox itself (task 0065), cell objects in the Jolt world, any change to the game's runtime, a C ABI for editor modules.

## Stage log (2026-11-06)

Every stage: tests written from the spec first and run red against a stub (stage a: the 1.2 types do not compile against the 1.1 headers, so its tests are red by construction; its version pins were red against the old number), then the code. Pure logic is in `csmodel`, no Qt types where avoidable, and tested without a display; the Qt and viewport glue is covered by the unattended checks. `eden-studio-tests` 877 pass on Windows. No new agents. Commits are local and not pushed.

**a. API shapes and the pinned version tests.** `kApiVersion` is 1.2 (`sdk/include/openeden/editor_module/types.hpp`, `registrar.hpp`). Added only: types `Selection`, `EditorEventType`, `EditorEvent`, `EventHandler`, `SettingDesc`, `TaskId`, `TaskControl`, `TaskOutcome`, `TaskDesc`; new virtual functions at the END of `EditorContext` (`selection`, `select`, `publish`, `setting`, `startTask`, `cancelTask`) and `EditorRegistrar` (`registerSetting`, `subscribe`), each with a do-nothing or refusing default naming "1.2". **Nothing a module implements changed** (`Gizmo`, `AssetDocument`, `PropertySource`, `Command`, `TimelineTrack`, `EditorModule`) and no struct that crosses the boundary (`GizmoHandle`, `PropertyDesc`, every `*Desc`): a new virtual function on a module-side interface would make the host read past an old module's vtable. So picking and dragging use the existing `Gizmo::handles()` and `Gizmo::drag()`, and the highlight is drawn by Studio. `OverlaySink::label` was already in 1.0 (its host side only dropped the call). Tests: `testapi12.cpp` (the new types and defaults, a context and registrar written for 1.0, a 1.2 module refused by a 1.1 and a 1.0 host with both versions in the message, 1.0 and 1.1 modules loaded by a 1.2 host), `testoldapimodules.cpp` (modules BUILT against the frozen 1.0 and 1.1 headers, two real shared libraries `sample_editor_module_api1_0` and `_1_1` from `apps/opencs_tests/oldapi/`: loaded by path, document, properties, gizmo, drag and track exercised through the old vtables, a 1.1 module refused by a 1.0 host).

**b. Selection and the event bus.** `EventBus` and `SelectionModel` (`model/module/eventbus.*`, 14 tests): handlers run in registration order across modules; a handler that throws is removed and reported once (the registry turns that into the module's withdrawal and message through its own failure path); events published from a handler wait behind the running dispatch, first in first out, with a cap of 256 (dropped events are counted); a handler or an owner removed during a dispatch is skipped; the selection publishes only when the value changes. `ModuleRegistry` owns the bus (`bus()`), `subscribe` belongs to the module being registered, `removeModule` removes its subscriptions (4 tests). `ModuleUi` implements `select`, `selection` and `publish`, clears the selection when an asset opens, and publishes `AssetOpened`, `SimulationStepped` (`PhysicsHub::tick`, once per fixed step) and `ParameterChanged` (a property form edit). **A fault found by the first check run:** a subscriber of Studio's own that emitted `changed()` ran before the modules' handlers, so the panel was rebuilt from the old selection; `ModuleUi::select` now emits after the bus is done, and panels and sections rebuild on `layoutRevision()` (asset or selection change) instead of `generation()` (which also reframes the Mesh view). CreativeMotion: `JointSelectable` on the rig document narrows the panel to the selected joint and draws it in the highlight colour; the module follows the selection, turns a click on a joint's handle into it, and has Next Joint and Previous Joint (10 + 1 tests).

**c. Picking and dragging.** `overlaypick.*` (ray to point, segment and triangle; a pixel tolerance as `pickSlope`; the nearest along the ray wins, ties go to the lower index, hostile input picks nothing; 18 tests) and `dragsession.*` (a drag on the camera-facing plane through the handle; every update undoes the previous preview and runs the gizmo's new command; `finish()` hands the last one over for the host to push, so one drag is ONE undo step; cancel, destructor and a throwing gizmo leave no preview applied; 10 tests). `ModuleUi::pressHandle/dragHandle/releaseHandle/hoverHandle` and `MeshViewWidget`'s mouse events (the press is consumed so the orbit does not start; a click selects `{"handle", id}`). The first user: CreativeMotion's cone half angle handles (`creativemotion.cone.plane` and `.normal` for the selected cone joint, `SetConeHalfAngleCommand`, the result checked with `validateRig`; 9 tests). In the real editor (synthetic mouse events on the Mesh view, `OPENEDEN_CS_HANDLECHECK`): hover highlights the handle, a press and eight moves drag the half angle from 0.785 to 0.882 (0 undo steps during the drag), the release leaves ONE step (0.877), undo restores 0.785, redo 0.877.

**d. Labels.** `OverlayBuffer::label` stores labels (printable ASCII, up to 64 characters, 256 labels, upper-cased; the rest refused or dropped and counted; 3 tests). Text is drawn through the SAME overlay path as lines: `labelstroke.*` turns a label into line segments of a built-in stroke font (a 4 x 6 glyph grid for A to Z, 0 to 9 and `. _ - : / + ?`, written for this project, nothing copied), 14 pixels tall at any distance, in the plane facing the camera, from a `LabelCamera` (`view/render/labelcamera.hpp`, from the view and projection matrices); `MeshViewWidget` and `WorldspaceWidget` lay them out again in `frameUpdate` when the view matrix changed (12 tests). Frames viewed: `I:\Projects\OpenEden-work\studio3\hc4\frames\h_labels.png`, `h_hover.png`, `h_drag.png` (the rig with "HEAD" next to the selected joint and the yellow highlight box on the handle), and the Cell view with the sample note's "FIRST" (`studio3\mc3\frames\module_overlay.png`).

**e. Settings and background tasks.** `ModuleSettings` over a `SettingsStore` (`modulesettings.*`; 15 tests): stored as text in `[module.<module id>]` under the setting's id; a default is written when absent; a stored value out of range is clamped, one that cannot be read or is not a listed choice falls back to the default, each with ONE warning for the setting and the repaired value written back; `set` is strict about the type; bad descriptions (empty or duplicate id, a Vec3, a default out of range or not listed, min above max) are refused with a reason. `ManagerSettingsStore` is `Settings::Manager`'s user settings (2 tests); `Editor::startModules` sets it before the modules load and saves `eden-studio.cfg` when defaults were written. `CSVPrefs::ModuleSettingsPage` is a "Modules" category of the preferences window (only when a module registered a setting; the dialogue's `dynamic_cast<PageBase&>` loop became a pointer cast). `TaskRunner` (`taskrunner.*`; 12 tests, 30 repeats clean): two pool threads; progress is clamped, coalesced and in order, `done` once with Finished, Cancelled or Failed (the work function's exception text); `cancelAsset` and `cancelAll` cancel AND WAIT for the work functions and drop their callbacks (a queued task never starts), so no work function runs past the module's code; closures that outlive the runner hold its shared state. `ModuleUi` posts to the UI thread with a queued invoke, cancels the old asset's tasks before it replaces it and all tasks in `releaseModuleObjects`. In the real editor (the module check's new step): the Modules page lists the sample's Greeting and Axis half length, an edit goes to the store, a value past the range is clamped by the box, and `eden-studio.cfg` holds `[module.sample]` with the three lines (`studio3\mc3\frames\module_prefs.png`).

The sample module uses every addition** (`sdk/examples/sample_editor_module`): two settings, one subscription (the note's read-only "events" count), the title as a label at the handle (yellow when the host's selection is that handle), a handle that drags, and the command "Say Hello" running a checksum as a background task with progress (the note's read-only "checksum"). `testsamplemodule12.cpp` (9 tests, red against the old sample first) and the old sample tests unchanged. **Decisions for toddhow.** (1) The four edited existing tests above. (2) `cancelAsset` blocks the UI until the asset's work functions return: the alternative is to let them run on and drop their results, which leaves module code running after the module is unloaded unless the host also waits at shutdown. (3) A click on a handle is the selection `{"handle", id}`, and a module maps it to its own kind: say if Studio should instead pick overlay LINES and TRIANGLES too (the picking functions exist and are tested, the viewport only feeds them handles). (5) Dialogs and canvases stay unbuilt, as answered.
