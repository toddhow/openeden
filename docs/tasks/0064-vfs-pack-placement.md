# Task: A pack takes a place in the data-folder order (`data=` names an Eden Archive)
Design doc section: `docs/design/eden-archive-format.md`, section 12 (virtual file system, priority and conflicts); `docs/tasks/0050-vfs-unified-archive-and-loose-files.md` (D6 and the stage g notes, which this task amends); `docs/tasks/0057-launcher-mod-organizer.md` (D5 and risk 1, which this task answers); decision record `docs/decisions/0010-rendering-and-studio-answers-2026-11-01.md`, "Answers of 2026-11-02": the launcher's pack priority (0057 D5) is settled by an engine task first, this one.
Goal: let a `data=` line name an Eden Archive (`.edenpak`) so that the pack is registered at the position of its line among the data folders and wins and loses exactly as a loose folder at that position would.
Inherited code touched, at commit `bff2b87399`: `components/vfs/registerarchives.cpp` (`registerArchives`, the data-directory loop), `components/files/configurationmanager.cpp` (`ConfigurationManager::filterOutNonExistingPaths`), `components/files/collections.cpp` (`Collections::getPath`, `Collections::doesExist`), `components/files/multidircollection.cpp` (`MultiDirCollection` constructor); read, not changed: `components/vfs/edenarchive.cpp` (`makeEdenArchive`, `EdenPackArchive::getDescription`), `components/vfs/manager.cpp` (`Manager::buildIndex`, `getOverrides`), `apps/openmw/main.cpp` (reads `data` and `data-local`, calls `filterOutNonExistingPaths`), `apps/openmw/vsgengine.cpp` (`Engine::prepareEngine`), `apps/openmw/mwworld/worldimp.cpp` (`World::loadContentFiles`), `components/esmloader/load.cpp` (`shallowLoad`), `components/config/gamesettings.cpp` (`GameSettings::validatePaths`, launcher side). Other callers of the changed functions: `apps/navmeshtool/main.cpp`, `apps/physicsobjecttool/main.cpp`, `apps/opencs/editor.cpp`, `apps/opencs/capture.cpp`, `apps/opencs/model/world/data.cpp` (they reach the new behaviour through the same functions and are not edited).
Inputs / outputs: no new `openmw.cfg` key and no new file format. A `data=` line may now name a file that ends in `.edenpak`. New free function `Files::isDataPackFile`; new function `VFS::findContentFilesInArchive`; new tests `apps/components_tests/vfs/testvfspackplacement.cpp` and `apps/components_tests/files/testdatapack.cpp`.

Status: draft, written 2026-11-02, implemented in the same session. **Full loop** (the VFS decides which file a mod's path resolves to and the task changes the registration order rules; the container track is on the full-loop list). ## What exists today (read from the code at this commit)

- **Where a pack goes now.** `registerArchives` (`components/vfs/registerarchives.cpp`) first registers every `fallback-archive=` name (resolved with `Collections::doesExist` and `getPath`, last has the highest priority), calling `makeArchive`, which recognises an Eden Archive by its seven magic bytes (`makeEdenArchive`). It then registers every data directory as a `FileSystemArchive`, last wins. So **a pack is always below every loose folder** (0050 D6, trap 1 of 0057).
- **Why a new key cannot give a position.** `apps/openmw/main.cpp` reads `variables["data"]` as one list. The configuration files are stored per key into a `boost::program_options::variables_map` (`ConfigurationManager::loadConfig`, `bpo::store`, `components/files/configurationmanager.cpp`), and `data=` lines from several configuration files are concatenated per key (`separateComposingVariables`, the `MaybeQuotedPathContainer` branch). The order of lines of *different* keys is not kept anywhere. A line `data-archive=pack.edenpak` would therefore know nothing about the `data=` lines around it.
- **What a path in `data=` goes through.** `main.cpp` and `Engine::prepareEngine` call `filterOutNonExistingPaths`, which drops everything that is not a directory (`std::filesystem::is_directory`) with the warning "No such dir". The list then becomes `Files::Collections` (`collections.hpp`), which is used for two different jobs: (1) `registerArchives` takes `collections.getPaths()` as the data-directory order; (2) content files (`content=`, `groundcover=`) and translation files are found with `Collections::getCollection(extension)`, whose `MultiDirCollection` constructor walks each directory with `directory_iterator`, and `Collections::getPath`/`doesExist` (used by `registerArchives` for `fallback-archive=`) call `directory_iterator` on **every** entry, which throws for a file.
- **Plugins are not read through the VFS** (trap 2 of 0057). `World::loadContentFiles` gets `col.getPath(file)` from the collection and passes a disk path to the loaders; `shallowLoad` (`components/esmloader/load.cpp`) does `reader->open(collection.getPath(file))`; `ESM::ESMReader::open` and the `.omwscripts` loader take disk paths. Nothing in that chain can open a file inside a pack.
- **The override report already names a pack.** `EdenPackArchive::getDescription()` returns "Eden Archive: <path>", and `logOverrides` (in `registerarchives.cpp`) prints it in the counts and in the debug-level list. The real Morrowind data gives "Data sources: 7, paths provided by more than one source: 8675" (measured 2026-11-02 on toddhow's install, before this task).
- **The launcher** (read only, not changed): `GameSettings::validatePaths` keeps a `data=` line only if `QDir(path).exists()`, which is false for a file. A launcher that reads and rewrites `openmw.cfg` would therefore drop a pack line. That is the launcher-side follow-up recorded in 0057.

## Design, in plain language

`data=` is the only list in the configuration whose order means "later wins" for loose files, so the pack has to stand in that list. The smallest change is to let a `data=` line **name a pack file instead of a folder**. The engine then does what it already does for each line in order, with one difference: when the line is a pack file it opens the pack (as `fallback-archive=` does) instead of scanning a folder, and puts it at that spot. Two sources are compared the same way as two folders: the later one wins for every path both provide. Nothing about the VFS index changes, because a pack is already an `Archive`; only the place where it is added changes.

Every existing configuration keeps working because nothing in use names a file on a `data=` line today: such a line was dropped with a warning, and now it is kept only if it ends in `.edenpak`. A file with another name is still dropped with the same warning. A `fallback-archive=` pack works as before (below all folders).

**Plugins in a pack (the shim rule).** A pack provides **no content files**: `.esm`, `.esp`, `.omwgame`, `.omwaddon`, `.omwscripts` and `.project` are found only in real folders, because the readers take disk paths (above). Making them readable from a pack would mean either changing the ESM readers (inherited, large) or unpacking the plugin to a cache folder at start (writes at start, staleness, and a second copy of the mod's files). Neither is justified when the shim folder already works. So the rule is: **a repacked mod keeps its plugins in a small shim folder, and the shim folder stands at the same position of `data=` as the pack.** The shim holds plugins only, so it does not change which resource wins; its position matters only for two plugins with the same file name in different folders, and the same position keeps that outcome as it was. To help whoever makes the mistake of leaving a plugin inside a pack, the engine logs a Warning for each content file it finds at the top level of a pack (`VFS::findContentFilesInArchive`): the pack is still used for everything else, and a `content=` line that names such a plugin fails exactly as it does today for a missing file ("the content file does not exist") with that warning just before it in the log.

**What the launcher must do** (recorded for 0057, not done here): write the pack as a `data=` line at the mod's old place; write the shim folder as a `data=` line at the same place; teach `GameSettings::validatePaths` to keep `.edenpak` lines; show the engine's answer to the swap proof as "no change" for a pack in place, which makes the swap check of 0057 (D5, risk 1) unnecessary for packs placed this way.

### Decisions toddhow can change (recommendation first)

| # | Decision | Recommended and implemented | Alternative |
| --- | --- | --- | --- |
| D1 | How a pack is placed | A `data=` line naming a `.edenpak` file; the pack stands where the line stands | A new key `data-archive=`: rejected, the order between keys is lost when the configuration is stored (above). Keeping the order across keys would mean replacing `variables_map` storage with `parsed_options` in the start-up code of every tool: far more invasive |
| D2 | Which files count as a pack on `data=` | A regular file whose name ends in `.edenpak` (any case); then recognised by magic bytes when opened, and a file that is not a pack stops start-up with a located error | Any regular file (a typo in an old config would now stop start-up instead of being dropped); only by magic (the configuration layer would need the pack reader) |
| D3 | A file that is named `.edenpak` but is not a pack, or is a broken pack | `registerArchives` throws, naming the file (as `fallback-archive=` does for a broken archive) | Skip it with a Warning (a silent change of which file wins) |
| D4 | Plugins inside a pack | Not supported; the shim folder rule above; Warning naming each plugin at the pack's top level | Unpack to a cache folder at start; or read ESM files from the VFS (inherited reader change). Both can be a later task if the shim folder proves a burden |
| D5 | A BSA on a `data=` line | Not supported (the line is dropped as today); BSAs stay in `fallback-archive=` | Allow any archive kind at a position |
| D6 | Editor and tools | They get the behaviour through the shared functions and are not edited | Opt-in per tool |
| D7 | `useLooseFiles == false` | Pack lines are skipped like folders (they are data-folder entries) | Packs always registered |

## Interface fixed for implementation (the tests are written against this)

- `components/files/collections.hpp`: `bool Files::isDataPackFile(const std::filesystem::path& path);` true when `path` is a regular file whose file name ends in `.edenpak`, compared without regard to case. False for a directory, a missing path, any other file.
- `ConfigurationManager::filterOutNonExistingPaths(PathContainer&)`: keeps an entry if it is a directory **or** `isDataPackFile`; drops the rest with the existing warning; the order of the kept entries is unchanged.
- `Collections::getPath(file)` and `doesExist(file)`: entries of the list that are regular files are skipped (they are not searched, no exception); everything else as before.
- `MultiDirCollection` constructor: a regular file in the list is skipped without a log line; a missing path is skipped with the existing Info line.
- `VFS::registerArchives(...)` (signature unchanged): in the data-directory loop, an entry that is a regular file is opened with `makeEdenArchive` and added at that position (after the `fallback-archive=` archives and the folders before it, before those after it). Duplicates of the same path are ignored as for folders. `makeEdenArchive` returning `nullptr`, or throwing, makes `registerArchives` throw `std::runtime_error` whose text names the file. The log line is `Adding data archive <path>` (Info). With `useLooseFiles == false` the entry is not registered. A directory entry is handled as before.
- `registerarchives.hpp`: `std::vector<std::string> VFS::findContentFilesInArchive(Archive& archive);` the normalized names, in index order, of the entries that have no `/` in their name and whose extension (after the last `.`) is one of `esm`, `esp`, `omwgame`, `omwaddon`, `omwscripts`, `project`. It lists the archive through `Archive::listResources` (set-up time only, one thread). `registerArchives` logs, at Warning level, one line per name: `Eden Archive '<path>' contains the content file '<name>'; content files are read from data folders only, so keep it in a folder (task 0064)`.

## Constraints

- Directory-only configurations resolve and log exactly as before (the new code is reached only for an entry that is a regular file).
- Thread safety as the VFS contract says: registration happens on the start-up thread; after `buildIndex()` nothing changes. Say in the pull request: no new function runs on another thread.
- Deterministic: the order of the lines is the order of registration; `findContentFilesInArchive` returns names in the index (sorted) order.
- No allocation change in lookups; the listing for the plugin warning happens once per pack at start-up.
- `components/` does not include `apps/`.
- No game assets: the tests and the Lua check use generated data and the example suite.
