# Research note 0048: a weather system for OpenEden (storms, lightning, better rain)

Status: DRAFT, docs only, 2026-11-09. Nothing built or run. Written for toddhow ("Another item to plan out is a weather system. Since we have volumetric clouds now we can do visually stunning weather like lightning and better rain"). The task spec is `docs/tasks/0094-weather-system.md`.

Evidence rules: facts about the repository cite a file and function at the working tree of 2026-11-09 (branch `main`, `ba3f79b670` plus uncommitted work in other areas). Anything recalled from outside the repository, and anything about shader internals I did not open, is marked **RECALLED-VERIFY**. No game asset was read.

## 1. Inventory: what exists today, per weather element

Authority first. `MWWorld::WeatherManager` (`apps/openmw/mwworld/weather.cpp`) decides which weather is active: per-region chances (`RegionWeather`), `changeWeather` (`WeatherManager::changeWeather`, the `ChangeWeather` script command), transitions (`Weather::transitionDelta`, `mTransitionDelta` from `Weather_<name>_Transition_Delta`), and the blend factor between current and next weather. It produces a `MWRender::WeatherResult` (`apps/openmw/mwrender/weatherdata.hpp`) every frame and hands it to the renderer. Save data holds the region weather state; nothing in this plan touches it.

What the renderer receives today is exactly the `WeatherResult` struct above plus a few extra calls the manager makes (`setWetness`, `setCover`, `setLightning`, `setSunColour`, `Sky::setStormParticleDirection`). There is no single "storm" value. Storminess today is the pair `mIsStorm` (wind above the storm speed: ash, blight, blizzard) and the particle effect name; a Morrowind thunderstorm is not `mIsStorm` (wind speed 20 in `addWeather("Thunderstorm", 0.5f, 20.0f)`, `weather.cpp` line 677; the arguments there are my reading of `stormWindSpeed`/`rainSpeed`, **RECALLED-VERIFY** which is which).

## 2. Hard constraints

1. **The weather manager stays the authority for which weather is active.** Regions, `ChangeWeather`, transitions and the thunder schedule (`calculateThunder`) are not replaced. The new system is a pure consumer: it reads a state derived from `WeatherManager` and changes only how that weather is drawn and heard. No save format change (the weather's save records stay as they are); no new record types; no script command changes.
2. **Default behaviour is Morrowind's** (CLAUDE.md). Every new feature is a `[Rendering]` (or `[Sound]`) setting, off by default, and "off means unchanged" is compared by frames and traces, not assumed. A mod that edits weather records (see section 5, mods) keeps working because we read the same fallback values.
3. **Determinism.** No wall clock. Lightning geometry and timing come from the existing schedule plus a hash of a fixed seed and the strike count (`Render::Lightning::direction`, as in 0040 D3). One caution found in the code: the vanilla strike is rolled on the shared game PRNG (`World::getPrng` in `lightningAndThunder`). Our stage must not draw extra numbers from that generator (that would change gameplay-visible random sequences and saved-game replays); it derives everything else from the strike index with a stateless hash.
4. **Performance budgets.** Volumetric clouds already cost 0.14 to 0.32 ms at 720p; volumetric fog is "the heaviest GPU effect"; point-light shadows add CPU and GPU cost per light; TAA costs 0.15 to 0.46 ms by resolution. The weather system as a whole should add at most about 0.3 ms (medium tier, 1080p, RTX 4070 class) in the worst storm and nothing when the weather is fair or the settings are off (**proposed**, toddhow decides the tiers). Cloud work happens in the existing compute pass (`files/shaders/comp/cloud/cloud.slang`), not in a second pass.
5. **Threading.** The weather manager and `Sky` update on the main thread. Rain simulation is CPU on the main thread (`Rain::update`); any new particle or bolt state is updated there and uploaded in the existing per-frame transfer, with no allocation per frame (CLAUDE.md "Hot paths"). Lightning bolt geometry is generated at the strike (rare, a few hundred vertices from a stateless hash) into a preallocated buffer.
6. **Shaders in Slang** (decision 0009) for new shader files, with the Slang-only convention used for the sun/cirrus (`Graphics::slangOnlyPaths`). Edits to existing GLSL (`default/main.frag`, `sky/*`) stay GLSL, as 0040 did.
7. **TAA / transparents.** New blended draws (rain layers, bolts, mist) join `DeferredBin` (task 0075), unjittered camera, drawn after the resolve.
8. **Photosensitivity.** The 0040 cap (peak 1) and 1.5 s minimum spacing stay as hard limits whatever any new setting says; new emissive flashes inside clouds count against the same cap (they are the same event).
9. **Interiors unaffected**, except what already works (no rain inside, `isExterior` gates in `updateWetness`/`updateCover`). Lightning through windows stays out (0040 out-of-scope).
10. **Editor (Eden Studio) and `.omwfx` post-processing** keep building; the new passes are created only with their setting on (the pattern of 0041/0042).

## 3. The missing pieces, in order of visual value

Ranked by what a viewer sees; each is independent enough for a stage.

**A. A weather state contract.** One small struct the renderer reads each frame (precipitation kind and intensity, wind vector, storminess, lightning schedule, cloud targets), built by `WeatherManager` from data it already has, plus the settings. This avoids every effect reading `WeatherResult` fields on its own and gives tests a pure input (the pattern of `Render::Wetness::target`). Costs nothing at run time.

**B. Better rain.** Candidates (all CPU-cheap or one extra instanced quad layer): near and far layers (near drops big, bright, few; far drops fine and denser, fading into fog), per-layer wind slant including a true wind direction (today only +Y), splashes and ripples where drops land on ground and water (the puddle ripples already exist in the wetness shader, **RECALLED-VERIFY** which water ripple code the rain uses; I did not open `water/main.frag`), a ground mist/spray sprite layer in heavy rain, a rain curtain under the cloud base (sheets that you see slanting from the cloud to the horizon: a screen-space or dome-space volume term, not particles), and rain occlusion made cheaper/default (the existing `PrecipitationOccluder`).

**C. Storm clouds.** Today the volume reads only coverage, wind and share. A storm needs: a lower cloud base, thicker layer, darker underside (more absorption), optional anvil (a wider flat top at the layer ceiling), and some cell structure (a large-scale noise that forms dark cores). All of these are parameters of the existing cloud density function (`cloudvolumemath.hpp`: density from shape, detail, coverage). Changes are a handful of uniform values plus a low-frequency "storm cell" modulation; cost is within the existing march.

**D. Lightning.** (i) Light *inside* the clouds: an emissive/in-scatter term at a point in the volume (the strike's cloud position) with an exponential falloff and the flash envelope. The march already walks the volume, so the term is a few ALU per step (**RECALLED-VERIFY**: exact cost; measure). (ii) A cloud-to-ground bolt: seeded branching geometry (a midpoint-displacement polyline with branches, generated once per strike from a hash) drawn as thin additive lines/ribbons in the deferred bin, with the 0040 double-flicker envelope. (iii) The flash lights wet surfaces: already there through the merged light; improve by moving the light direction to the bolt's actual position (the strike has a place now). (iv) Thunder delay: distance in the strike's place divided by the speed of sound; the vanilla distance index 0 to 3 maps to a distance range, the sound is queued with that delay on game time. Sound changes need toddhow's approval (open question), and without them the vanilla instant play stays.

**E. Transitions.** The volume coverage already blends with the transition factor. Extend the blend to the new storm parameters, add hysteresis so a short `ChangeWeather` does not flicker the cloud base, and couple wetness and cover to the same state (they already follow the weather manager).

**F. Extras.** Rainbows after rain (needs: rain recently stopped, sun low enough, a rain-filled region opposite the sun; a simple analytic arc in the sky pass, cheap), sun shafts under broken storm cloud (already possible through 0041 and cloud shadows 0042 `volumetric clouds shadows`; mostly tuning), volumetric haze for ash, blight and snow storms (density term in the volumetric fog pass with the wind direction as streaming), mist after rain.

## 5. Risks

1. **Look vs vanilla feel.** Stunning storms may read as non-Morrowind. Mitigation: presets, off by default, frames reviewed by toddhow before any default changes.
2. **Cloud cost.** Storm modulation raises step counts if the density is higher; the march is the "one of the two heaviest" effects. Mitigation: tiers (low/medium/high of `volumetric clouds quality`), a measured budget per stage, and "no storm term evaluated in fair weather".
3. **Photosensitivity.** New flashes (cloud glow, bolt) must obey the 0040 cap and spacing. One event, one envelope; tested.
4. **Shared PRNG.** Do not consume `World::getPrng` numbers (section 2.3). A test pins that the vanilla schedule rolls the same sequence with the new system on and off.
5. **TAA ghosting / temporal features.** Bolts and mist are transient; they need the deferred bin and must not enter the temporal history (`taa`, `ao temporal`).
6. **Mod compatibility.** Weather mods that replace the weather records (`Weather_<name>_*` fallbacks, `.omwaddon` or `openmw.cfg` fallback lines **RECALLED-VERIFY** the mechanism), add weather types or replace the rain/ash NIFs. Our state derives from the same fallbacks and compares particle effects by the configured model names (as `updateCover` does), so new weather types that use rain or snow NIFs behave like those; unknown effects get the "none" treatment. Mods that rely on OpenMW's `Lua` weather API (**RECALLED-VERIFY**: whether a weather Lua API exists in the 0.51 base) are not affected because the manager is unchanged.
7. **Linux/GPU variance.** Every new shader goes through the Slang permutation tests (`SlangPermutations`) and the Linux gate; draws that rely on float precision at long range (bolts at kilometres) need camera-relative coordinates (the cloud and cirrus code already work in metres at a named boundary).
8. **Sound.** Delaying thunder changes when players hear it relative to scripts that react to the `Weather` global? (Scripts do not receive the thunder event as far as I know, **RECALLED-VERIFY**; check before stage W3's sound option.)
9. **Interaction with the world map view** (`[WorldLod] haze`): the aerial perspective already reads weather; the new fog terms must use the same pure functions to avoid two different hazes.
