# 0032 A merged body from Morrowind's legacy parts: what the code says

Date: 2026-11-03 · Commit: `1b1f63391f` (branch `vulkan`) · Status: research, nothing decided · Feeds `docs/design/advancedbodies-in-openeden.md` section 7A and `docs/tasks/0069-advancedbodies-merged-legacy-body.md`

Request (toddhow, 2026-11-03): sideline modelling a full body mesh by hand ("I'm not a modeller or artist"). Merge the legacy parts **programmatically** into one mesh and **cache** it, so no mesh has to be shipped by us, and so modders can later bring their own assets as a full body mesh.

How to read this: every engine statement names a file and function at the commit above, or is marked **verify**. "Verify" means the answer needs the user's own installed game data (which can never be in the repository) or a source I did not open. Section 8 lists every open fact and how stage a of task 0069 settles it.

## 1. How the stock parts are bound to the skeleton

**Plain language.** Each stock part is a small mesh stored in its own NIF file. The engine hangs it on the bone the part belongs to (a forearm part on the forearm bone). Most parts are *skinned*: every vertex stores which bones pull it and how strongly, so the surface bends smoothly at a joint. Where two parts meet at a joint, the two meshes are authored to meet at their edges in the rest pose; nothing in the engine joins them.

**Facts.**

- **One part, one bone.** `MWAnim::sPartBones` (`components/mwanimation/partbones.hpp`) maps each `ESM::PartReferenceType` to a bone name ("Neck", "Chest", "Groin", "Right Upper Arm", "Right Forearm", "Right Wrist", "Right Hand", "Right Upper Leg", "Right Knee", "Right Ankle", "Right Foot", "Head", and the left twins; hair uses "Head"; the clavicle bones are the pauldron slots). `Npc::insertBoundedPart` (`apps/openmw/mwrender/npc.cpp`) reads the model and calls `MWAnim::attachBonesAndNode` (`components/mwanimation/attach.cpp`), which hangs the node under that bone's group (`Anim::getOrAttachBone`).
- **One NIF can hold several parts.** The reader is given an option `skinfilter` per part type (`partBoneOptions`, `apps/openmw/mwrender/animcontext.cpp`: the bone name, or `"hair"` for hair). With skinning on and a filter set, the node walk keeps only nodes whose name starts with the filter or with `"tri " + filter` and drops the other branches (`components/vsgadapters/nif/nif.cpp`: `mSkinFilter`, `mSkinFilter2`, `filterMatches`, and the `filterMatched` test with `mNif->getUseSkinning()`). `getBodyParts` also maps one record part to two slots: `sBodyPartMap` (`apps/openmw/mwrender/bodyparts.cpp`) sends the hand, wrist, forearm, upper arm, foot, ankle, knee and upper leg record parts to **both** the right and the left slot (the list is the one in that function; read it before relying on it). So the same model file is read twice, once with the right bone's filter and once with the left's, and the left side of such a file would be a separate shape (**verify**: that a stock hand NIF holds a "Tri Right Hand" and a "Tri Left Hand" shape; stage a counts shapes per file).
- **Skinned parts.** `handleSkin` (`nif.cpp`) turns a `Nif::NiSkinInstance` plus `Nif::NiSkinData` (`components/nif/data.hpp`: `NiSkinInstance::mBones`, `NiSkinData::mTransform`, `BoneInfo::mTransform`, `mBoundSphere`, `mWeights`) into per-vertex bone indices and weights, **keeping the 4 largest weights per vertex** (`maxInfluenceCount = 4`) and **not renormalising** after the cut, and builds an `Anim::Skin` controller (`components/animation/skin.hpp`) holding one bind matrix per bone, found by **bone name** (`skin.mBones[i].getPtr()->mName`). The vertex shader blends four matrices (`SKIN` define, `files/shaders/default/main.vert`) and reads `boneMatrices.length()` (a storage array: no fixed bone cap in the shader; the second half is the previous frame's matrices, `keepPreviousMatrices`, task 0026).
- **The sort is not a total order.** `handleSkin` sorts each vertex's influences with `std::sort` on weight only, so equal weights have an unspecified order. The merger must break ties itself (by canonical bone order) or its output would not be byte-identical across runs and compilers.
- **Rigid (unskinned) parts.** If a part has no skin, `MWAnim::decorate(node, light, mirror)` (`components/mwanimation/decorate.cpp`) applies a mirror (negative scale) for names containing "Left", **only when the part has no skins** (`!result.contents.contains(Anim::Contents::Skins)`), and `partBoneOptions` flips the front face for left non-skin parts (`VK_FRONT_FACE_CLOCKWISE`). So the engine supports rigid mirrored parts. Whether any *stock body* part is rigid is **verify** (stage a counts skinned and rigid parts).
- **Where parts meet.** From the slot list in `sPartBones` and `Npc::updateParts`: neck meets chest and head; chest meets groin, upper arms and the clavicle slots; upper arm meets forearm; forearm meets wrist; wrist meets hand; groin meets the two upper legs; upper leg meets knee; knee meets ankle; ankle meets foot. Which seams share exact boundary vertices, which overlap and which leave a gap is **verify**; no code in the engine welds them (`npc.cpp` and `bodyparts.cpp` contain no seam logic; research note 0027 section 2).
- **Head and hair** are chosen per NPC record (`getHeadModel`, `getHairModel`, `ESM::NPC::mHead`, `mHair`), not by race and sex alone; a body for "race and sex" therefore **cannot include the head** without multiplying by the number of head records (section 5).

## 2. What a merge has to do

1. **Put every vertex in one space.** Each part's vertices are in its NIF's own local space; the bind pose that matters is the skin's (`NiSkinData::mTransform`, the `openmw-4437-niskininstance-transformation` branch in `handleSkin`, and each bone's `mTransform`). A merge brings all parts into one **bind space** (the skeleton root's rest pose). The check that it is right: CPU-skin the stock part and the merged mesh at several poses with `Anim::SoftwareSkin` (`components/animation/softwareskin.hpp`); positions must agree at every vertex that is not on a seam (stage d numeric test).
2. **Weld coincident vertices across parts** inside a tolerance, and remove exact duplicates. The tolerance is **derived from the data** (stage a). The rule: cut the histogram of nearest cross-part distances at the largest gap below a fraction of the median boundary edge length. That is a rule, not a number; the number becomes a named constant with a written reason, as B1 did for its thresholds (`components/body/CLAUDE.md`).
3. **Keep UV and normal seams honest.** A position shared by two parts with different UVs or normals is **not** collapsed into one vertex: the vertices stay and go into one **weld group**, so that a later morph moves them identically (design section 7.2 items 2 and 3). Normals: when the two normals differ by less than a named angle the weld averages them (area weighted); otherwise the crease is deliberate (a cuff) and both stay.
4. **Skin weights at a seam.** After the 4-influence cut the weights of a vertex may not sum to 1; the validator requires a sum of 1 within `sWeightSumTolerance` (1e-3, `components/body/CLAUDE.md`), so the merger renormalises. For a weld group whose members have different weight sets, the merged set is the **equal-weight mean of the members' sets, renormalised, top 4 by weight, ties by canonical bone order**. How large the disagreement is at stock seams is **verify**; stage a prints it per seam (`max |wA - wB|`). If it is zero the rule changes nothing; if it is large the animated seam differs from stock, and the stage d numeric test bounds the difference by exactly that measured number.
5. **One bone list.** Parts name bones by string; the merged mesh has one bone list in a canonical order (the skeleton profile's mapped bones in profile order, then unmapped bones sorted by name) and one remapped index per influence.
6. **Materials.** Parts carry their own textures (read by `nif.cpp`); a merged mesh keeps **one submesh per material key** (texture path, alpha flags, vertex-colour flag), sorted by key. Whether the stock body parts of one race share one texture or use a few is **verify**. No texture atlas in the first version (the same call the LOD cluster layout made, `docs/tasks/0059-*.md`).
7. **Deterministic order.** Vertices ordered by (slot number, original vertex index); a welded vertex keeps the lowest (slot, index) of its group; triangles keep the source order inside their region; submeshes by material key then region; regions by slot number; weld groups by their lowest member. One thread per body. No clock, no unseeded randomness, no unordered iteration (root `CLAUDE.md`, Determinism). Cross-machine byte equality is **not promised**, as for the LOD bakes (`docs/design/world-lod-and-streaming.md` 4.4: fused multiply-add differences).

## 3. The NIF reader a merger can use

`components/lod/nifflatten.*` already reads parsed `Nif` records (not the scene graph) into plain arrays for the object cluster baker and notes that a model is skinned (`nifflatten.cpp`, `geometry.mSkin`), but the cluster baker treats actors as dynamic and does not read weights. The merger needs a sibling reader of **skinned** geometry: positions, normals, UVs, triangles, per-bone weights, bone names, bind matrices, material facts and shape names (for the skin filter), all from `Nif::NiGeometry`, `NiSkinInstance`, `NiSkinData`. It must live below `components/body` (which has no engine types, `components/body/CLAUDE.md`): a small library over `components/nif` only, proposed `components/bodynif` (no ESM, no VSG), used by the engine adapter and by the analysis and bake modes.

## 4. The cache

- **Pattern.** The LOD baker's: derived Eden Archive packs in the user data folder, a staleness key from source hashes plus tool version plus parameters, written whole under a new name and published by an atomic rename, never edited while in use, stale data never shown (`docs/design/world-lod-and-streaming.md` 4.5 to 4.7; `docs/tasks/0061-lod-s8-background-baker.md`: units, a `current` pointer, `status.json`, and the bake as a mode of the game executable because it needs the ESM store and the VFS).
- **Source hashes.** `VFS::File::getContentHash()` (`components/vfs/file.hpp`) returns `std::nullopt` by default; only pack-backed files answer. Loose files and BSA entries must be hashed from their bytes (LOD design 4.5 says the same and marks a modification-time shortcut **verify**). The size of a part model is **verify** (stage a records bytes per part), so hashing every part at bake time is believed cheap but not measured. The runtime does **not** re-hash at load: it trusts the `current` pointer the bake wrote, and the key it checks is computed from the ESM selection (record ids, model paths) plus the file sizes (decision H15).
- **Key inputs.** For one body: the merger version; the merge parameters (weld tolerance, normal angle, influence limit); (race id, sex, view); for each selected part: record id, part type, flags, race, model path **and the hash of the model's bytes**; the skeleton file chosen by `Context::pickSkeleton` and its hash (parts name bones, so a changed skeleton can make a body wrong). A mod that replaces a part model, a body-part record or a skeleton changes a hash and invalidates exactly the bodies it touches.
- **Where.** `<user data>/openeden/bodies/`, next to `lod/` in the existing `openeden/` folder. One pack `merged.edenpak` plus a tiny `current` pointer file at first; the generation layout of task 0061 once the unified baker exists.
- **Never committed, never shipped.** A merged body is a derivative of the game's meshes: the same rule as the LOD bakes (root `CLAUDE.md`, Guardrails: no game assets). Only a modder's own package may be shipped, by its author.
- **Size.** A formula, not a measurement. One vertex is 44 to 52 bytes (position 12, normal 12, UV 8, four bone indices as bytes 4, plus four weights as float16 8 or as float32 16); a body of V vertices costs about 44 V to 52 V bytes plus 6 bytes per triangle with 16-bit indices; with R races and 2 sexes the pack is about 2 R times one body. V and R are measured by stage a; no number is claimed here.
- **Loading cost.** Today a person costs about 20 part reads and attaches (`Npc::insertBoundedPart` runs inside the `npc.part.read` and `npc.part.attach` load-trace scopes, task 0060). The merged path should replace most of them with one body node plus head and hair. That saving is a **hypothesis**; stage d measures it with `[Cells] load trace`.

## 5. Head, hair, face, equipment, beasts

- **Head.** Recommendation (decision H14): merge **neck-down** (neck, chest, groin, arms, hands, legs, feet, and the tail for beasts) and keep head and hair as parts. The head is chosen per NPC; merging it too multiplies bodies by the number of head records per race and sex (**verify**: stage a counts head skin records per race and sex) and gains little: the neck-to-head seam is a weld group computed once per (body, head) at morph time. A later stage can merge head records if they turn out to be few.
- **Equipment.** `Npc::updateParts` keeps the slot logic: equipped items add parts with priorities; `reserveIndividualPart` hides a slot without adding a part (robe and skirt reserve groin and legs); at the end the default skin parts fill every slot whose priority is below 1 (`npc.cpp`, the loop after `getBodyParts`). With a merged body that final loop becomes "show the merged body's regions for every slot whose priority is below 1, hide the others". A region is a **contiguous triangle range** (the merger sorts triangles by region; B1's `regionMap` is already a sweep over sorted ranges, `components/body/CLAUDE.md`), so hiding a region is a separate indexed draw that is switched off; the engine already switches subtrees for weapons (`addSwitch`, `npc.cpp`). `removeIndividualPart` (unequip) switches it on again. Welded vertices are shared with the neighbouring region, so hiding a region leaves no gap in the visible neighbour, as with stock parts.
- **Strictness** (design 7.2 item 4, decision H4): legacy equipment stays separate skinned parts, **never merged and never morphed**. The merged body is only the skin.
- **Werewolf.** `getBodyParts(... werewolf == true)` returns an empty slot list (`bodyparts.cpp`: `if (werewolf) return parts;`) and `getHeadModel` has a special case: untouched, stock path. **Vampire** only changes the head selection (`sVampireMapping`); the body is the race's.
- **Beast races.** A different skeleton (`isBeast`, `Npc::updateNpcBase`) and a tail slot (`PRT_Tail`). The merger is generic over the part list, so a beast body is one more (race, sex) entry if stage a shows its parts follow the same structure; otherwise it stays stock (decision H18).
- **First person.** `getBodyParts(... firstPerson == true)` returns arms only, read with the first-person context (`apps/openmw/mwrender/player.cpp`). Not merged: the view part of the key is third person only in the first stages.
- **Skin marks.** `markSkinModel` is keyed by model path (`npc.cpp`); a merged body has no stable path, so the body node gets the subsurface flag from its region roles (design 6.5, decision H10). Head and hair marks are unchanged.

## 6. Morphing on the merged mesh

Tier 2 surface morphs (design 6.1) become simple: one vertex array, one displacement field evaluated at rest position. Welded UV or normal duplicates are in weld groups, so they receive the same displacement and the seam stays closed (design 7.2 item 3 is unchanged and still the rule). What disappears is the per-part bookkeeping and the gaps between *parts*. The CPU bake per unique body (design 6.2) runs over one array. Equipment regions limit morph amplitude exactly as before (the strict level).

## 7. A merged body is an ordinary body package

B1's package model (`components/body/bodypackage.hpp`, format `openeden.body` v1) already has `meshes[]` with `meshFormat` (`"nif"`, `"gltf"`, `"summary"`), `role`, `partType`, a `regionMap`, `provenance` and `measurements`. A merged body has the same shape: one `skin` mesh (LOD 0), a `regionMap` by slot, `provenance` naming the merger, the key and the part digests, parts labelled `derived`. Two additions are needed, both small changes to B1 made in stage b: a `meshFormat` value for the cache's own mesh payload (`"bodymesh"`), and an optional `weldGroups` part with a seam-quality summary plus its validator rules. A modder's full-body package (glTF or the same payload) then goes through the same loader, the same validator and the same renderer path, **with no merge step**. Every rule the validator already has (weight sums, influence limit, bone indices, index ranges, region coverage with no gaps or overlaps, bounds range) applies unchanged to a merged body. That makes the validator the merger's first correctness test: the merger must never emit a package the validator refuses.

## 8. Open facts and how stage a settles each

| # | Fact | Stage a measurement |
| --- | --- | --- |
| 1 | Are stock body parts skinned, rigid, or mixed? | Per part: skinned yes or no, influence histogram, rigid parts listed |
| 2 | Does one NIF hold both left and right shapes? | Shape names per part file; count per file |
| 3 | At each joint: shared boundary vertices, overlap, or gap? | Nearest cross-part boundary distance per seam: count exact (under 1e-4 units), minimum, median, 95th percentile, maximum; overlap depth; gap size |
| 4 | Do seam vertices carry the same weights on both sides? | `max abs(wA - wB)` per seam |
| 5 | Do UVs and normals match at seams? | Count of seam vertices whose UV differs; angle between normals (maximum, median) |
| 6 | Vertices, triangles, bones, textures per body | Totals per (race, sex), beast races included |
| 7 | How many head records per race and sex? | Count of head skin records |
| 8 | Do beast races follow the same structure? | The same table for beast races |
| 9 | Part file sizes (hash cost) | Bytes per part and per body |
