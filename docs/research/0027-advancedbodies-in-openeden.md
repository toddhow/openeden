## 1. How Morrowind builds an NPC today

**Plain language.** A Morrowind person is not one mesh. It is a skeleton (a tree of named bones) with a pile of separate small meshes hung on it: a head, hair, a neck, a chest, hands, forearms, upper arms, legs, feet and more. Each small mesh is a "body part". When the person wears armour or clothes, the armour's own parts take the place of the matching body parts. Nothing is stored about how a person looks in a saved game; the look is worked out again from the records every time the person is created.

**Facts.**

- **The record.** `ESM::BodyPart` (`components/esm3/loadbody.hpp`) has a part (`MeshPart`: head, hair, neck, chest, groin, hand, wrist, forearm, upperarm, foot, ankle, knee, upperleg, clavicle, tail), a type (`MT_Skin`, `MT_Clothing`, `MT_Armor`), flags (female, not playable), a vampire flag, a race and a model path. `ESM::NPC` holds the race, the head and hair record ids and a female flag (`components/esm3/loadnpc.hpp`: `mRace`, `mHair`, `mHead`, `isMale()`).
- **Choosing the parts.** `MWRender::getBodyParts(race, female, firstPerson, werewolf, store)` (`apps/openmw/mwrender/bodyparts.cpp`) scans the whole body-part store once per race, sex and view and caches the answer in a static map (`sRaceMapping`). It keeps only `MT_Skin` parts of that race, with fallbacks (male parts for a female with no female part; third-person arms for first person). `getHeadModel` and `getHairModel` pick the head and hair; vampire and werewolf heads are special cases.
- **Building the actor.** `MWRender::Npc` (`apps/openmw/mwrender/npc.cpp`). `Npc::updateNpcBase` picks the skeleton and animation sources (`Npc::animationSources`: `base_anim`-style skeleton from `MWAnim::Context::pickSkeleton`, the `[Models] xbaseanim` file as an animation source unless the skeleton is the base one, an extra swim file for Argonians), reads the skeleton with `mContext.readActor`, makes an `MWAnim::Play` over its `Bones`, then calls `updateParts`.
- **Slots, priorities and replacement.** `Npc::updateParts` walks a fixed slot list (robe, skirt, helmet, cuirass, greaves, pauldrons, boots, gauntlets, shirt, pants, hands) in the inventory. For each equipped item, `addPartGroup` finds the item's `ESM::PartReference` list and calls `addOrReplaceIndividualPart(type, slot, priority, model)`. A part is replaced only if the new priority is higher (`mPartPriorities`), and clothing gets priority `((basePriority + 1) << 1)` while armour gets that plus one, so armour beats clothing in the same slot. A robe or skirt can only *reserve* part types (`reserveIndividualPart`) so the body part underneath stays hidden. Last, head, hair and every body part type whose priority is still below 1 get the default skin parts from `getBodyParts`. This is the "assembled parts" problem in code: there is no body, only a set of part slots.
- **Attaching a part.** `Npc::insertBoundedPart` reads the part model with the part type's own options (`mPartContext->partBoneOptions[type]`), then `MWAnim::attachBonesAndNode(node, root, animation->bones, bonename)` (`components/mwanimation/attach.hpp`) hangs the part under the bone named in `MWAnim::sPartBones` (`components/mwanimation/partbones.hpp`: for example head and hair on "Head", cuirass on "Chest", right hand on "Right Hand"). Missing bones the part needs are attached with it (`Anim::getOrAttachBone`, `components/animation/attachbone.hpp`).
- **Skinning.** A NIF part with a skin is turned into a vertex array with bone indices and weights plus an `Anim::Skin` controller (`components/vsgadapters/nif/nif.cpp`, `handleSkin`; `components/animation/skin.hpp`). The controller gathers one matrix per bone each frame. The vertex shader applies them (`SKIN` define in `files/shaders/default/main.vert`). With the G-buffer on, `Anim::Skin::keepPreviousMatrices` doubles the matrix array so the previous frame's matrices are available for motion output (`skin.hpp`, task 0026). `Anim::SoftwareSkin` (`components/animation/softwareskin.hpp`) gives the CPU the skinned vertices for ray tests.
- **Race body size.** `MWClass::Npc::adjustScale` (`apps/openmw/mwclass/npc.cpp`) scales the whole actor by the race's height (z) and weight (x, y) for the sex (`ESM::Race::RADTstruct::mMaleHeight`, `mFemaleHeight`, `mMaleWeight`, `mFemaleWeight`, `components/esm3/loadrace.hpp`). In first person only height is applied. So Morrowind already has one built-in "slider": a uniform per-race stretch. Collision does not use it (`rendering == false` returns early).
- **Beast races** use a different skeleton (`isBeast` from `ESM::Race::Beast` in `updateNpcBase`) and have a tail part type (`MP_Tail`/`PRT_Tail`).

## 2. Seams, and whether the engine has morph targets

- **Seams today.** The parts are authored to meet at their edges in the bind pose; nothing in the engine welds them. I found no seam logic in `npc.cpp` or `bodyparts.cpp`. Whether stock parts share exact boundary vertices or merely overlap is **verify** (needs the user's own game data, which cannot be in the repository). Any scheme that moves vertices per part will open gaps unless it moves coincident vertices identically (see the design, section 7).
- **NIF morphs exist, as keyframed vertex animation.** `Nif::NiGeomMorpherController` and `NiMorphData` (`components/nif/controller.hpp`, `components/nif/data.hpp`) are parsed. `handleGeomMorpherController` (`components/vsgadapters/nif/nif.cpp`) builds a dense `vec4` storage buffer of per-vertex, per-target offsets (`numMorphs * numVertices` entries, the first entry's `w` holding the count) and a float weights buffer; `Anim::Morph` (`components/animation/morph.hpp`) copies the animated weights into it each frame; the vertex shader adds `weight[i] * offset[vertex * numMorphs + i]` under the `MORPH` define (`files/shaders/default/main.vert`, around lines 14 to 52). So there **is** a GPU morph path that is correct for a handful of targets. It is dense (memory grows with vertices times targets) and driven by animation keys, so it does not fit fifty body sliders on a whole body. Which stock Morrowind models use it is **verify**.
- **No compute skinning or morphing.** Skinning and morphing run in the vertex shader. Compute passes exist for other features (`files/shaders/comp/`: cloud, light, volume, particle, fogofwar, worldoverlay; GLSL). New shaders are Slang (decision 0009), so a compute morph pass would be a new Slang shader.

## 3. Skin marks for PBR and subsurface scattering

- `markSkinModel` in `apps/openmw/mwrender/npc.cpp` calls `Render::Pbr::OverrideTable::markSubsurfaceModel(modelPath)` (`components/render/materialoverrides.cpp`) for the head and every part that `getBodyParts` returned or whose `ESM::BodyPart::mData.mType == MT_Skin` (`addPartGroup`). The mark is keyed by **model path** and is needed before the model is first read.
- Task 0027's reviewer already recorded the weakness: a model is loaded and cached once, so a mark added after a first load without the mark is not seen (task 0027 stage log, "Risk, not fixed"). Task 0060's preloader (`Npc::defaultPartModels`) calls `markSkinModel` before it reads, to avoid this.
- Eyes: stock heads carry the eyes inside the face texture; replacers with separate eye shapes are excluded by texture name (`Render::Pbr::isEyeTexture`, task 0033's 2026-11-01 note).
- **Consequence for AdvancedBodies.** A morphed or baked body part is a *new* mesh with no stable model path, so the path-keyed mark cannot be reused as is. The body system should mark skin by the part's role (the region map says skin or garment) when it creates the material, not by file name. The design proposes this.

## 4. What a save stores for a look, and the player's character creation

- **Residents.** `NpcState` (`components/esm3/npcstate.hpp`) holds inventory and stats; **no appearance**. The look comes from the NPC record in the content files each time.
- **The player.** The player's record is an `ESM::NPC` with the id "Player"; `ESMStore::insert` stores it directly (`apps/openmw/mwworld/esmstore.cpp`, the branch `npc.mId == "Player"`), other dynamic NPCs get generated ids. `ESMStore::write` writes the dynamic NPC records into the save (`get<ESM::NPC>().write(writer, progress)`, same file). So the player's race, head, hair and sex already travel in the save as a dynamic record.
- **Character creation.** `MWGui::RaceDialog` (`apps/openmw/mwgui/race.cpp`) holds three indices (`mGenderIndex`, `mFaceIndex`, `mHairIndex`) over lists of available heads and hairs filtered by race and sex; accepting writes `mProto.mHead`, `mProto.mHair` and the sex flag. The preview is `MWRender::RaceSelection` (`apps/openmw/mwrender/preview.hpp`), which takes a prototype `ESM::NPC` (`setPrototype`) and draws it. There are no continuous sliders; choices are discrete body-part records.
- **Unknown records in a save** are skipped with a warning (decision 0005, consequences about `OEPL`). That is the precedent for a new core save record. What exact registration a new record type needs in `ESM::` is **verify** (a task reads `components/esm/defs.hpp` and the save writer first).

## 5. What CreativeMotion offers today (vendored in `components/creativemotion`)

- **Rig and profile** (`core/rig`, `opas::rig::Rig`, `Body` with `CapsuleShape`/`BoxShape`/`SphereShape`, `Joint`): the physical body CreativeMotion simulates; JSON, canonical writer, located errors (`core/rig/CLAUDE.md`). The format docs (`docs/formats/*.md`) and the sample `humanoid.rig.json` are in CreativeMotion's own repository; this vendored copy has `data/clips` and `data/profiles` only. After decision 0010 item 20 (CreativeMotion is edited here), these docs belong in this repository: **verify** and move them in the first CreativeMotion task that needs them.
- **Skeleton profile** (`anim/clip`, `opas::anim::SkeletonProfile`, `BoneMapping`, `loadSkeletonProfile`, `writeSkeletonProfile`, `validateSkeletonProfile`, `identityProfile`): canonical bone name to target bone name plus a leg chain. The shipped example `data/profiles/humanoid-to-eden.skeletonprofile.json` maps 17 canonical bones to the Morrowind `Bip01 ...` names. This is the base for the single bone-map format (handoff D7).
- **Body maps, measurements, capsule fit** (`kinematic/markers`, `opas::markers`): `BodyMapping` (limbs, capsule rules, IK chains, fingers), `measureBody(skeleton, mapping)` giving `BodyMeasurements` (limb lengths and `SurfaceCapsule`s from the rest pose), `CapsuleFit` (radii fitted to skin sample points). These are the working prototype of the guide's measurements and capsule proxy.
- **Markers and alignment** (`InteractionMarker.hpp`, `Alignment.hpp`): contacts between two actors; the part that should stay with animation (handoff D3).
- **Style layer and pose driver** (`apps/openmw/mwrender/creativemotiondriver.*`, `creativemotionstyle.*`): the engine adapters; they map Morrowind bone names and axes at one boundary (`mwrender/CLAUDE.md`, task 0053). Foot IK, look-at and compound hitboxes live in `ActorIkController` and read bones only through `BonePose` (`mwrender/CLAUDE.md`, "Bones through the bone interface").
- **Assumptions body changes must respect** (handoff section 4, `core/behaviors/CLAUDE.md`): unrotated bone rest frames, nothing rotating above the animation root, two box feet for balance, units metres and Z up. Morrowind units convert at one boundary (`Constants::UnitsPerMeter`).

## 6. What the renderer and the rest of the engine offer

- **Vulkan on VSG, one scene graph per actor**, deletions through `vsgUtil::DeletionQueue` (mutex guarded since the LOD S0 crash fix), node compile only on the main thread (`mwrender/CLAUDE.md`).
- **G-buffer, material model, SSS** (tasks 0026, 0027, 0033): skin is a flag in `material.a`; SSS blurs only marked pixels. Motion output needs previous-frame bone matrices (`Anim::Skin::keepPreviousMatrices`) and, for any new vertex motion, previous-frame morph weights.
- **Actors are never in LOD clusters.** The cluster bake takes statics only (`ESM::REC_STAT`; task 0059 design D1) and the LOD design classes actors as "dynamic (never baked)" (`docs/design/world-lod-and-streaming.md`, section 3.5).
- **Derived data and archives.** Derived caches are Eden Archive packs flagged `derived`, keyed by source hashes plus tool version plus parameters, written beside the user data and never inside an author's pack (`docs/design/eden-archive-format.md` sections 11 and 14.7; world-LOD doc 4.5). A path-keyed generic entry (type 0x0000) needs no registry change (`docs/spec/eden-archive-format-v0.1.md` section 11.2).
- **Jolt.** Pinned v5.5.0 (`extern/CMakeLists.txt`). Soft bodies exist in Jolt since v4.0.0 (release notes, "Added support for soft bodies"), and `Jolt/Physics/SoftBody/` is present in a fetched v5.5.0 tree in a build folder (`SoftBodySharedSettings.h`, `SoftBodyMotionProperties.h`). The handoff's "v5.6.0" is wrong for this repository (the pin is 5.5.0). Whether Jolt soft bodies suit cosmetic skinned regions, and whether one can live in a separate `PhysicsSystem` run off the gameplay step, is **verify** (needs a prototype, as the guide says).
- **Eden Studio editor modules.** `sdk/include/openeden/editor_module/{module,registrar,types}.hpp`; the worked example is `editor_modules/creativemotion_editor/` (a separate library, no Qt, no engine types, `CLAUDE.md`). Decision 0007: core systems' modules come from a fixed core list; the list's format is not decided.
- **File names.** `CI/check_file_names.sh` requires lowercase letters and digits for C and C++ files except the listed trees (`components/extension`, `components/creativemotion`, `sdk`, `extensions`, `editor_modules`, a few named tests). New directories `components/body`, `components/garment`, `components/softbody` need no exception if files are lowercase (`bodypackage.cpp`). `editor_modules/` is already excluded, so `editor_modules/advancedbodies_editor/` may use snake_case. Directory names are not checked by the script (only file names).

## 8. Community body ecosystems: formats and licences (summaries in my own words)

- **BodySlide and Outfit Studio** (github.com/ousnius/BodySlide-and-Outfit-Studio, page read 2026-11-02). Described as a tool to convert, create and customise outfits and bodies for several Bethesda games. The repository page lists its licence as **GPL-3.0** and says its NIF handling is the separate library nifly. The page does not say what slider-set or morph files contain. So: reading *its data* is a format question (**verify** the slider-set and morph-file formats from its wiki), and reusing *its code* needs the exact licence header of each file: GPL-3.0-**only** code cannot be relabelled "or later", and OpenEden's rule is GPL-3.0-or-later (root `CLAUDE.md`, Guardrails). Default: write our own reader from the documented format; do not copy code (**verify** before any copy).
- **Slider presets and body meshes made by modders** carry their authors' own licences; a preset is data someone else wrote. OpenEden bundles none (guide section 10: "bundled content must be original or clearly licensed"; root guardrail: no game assets).
- **Morph targets in NIF** (Morrowind era): `NiMorphData` is read by this engine (section 2). Other NIF generations and `.tri` morph files (FaceGen's format) are **verify**.
- **glTF morph targets** are part of core glTF (the Eden Archive design lists them as needed for facial and body animation, `docs/design/eden-archive-format.md` section 9). Whether the engine loads glTF meshes for rendering is **verify** there as well; CreativeMotion's reader loads clips and skeletons only (`anim/gltf`).
- **HDT-style physics XML** is mentioned on the BodySlide page as a preview target; its format and licence are **verify** and out of scope until B9 and B10.

## 9. Findings that change the guide's plan

1. Morrowind has no body mesh to morph. The guide's "body package with one render mesh" needs a *virtual assembled body* for the legacy adapter (design section 7).
2. The engine already has one working GPU morph path and one race-wide scale; both are useful, neither is a slider system.
3. The skin mark is keyed by file path and load order; it must move to the part's role.
4. A saved look exists only for the player (a dynamic NPC record). Residents need no storage if variety is seeded.
5. The Jolt pin is 5.5.0, not 5.6.0.
6. CreativeMotion's format docs and rig sample are not in this repository yet.
