## 2. What VulkanSceneGraph does with textures (read, v1.1.16)

1. **One allocation for the whole chain.** `DescriptorImage::compile` calls `imageInfo->computeNumMipMapLevels()` if `image->mipLevels == 0`, then `imageView.compile(context)`, which creates the `VkImage` and binds memory reserved from `context.deviceMemoryBufferPools->reserveMemory(...)` (`src/vsg/state/DescriptorImage.cpp`, `src/vsg/state/ImageView.cpp` line 186). The data is copied by `TransferTask` or `context.copy`. There is no way to bind some mips and not others: without sparse binding, memory for every level is allocated at creation.
2. **The descriptor is written once.** `DescriptorSet::Implementation::assign` calls `vkUpdateDescriptorSets` from `compile` (`src/vsg/state/DescriptorSet.cpp`). Nothing in `src/` updates a descriptor later. Replacing an image therefore means a new `vsg::Image`/`ImageView`/`ImageInfo` and a new compiled `DescriptorSet` (or a new `StateGroup` child) for every state that uses it, swapped on the main thread between frames, the old one going to the project's `DeletionQueue`. (Whether a descriptor set may be rewritten while a queued frame uses it depends on `VK_EXT_descriptor_indexing` update-after-bind, which VSG does not enable: **verify**.)
3. **Memory pools keep freed capacity.** Device memory comes from pools (`MemoryBufferPools`, `minimumDeviceMemorySize = 16 MiB`); freed slots return to the pool, and `releaseUnusedPools()` ("call this on application memory pressure rather than routinely") frees only **wholly unused** pool entries (`include/vsg/vk/MemoryBufferPools.h`, `src/vsg/vk/MemoryBufferPools.cpp` line 352). **Consequence for any scale-back: dropping a texture does not lower `heapUsage` until its pool entry is empty and released.** Fragmentation can keep a 16 MiB entry alive for one live 64 KiB texture. This is the largest finding of this note (section 4).
4. **Mip generation.** With a single-level `vsg::Data` and a sampler whose `maxLod` is `VK_LOD_CLAMP_NONE`, VSG counts levels from the image size and generates them on the GPU with blits (`computeNumMipMapLevels`, `TransferTask` loop with `baseMipLevel = i - 1`). With `data->properties.mipLevels > 1` it uploads the levels given. A sampler with `maxLod` 1 asks for one level (`ImageInfo.cpp`).
5. **`ImageView::subresourceRange`** is public (`baseMipLevel = 0`, `levelCount = VK_REMAINING_MIP_LEVELS` by default, `ImageView.cpp`). A view with `baseMipLevel > 0` hides the top levels from the shader but **saves no memory** (the image still owns them). A sampler `minLod` clamp has the same property: it makes unwritten top mips harmless to sample (the hardware never reads below `minLod`: Vulkan spec, sampler LOD clamp; **recalled, verify** for anisotropic filtering), which is what a "tail first, top later" scheme needs to avoid garbage while a top level uploads, but again saves no memory.
6. **No sparse support.** `grep -i sparse` over `src/` and `include/` of VSG finds nothing. Sparse residency would mean our own `vkQueueBindSparse` code on VSG's queue, our own image creation, and a transfer path VSG does not know. The device report has the features (llvmpipe reports `sparseResidencyImage2D`, note 0025 section 5; the RTX 4070 was not recorded here: verify; a real weak card may not have it).
7. **`vsg::Device::availableMemory`** already reads `VK_EXT_memory_budget` (`src/vsg/vk/Device.cpp` line 214) and VSG enables the extension when present (line 117); it is a helper VSG uses to size pools, not a pressure API.

## 3. How games and APIs cope (recalled, verify every item before relying on it)

- **Texture streaming pools.** Unreal Engine's texture streamer keeps a fixed pool (`r.Streaming.PoolSize`, a size in MiB) and drops resident mips of the least-needed textures when wanted mips exceed it; "wanted mip" comes from the screen-space size of the primitives that use the texture, with a per-texture bias (Unreal documentation, "Texture Streaming Overview"; recalled, verify). Unity's "Mipmap Streaming" has a "Memory Budget" setting and a "Max Level Reduction", and reduces mips of the least important textures first (Unity manual, "Mipmap Streaming"; recalled, verify). Both are the shape proposed here: a budget, an importance per texture, a global fall-back when the budget cannot be met.
- **Software virtual texturing / feedback.** id Software's MegaTexture and the GDC talks by J. M. P. van Waveren ("Software Virtual Textures", 2012) and M. Mittring ("Advanced Virtual Texture Topics", SIGGRAPH 2008) read the needed mip per page from a low-resolution feedback render (recalled, verify). DirectX 12 Sampler Feedback (Microsoft documentation, 2020; recalled, verify) gives the GPU's exact sampled mips; Vulkan has no portable equivalent. The estimates below are the **sampler-feedback-free** alternative the task asked about.
- **Budget-driven quality ladders.** Console and PC titles commonly expose one dynamic setting that degrades in a fixed order (texture pool, shadow resolution, volumetrics, draw distance) when memory or frame time exceeds a target (recalled from public developer talks; no specific source named, so this is background, not evidence). Dynamic resolution is the same shape for frame time.
- **`VK_EXT_memory_budget`** (Vulkan specification, extension appendix; recalled, verify): per heap, `heapBudget` is "an estimate of how much memory the process can use before allocations start to fail or performance degrades", `heapUsage` "an estimate of how much the process is using". The spec calls both estimates; they "may change at any time" and are updated by the driver, so reading them every frame is wasted work and a sample every few hundred milliseconds is typical. The budget is **less than the heap size** because it excludes what other processes (the compositor, the browser) hold, so it is the right limit for "what may I use", and **it moves** when another application starts. `heapUsage` counts the **process's** allocations only. Neither says anything about a failure to come: `vkAllocateMemory` can still return `VK_ERROR_OUT_OF_DEVICE_MEMORY`, and some drivers over-commit and page device memory into system memory instead of failing (Windows' WDDM does; recalled, verify), after which the first symptom is stutter, not an error.
- **No "out of memory" callback.** Windows' DXGI offers `IDXGIAdapter3::QueryVideoMemoryInfo` and a budget-change notification event (`RegisterVideoMemoryBudgetChangeNotificationEvent`; recalled, verify); Vulkan offers polling only. VMA's documentation ("Staying within budget") describes the same polling and a "budget" query per heap (Vulkan Memory Allocator docs, GPUOpen; recalled, verify). We poll.
- **`VK_EXT_memory_priority`** (recalled, verify): a hint per allocation (0 to 1) telling the driver what to evict first when it over-commits. Cheap to use for render targets (high) against streamed textures (low) and it needs `VkMemoryPriorityAllocateInfoEXT` on VSG's allocations, which VSG does not set (**verify**; `reserveMemory` takes a `pNextAllocInfo`, so a hook exists for pools). The device report records the extension. Treat as a stage-d option, not part of the first build.
- **Hysteresis and flicker avoidance.** The standard remedies are: two thresholds (act above a high mark, undo below a lower mark), a minimum dwell time between actions, acting on a smoothed signal rather than a sample, and one step at a time. A further rule that this project adds in the spec: **only undo a step when its known cost still fits under the high mark** (undoing must not immediately re-trigger the reduce). This turns oscillation from a tuning problem into an invariant that a test can state.
- **Per-object mip selection without feedback.** Standard approach (recalled, verify against Unreal's and Unity's descriptions above): for each renderable, texels per world unit `td` of its texture on its mesh (`td = texSize * sqrt(uvArea / worldArea)`, a constant computed once from the mesh) and the world size of a pixel at the object's nearest point `wp = 2 d tan(fov/2) / screenHeight`; the wanted level is `max(0, floor(log2(td * wp)))`, plus a bias for anisotropy and a floor. This is derivable from first principles (a texel should project to about one pixel) and no source is needed for the formula; the bias constants are the part that needs measuring.

## 4. What the evidence says about feasibility

1. **The pressure signal cannot be `heapUsage` alone.** Because the pools retain freed memory (section 2, item 3), usage may not fall after a reduction, and a controller reading only usage will keep reducing (a ratchet) or, once pools are released, jump. The controller therefore works from **our own accounting** (bytes each system holds, section 5 below) against the **budget** (the driver's `heapBudget` times a safety factor, or a number the user gave), and uses `heapUsage` as a cross-check and as the "other processes" and "untracked" remainder (`usage - accounted`). After a reduce step, the pool release (`releaseUnusedPools()`, main thread, at a safe point) is part of the step's cost, with its measured effect logged.
2. **Few of the reducible systems can change at run time today.** The shadow, point-shadow, volumetric and history targets are created in `RenderManager`'s constructor from settings read at start. Reducing one means rebuilding a render graph, command graph and descriptor set mid-session: a hitch of unknown size and a risk (resize paths exist for the swapchain, `syncExtents`, but not for these). Honest ordering by cost to implement: the texture cap and mip streaming (new work anyway), the far cluster/tile budgets (already live), point-light shadow count (slots can be switched off without recreating the image), then everything that must be rebuilt.
3. **Mip streaming is the one that can give back large memory** and also the hardest. Arithmetic (derived): a 2048 x 2048 RGBA8 texture with a full chain is 2048 * 2048 * 4 * 4/3 = 21.3 MiB; BC1 is 2.7 MiB, BC3 and BC7 5.3 MiB. A scene with 400 unique materials of two BC7 2K maps each holds 400 * 2 * 5.3 = 4.3 GiB (derived, illustrative), which is a Skyrim-class view on a 6 GiB card. A level 8 times smaller in each dimension is 1/64 of the memory (1/256 for 128 px against 2K, as toddhow said). Keeping only levels the camera can use is where the saving is; a flat cap gives up the nearby detail too.
4. **Streaming needs a data path.** The container's mip-tail layout covers `.edenpak` KTX2 entries only (task 0060). Loose DDS files from mods have their full chain in memory after the VFS read; mips beyond the wanted ones are CPU-side data to keep or to re-read. A mip-streamed texture from loose DDS has its upload cost paid once at load (everything is read), so streaming then saves GPU memory, not load time or RAM. That is acceptable for the stated goal (VRAM) and cheap to build: **mip dropping is the existing `dropMipLevels`**; the new part is doing it per texture, later, and swapping.
5. **Swap cost is real.** Section 2, item 2: each swap is a new image, an upload of the wanted levels, and a descriptor-set rebuild for each material state sharing the texture. VSG shares textures through `vsg::SharedObjects`, and a material's `StateGroup`/`DescriptorSet` is shared by many nodes; the swap point is the shared `DescriptorSet`, which is good (one rebuild per material) but only if the project's NIF-to-VSG path keeps them shared (**verify** in `components/vsgadapters/nif/nif.cpp`; the task's stage d0 measures it).
6. **Steps are powers of four.** A full chain is 4/3 of its top level. Dropping the top level leaves 1/4 of the chain's memory, dropping two leaves 1/16 (derived). One reduction step = one level therefore has a large, predictable effect, which suits a ladder, and the tail (levels below 64 px, a few hundred KiB for a 2K texture) is never worth evicting.
7. **Sparse residency is not worth planning around.** VSG has none (section 2, item 6); the feature may be absent on the cards that need help; standard sparse blocks are 64 KiB (Vulkan spec; recalled, verify) so only the top few levels of 1K+ textures benefit. Recorded as an option in design doc 8.2 tier Ultra; this task leaves it out.

## 5. Accounting categories to expose (design input for stage a)

What the renderer holds, in bytes, by owner (each owner computes its own number from its dimensions and formats; none can be read back from Vulkan per allocation, because VSG's pools hide per-object use): object and terrain textures (by `ImageUse` category, from the loader that knows the capped size), tile albedo pictures and far cluster geometry (the LOD planner already counts `mResidentBytes`), render targets (HDR colour, depth, G-buffer, TAA and AO history, bloom chain), shadow cascades and point-shadow atlas, volumetric froxel images, GI probes and reflection images, cloud volume images, UI atlases and everything else = `heapUsage - accounted` (reported as "untracked"). A budget of 0 / unknown (no `VK_EXT_memory_budget`) falls back to `deviceLocalMiB()` times the same factor as task 0049's `auto` table and says so in the log line.

## 6. Open items this note could not settle

- The update cadence and accuracy of `heapBudget` and `heapUsage` on NVIDIA, AMD and Intel drivers: measure (task stage a logs both every 500 ms for a session).
- Whether a descriptor set can be safely rewritten after queue submission in VSG's frame structure (it cannot, without update-after-bind); the swap must go through the deletion queue instead.
- Whether the second device-local heap on resizable-BAR cards (a small host-visible, device-local heap) makes the sum in `deviceLocalUsageMiB` misleading: log per heap in stage a.
- The cost of `releaseUnusedPools()` (a stall in `vkFreeMemory`) on each driver: measure.
- Whether `VK_EXT_memory_priority` changes behaviour under oversubscription on the test card: measure once, only if the first build shows paging.
