## 1. What exists

### 1.1 In the neutral model and the Skyrim pack

- `sdk/include/openeden/game/world_model.hpp` (FROZEN 1.0, with 1.1 additions): `WorldCell` has `interior`, `hasGrid`, `gridX`, `gridY`, `world` (a `WorldId`), objects, lighting. **It has no terrain, no water, no worldspace record type.** `WorldCellSource` (`world_source.hpp`) already has `findCellByGrid(world, x, y)`, `findWorldByEditorId` and `unitsPerMetre` (Skyrim: 69.99125109 per `world_view.cpp`; RECALLED-VERIFY that this is right for Skyrim, `docs/design/neutral-world-model.md` says so too).
- `game_packs/skyrimse/include/game_skyrimse/records.hpp`: `WorldRecord` holds only `mCommon`, `mName`, `mParent` (WNAM). `CellRecord` holds `mGrid` (XCLC), `mWaterHeight` (XCLW), flags (DATA), `mWorld`, the exterior block and sub-block labels, `mWorldPersistentCell`, and the persistent / temporary / visible-distant reference lists. **LAND is only a name in the recognised-type table (`pack_core.cpp` line 32); there is no LAND, LTEX, TXST or WATR decoding.** Not decoded in WRLD: PNAM (parent usage flags), DNAM (default land and water height), NAM0 and NAM9 (bounds), NAM2/NAM3/NAM4 (water, LOD water), CNAM (climate), the map data.
- `game_packs/skyrimse/src/world_view.cpp`: the exterior grid works for objects. `kCellSize = 4096`, `mCellByGrid` keyed by `(world, x, y)` (lines 454 to 528), `findCellByGrid` (line 625), and a world's persistent placements are assigned to the grid square they stand in (lines 923 to 946). `neutral_world.cpp` `loadNeutralCell` copies `hasGrid/gridX/gridY/world` (line 269) but nothing in the engine builds an exterior from it.
- Engine side: `WorldModel::emplaceNeutralInteriorCellStore` (`apps/openmw/mwworld/worldmodel.cpp` about line 219) refuses an exterior with "exterior neutral cells are not supported yet" (about line 239). The neutral session starts in a named interior (`MWState::NeutralNewGame`, task 0109).

### 1.2 In the engine, inherited: an incomplete ESM4 exterior path

- `components/esm4/loadland.hpp`: `ESM4::Land` parses LAND: `sVertsPerSide = 33`, `sRealSize = 4096`, `sHeightScale = 8`, `sQuadTexturePerSide = 6`, VHGT/VNML/VCLR, and per quadrant a `BTXT` and a list of `ATXT` layers each with `VTXT` alpha entries. `ESM4::Land` is a store in `ESMStore` (`esmstore.hpp` line 154).
- `components/esmbridge/esmterrain.cpp`: `ESM::LandData(const ESM4::Land&, int)` integrates VHGT into floats and fills `mSize = Constants::ESM4CellSizeInUnits` and `mLandSize = 33`. **Nothing in the Vulkan terrain uses it**: `grep` finds `ESM::LandData` only in its own files. `MWRender::LandManager::create` (`apps/openmw/mwrender/landmanager.cpp`) returns an empty `LandObject` for every non-default worldspace with the comment "ESM4 terrain is not ported (task 0012)", and `Scene::loadCell` (`apps/openmw/mwworld/scene.cpp` lines 454 to 475) adds no heightfield for an ESM4 worldspace (`else if (!ESM::isEsm4Ext(worldspace))`).
- Worldspace-keyed plumbing that **does** exist and is useful: `ESM::isEsm4Ext(worldspace)` is "any worldspace other than Morrowind's default" (`components/esmbridge/util.hpp`), `ESM::getCellSize(worldspace)` returns 4096 or 8192, `ESM::getLandSize(worldspace)` 33 or 65 (`util.cpp`), `positionToExteriorCellLocation` uses them, and `Constants::ESM4CellGridRadius = 2` (`components/misc/constants.hpp`) gives a 5x5 active grid instead of Morrowind's 3x3 (`Scene::` line 315 and 878). `Scene::preloadExteriorGrid` (line 1331), `Scene::loadCell` (line 598), `World` (`worldimp.cpp` lines 1270, 1307), the navmesh manager (`detournavigator/navmeshmanager.cpp` line 63) and the Lua land bindings (`mwlua/landbindings.cpp` line 93) already call `getCellSize(worldspace)`.

### 1.3 The terrain component

- `Terrain::Storage` (`components/terrain/storage.hpp`) is already generic in the two numbers that matter: its constructor takes `cellWorldSize` and `cellVertices`, `numVerts(chunkSize, lod)` uses them, and `Terrain::Builder` (`builder.cpp` lines 684, 773, 776, 823, 824) and `Terrain::Paging` (`paging.cpp` lines 44, 87 to 92) only use those members. The interface is three methods in **cell units, with no worldspace**: `getVertexData(lodLevel, bounds)`, `getBlendmap(bounds)`, `getLayers()`, plus `getHeightAt(pos, worldspace)` and an optional `getDiffuseOverride`.
- `ESMTerrain::Storage` (`components/esm3terrain/storage.cpp`) is the Morrowind implementation: its constructor is `Terrain::Storage(ESM::Land::REAL_SIZE, ESM::Land::LAND_SIZE)` (line 37), and the body uses `ESM::Land::LAND_SIZE` (65) and `LAND_TEXTURE_SIZE` (16) as literals throughout (`fixNormal`, `fixColour`, `getVertexData` lines 181 to 270, `getVtexIndexAt` lines 289 to 311, `getBlendmap` lines 351 to 387, `getHeightAt` lines 389 to 420). `getLand(int, int, cache)` asks `getLand({x, y, {}})` with an **empty worldspace** (line 477): the whole terrain system serves one worldspace at a time and is never told which.
- The terrain fragment shader (`files/shaders/terrain/main.frag` lines 117 to 125, 217 to 236) draws **four layers per blend-map texel with fixed bilinear weights**: the blend map is an RGBA8 image of layer indices, one index per corner, and the weights are the bilinear coordinates inside the texel. This is Morrowind's model (one texture index per cell of a 16x16 grid, per `getBlendmap`). `Terrain::Builder` supports up to 256 layers in an array texture (`builder.cpp` line 248).

## 2. The format facts (measured unless marked)

All counts are of `Skyrim.esm` alone unless a master is named; the four other masters mostly override.

- **Vertex count and spacing.** VHGT is 1,096 bytes in 15,410 of 15,410 records that carry it: a float offset, 33 x 33 = 1,089 signed gradient bytes, three pad bytes. VNML is 3,267 bytes (33 x 33 x 3), VCLR 3,267 bytes (6,058 lands carry it), DATA is 4 bytes (a flag word: values 31, 29, 25, ... meaning which data are present, RECALLED-VERIFY the bit meanings). **A cell is 33 x 33 vertices, 32 intervals, 4,096 units, so the spacing is 128 units, the same as Morrowind's 8192 / 64.** The height scale is 8 per step as in Morrowind. A cell therefore has a quarter of Morrowind's area and a quarter of the vertices (1,089 against 4,225).
- **Heights.** Decoding VHGT as upstream does (offset plus cumulative gradient times 8, row by row; `components/esm4/loadland.cpp`'s layout, my own decode here): Tamriel's LAND heights run from -37,032 to 39,392 (a range of 76,000 units, larger than Morrowind's 21,000: a 16-bit height of 1/8 unit does not fit it, see risks). A cell's edge vertices **do not always match its neighbour's**: of 22,159 shared Tamriel edges, 49 (0.2 percent) differ, the largest by 96 units. So the terrain cannot assume a perfectly shared edge, as Morrowind also cannot (`ESMTerrain::Storage::averageNormal` and `fixNormal` handle the seam for normals). Orientation of rows and columns (which axis the first row is) is RECALLED-VERIFY; it must be settled by the same method as the rotation (statics resting on the ground).
- **Texture layers.** Each LAND has per quadrant (the cell is four 17 x 17 vertex quadrants; quadrant 0 is south-west, 1 south-east, 2 north-west, 3 north-east, RECALLED-VERIFY against upstream's comment in `loadland.hpp`): up to one **BTXT** (8 bytes: LTEX form id, quadrant byte, padding) and a list of **ATXT** (8 bytes: LTEX form id, quadrant byte, padding, u16 layer index) each followed by one **VTXT** (n x 8 bytes: u16 grid position, 2 pad bytes, f32 opacity). Measured in `Skyrim.esm`: 35,283 BTXT and 102,968 ATXT/VTXT, all with these exact sizes; VTXT positions are sorted ascending in all 102,968 and the maximum is 288 (so a position is `row * 17 + column` of the quadrant's 17 x 17 grid, RECALLED-VERIFY for the row/column order); opacity is in (0, 1]; the layer indices of a quadrant are contiguous 0..n-1 in all 34,291 non-empty quadrants. **Layers per quadrant: 0 (27,965 quadrants), 1 to 6 (at most 6 observed); layers per whole cell: up to 23.** BTXT per LAND: 4 in 7,852 lands, 3 in 767, 2 in 595, 1 in 384, **0 in 5,966 (38 percent: a default ground texture must apply, RECALLED-VERIFY which; upstream's `assignDefaultTextures` in `esm4/loadland.cpp` does this)**. **10,914 ATXT entries (10.6 percent) name a null LTEX** (BTXT never does); meaning unknown, to be treated as "no layer" until checked.
- **Ground textures.** `Skyrim.esm` has 68 LTEX records (each with `TNAM` the texture set, `MNAM` material, `HNAM` havok data, `SNAM` specular exponent, `GNAM` grass list) and 572 TXST. LAND references 69 distinct LTEX forms in `Skyrim.esm`, 66 in `Update.esm`, 58 in `Dawnguard.esm`, 45 in `Dragonborn.esm`, 37 in `HearthFires.esm`. The TXST path (diffuse, normal, parallax and so on) is the existing material question of 4.7; the terrain array texture needs the ground set resolved to file paths.
- **Worldspaces.** `Skyrim.esm` has 37 WRLD records (all 37 have cells). **Tamriel: 11,187 cells with an XCLC grid (a full rectangle 119 x 94 = 11,186 from x -57 to 61, y -43 to 50, plus one more record), 11,186 LAND records, 15,193 persistent placements, 240,889 temporary placements.** Bounds NAM0/NAM9 (-233,472, -176,128) to (253,952, 208,896) in units (cells -57..62 by -43..51). Default land height -27,000 and default water height -14,000 (DNAM), LOD water height -14,000 (NAM4), a climate (CNAM) and a water type (NAM2). Other big worlds: Sovngarde 3,135 cells with 2,966 LAND, SkuldafnWorld 396 / 364, Blackreach 320 / 125, MarkarthWorld 147 / 140, **WhiterunWorld 114 cells with 7 LAND records and 485 persistent placements**, with Update.esm adding 16 cells and Hearthfires 8. Dawnguard adds DLC01SoulCairn (9,448 cells, 913 LAND), DLC01FalmerValley (618 / 551); **Dragonborn adds DLC2SolstheimWorld with 34,558 cells and 34,383 LAND over a 192 x 192 grid (-64..127), which is far larger than the playable island; I did not find out why (probably flat sea-floor or empty land cells), so any "Solstheim" cost estimate is unreliable**, and DLC2ApocryphaWorld 10,548 cells with 122 LAND.
- **Parent worlds.** 34 of 37 worlds have WNAM (parent) and a PNAM u16 flag word. Whiterun, Windhelm and Solitude have PNAM 0x7F, Riften 0x77, Markarth 0x44, Sovngarde 0x04. Upstream and UESP describe the bits as "use parent's land / LOD / map / water / climate / imagespace / sky cell data" (RECALLED-VERIFY the exact bit order). **WhiterunWorld shares Tamriel's coordinate space: its own seven LAND records are at Tamriel cells (4,-3) (4,-1) (5,-3) (6,-3) (6,-2) (6,-1) (7,-2), and of these 4 have heights identical to Tamriel's LAND in the same cell and 3 differ (the city's flattened ground).** So a city worldspace uses its own LAND where it has one and falls back to the parent's for the cells around it. The neutral model must therefore carry a **parent chain with usage flags** for land (and, for the same reason, water and climate).
- **Water.** XCLW is a float per exterior CELL. In Tamriel 10,630 of 11,187 cells have the "max float" value 3.4028235e38 (use the world's default, RECALLED-VERIFY), 23 have -2,147,483,648 and 37 have 4.29e9, both of which look like an integer written as a float (a "no water" marker, RECALLED-VERIFY), and about 500 have real heights (for example 600 in 51 cells, 10,624 in 85, -5,050 in 21, -13,670 in 10). Cell DATA flags: 0x0200 (15,521 exterior cells), 0x4200 (1,121), 0x02 (331), 0x00 (5); `CellFlags::HasWater` is 0x0002 in the pack, so the exterior cell flag word has bit 0x0200 set in most cells (its meaning is not in the pack, RECALLED-VERIFY: probably "can have water / use LOD"). `WATR` has 34 records in `Skyrim.esm`. Tamriel's default water height of -14,000 is **far from sea level at z = 0**; this must not be confused with Morrowind's sea level 0.
- **Persistent references.** Each world has a persistent exterior CELL with no XCLC directly in its children group (the pack's `mWorldPersistentCell`); the pack already hands each persistent placement to the grid square it stands in. 15,193 for Tamriel, 485 for WhiterunWorld.
- **LAND without heights.** 154 of 15,564 LAND records have no VHGT/VNML (DATA flags): the default land height then applies. LAND exists in the group chain at `(0, 1, 4, 5, 6, 9)`: world group, world children, exterior block, sub-block, cell children, temporary children, so a LAND record is always in the cell's temporary group (15,564 of 15,564).

## 3. The engine's assumptions that break

1. **The terrain system serves one worldspace at a time and is never told which.** `Terrain::Storage::getVertexData/getBlendmap/getLayers` have no worldspace parameter, and `ESMTerrain::Storage::getLand(int, int, cache)` hard-codes an empty worldspace (`esm3terrain/storage.cpp` line 477). `MWRender::TerrainStorage::getLand` forwards to `LandManager::getLand`, which for the default worldspace reads `ESMStore::get<ESM::Land>()`. A Skyrim session has one worldspace active at a time too (Tamriel or WhiterunWorld, one game per session) but needs it switched when the player passes through a load door, which the terrain/paging objects (constructed once in `RenderManager`, line 899 and following) do not support.
2. **Cell size.** The terrain component is generic in `cellWorldSize` (4096 would work), but `Constants::CellSizeInUnits` and `ESM::Land::REAL_SIZE` appear as literals in the consumers of section 1.4. `getCellSize(worldspace)` is the existing right answer for the ones that have a worldspace in hand, and it hard-codes `isEsm4Ext` = not Morrowind: Skyrim worlds would get 4096 and 33 by that rule, which is correct for Skyrim SE. It is **not** a per-game or per-world constant, so a future game with a third size needs a table (a neutral `WorldInfo`).
3. **Grid radius.** `ESM4CellGridRadius = 2` (5 x 5 active cells, 20,480 units across) for non-Morrowind worlds is already there. With 4096-unit cells and a 5 x 5 grid the active square is 20,480 units; Morrowind's 3 x 3 grid is 24,576. Fine for M-S2; the view distance is then carried by object paging and the LOD system, which both assume 8192 (1.4).
4. **LAND resolution.** 33 versus 65 is a constructor argument of `Terrain::Storage` and a literal in `ESMTerrain::Storage`, `Lod::landVerticesPerCell`, and `albedobake.cpp`. The terrain LOD levels inside `Terrain::Builder` rely on `(cellVertices - 1)` being a power of two (32 is).
5. **Texture blending cannot express Skyrim's layers.** The shader mixes four layers with bilinear weights from a corner-index texture; Skyrim gives a base texture per quadrant plus up to 6 (23 per cell) alpha layers with per-vertex opacity on a 17 x 17 grid. A faithful draw needs **weights, not indices** (see section 4).
6. **Water is a single plane per cell, set globally.** `Scene::loadCell` applies `mRendering.setWaterHeight(level)` and `mPhysics->enableWater(level)` for the last loaded cell. With a 5 x 5 grid of Skyrim cells with different heights this is wrong, and for a world whose default water is at -14,000 with scattered lakes at 600 or 10,624 it is wrong in a visible way. Morrowind has one water height per exterior (0) so the problem never appeared.
7. **LOD baker and pack.** Reads `ESMStore::get<ESM::Land>()` (`lodterrainbaker.cpp` line 82) and `rendermanager.cpp` 1445 to 1450; the pack manifest names the world "Morrowind"; tile geometry assumes 65. A Skyrim bake needs a land source from the neutral model and a pack per world.
8. **Save, maps, minimap, groundcover, Lua `core.land`, AI edges, puddle bake:** all use the Morrowind constants (1.4). None blocks M-S2 except the minimap if it is on screen; they can be fenced behind "neutral world" off-states.
9. **The cell identity.** An exterior `ESM::ExteriorCellLocation` is `(x, y, RefId worldspace)`. The neutral store identifies cells by `<gameId>:` ids; a Skyrim world needs a stable `RefId` (for example `skyrimse:w<n>`), and `isEsm4Ext(worldspace)` becomes true for it for free.

## 4. Options

### (a) A neutral `TerrainSource` and a new `Terrain::Storage` subclass (recommended)

- The pack decodes WRLD, CELL water, LAND, LTEX/TXST and gives them through an additive SDK method; the core has a `NeutralTerrain::Storage : Terrain::Storage` (cell size and vertex count from the world's description) and a neutral height lookup for physics. `ESMTerrain::Storage` is **not touched** (Morrowind unchanged by construction).
- Cost centres: the storage class (a re-implementation of `getVertexData` for the neutral grid, with the seam fix for normals and colours; about 300 lines modelled on `esm3terrain/storage.cpp`), the layer model (section 4.1), the world switch (the storage and its `Paging` need to be rebuilt or re-pointed when the worldspace changes), and the consumers of 1.4 that matter for M-S2.
- The terrain component's genericity in `cellWorldSize/cellVertices` is the reason (a) is not a rewrite.

### 4.1 Layer blending (applies to all options)

1. **Weight splat, 4 dominant layers per texel (recommended for v1).** Per quadrant, rasterise the layers' VTXT opacities onto a texel grid (for example 2 x 17 - 1 = 33 texels a quadrant side or one texel per vertex pair), compute the four strongest layers by `opacity * (1 - sum of the higher layers' opacity)` (Skyrim composes layers in index order over the base), normalise, and store four indices and four weights (RGBA8 index map plus RGBA8 weight map). One new shader mode in `terrain/main.frag` and its Slang twin (the weights replace `blendCoeffs`), selected by a define so Morrowind's pipelines are unchanged; the Slang interface records change (golden data). Layers per quadrant are at most 7 (base + 6), so four loses information only where more than four overlap; a cell-level check in the pack can count how often (not measured here).
2. **Corner index quantisation (the Morrowind scheme):** drop weights, keep the dominant index per 17 x 17 vertex. Works with the existing shader, so it is the cheapest spike, and looks coarse.
3. **Per-quadrant splat with up to 8 weights in two RGBA textures:** exact for the data, needs a larger shader and two samples; later.

### (b) Reuse and extend the ESM4 terrain path

- The inherited path already has: `ESM4::Land` (parsing), `ESM::LandData(ESM4::Land)` (in `esmbridge`), `getCellSize/getLandSize(worldspace)`, `ESM4CellGridRadius`, and `WorldModel::createExteriorCell` for ESM4 worldspaces (`worldmodel.cpp` lines 74 to 100). What is missing: `LandManager::create` returns empty land, `Scene::loadCell` adds no heightfield, `ESMTerrain::Storage` still reads 65-vertex Morrowind tables, textures are `mEsm4Textures` that nothing blends, and `ESMStore` must hold `ESM4::Land/Cell/World` loaded by the typed ESM4 reader.
- Against: decision 0016 retires the ESM4 path (N7) and the plan makes the neutral model the only route; `ESMStore` population for Skyrim's 535-plugin mod lists is the memory and load-time problem the neutral model was created to avoid; the ESM4 reader does not do the parent-chain, `PNAM` or `XCLW` semantics; and it would keep Skyrim exteriors coupled to the Morrowind-shaped `ESMTerrain::Storage`. It is valuable as **a reading reference** (its `loadland.cpp` layouts agree with my measurements, apart from the unknown padding bytes) and as an interim visual spike (a day or two with a hand-fed `ESM4::Land` to prove the 4096 / 33 numbers draw), not as the base.

### (c) Other

- **c1. Resample into a Morrowind-shaped `ESM::Land`** (33 to 65 vertices, layers to a 16 x 16 index grid), cell size 8192 by merging 2 x 2 Skyrim cells. Fastest to see something and wrong in four ways (object coordinates would not match any cell, the cell grid and physics would be on 8192 squares, layer weights lost, heights resampled). Not recommended even as a spike beyond a throw-away.
- **c2. Bake Skyrim terrain into static meshes** (a mesh per cell with a baked albedo, no layers): good for LOD (the existing tile bake is this idea) and for a first picture, loses the ground texture system, parallax, wet/snow cover interplay; **use it only for far LOD, which is separate from near terrain**.
- **c3. Generalise `ESMTerrain::Storage` in place** by turning its literals into members: fewer new classes, but it touches the Morrowind code path (guide: "change it only for a reason a task spec states" and "unchanged when off") and its `LandObject` is tied to `ESM::Land`. A cheaper variant, a **shared base class** for the seam logic that both derive from, can come after (a) works.

**Recommendation: (a) with layers by weight splat (4.1 option 1), the ESM4 path as reading reference only, and a throw-away check of the layout against `ESM4::Land` numbers.** It keeps Morrowind untouched, fits decision 0016, and the terrain component's `cellWorldSize/cellVertices` generality means the new storage is a bounded class. The cost is the world switch, the water model, and the LOD/maps work, which are real regardless of option.

## 6. Exterior streaming through neutral cells

- **Cell identity.** The pack mints `WorldId` per cell already; add a `RefId` worldspace for each Skyrim world (`<gameId>:w<n>`) as the `ExteriorCellLocation::mWorldspace`. The Skyrim worlds are then `isEsm4Ext` true and use 4096 / 33 / radius 2 from the existing plumbing.
- **`WorldModel::getExterior(location, ...)`** (`worldmodel.cpp` line 209) and `createExteriorCell` (line 83) get a neutral branch: ask `NeutralWorldStore::findCellByGrid(gameId, world, x, y)` (the pack's `findCellByGrid` exists), build the `WorldCell`, emplace a `CellStore` the way `emplaceNeutralInteriorCellStore` does for interiors (a synthetic `ESM::Cell` record with grid and `setNeutralCell`), and return an **empty cell** (no objects, but with land) if the grid square has no cell record (Tamriel is a full rectangle but the borders and Solstheim are not).
- **The cell grid loop** (`Scene::changeCellGrid`, `scene.cpp` 648 to 730) already iterates by `ESM::ExteriorCellLocation` and uses `getCellSize(worldspace)` and `ESM4CellGridRadius`; no change to the loop, only to what `getExterior` returns. Preloading (`preloadExteriorGrid`) skips neutral cells (R9: the preload thread must not touch the store); the incremental queue (task 0060) takes neutral `Ptr`s unchanged.
- **Terrain**, not the cell store, drives the ground: `Terrain::Paging` asks the storage for chunks around the camera, independent of the active grid. For a neutral world the storage's `getVertexData` pulls `TerrainCell` from the neutral store (a cache that the incremental thread fills). **`getVertexData` and `getBlendmap` are called on loader threads** (`Builder` builds chunks on workers); the neutral store is main-thread only (adopted answer 5). So the terrain storage needs its own thread-safe cache fed by the main thread (a pre-fill of the cells a chunk will need, on the main thread, just ahead of the camera), or the pack must hand over immutable `TerrainCell` shared pointers. This is the **main design risk of streaming** and has no Morrowind precedent (Morrowind's `LandManager` reads the immutable `ESMStore`).
- **Parent worlds.** `TerrainCell` lookup follows the parent chain: a cell without LAND in the active world uses the parent's, when `parentUsage` says so (WhiterunWorld: 7 own LAND, the rest from Tamriel). The terrain for a chunk can mix both within one view, so the storage resolves per cell. Object placements are not inherited (WhiterunWorld has its own 114 cells), but the visible-distant references and the LOD of the parent are (4.6).
- **Persistent references** are already placed in their squares by the pack; a persistent reference far from the player (an NPC that lives in another cell) is not loaded by this scheme and is N5/quests work.
- **Heightfield for physics:** one `addHeightField(heights, x, y, 4096, 33, min, max, holder)` call per loaded cell, exactly as `Scene::loadCell` does for Morrowind with different numbers; `HeightField` uses the size and vertex count it is given (generic). The Jolt heightfield for 33 x 33 samples needs checking against the "convex radius" rule only for shapes, not heightfields. Cross-cell seams: a 96-unit crack at 0.2 percent of edges exists in the data; the physics heightfield should not be asked to fix it.
- **Object floating on terrain / spawn:** the first Skyrim exterior start needs a spawn rule (the player does not stand in a cell of its own; N3a-3's `--start` takes an interior name today).

## 7. Water

- **What the data says.** Per-cell XCLW (mostly "default"), per-world default water height and water type (NAM2), the world's `LOD water height` (NAM4), plus `WATR` records for the type, plus **interior water** (already carried? the neutral `WorldCell` has none). Tamriel's default of -14,000 is the sea; other heights are lakes and rivers placed by cell, with the shore defined by terrain. In Skyrim the water draws as one surface per cell at the cell's height where the cell has water; cells with the "max float" value use the world default only if the cell's terrain dips below it.
- **Engine today.** One global plane: `setWaterHeight`, `enableWater` (physics), `Navigator::addWater(cell, size, level)` per cell (that one is per-cell, generic in size apart from the `ESM::Land::REAL_SIZE` literal). `SimpleWater` is sized by `Constants::CellSizeInUnits` and is the "water plane" renderer in use; the water shader (task 0072 stages) reads the height from the single plane.
- **Plan.** v1 for M-S2: one plane per active worldspace at the world's default height (-14,000 in Tamriel is under the whole of Whiterun; irrelevant there), plus **per-cell planes** as additional `SimpleWater` quads (4096 units square) at each loaded cell's own XCLW when it is a real height, drawn by the same shader with the same type parameters; physics `enableWater` becomes a per-cell query (Jolt: a water volume per cell) rather than a single level. Water types (WATR: colours, fresnel, wave parameters, shallow/deep) are plan item 4.5 and need the neutral type; v1 may use Morrowind-like defaults.
- **Whiterun specifically:** the city has no water in the cells measured (7 own cells have XCLW of -2,147,483,648 = no water, RECALLED-VERIFY), so M-S2 can ship with the default water off and water in the following milestone; Riften and Solitude need it.

## 9. Risks (ranked)

1. **The thread boundary** (section 6): terrain chunks are built on workers, the neutral store is main-thread. A wrong design either stalls the main thread or races. Mitigation: immutable `TerrainCell` snapshots in a bounded, locked cache, filled from the main thread ahead of the camera; test with a stress stream.
2. **Layer weights at 4 layers.** A cell with 23 layers may need more than four per texel; the result differs from the original visibly where grass, snow and rock overlap. Mitigation: measure how often more than four layers overlap per texel in E0, then choose between option 1 and 3 of 4.1.
3. **Parent-chain semantics** (PNAM bits, which data a child inherits, and where a child's cell without LAND draws from): only partly established; Whiterun's seven own cells are the one clear case. Getting it wrong leaves holes or double terrain at city boundaries.
4. **Orientation and quadrant conventions** (rows of VHGT and VNML, quadrant numbering, VTXT position layout) are RECALLED-VERIFY; a wrong one mirrors the ground against the objects. Mitigation: E0 settles it with placements that rest on the ground (the same method as the rotation convention, task 0086).
5. **Scale of the height range** (-37,032 to 39,392): affects the 16-bit height storage in the puddle map (task 0095), the LOD tile quantisation, the physics world bounds, the far plane and depth precision. Check each consumer against the 76,000-unit span.
6. **Water model** (single plane, per-cell heights, sentinel meanings).
7. **Unexplained data:** the 10.6 percent null-LTEX ATXT layers; Solstheim's 34,383 LAND records; the 0x0200 cell flag; the PNAM bit order. Each could hide a decoding mistake.
8. **Memory:** a 5 x 5 grid of 4096 cells with 4 quadrant layers each is small, but a modded profile adds worlds (the five masters give 37 + DLC worlds; the MO2 profile in the machine had 530 plugins) and the neutral store's caps apply to terrain too.
9. **LOD.** Skyrim has its own LOD files (BTR/BTO/BTT) which are a mod-compat matter (4.6); our baker would generate from LAND, which loses what the game's own LOD textures carry. Not needed for M-S2 if the far field is a chosen "LOD-lite".
10. **The WhiterunWorld premise:** if M-S2 means the city worldspace, the acceptance involves two worlds (Tamriel for the plains, WhiterunWorld for the city) and a load door between them (N4); if it means the plains only, it is Tamriel alone. The milestone text should be pinned (question 1).
