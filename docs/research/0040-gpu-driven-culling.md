# GPU-driven culling and indirect draws for OpenEden (research for task 0078)

Date: 2026-11-04. Author: the research agent for tasks 0078 and 0079 (docs only; nothing was built or run). Nothing here is code from any engine or SDK; techniques are described from the talks and papers named below. What I could read myself this session is marked **read**; what I know from the literature or from memory is marked **recalled** and must be checked before anyone relies on a number from it. What the code says is cited by file and function at `7bc9c7fcc9`; VSG facts are from the VSG 1.1.16 source fetched into `build-jolt/extern/fetched/vsg` (read, not built). No dependency is needed (nothing is added to `docs/dependencies.md`).

The short answer, before the detail: **the evidence in the repository does not yet show that the CPU cost of drawing static objects is large enough to justify a GPU-driven path, and the object clusters already took away most of the draws that the baseline blamed.** Section 6 says what has to be measured before anyone writes a compute shader, and section 7 names a cheaper alternative that may win.

## 2. How the scene reaches the GPU today (read from the code)

- **The viewer records a command graph by walking the scene graph every frame.** `vsg::RecordTraversal` (`RecordTraversal.cpp`) visits `CullNode`/`CullGroup` (a sphere against the frustum stack, `State::intersect`), `Transform`/`MatrixTransform` (pushes the modelview stack and marks `dirty`; if `subgraphRequiresLocalFrustum` it also pushes a frustum), `StateGroup` (push, traverse, pop of its state commands), and the draw nodes (`VertexIndexDraw::record` after `State::record()`). `State::record()` binds what changed and, when the matrix stack is dirty, calls `vkCmdPushConstants` with the 4x4 float modelview (`MatrixStack::record`, `State.h`, built from double precision). There is no GPU culling anywhere: the only culling is the CPU sphere tests.
- **The engine adds those cull nodes itself:** `vsgUtil::addLeafCullNodes` (`components/vsgutil/cullnode.cpp`) wraps every `StateGroup` that has no `prototypeArrayState` in a `CullNode`, so a placed model is `MatrixTransform` over shared `StateGroup`s over `VertexIndexDraw`, each leaf with its own bounding-sphere test.
- **One draw per model part per placed object.** `DistantObjects` says so in its header: "Not ported: merging objects into shared geometry ... So each object is its own draw" (`apps/openmw/mwrender/distantobjects.hpp`). Instances of one model share graph, pipeline and descriptors (`Scene::insertModel`, note in task 0062).
- **Per-draw state the shaders read:** push constants `projection` and `modelview`, 128 bytes (`files/shaders/lib/pushconstants.glsl`, `Pipeline::getCompatiblePushConstantSize`); a per-material descriptor set of 18 bindings (a material uniform block, optional particle, morph and bone storage buffers, thirteen combined image samplers by role, and the texture matrix block: `Pipeline::Graphics::Graphics`, `components/pipeline/graphics.cpp`). The view set (set 0) is bound once per pass (`getViewDescriptorSetLayout`).
- **Recording is threaded by command graph, not within one.** `RenderManager` calls `mEngine.setup(threads, getenv("VSGOPENMW_NO_VIEWER_THREADING") == 0)` (`rendermanager.cpp`, line 1258), i.e. threading is ON unless the variable is set. In VSG 1.1.16, `Viewer::setupThreading` (`Viewer.cpp`, from line 598) starts one thread per `CommandGraph` of a task and barriers them; a task with one graph gets one thread. The main scene is one graph, so its whole cull-and-record traversal is one thread, and the main thread waits for it in `recordAndSubmit` (what that wait hides is exactly what stage a must measure; **verify** the wait in `Viewer::recordAndSubmit`).
- **Shadow passes record the scene again.** Every cascade (`MWRender::Shadow`, submit order -3) and, with task 0077, every point-light face (a `vsg::View` per face) is its own command graph with its own record traversal over the casters (note 0039 section 5: "the CPU cost (a record traversal per face) usually matters more"). Separate graphs record on separate threads, which spreads the cost over cores but does not remove it.
- **Compute is already wired into the frame as bins with their own submit order:** `Bin_Cloud` (-4), `Bin_Volume` (-1), the shadow cascades (-3) and the light grid (-2) are `vsgUtil::ComputeBin` command graphs (`components/vsgutil/computebin.hpp`; `components/render/CLAUDE.md`, "Order on the GPU"). **Graphs with the same order submit in whatever order their threads finish recording**, so a graph that reads another's output needs its own number. A GPU cull pass would be one more of these (-5, before the shadow graphs).
- **Instancing exists in the repository once:** groundcover. `MWRender::Groundcover` copies a model's `VertexIndexDraw` and sets `instanceCount`, with per-instance vertex attributes (`Pipeline::Mode::INSTANCE`, `files/shaders/lib/groundcover.glsl`, `groundcoverinstances.*`); the pitfall recorded for it is that instance attributes must come before texture coordinates because the vertex inputs are numbered in binding order (`apps/openmw/mwrender/CLAUDE.md`).
- **Draw nodes VSG offers (1.1.16, `include/vsg/commands`):** `Draw`, `DrawIndexed`, `DrawIndirect`, `DrawIndexedIndirect`, `Dispatch`, `PipelineBarrier`, `CopyAndReleaseBuffer`... `DrawIndexedIndirect::record` is `vkCmdDrawIndexedIndirect(buffer, offset, drawCount, stride)` with a fixed host-side `drawCount` (`src/vsg/commands/DrawIndexedIndirect.cpp`). There is **no `...IndirectCount` variant**; a count read from a GPU buffer needs a custom `vsg::Command` subclass whose `record` calls the Vulkan function (VSG records any `Command`). `vsg::InstanceNode` and `InstanceDraw`/`InstanceDrawIndexed` exist for another instancing scheme (a per-node instance list); the engine uses none of them.
- **VSG has hooks for CPU profiling:** `vsg::Instrumentation` (`include/vsg/utils/Instrumentation.h`, `Viewer::assignInstrumentation`; `RecordTraversal.cpp` has `CPU_INSTRUMENTATION_L2` and `GPU_INSTRUMENTATION_*` calls around every node type). `vsg::Profiler` (`include/vsg/utils/Profiler.h`) and a Tracy bridge (`TracyInstrumentation.h`) implement it. Whether it works with the engine's custom nodes, threads and `-DNDEBUG`, and what it costs, is **verify**; note 0025 section 1 recorded that "VSG's record traversal is not hookable and no capture layer is installed", a statement that this hook may contradict (stage a settles it).

## 3. What the machine can do (device report)

The RTX 4070 report of the S0 run (`device.apiVersion` 1.4.351, `instance.loaderApiVersion` 1.4.341) records: `feature.multiDrawIndirect` present, `feature.drawIndirectFirstInstance` present, `feature.drawIndirectCount` present, `feature.descriptorIndexing` present, `feature.descriptorBindingVariableDescriptorCount` present, `feature.bufferDeviceAddress` present, `feature.meshShader` and `ext.mesh_shader` present; six queue families (family 0 graphics+compute+transfer x16, **family 2 compute+transfer x8**, family 1/3/4/5 transfer only). The same keys are present for llvmpipe in note 0025 section 6 (one queue family, multi-draw and first-instance true, mesh shaders true), which is why a software device proves nothing about a small GPU (its own sentence).

**What the game enables is much less.** `Engine::requestDeviceFeatures` (`apps/openmw/vsgengine.cpp`, lines 325 to 336) turns on `samplerAnisotropy`, `occlusionQueryPrecise`, `depthClamp` and `fillModeNonSolid` and nothing else. The probe's instance reports what the hardware has, not what the game's device was created with. So `multiDrawIndirect`, `drawIndirectFirstInstance`, `drawIndirectCount` (a Vulkan 1.2 feature struct field), `shaderDrawParameters` (a Vulkan 1.1 one) and descriptor indexing are all **not enabled on the game's device today**. Enabling them is a change at device creation. Whether `vsg::DeviceFeatures` can chain the Vulkan 1.1 and 1.2 feature structs (`VkPhysicalDeviceVulkan12Features`) is **verify**: `DeviceFeatures::get()` returns the base features struct in the code read (`components/render/engine.cpp`, `getEnabledFeatures`, `traits->deviceFeatures->get()`).

The engine uses the graphics queue for everything; the dedicated compute family 2 would allow asynchronous compute, which VSG's single-queue `RecordAndSubmitTask` does not use. Not needed here and not proposed.

## 5. The techniques, and what each needs

1. **GPU frustum culling.** A compute shader tests an array of bounding spheres or boxes against the frustum planes and writes either a visible-instance list (compacted with atomics) or an indirect-draw argument. It removes the CPU loop over objects. Source: Haar and Aaltonen 2015, Wihlidal 2016 (**recalled**).
2. **Hi-Z occlusion culling.** Build a depth pyramid (each level the farthest or nearest depth of the 2x2 below, depending on the depth convention; this renderer's is **reversed**, `components/render/CLAUDE.md` "Depth is reversed"), then test each bounding box's projected rectangle against the pyramid level whose texel covers it. Using the previous frame's depth causes false "occluded" results for things that appear from behind a moving occluder, so the production method tests twice: first against last frame's pyramid, draw what passes, build a new pyramid, then re-test only what failed against the new one and draw the survivors (Karis et al. 2021, **recalled**). The test needs a **sampleable depth image of the right frame**: the stored G-buffer linear depth (R32F, `HdrTarget::linearDepthView()`) exists only with `hdr` and `gbuffer`; the reflection pass keeps its own copy (mwrender `CLAUDE.md`, HDR path), the shadow passes have theirs. Occlusion culling reduces GPU work and issued draws, not the CPU work that was already gone after step 1.
3. **Indirect draws.** The compute pass writes `VkDrawIndexedIndirectCommand` records (index count, instance count, first index, vertex offset, first instance); the CPU records a fixed number of indirect draw calls. Two ways to get a GPU-chosen number of draws: `vkCmdDrawIndexedIndirectCount` (the count in a buffer; core in Vulkan 1.2, needs `drawIndirectCount`), or a fixed `drawCount` with `instanceCount = 0` for what was culled (needs only `multiDrawIndirect` for `drawCount > 1`; a zero-instance draw costs the GPU almost nothing but is still processed). `firstInstance != 0` needs `drawIndirectFirstInstance`.
4. **Per-draw data.** With `vkCmdPushConstants` per draw (today) an indirect draw cannot carry a per-object matrix. The vertex shader must read it from a storage buffer indexed by `gl_InstanceIndex` (with the instance base from `firstInstance`) or `gl_DrawID` (**`shaderDrawParameters`**, Vulkan 1.1; Zeux's design, **read**). The groundcover mode (`Mode::INSTANCE`) already reads per-instance attributes from vertex buffers. Both need a new vertex path in `default/main.vert` (under a define, so the SPIR-V of every existing pipeline stays byte-identical: the discipline of task 0077), its Slang twin (`default.vert.slang` and the permutation lists, `files/shaders/CLAUDE.md`) and the matching C++ pipeline mode.
5. **Material access.** An indirect draw cannot switch descriptor sets. Either (a) **bucket by (pipeline, descriptor set, vertex and index buffers)**, so one indirect command covers the instances of one model part, which is how an instanced renderer without bindless works (each distinct model part is one indirect command with a GPU-written instance count; the number of commands equals the number of distinct model parts in range, not the number of objects); or (b) **bindless**: descriptor indexing with a large array of textures, materials in a storage buffer, one draw for many materials (Zeux's design, **read**). (b) needs `descriptorIndexing` features enabled and a rewrite of how the object shader reads its thirteen differently-roled textures (specialization constants and defines choose the roles per pipeline); it is a large change to the most complicated shader in the game (71,424 reachable define sets for one alpha-tested draw alone, `files/shaders/CLAUDE.md`). **Not proposed.** The recommendation is (a).
6. **Meshlets and mesh shaders.** Splitting meshes into clusters of ~64 to 128 triangles that are culled individually (cone, frustum, Hi-Z) and drawn through `VK_EXT_mesh_shader` or by indirect draws of fixed-size clusters (Nanite, Karis et al. 2021, **recalled**). The hardware has the extension (section 3); Morrowind's meshes are tiny (a typical static is a few hundred triangles) and the S0 GPU time is 0.35 ms: there is no triangle-bound problem to solve (task 0062's own finding for model LODs). **Out of scope**, as in the design doc (tier Ultra, "may never be built", section 11 row S13).
7. **Device generated commands** (`VK_EXT_device_generated_commands`) would let the GPU choose pipelines and descriptor sets too. Not in the device report, no VSG support; out of scope.

## 6. What is realistic inside VulkanSceneGraph

VSG owns the scene graph and command recording, so a GPU-driven path is a **custom node and custom commands inside it**, not a replacement for it:

- **A "batch" node** holds, for one (pipeline, descriptor set, vertex and index buffers) combination, an instance buffer (storage buffer of per-instance data), an indirect-argument buffer, and the commands to draw it (`BindGraphicsPipeline`, `BindDescriptorSet`, `BindVertexBuffers`, `BindIndexBuffer`, then a custom `DrawIndexedIndirect`-like command). It is a normal `vsg::Node` in the scene graph, recorded by VSG's traversal; being one node it costs the traversal one visit, not one per object.
- **The cull pass** is a `ComputeBin` (or a node ahead of the render graph) with its own submit order (-5), a `Dispatch` per frame per view, and `PipelineBarrier`s (compute write to `DRAW_INDIRECT` read and to vertex-shader read). Same pattern as `Bin_Volume`. Each view that draws (main, cascades, point-light faces) needs its own frustum and its own output buffers, or one dispatch per view.
- **What VSG cannot do for us:** it will not cull inside a batch (our compute pass does), it gives no hook that tells a node "your parent was culled" (the batch node needs its own CPU-side coarse test per chunk, so a chunk behind the player is skipped without a dispatch), and it does not know about our buffers' lifetimes (they follow the rule for retired objects: `CompileContext::detach`, `components/render/CLAUDE.md`).
- **Precision.** The scene's modelview is formed in double precision on the CPU (`MatrixStack::record` converts the `dmat4` to float after multiplying). Morrowind coordinates are large (a cell is 8192 units; the world spans ±100,000 or more), and a float world matrix has about 0.008 units of precision at 100,000. The GPU path must therefore store each instance's matrix **relative to a per-chunk origin** (a cell centre, small in float), and push one `view * translate(origin)` per chunk per frame (computed in double, converted once), then multiply in the vertex shader. This is a design rule, not an option.
- **What it cannot do:**
  - **Skinned actors.** Bone matrices are written per frame by animation controllers into per-actor storage buffers (`BONE_BINDING`), each actor has its own descriptor set, and the skin's previous-frame matrices double the arrays with the G-buffer on. Actors stay on the CPU path. They are also the draws that cost the most per object (note 0026: NPC creation) and are few in number.
  - **Anything with a per-object controller or state:** UV-scroll and flip controllers (`TEXMAT_BINDING`), alpha and colour controllers, rotating or animated models, particle systems, morph targets, switches that differ per instance (`makeSwitchesUnique`), item lights, `DistanceLOD` models (a model with several LOD children records only the children in range). The statics that are "pure" (no controller, no per-instance material) are the eligible set; stage b must define it by a predicate on the loaded model graph and count it.
  - **Depth-sorted and blended draws** (`DepthSorted`, alpha-blended statics) and **alpha-to-coverage** draws, whose result depends on draw order or on the per-sample coverage: they stay on the CPU path.
  - **Ordering.** Indirect batching changes the order of opaque draws, so two coplanar surfaces with equal depth can swap (z-fighting is resolved differently). "Identical pixels" is therefore not a valid acceptance criterion with the path on; "within the noise of two off runs" is (task 0078).
- **What the CPU still does:** one pipeline bind, one descriptor bind, buffer binds and one indirect draw per batch per view. The draw count falls from the number of placed model parts to the number of distinct batches. This is the same saving that plain hardware instancing gives (section 7).

## 7. The cheaper alternative the evidence points to: instancing without GPU culling

Of the 28k to 33k census draws at a long view, the **distinct models in range are far fewer**: the cluster baker found 1,175 static models in the whole of Morrowind's distant objects (root `CLAUDE.md` changelog row "World LOD S4c and size", 2026-11-02: "119,122 statics in 1,175 models"), about 100 placed objects per model on average over the world and, in a 30000 view, a few dozen. If objects are drawn as `instanceCount = N` of one model part with the instance transforms in a buffer (section 5.4) and **culled on the CPU per chunk** (a cell's chunk is already one unit: `DistantObjects::buildChunk`), the number of draws falls by an order of magnitude with no compute shader, no indirect draw and no device-feature change beyond what the vertex path needs. The CPU culling of ~30k spheres is then done in a tight loop over a packed array (no scene graph visit, no state stack, no push constants), which is likely a small fraction of what VSG's traversal costs per node (an estimate, not a measurement; stage a measures it). GPU culling becomes worth its complexity only when the instance count is far larger than Morrowind's (hundreds of thousands: dense modded grass, a Skyrim-style world, which the project does not target) or when the CPU loop itself is the bottleneck.

Decision for toddhow in the spec: do stage a, then choose between **instancing only** (the recommendation if the record traversal is the cost) and **instancing plus a compute cull** (only if the packed CPU loop is itself a measured cost).

## 8. How other games do it, and why it may not transfer

GPU-driven pipelines were built for scenes with hundreds of thousands of unique objects and meshes of many triangles, on consoles where the CPU is weak and draw calls are expensive (Assassin's Creed Unity's Paris, Haar and Aaltonen 2015; Frostbite's compute culling, Wihlidal 2016; Nanite's billions of triangles, Karis et al. 2021; all **recalled**). Morrowind's exterior is a few thousand objects of a few hundred triangles each on a 12 GB desktop GPU measured at 0.35 ms of GPU time. The techniques are real and sound; the problem they solve is the problem of a bigger world than this engine draws. The honest framing for toddhow: this is the feature in the list whose payoff on **this machine** is least supported by data, and it earns its place only on a weaker CPU (the stated reason in note 0025 section 9) and when shadows multiply the passes. Stage a must test exactly those two conditions.

## 9. Open points that stage a closes

1. How much of the 3.87 ms (30000 view, clusters on) is the record traversal, by thread and by graph, with shadows off and on (section 2: the cull-and-record runs per graph on its own thread).
2. How many draws are really issued (VSG's instrumentation, section 2) against the census.
3. The share of the draws that are pure static (the eligible set, section 6) by model, and how many distinct model parts they are (section 7).
4. Whether the record thread is the critical path at all: with the engine's frame queue the record, submit and GPU overlap across frames; if the main thread's `loop.callback` is longer than the record thread, shortening the record gains nothing.
