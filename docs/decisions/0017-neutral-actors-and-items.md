## 1. Context

Milestone M-S3 ("NPCs stand, idle and path") and stage N5 of the neutral world model need Skyrim actors (NPC_ placed as ACHR) and items (ARMO, WEAP, MISC, ...) to exist in the engine. Stages N3a-1 to N3a-5 are built (design doc section 10; tasks 0103, 0105, 0107, 0109, 0110, 0113/0114): a Skyrim SE interior is drawn, collides, and is lit. Today an actor or an item in such a cell is an **inert reference**:

- Every neutral object is a `LiveCellRef<MWWorld::NeutralBase>` of record type `REC_NEUT` (`apps/openmw/mwworld/neutralstore.hpp`, `NeutralBase::sRecordId`), whose class is the single `MWClass::Neutral` (`apps/openmw/mwclass/neutral.cpp`). `Neutral::getModel` returns an empty model for `ObjectKind::Actor` and `LeveledList` (`isLiveThing`), so actors draw nothing; items (`ObjectKind::Item`) are drawn as static meshes and collide as their triangle mesh or box (`insertObjectPhysics`).
- `NeutralBase` holds only kind, editor id, model, collision hint, light and an opaque `PackPayload { uint64 handle }` (for Skyrim the base form id). It carries no stats, inventory, AI, race, equipment, script or appearance data (design doc 2.2: "what is deliberately not in the model").
- `Neutral` is not an actor: `isActor()` is the `Class` default `false` (`apps/openmw/mwworld/class.hpp:324`), no stats and no stores (the defaults throw, `apps/openmw/mwworld/class.cpp:71-79, 138-146, 193-196`). Neutral objects are not entered by `Actors`: `MechanicsManager::add` sends a `Ptr` to `mActors.addActor` only when `getClass().isActor()` (`mwmechanics/mechanicsmanagerimp.cpp:205-210`), and `Scene::addObject` makes the same split (`mwworld/scene.cpp:138-141`).
- The player of a neutral session is `neutralstub`'s Morrowind-shaped dummy: an NPC record `Player`, a stub race and class, 27 blank skills (`apps/openmw/mwworld/neutralstub.hpp`), never saved.
- Decision 0016 settled that `Ptr` stays the runtime handle (neutral-world-model.md section 1.4: 376 files name `Ptr`) and that the engine reads actors and items through typed handles with pack payloads (stage N5 row: "NPCs appear at their placements with their meshes; none of the Morrowind actor code is entered").

Decision 0013 sets the border this decision must respect: the core names no game and no feature; a game pack (`kind: "game"`) owns record types, rules and save chunks; a feature never moves into the core to help a pack, the host API grows instead.

The Skyrim SE pack decodes thin actor and item data today (`game_packs/skyrimse/include/game_skyrimse/records.hpp`): `NpcRecord` has name, RNAM race, CNAM class, ACBS flags/level/calc range, the DNAM 18 skills and three dynamic stats; `ItemRecord` (ARMO, WEAP, MISC) has name, model(s), ARMO armature (ARMA) form ids, value, weight, WEAP damage, keywords. **There is no RACE, ARMA, OTFT or CLAS record, and NPC_ lacks inventory (CNTO), default outfit (DOFT), sleep outfit, body/face data (WNAM, head parts, tint layers), template (TPLT), AI packages (PKID), factions and spell/perk lists** (`grep` of `records.cpp` finds only a WNAM read inside the WRLD handler, the parent world; subrecord names are RECALLED-VERIFY). `ObjectKind::Actor` is assigned to any placed NPC_ base (`world_view.cpp`, `case BaseTable::Npc`).

### 2.3 Three findings that shape everything below

1. **An item cannot be put in an inventory today.** `ContainerStore` is hard-wired to twelve Morrowind record types (`Type_Potion` ... `Type_Weapon`, `containerstore.hpp:233-246`). A Skyrim item as a `LiveCellRef<NeutralBase>` would throw in `ContainerStore::getType`. Any option that gives an NPC an inventory therefore either (i) maps Skyrim items to Morrowind item records, (ii) adds a neutral-item list to `ContainerStore`/`InventoryStore` (a change in the most heavily used inherited store code), or (iii) keeps Skyrim inventories outside `ContainerStore` altogether, in the pack.
2. **`MWRender::Npc` cannot render a Skyrim NPC.** Its constructor and rebuild path are written against `ESM::NPC`, `ESM::Race`, `ESM::BodyPart` and the Morrowind `InventoryStore` (`npc.cpp:96, 284-298, 454`). There is no generic "dress this skeleton with these models" in the game. And the game's Skyrim model path (`components/nifscene/flatten.*`, task 0110) **leaves skinned shapes out** ("skinned shapes (actors, worn armour) are left out: they need the animation system", `components/nifscene/flatten.hpp:18`; the pass counts `mSkippedSkinned`). A skinned `BSTriShape` render path in the game is a hard prerequisite for "an NPC with its body"; the only existing consumer of the skinned `Nif::Scene` is Eden Studio's `scenemodel` (task 0086 stage e), a static bind-pose drawing.
3. **The Skyrim pack is a shared library that links `components` only** (`game_packs/skyrimse/CMakeLists.txt`: `openeden_add_game_pack(skyrimse ...)`, include dirs `components` and `sdk/include`, link `components`, zlib, lz4). The Morrowind pack is the opposite, a static target `game_morrowind` that includes `apps/openmw` headers and links `openmw-lib` ("Shape A", task 0098). A Skyrim `MWWorld::Class` subclass lives in `apps/openmw`'s type system (`MWWorld::Ptr`, `MWMechanics::CreatureStats`, `MWWorld::InventoryStore`, `vsg::dquat` in signatures). **Option A below therefore means turning the Skyrim pack into a static Shape-A target, or splitting a static `game_skyrimse_engine` library out of it.** Shape A isolates code but is not a contract a second pack could implement (task 0098's own caveat); this is the cost of A.

## 3. Options

Each option is judged on: the core/pack boundary (0013), saves (N6), mechanics, rendering (Skyrim skeleton, note 0036), AI, Lua bindings (task 0097) and "Morrowind unchanged". The common shape of the decision: **how much of the existing actor machinery (Actors, CharacterController, AiSequence, CreatureStats, ContainerStore, MWRender::Npc) does a Skyrim actor go through?**

### Option A: the game pack supplies its own `MWWorld::Class` subclasses (this note's A = the plan's D3 (c))

A Skyrim-only family (`SkyrimNpc`, `SkyrimCreature`, `SkyrimArmor`, `SkyrimWeapon`, `SkyrimMisc`...) registered through `MWBase::RulesRegistry::mClasses` / `MWClass::installClassRegistrar`, the way `game_morrowind::registerMorrowindClasses()` does (`apps/openmw/mwclass/classes.cpp`: `registrar()()`), with a Skyrim `CustomData` subclass (via `CustomData::as<T>()`, `customdata.hpp`).

- **Core changes needed (all additive, none Skyrim-named):** (1) new neutral record types so `Class::get(type)` can tell an actor from an item (for example `REC_NEUT_ACTOR`, `REC_NEUT_ITEM` as extra `RecNameInts` values, each with a `LiveCellRef<NeutralBase>`-shaped list appended to `CellStoreTuple` and a `Store<NeutralBase>` per type); or a dispatch table keyed by `NeutralBase::mKind` inside `MWClass::Neutral` that forwards every virtual to a pack-registered `Class` (which is itself the "decorator" form of B). (2) The pack becomes a Shape-A static target (finding 3). (3) `ContainerStore` must learn a neutral-item list, or Skyrim actors must not use it (finding 1).
- **Boundary (0013):** the pack owns behaviour and data (good), but it links the engine's internals; a Skyrim pack and a Morrowind pack cannot be loaded together anyway (one game pack per session), yet nothing keeps the pack from reaching any `apps/openmw` header. The layer checker already scans `game_packs/`; the Morrowind pack's residue is the metric to watch. Not a contract, so third parties cannot write a game pack (P6 stable ABI is not served).
- **Saves (N6):** natural: the Skyrim `CustomData` + `readAdditionalState`/`writeAdditionalState` write into the engine's `ObjectState` stream (which is a Morrowind-format stream in `.omwsave`), or into pack save chunks (`GPCH`, task 0084 I4) which is the decision-0013 route. Both are workable; chunks are cleaner and keep the engine's record numbers free of Skyrim.
- **Mechanics:** maximum reuse is tempting and wrong. To go through `Actors`/`CharacterController` the class must return a `CreatureStats` (Morrowind attribute map, 3 dynamic stats, `Spells`, `AiSequence` of Morrowind packages). Skyrim actor values (18 skills, health/magicka/stamina with different regeneration, 100+ AVIF entries, perks) do not fit; they would be a second copy in `CreatureStats` for the engine plus the real values in the pack, kept in sync. Reusing `CharacterController` also requires `getInventoryStore` (finding 1) and Morrowind animation group names on the `MWAnim::Play`.
- **Rendering:** needs a new render object anyway (Option A does not remove the skinned-shape and body/equipment work). It would derive from `MWAnim::Actor` rather than `MWRender::Npc`; `Class::insertObjectRendering` calls a new `Objects::insertActor(ptr, factory)`.
- **AI:** if routed through `Actors` it uses `AiSequence`, which is Morrowind packages; the Skyrim package stack (plan 4.19: PACK, sandbox, schedules) would be a second AI inside a first one.
- **Lua (0097):** `isActor()` true makes `core.types.NPC`-style APIs take the object; they would read `getNpcStats` that is faked. Pack namespaces `core.skyrimse.*` are separate and fine.
- **Morrowind unchanged:** unchanged by construction when the new record types and ContainerStore list are only populated in neutral sessions; the `worldobjects_check` dump and frame hash prove it, as in the N3a rows.
- **Effort (mine):** 40 to 70 days for the class family and the stats/inventory adaptation, before any Skyrim rule.

### Option B: one neutral actor/item model in the core with a pack payload and a hooks contract (the plan's D3 (a) plus (b))

Keep `MWClass::Neutral` and `NeutralBase` as the only class and record; widen what the core knows about actors and items to a small **game-neutral** description (a "life" component), and make the pack supply behaviour through an SDK contract instead of through engine classes.

- **What the core adds (all game-neutral):**
  - `NeutralBase` gains an optional `ActorComponent` (a skeleton asset key, a body/outfit render description as a list of model paths, a capsule size, flags: can fly/swim, bipedal) and an optional `ItemComponent` (a carried-item description: weight, value, equip slots as opaque small integers, worn model list). These are *data the pack computes and hands over by value*, like `LightComponent` (world_model.hpp 1.1).
  - A new core service, **a neutral actor runtime**, for what the engine needs to put a thing on the screen and move it: a render object (`MWAnim::Actor`-based, built from the component, skinned-shape capable), a physics capsule and movement (`Movement` request: desired velocity/heading from the pack, the engine integrates against Jolt), an animation-clip request interface (the pack asks for a clip by name; CreativeMotion plays it).
  - A **mechanics hooks contract** (`openeden/game/actor_rules.hpp`, SDK minor or 4.1; the thing `game-packs.md` 5.5 sketches): per frame `update(dt)`, `onCellLoaded/Unloaded(handles)`, `onActivate(actorHandle, targetHandle)`, `onDeath`, `isHostile`; the core calls it, the pack does the rules. Handles are `WorldId` + session `RefNum`, never pointers.
  - `isActor()` stays **false** for `Neutral` objects in the first slices; a new predicate `Class::hasLife()` (default false) gates the neutral runtime, so none of the 129 `isActor()` sites (and none of `Actors`, `CharacterController`, `AiSequence`, `CreatureStats`, `MWRender::Npc`) is entered. This is what the design doc N5 row asks for: "none of the Morrowind actor code is entered".
  - Inventories stay in the pack (finding 1, route iii); the core sees only the **worn-model list** the pack resolves. Containers in the world (CONT) are a separate kind and a later stage.
- **Boundary (0013):** the strongest of the options. The core learns "a thing with a skeleton, a worn-model list, a capsule, a movement request and clip requests", which is game-neutral and is also what Fallout 4 or a Morrowind-through-neutral path would need. The pack keeps every rule and all records. This is a contract a second pack or third-party pack can implement (P6 compatible).
- **Saves (N6):** the pack writes its actor state (inventory, actor values, AI position, package stack) into a chunk (`GPCH`); the core stores only the session identity table. Identity: the stable key is `{pack id, WorldId}` for base placements and a pack-minted id for created objects. Straightforward.
- **Mechanics:** all Skyrim rules in the pack: actor values, perks, magic, combat in the pack's formula library (plan 4.13 to 4.15). No Morrowind types pretend to hold Skyrim state. The cost is that **every interaction the pack wants with the engine's existing systems has to be a hook or a service** (damage events to the animation layer, hit detection through physics queries, sounds), and the mechanics hooks have to be designed carefully and widely enough for combat and magic (plan 3.4 item 5: "probably SDK 4.1 or 5.0").
- **Rendering:** a Skyrim skeleton through the skeleton map (task 0070, note 0036: XP32 has 542 to 649 bones; ZeX 374; most body mods need the map; the stock body is the fallback). The neutral actor runtime builds one `MWAnim::Actor`-derived object from the skinned `Nif::Scene` plus addons. The merged-body machinery (task 0069) can be reused for cost.
- **AI:** pack-side `AIProcess` owns the package stack and emits movement targets to the core navigator and clip requests to CreativeMotion (plan 4.19). Needs a **locomotion request API** in the core (target position, speed class, path request via the existing navigator); no `AiSequence`.
- **Lua (0097):** `core.skyrimse.*` descriptor namespaces expose Skyrim actor state; the generic object API sees a neutral object (`isActor()` false) until a deliberate decision to widen it. This keeps `openmw.types.NPC` out of Skyrim; the Lua UI reads pack namespaces.
- **Morrowind unchanged:** by construction (new components optional; new service only created with `[Game] neutral world`); the same comparison as every N3a stage.
- **Effort (mine):** neutral actor runtime and render object 25 to 45 days; hooks contract and loop wiring 15 to 25; locomotion and clip request API 10 to 15. The pack-side rules are plan workstreams (4.13 to 4.19), not counted here.

### Option C: map Skyrim actors and items onto Morrowind's NPC and item records

The neutral session's stub player is the precedent: `insertNeutralStubPlayer` already fabricates an `ESM::NPC`, a race and a class (`neutralstub.hpp`). Option C would synthesise an `ESM::NPC`/`ESM::Race`/`ESM::BodyPart`/`ESM::Armor`/`ESM::Weapon` per Skyrim record at load, so that `MWClass::Npc`, `Actors`, `CharacterController`, `MWRender::Npc` and the inventory all work unchanged.

- **Boundary:** poor. Morrowind's types become the lingua franca of every game; every Skyrim fact that Morrowind has no field for (18 skills against 27, no attributes in Skyrim, weight morphs, 30-plus biped slots against Morrowind's fixed part references, body addons per race and sex) is lost or encoded in misused fields. It drives the opposite way from decisions 0013 and 0016, and from the stage N7 plan to retire the old ESM4 path. The ESM4 path already did a version of this and stalled ("experimental"; `MWClass::ESM4Npc` is not even an actor: no `isActor`, no stats, `esm4npc.cpp`).
- **Saves:** Skyrim actors would be written as Morrowind NPC states: wrong data, and a Morrowind save reader would meet records it cannot interpret.
- **Mechanics:** the Morrowind rules (hit chance, spells, skill use) would run on fabricated numbers. Plausible for a "walk-around" demo, wrong for any real Skyrim rule. Skill and magic systems cannot be reinterpreted without rewriting the Morrowind game pack's rules.
- **Rendering:** Morrowind's `MWRender::Npc` builds bodies from `ESM::BodyPart` records (one model per part per race); Skyrim has one body mesh plus armour addons plus weight morphs. A synthetic `BodyPart` list could point at whole-body models, but the renderer's part model expects Morrowind skeleton names (`bip01`, `1st`; `GameConventions`) and does not read skinned `BSTriShape`.
- **AI:** Morrowind `AiSequence` only (wander, travel, follow, ...); no schedules by package, no sandbox, no conversations.
- **Lua:** Morrowind-shaped, which is exactly what the Lua UI and mods would be told is a lie for Skyrim.
- **Morrowind unchanged:** unchanged, but only because the synthesis happens in a Skyrim session.
- **Use:** none beyond a stopgap. Its one honest use is the stub player, which stays a stub: it is never saved (the store refuses) and is only the thing the World constructor needs.
- **Effort:** cheapest to the first picture (about 10 to 20 days: build the records, fix the skinned render), most expensive to unwind. **Not recommended.**

### Option D: other routes

- **D1. Extend the existing ESM4 experimental path** (`MWClass::ESM4Base`, `ESM4Npc`, `CellStore::loadRefs(const ESM4::Cell&)`) with actor behaviour. Retired by plan D14 at N7, built on cc9cii's reader and `components/esm4` types rather than the pack's decoders; not a contract. Rejected.
- **D2. A Ptr-free actor path** (actors are core-owned entities with their own handle, not `Ptr`s): the N3b stance for actors only. Attractive for a clean core, but `Ptr` is used by the physics system, the render scene (`Scene::addObject` keys by `Ptr`), `Actors`, Lua (`GObject`), the navigator, and the cell's `CellStore`; a parallel handle for actors would split every one of them. Decision 0016 already took `Ptr` as the runtime handle. Rejected for the same reason N3b was.
- **D3. B first, A's `Class` shape later.** Build the neutral actor runtime of option B, keep `isActor()` false, and revisit whether a Skyrim `Class` family is wanted if, after M-S3, enough of the engine's systems (Lua object API, tooltips, activation) turn out to need `isActor()`. This is the recommended path.

## 4. Recommendation

**Take option B, built as D3 (a neutral actor runtime in the core and pack-side rules behind a hooks contract), with `isActor()` staying false for neutral objects for now; do not do A or C.** The first slice of N5 draws and animates a skinned NPC from the pack's description without entering `Actors`, `CharacterController`, `AiSequence`, `CreatureStats`, `ContainerStore` or `MWRender::Npc`, so no Morrowind rule can silently run on Skyrim data and no Morrowind type has to pretend. Inventories, actor values, perks, AI and Papyrus state live in the pack and its save chunk; the core grows only game-neutral things (a skinned actor render object, a capsule-and-movement service, a clip request interface, a locomotion request interface and the hooks contract).

Why not A: it buys reuse that is not real. `Actors`/`CharacterController` need `CreatureStats` with Morrowind attributes and `AiSequence`, `ContainerStore` rejects non-Morrowind items (finding 1), and the Skyrim pack would have to become a Shape-A static target that reaches into `apps/openmw`, which is the form of isolation task 0098 already marks as not a contract. Why not C: it puts Morrowind's data model under every game. The honest cost of B is that anything the engine already does for actors (hit detection, sounds on hit, activation prompts, tooltips, Lua object APIs) must be reached through a hook or service, and the hooks contract has to be designed wide enough up front (plan 3.4 item 5, risk: the minor/major SDK bump).

Assumptions the recommendation rests on, to confirm in the stage N5a spike: the skinned `BSTriShape` path can be drawn in the game on `MWAnim::Actor`-derived objects (finding 2); CreativeMotion can play a clip set on a Skyrim skeleton through the skeleton map (note 0036, plan 4.12 O1+O2; the converted clip data does not exist yet); the existing navigator gives paths across a Skyrim triangle-soup floor (design doc R8; untested).

## 6. Consequences

- **The core gains** a neutral actor runtime and four narrow interfaces (render description, movement request, clip request, locomotion request) plus the hooks contract; all game-neutral and named in `docs/design/`; the layer checker stays at 104 exceptions or fewer (the new runtime goes in a layer that does not include a game pack).
- **The Skyrim pack** stays a shared library against `components` and the SDK (it does not become Shape A) and grows an actor table, the outfit resolver and later the rule libraries.
- **`isActor()` is not widened** now. Deciding later to widen it (so Lua's `types.Actor`, the activation prompt and tooltips apply) is a separate decision with the 129-site audit in front of it.
- **Items** stay `ObjectKind::Item` statics in the world and become pick-up-able in a later stage by a pack action (pick-up removes the neutral object and adds an entry to the pack's inventory); they never enter `ContainerStore`.
- **Docs to update with this decision (when accepted):** `neutral-world-model.md` section 5 N5 row; the implementation plan D3, 3.4 item 4 and 5, section 8 item 8; `game-packs.md` 5.5 (the hooks contract replaces `MechanicsHooks`); CLAUDE.md changelog row.

## 7. Open questions for toddhow

1. **Is option B (and D3: `isActor()` stays false for now) the model?** Recommendation: yes. The alternative, A, is faster to a first picture only if you accept the Shape-A pack and the Morrowind-shaped stats.
2. **May the core grow the neutral actor runtime and the hooks contract (an SDK minor, probably 4.1)?** Recommendation: yes, with the hooks designed in N5-5 from the pack's real needs and bumped to a major (5.0) only if combat and magic prove they need a changed call shape. Cost of "no": Option A.
3. **Items: do Skyrim items ever enter `ContainerStore`?** Recommendation: no; the pack keeps inventories (the engine would need a thirteenth typed list and changes in `InventoryStore`, the most heavily used inherited code). Cost: the inventory, barter and container UIs are pack-driven (plan 4.17 and the RmlUi screens of decision 0015 read `core.skyrimse.*`), and the `Class::canBeEquipped`-style engine paths are not used for Skyrim.
4. **Should the player be a neutral actor too?** The stub player (an NPC `Player`, `neutralstub`) is a Morrowind-shaped dummy that the World constructor needs. Recommendation: keep it as a hidden stub; the Skyrim player becomes a neutral actor with an extra "controlled by input" flag, and the first-person/third-person camera uses the neutral runtime. Defer to M-S3/M-S6; until then the Skyrim player can walk as the stub does today.
5. **Skeleton and body policy (decided by note 0036 only as a design):** accept that most mod-list bodies need a skeleton map, and that a missing or refused map must show the stock body? Recommendation: yes (plan 4.11 already says so). Also: which skeleton is the stock one for the first slice (the vanilla Skyrim SE `skeleton.nif` is on the user's machine; note 0036 measured XP32 and ZeX)? Recommendation: vanilla first; the map comes in N5-2 only for the vanilla skeleton, and the XP32 map as its own task.
6. **Animation route for N5-4 (plan D4):** until the Havok clip converter exists (plan item F), is a generated idle (breathing style layer on the rest pose) an acceptable first "idles" for the M-S3 slice? Recommendation: yes, labelled as a placeholder; the converter spike decides O2 viability before the locomotion graph is built.
7. **Creatures, dragons, horses:** the first slice is humanoid NPCs only. Recommendation: yes; creatures need other skeletons (plan 4.12 lists 15 to 30 days).
8. **Process:** full loop for N5 (it touches `apps/openmw` world and render code, the SDK and, later, saves). Recommendation: full loop; N5-0 (pack decoding) alone may be marked lighter by you if you prefer, as it changes no engine code.
9. **The count of the plan's D3 estimate.** The plan's D3 text recommends "(a) with (b) additions". This note's reading is that (a) alone is not enough because `Class` cannot dispatch on kind and `ContainerStore` cannot hold the items; the hooks of (b) are required, and the extra core pieces (render, movement, clip, locomotion interfaces) are not in the plan's estimate. Please confirm that the D3 estimate should be raised by the 25 to 40 days above.
